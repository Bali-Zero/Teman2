# pip-audit ignored vulnerabilities

Advisories in this list are skipped by the `pip-audit` step in `.github/workflows/tests.yml`. Each entry MUST document why the CVE is not applicable to this codepath, with enough detail for a security reviewer to re-validate the decision without running the audit themselves.

Re-evaluate every entry here when the upstream package version changes or when adding new code paths that touch the affected module.

---

## GHSA-69w3-r845-3855 (CVE-2026-1839) — transformers 4.57.6

**Package:** `transformers` (transitive via `sentence-transformers>=5.3.0`)
**Fix version:** `5.0.0rc3` (pre-release)
**Ignored:** 2026-04-12

**Summary:** `Trainer._load_rng_state()` in `src/transformers/trainer.py` calls `torch.load()` without `weights_only=True`. An attacker supplying a malicious `rng_state.pth` checkpoint file can execute arbitrary code when the training loop restores state.

**Why not applicable to this codepath:**

1. **The vulnerable `Trainer` class is not used by `apps/backend-rag/`.** Verified with:

   ```bash
   grep -rn "from transformers\|import transformers" apps/backend-rag/backend/
   # Zero matches — the backend codebase never imports transformers directly.
   ```

   The only transformers imports are inside `sentence_transformers/losses/*` (in the installed venv), which are **training losses** this project does not invoke. `backend-rag` uses `sentence_transformers.CrossEncoder` for inference only.

2. **PyTorch 2.11.0 mitigates the underlying issue.** The advisory states the problem affects "`torch>=2.2` when used with PyTorch versions below 2.6." `apps/backend-rag/requirements.txt` pins `torch==2.11.0`, which is above the mitigation threshold. On torch ≥ 2.6, `torch.load()` enforces safe globals by default — the exploit vector does not exist.

3. **No user-supplied checkpoint files.** The RAG pipeline loads model weights from Hugging Face Hub on startup (trusted source, verified by `huggingface-hub`'s own integrity checks). There is no code path that deserializes an attacker-controlled `rng_state.pth`.

**Re-evaluate when:**

- `torch` version drops below 2.6
- `backend-rag` adds direct imports from `transformers` (especially anything touching `Trainer`)
- Model weights start being loaded from untrusted sources or user uploads
- `transformers 5.0.0rc3` stabilizes to 5.0.0 (at that point, upgrade and drop the ignore)

**How to re-check:**

```bash
cd apps/backend-rag
pip-audit --strict --requirement requirements.txt
```

Adding `--ignore-vuln GHSA-69w3-r845-3855` should then fail the audit (no vulns left) and this entry can be removed.

## fastmcp 2.1.0 — six advisories (CVE-2025-62800, CVE-2025-62801, GHSA-rcfx-77hg-w2wv, CVE-2025-69196, CVE-2025-64340, CVE-2026-27124)

**Package:** `fastmcp` (transitive — required by `nuzantara-mcp*` apps; pulled into backend tests indirectly through workspace install resolution)
**Fix versions:** 2.13.0 / 2.14.0 / 2.14.2 / 3.2.0 (CVE-by-CVE)
**Ignored:** 2026-04-26

**Why pinned at 2.1.0:** `apps/backend-rag/requirements.txt:154` was downgraded from `>=3.1.0` on 2026-04-25 to resolve a dependency conflict with `litellm 1.83.7` over `python-dotenv` (litellm requires `<2.0`, fastmcp 3.x requires `>=2.0`). The downgrade is documented in-line in `requirements.txt`.

**Why not applicable to this codepath:**

1. **`fastmcp` is not imported by `apps/backend-rag/`.** Verified:

   ```bash
   grep -rn "from fastmcp\|import fastmcp" apps/backend-rag/backend/
   # Zero matches. The package is only consumed by apps/nuzantara-mcp*, which are
   # standalone MCP servers running locally on Pro/Air via OpenClaw and stdio
   # transport — they are NOT exposed to untrusted networks.
   ```

2. **All six advisories require attacker-controlled MCP server inputs over network transports** (HTTP SSE, WebSocket). The Nuzantara MCP servers run stdio-only, on the user's own machine, consumed by Claude Code itself. There is no untrusted network surface.

3. **`backend-rag` ships fastmcp transitively** because pip resolves it during `pip install -r requirements.txt` for the workspace, but the runtime image does not load it at boot — it sits on disk unused.

**Re-evaluate when:**

- The litellm/python-dotenv conflict is resolved upstream (litellm relaxes its dotenv pin, or fastmcp 3.x relaxes its dotenv pin) — at that point, restore `fastmcp>=3.2.0` and drop ALL six entries.
- An MCP server starts being exposed over network transport (HTTP/SSE/WebSocket).
- `backend-rag` adds direct `fastmcp` imports (currently zero).

**Tracking:** see follow-up issue / WR2 on resolving `litellm 1.83.7 ↔ python-dotenv 2.x` conflict so fastmcp can return to 3.x.

## python-dotenv 1.0.1 — CVE-2026-28684

**Package:** `python-dotenv` (transitive — pinned at 1.0.1 by `litellm 1.83.7`)
**Fix version:** 1.2.2
**Ignored:** 2026-04-26

**Why pinned at 1.0.1:** `litellm==1.83.7` requires `python-dotenv<2.0,>=0.21.0`. Upgrading dotenv to 1.2.2 would force a litellm upgrade, which has its own breaking-change implications across the LLM client layer. Keeping dotenv at 1.0.1 is the upstream-driven status quo until litellm relaxes the constraint.

**Why not applicable to this codepath:** CVE-2026-28684 affects `dotenv_values()` parsing of attacker-controlled `.env` files. Nuzantara only loads `.env` files written by the developer at deploy time (Fly secrets in production); there is no code path that reads dotenv-formatted content from untrusted input.

**Re-evaluate when:**

- `litellm` relaxes its `python-dotenv<2.0` constraint (or drops the dotenv dep entirely).
- An admin endpoint starts accepting dotenv-formatted blobs as user input (currently impossible).

## litellm 1.83.7 — CVE-2026-40217

**Package:** `litellm` (direct dep)
**Fix version:** 1.83.10
**Ignored:** 2026-05-12

**Why we cannot bump:** Bumping `litellm` to 1.83.10+ pulls in a hard pin `openai==2.24.0`, which conflicts with `langchain-openai>=1.1.11` (the latest pre-CVE version) requiring `openai>=2.26.0`. The result is `pip resolve` ResolutionImpossible at install time. No combination of litellm 1.83.x + langchain-openai 1.1.11+ resolves cleanly.

**Why not applicable to this codepath:** CVE-2026-40217 affects litellm's proxy mode (admin endpoint). Nuzantara uses litellm as a CLIENT library (`backend/llm/litellm_router.py`), never exposes the proxy server. No HTTP attack surface from litellm.

**Re-evaluate when:**

- `litellm` relaxes the `openai==2.24.0` pin (track upstream releases).
- `langchain-openai` ships a version compatible with `openai<2.26.0`.
- Backend starts running `litellm.proxy` mode (currently zero references).

**How to re-check:**

```bash
# Verify still pinned upstream
pip download --no-deps litellm==1.83.10 -d /tmp/check
unzip -p /tmp/check/litellm-1.83.10*.whl */METADATA | grep -i "openai"
# Expected: Requires-Dist: openai==2.24.0 (still pinned)
```

## langchain-openai 1.1.10 — CVE-2026-41488

**Package:** `langchain-openai` (direct dep)
**Fix version:** 1.1.14
**Ignored:** 2026-05-12

**Why we cannot bump:** `langchain-openai>=1.1.11` requires `openai>=2.26.0`, which conflicts with `litellm 1.83.7` transitive pin `openai==2.24.0`. See litellm CVE-2026-40217 entry above for the full transitive constraint analysis. Keeping `langchain-openai` at 1.1.10 (last version compatible with openai 2.20+) is the upstream-driven status quo.

**Why not applicable to this codepath:** CVE-2026-41488 affects langchain-openai's handling of attacker-controlled prompts in the `embed_documents()` path. Nuzantara uses langchain-openai only as a fallback path in `backend/services/kg/langgraph_orchestrator.py` and never embeds untrusted user content directly (RAG queries pass through prompt-builder sanitation in `backend/prompts/zantara_core.py`).

**Re-evaluate when:**

- `litellm` relaxes the `openai==2.24.0` pin → we can bump both packages.
- Backend adds a code path that embeds raw user input via langchain-openai (currently zero).
- A langchain-openai 1.1.x release lands that supports openai<2.26.0.
