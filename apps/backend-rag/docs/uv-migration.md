# uv Migration — backend-rag (Pilot)

**Status**: Pilot landed 2026-05-19 (audit modernization finding #9).
**Scope**: `apps/backend-rag/` only. Other apps still use plain `pip`.
**Source of truth**: `requirements.txt` and `requirements-prod.txt` remain
the human-edited input. The `.lock.txt` files are derived artifacts.

## Why uv

[`uv`](https://github.com/astral-sh/uv) is Astral's Rust-based pip
replacement. The two properties we care about:

1. **10–100× faster resolution + install** in CI. The slowest deps in this
   project (`torch`, `transformers`, `sentence-transformers`, `presidio-*`)
   used to dominate cold-cache CI runs at ~3-5 min; with uv + warm
   `~/.cache/uv`, the same work is ~20-40s.
2. **Hash-pinned reproducibility** via `--generate-hashes` + `--require-hashes`.
   Every wheel installed in CI and in the Fly.io build is verified against
   a SHA256 recorded in `requirements*.lock.txt`. A PyPI re-upload, MITM,
   or accidental wheel swap fails the install instead of silently shipping.

## File layout

```
apps/backend-rag/
├── requirements.txt              # human-edited, dev + test deps (332 lines)
├── requirements-prod.txt         # human-edited, prod-only subset
├── requirements.lock.txt         # autogenerated, hash-pinned, 264 packages
├── requirements-prod.lock.txt    # autogenerated, hash-pinned, 205 packages
└── requirements-test.txt         # untouched (legacy test-only, not in pilot)
```

`requirements.lock.txt` is consumed by `.github/workflows/tests.yml`
(both `backend-tests` and `e2e-tests` jobs).
`requirements-prod.lock.txt` is consumed by `apps/backend-rag/Dockerfile`
builder stage (Fly.io production image).

## Day-to-day workflows

### Add a new dependency

1. Edit `requirements.txt` (and `requirements-prod.txt` if it should ship
   in the production image — most app deps go in both, dev/test tools only
   in `requirements.txt`).
2. Regenerate the lock files:
   ```bash
   cd apps/backend-rag
   uv pip compile requirements.txt -o requirements.lock.txt \
       --generate-hashes --python-version 3.11
   uv pip compile requirements-prod.txt -o requirements-prod.lock.txt \
       --generate-hashes --python-version 3.11
   ```
3. Commit `requirements*.txt` AND `requirements*.lock.txt` together — they
   must always agree.

### Upgrade an existing dependency

Same as add, but pass `--upgrade-package <name>` (or `--upgrade` for all):

```bash
cd apps/backend-rag
uv pip compile requirements.txt -o requirements.lock.txt \
    --generate-hashes --python-version 3.11 \
    --upgrade-package fastapi
```

### Local development install

```bash
cd apps/backend-rag
uv venv                                              # creates .venv/
source .venv/bin/activate
uv pip install --require-hashes -r requirements.lock.txt
```

Editable `cell-core` is included via the `-e ../../packages/cell-core` line
in the lock file — runs from `apps/backend-rag/` cwd, same as pip used to.

### Run tests locally

After `uv pip install -r requirements.lock.txt`, the workflow is unchanged:

```bash
PYTHONPATH=. pytest backend/tests/services/rag/ -q
```

## Rollback

If anything breaks:

1. Revert the merge commit of this PR (`git revert -m 1 <merge-sha>`).
2. The lock files will disappear; Dockerfile + tests.yml reset to plain pip.
3. No production data is affected (this is a build-time-only change).

## Install uv locally

```bash
# Homebrew (macOS)
brew install uv

# Or via pip
pip install uv

# Or via the official installer (Linux / WSL)
curl -LsSf https://astral.sh/uv/install.sh | sh
```

Verify: `uv --version`.

## Gotchas

- **`--require-hashes` is strict by design.** If PyPI re-publishes a wheel
  (e.g. with new metadata but same version), the SHA256 changes and the
  install fails. Regenerate the lock file — don't disable the flag.
- **Editable install path is cwd-sensitive.** The `-e ../../packages/cell-core`
  line in the lock file resolves relative to wherever you run
  `uv pip install`. Always `cd apps/backend-rag` first (Dockerfile already
  does this via `WORKDIR /app/apps/backend-rag`).
- **uv has no `--user` flag.** The Dockerfile uses `--prefix /root/.local`
  which produces the same `lib/python3.11/site-packages` + `bin/` layout
  that `pip install --user` did, so the runtime-stage COPY is unchanged.
- **Lock-file regeneration is slow** (~30-90s for 332 deps with hash
  generation) because uv fetches metadata from PyPI for every package. The
  install step is fast; only `compile --generate-hashes` is network-bound.
- **`uv pip compile` does not write `uv.lock`.** That's the format for
  uv-native projects with `pyproject.toml` + `uv sync`. We're staying on
  the pip-compile workflow for backwards compatibility with the existing
  `requirements*.txt` source files. A future PR could promote backend-rag
  to native `uv sync` if there's appetite.

## Out of scope

- Other apps in the monorepo (`mouth`, `bali-intel-scraper`, etc.) — they
  still use plain pip. Promote one at a time after this pilot bakes.
- `requirements-test.txt` is untouched. It's not in any CI workflow path;
  re-evaluate when the test suite is reorganized.
- Native `uv sync` migration (drop `requirements*.txt`, use `pyproject.toml`
  - `uv.lock` as the single source). Defer to a follow-up PR — the current
    pyproject.toml is configured for tooling (mypy/ruff/black), not deps.
