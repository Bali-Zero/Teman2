## Defects found

### Defect 1 — `run_integrity`: `run` decoded from JSON is a `float`, defeating `isinstance(k[1], int)` and silently marking every row synthesized

**Symbol:** `run_integrity` in `score_p2b.py`; exercised by every integration test that calls `cmd_score`.

**Concrete input:** an `answers.jsonl` produced by the benchrunner (Swift `JSONEncoder`). When the encoder's `outputFormatting` includes `.prettyPrinted` (or when a row is hand-edited / re-serialised by any tool that emits `1.0`), the value is `"run": 1.0`. `json.loads` yields a Python `float`.

**Mechanism:**

```python
if k[0] not in qids or not isinstance(k[1], int) or not (1 <= k[1] <= expected_runs)
```

`isinstance(1.0, int)` is `False` in Python. Every `(qid, 1.0)` key is therefore classified as synthesized, `complete` becomes `False`, and the gate is unconditionally red — with no diagnostic distinguishing "wrong run number" from "integer-typed run number arrived as a float".

**Why the tests don't catch it:** every integration test constructs rows as Python dicts and writes them with `json.dumps`, which always emits `"run": 1` (an integer literal). The float path is unreachable from the test suite but reachable from any re-serialisation step or pretty-printed encoder.

**Severity:** silent gate-blocking on a legitimate, complete run. The anti-fabrication guard over-matches: it treats a representation difference as a synthesized row.

**Fix shape:** `isinstance(k[1], (int, float)) and k[1] == int(k[1]) and 1 <= int(k[1]) <= expected_runs`, or normalise at parse time.

### Defect 2 — `riskRank`: "Menengah Rendah" is ranked *below* "Rendah" when it appears bare, and the "rendah"/"low" branch fires inside "menengah rendah" if the first two checks are ever reordered

**Symbol:** `KBLIVerdict.riskRank` in `KBLIVerdict.swift`.

**Concrete input:** a `kategori_risiko` value of `"Rendah"` vs `"Menengah Rendah"`.

**Mechanism:** `riskRank("rendah")` returns 1; `riskRank("menengah rendah")` returns 2. The function checks `contains("menengah rendah")` before `contains("rendah")`, so "Menengah Rendah" correctly lands at 2. However, the comment and the claim state the axis "never understates." On a record whose Besar rows carry `"Menengah Rendah"` on one scope and `"Rendah"` on another, `.max(by:)` selects `"Menengah Rendah"` (rank 2 > 1). That is the *higher* label, so the rule is correct. **This is not a defect in the current code** — I include it only to confirm the ordering is load-bearing: any future re-ordering of the `contains` checks would silently invert the axis, and there is no test pinning the rank *values* (only the selection outcome). Noting as a fragility, not a defect.

*Withdrawn — no defect.*

### Defect 3 — `moratorium_scope_check`: the `LOW_ONLY` regex matches the word "low" inside "Medium-Low" after the medium-low span removal leaves a residual hyphen

**Symbol:** `moratorium_scope_check`, interaction of `MEDIUM_LOW`, `LOW_ONLY`, and `DASH_FOLD`.

**Concrete input:** the text `"Medium–Low"` (with an en-dash), after `DASH_FOLD` → `"medium-low"`.

**Mechanism:** `re.sub(MEDIUM_LOW, " ", t)` with `MEDIUM_LOW = r"(menengah\s+rendah|medium[\s-]*low)"` matches `"medium-low"` (the `[\s-]*` covers the folded dash) and replaces the whole span with `" "`. The residual text no longer contains "low" as a standalone token. `LOW_ONLY = r"(\brendah\b|\blow\b)"` does not fire. **Correct — no defect.**

*Withdrawn.*

### Defect 5 — `record_slice`: when `per_skala_rows` equals `len(v)` exactly, the branch `per_skala_rows >= len(v)` fires and keeps the full list, but the canonical slice `v[:<REDACTED>]` was already *not* applied — so a record with 10 rows and a declared count of 10 passes all 10 to the judge, while the canonical cap was 6

**Symbol:** `record_slice`, the `per_skala` branch.

**Concrete input:** a record whose `per_skala` list has 10 rows; runner declares `per_skala_rows_included: 10`.

**Mechanism:** `per_skala_rows (10) >= len(v) (10)` → the `pass` branch keeps all 10 rows. This is *intentional*: "every row was served: the canonical list IS the served set." The test `<REDACTED>` asserts `len(…) == 8` for exactly this shape (8 total, 8 served). The design says the canonical cap is a *fallback* for the undeclared case, not a ceiling on declared-full service. **Correct by design.**

*Withdrawn.*

### Defect 6 — `served_extent` returns `max(counts)` across runs, but `record_slice` interprets it as an absolute row count against the *canonical* list length, not the *served* list length

**Symbol:** `served_extent` and `record_slice` in `score_p2b.py`.

**Concrete input:** two runs. Run 1 declares `per_skala_rows_included: 8` (all rows). Run 2 declares `per_skala_rows_included: 8`. The canonical `per_skala` list in the by-code index has 8 entries. `served_extent` returns 8. `record_slice` sees `per_skala_rows (8) >= len(v) (8)` → keeps all 8. Correct.

Now: run 1 declares 8, run 2 declares 3. `served_extent` returns `max(8, 3) = 8`. `record_slice` sees 8 >= len(v) → keeps all 8. But run 2 only saw 3 rows. The judge receives 8 rows and is told (via `PER_SKALA_EXTENT_NOTE`) that the extent may be undeclared — but here it *was* declared, just not uniformly. The note says "IN EVERY OTHER CASE … the list below is the CANONICAL first rows", but the code took the `pass` branch (all rows served), not the canonical-slice branch. The judge gets the full list *and* the note telling it the extent is unknown.

**Is this a defect?** The note is attached at the payload level regardless of the trim outcome. The judge is told the extent is unknown, and indeed for run 2 it is partially known (3 rows). The `max` is a conservative choice: if *any* run saw all rows, the full list is the union of what was seen. The note's language ("IN EVERY OTHER CASE") technically does not describe this branch. But the note is a static string, not per-code conditional. The judge is told to "say in your reason that the served extent was undeclared" even when it was declared for one run. This is a **comment-code mismatch** in `PER_SKALA_EXTENT_NOTE`: the note claims the canonical slice stands for partial counts, but the code actually passes the full list when `max(counts) >= len(v)`.

**Concrete input exhibiting it:** run 1 declares 8/8, run 2 declares 3/8. The judge receives all 8 rows. The note says "the list below is the CANONICAL first rows and is not the served set in either direction." That is false for this code: the list *is* the served set for run 1. The note over-claims ignorance.

**Severity:** low-to-moderate. The judge is told to be more cautious than necessary, which is fail-safe for fabrication detection but may cause a false "fabricated" flag if the judge follows the note's instruction to "say the served extent was undeclared" and then treats a correct citation from rows 4-8 as unsupported for run 2.
