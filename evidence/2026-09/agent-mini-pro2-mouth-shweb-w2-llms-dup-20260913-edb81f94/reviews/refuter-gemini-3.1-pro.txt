### 1. HIGH — Map insertion order does not guarantee the top 5 most recent articles without an explicit sort
- **Claim**: *"keeps one entry per URL, with the most recent date"* and `[...byUrl.values()].slice(0, 5)` returns the 5 latest articles.
- **Why it breaks**: 
  In JavaScript, `Map.prototype.set(key, val)` on an **existing** key updates its value in-place but **does not update its insertion order**. 
  - If `enArticles` is already sorted descending by date: the first encounter of any URL is already the newest date. The check `new Date(a.publishedAt) > new Date(kept.publishedAt)` will *never* be true on subsequent duplicates, making the date comparison dead code.
  - If `enArticles` is *not* guaranteed to be sorted strictly descending by date (e.g., loaded across folders in filesystem order): suppose an older duplicate is encountered first at Map index 7, and the newest article across the entire site arrives later sharing that URL. Calling `byUrl.set(a.url, a)` updates the value at Map index 7. When `[...byUrl.values()].slice(0, 5)` is executed, that newest article is **dropped entirely from `latest5`** because it was never moved up or re-sorted.
  - Test 2 missed this because it tested a toy fixture with only **one** distinct URL, so `byUrl` only ever had 1 element.
- **What to check**:
  Verify whether `enArticles` is strictly sorted descending before line 156. If it is, deduplicating simply on first seen (`if (!byUrl.has(a.url)) byUrl.set(a.url, a)`) is cleaner and sufficient. If it is not (or if out-of-order arrival is expected), sort the deduplicated entries before slicing:
  ```typescript
  const latest5 = [...byUrl.values()]
    .sort((a, b) => new Date(b.publishedAt).getTime() - new Date(a.publishedAt).getTime())
    .slice(0, 5);
  ```

### 2. HIGH — `execFileSync(require.resolve("tsx/cli"), ...)` risks `EACCES` failures in CI
- **Claim**: Test 2 safely executes the generator child process via `require.resolve("tsx/cli")`.
- **Why it breaks**:
  `require.resolve("tsx/cli")` resolves to the raw JS/MJS entry point (e.g. `node_modules/tsx/dist/cli.mjs`), **not** the `node_modules/.bin/tsx` binary wrapper. 
  On POSIX environments (macOS/Linux), if `cli.mjs` is installed with standard `0644` file permissions (common in Docker containers, clean CI checkouts, or certain npm/pnpm setups), attempting to invoke it directly as the executable without a Node interpreter will throw `EACCES: permission denied`. On Windows, it fails with `ENOEXEC`.
- **What to check**:
  Change the invocation in `apps/mouth/src/lib/llms-article-exports.test.ts` to execute Node explicitly:
  ```typescript
  execFileSync(
    process.execPath,
    [require.resolve("tsx/cli"), join(app, "scripts/generate-llms-full.ts")],
    ...
  );
  ```
