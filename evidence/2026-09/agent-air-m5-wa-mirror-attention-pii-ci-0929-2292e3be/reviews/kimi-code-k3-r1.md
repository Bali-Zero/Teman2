• ## Verdict: ACCEPT-WITH-NOTES

The diff achieves both goals with sound fail-closed mechanics: the sentinel ends green on path-miss, merge_group always runs the corpus, cancel-in-progress is correctly disabled for the queue, the pytest pipeline propagates failure via `pipefail`, and the PG-discovery step fails red if no binaries exist. The notes below are hardening items, not blockers — the two MEDs deserve follow-up precisely because they are the same "armed vs. exists" failure mode the workflow comments rail against.

---

**1. (MED) Skip gate is evadable via xfail/xpass/deselect — line: `if grep -Eq '[0-9]+ skipped' pytest.out; then`.** The gate only matches `N skipped`. A test marked `pytest.mark.xfail` reports `N xfailed`, an xpass with `strict=False` reports `N xpassed`, and both are green. Likewise `N deselected` (e.g., via a future `--deselect`, `-k`, or `collect_ignore` — none shown in the diff) is invisible to the pattern. Whether the three suites use xfail is **not shown**, so this may be theoretical today, but the gate is meant to outlive the current files. Recommend widening to `'[0-9]+ (skipped|xfailed|xpassed|deselected)'` (plus `-rxX` for visibility), or adding `--strict-markers` and an ini-level `xfail_strict=true`. Positive notes on what _is_ covered: pytest exits nonzero on failures/errors/collection errors and `set -o pipefail` propagates the left side of the `| tee` correctly; pytest omits zero-counts so `[0-9]+ skipped` cannot false-positive on a clean run; piped output disables color codes; an unmatched glob reaches pytest as a literal and exits 4 (red). All good.

**2. (MED) Relevance regex under-matches disarm-by-config — line: the `git diff --name-only "$base"...HEAD | grep -qE '^(scripts/wa-mirror-attention-telegram\.py|scripts/tests/test_wa_attention_[^/]+\.py|\.github/workflows/check-wa-attention-pii\.yml)$'`.** The pattern covers the alerter, the test glob, and the workflow itself — internally consistent with the pytest glob (`test_wa_attention_*.py`), so no over-match of consequence. But a PR touching `scripts/tests/conftest.py`, `pytest.ini` / `pyproject.toml` / `setup.cfg` (addopts, markers, `--deselect`, `--ignore`), the lockfile behind the `asyncpg==0.31.0` pin, or any repo module the alerter imports at collection time would sentinel-pass while changing what the gate actually executes. None of these files are shown in the diff, so their existence is **not shown** — but `conftest.py` in particular can silently disarm the corpus (the exact superscar #2 shape in prose form). Recommend adding `scripts/tests/conftest\.py` and the pytest-config path(s) to the alternation.

**3. (LOW) `pull_request` types omit `ready_for_review` — line: `types: [opened, synchronize, reopened]`.** A draft PR marked ready does not retrigger; the last check result (from the last push) stands. Not a pending-forever trap (a status exists), and `synchronize` covers the common path, but if this mirrors guard-conformance.yml exactly it's a conscious inheritance — worth a one-line comment either way.

**4. (LOW) merge_group / fetch / base.sha handling is correct — no defect, one cost note.** Lines: `fetch-depth: 0` + `filter: blob:none`, and `base="${{ github.event.pull_request.base.sha }}"`. For PRs, checkout lands on the merge commit whose second parent is the base tip, so `base.sha` is reachable under fetch-depth 0, and `base...HEAD` (three-dot) diffs from the merge-base — standard and race-tolerant if base advances after the event. `blob:none` makes `git diff` lazily fetch blobs for changed files; works against GitHub's partial-clone support, just extra round-trips on large diffs — acceptable. For merge_group, the `!= "pull_request"` branch forces `run=true`, which is the correct posture for a queue gate (the queue must always execute the corpus). Concurrency group `...${{ github.event.pull_request.number || github.ref }}` resolves to `github.ref` for merge_group, so PR and queue runs don't collide. All sound.

**5. (LOW) Required-check trap: residual surfaces are acceptable — line: `cancel-in-progress: ${{ github.event_name != 'merge_group' }}`.** The pending-forever trap is genuinely closed: no top-level `paths:`, every PR triggers, path-miss ends in job-level success (all four work steps gated on `steps.relevant.outputs.run == 'true'`, and the gated steps _skip_ rather than fail), and merge_group cancellation is disabled so a queued run can't be axed by a newer push. Residuals: (a) on PRs, a superseded run reports _cancelled_ — for a required check that's a visible red/cancelled state needing a re-run, not a silent pend; acceptable and matches the stated pattern. (b) Fork PRs still need maintainer workflow approval, which holds a required check at "Expected" — that's platform behavior, out of scope, just be aware before flipping the branch-protection switch.

(LOW) Shell quoting/injection: clean.** Lines: the `run:` blocks. `${{ github.event.pull_request.base.sha }}` is interpolated unquoted-by-design but is a hex-only SHA from the event payload — not attacker-controllable text (PR titles/bodies never appear); `${{ github.event_name }}` is an enum; both are safely quoted inside `[[ ]]`.
