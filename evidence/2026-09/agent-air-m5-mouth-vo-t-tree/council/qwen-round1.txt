## Findings

**1. `ProcessRail.tsx` (`ProcessProgress`, `mapping === "HUMAN_CONTEXT"` branch) + `i18n.ts:~694` EN / `~1590` ID — the rail tells the visitor an eligibility-bearing answer is never sent to the engine, and it is.**
`process.decides_context` renders "Context for a human reader only — **this answer is never sent to the engine**" / "jawaban ini **tidak pernah dikirim ke mesin**", driven purely by `decisionMapping.kind`. The question the new test picks as its example, `holds_stay_permit`, is declared `{kind: "HUMAN_CONTEXT"}` (`tree.ts:263`) **and** is mapped: `mapCurrentStatusCode` does `if (facts.holds_stay_permit === "no") return known("NO_STAY_PERMIT")` (`fact-mapper.ts:680-681`), wired into the payload at `fact-mapper.ts:900` as `immigration.current_status_code`. So for every offshore applicant answering "no" — the majority path per the 2026-08-24 P0 funnel-cost fix, and the `OFFSHORE` default in this diff's own e2e — the rail asserts the engine never reads it while the client sends it as a **KNOWN** value on the fact path that feeds `derived.has_active_stay_permit`.
*Why it matters:* a false visitor-facing absolute about what decides their eligibility, in both languages, on the second question of the funnel. It also publishes the `tree.ts` invariant violation ("HUMAN_CONTEXT … must never be mapped into an engine FactPath") to the applicant instead of surfacing it. `ProcessRail.test.tsx`'s "says plainly when an answer is human context the engine never reads" pins the false sentence — it asserts the copy, not the behaviour.
*Minimal fix:* drop the "never sent to the engine" clause (EN+ID) and state only what the projection knows ("this question sets no fact of its own"); file the `holds_stay_permit` declaration-vs-mapper contradiction separately, since rule 2 forbids touching `fact-mapper.ts`/`tree.ts` semantics here. Re-point the unit test at the mapper.

**2. `OracleShell.tsx:890-900` + `ProcessRail.tsx` (`ProcessBranches`, `candidates.length === 0`) — provenance is dropped, so a guard/transport/shadow abstention is reported as an engine finding.**
The prop is built from `{state, candidates}` only. `process.candidates_none` then renders "**The engine named no product for these answers.** The outcome below says why." for *every* zero-candidate outcome. But `outcome-view-model.ts:20-28` exists to keep these apart ("visibly distinguishable from local safety abstentions, transport failures, public shadow verification and developer previews. Every non-ENGINE origin must carry zero candidates"), and `outcome-fallbacks.ts:59-66` gives CLIENT_GUARD/NETWORK_FAILURE/SHADOW → `TEMPORARILY_UNAVAILABLE, candidates: []`, `:124-127` gives CLIENT_GUARD → `HUMAN_REVIEW_REQUIRED, candidates: []`.
*Why it matters:* the sentence is true only for `NO_SUPPORTED_PATH` + `provenance === "ENGINE"`. It is false for CLIENT_GUARD (client refused the response), NETWORK_FAILURE (engine never reached), SHADOW (no real decision), an ENGINE outage, NEEDS_INPUT and HUMAN_REVIEW_REQUIRED — in each case telling the applicant *their answers* produced no path. That is the rail stating an eligibility conclusion no engine reached.
*Minimal fix:* carry `provenance` into `ProcessOutcomeSummary`; render `candidates_none` only for `provenance === "ENGINE" && state === "NO_SUPPORTED_PATH"`, otherwise the existing `verdict.provenance_headline.*` framing.

**3. `ProcessRail.tsx` (`ProcessProgress`, `model.decision === null`) + `i18n.ts:~696` — the entry screen says the engine has read answers that do not exist.**
`getProcessModel` returns `decision = null` for any non-question node: `framing`, `confirmation`, `verdict`. `LivingTree` is rendered unconditionally inside `<main>` (`OracleShell.tsx:884-890`), and `{kind: "framing"}` (`flow.ts:27`) is the first node of every interview. So before a single question is asked the rail reads "**No question is open. The engine reads the answers you confirmed.**" with zero facts on record — and repeats it on the confirmation card, before the applicant confirms.
*Why it matters:* an eligibility-relevant claim on the highest-traffic node in the funnel, where it is false and reads as broken.
*Minimal fix:* key the copy off the node, not off `decision === null` — `model.atOutcome` already exists; add framing/confirmation variants.

**4. `flow.ts` (`getProcessModel`, `showCategories`) — the skipped-`category` lane promises a choice the visitor cannot make.**
`showCategories = categoryLeaves !== null`, and `getTreeSteps` returns non-null leaves on **ordinal** position alone (`atOrPastCategory`), including when `category` was never asked. Reachable: the onshore urgent/expired/unsure `permit_expiry` lane that routes straight to `review_gate`, skipping `category` — documented in `getTreeSteps`'s own P0 comment. There `facts.category === undefined` → all 11 chips `pending` → `process.pruned_none`: "Every purpose branch is still open. **Choosing one closes the others.**" Yet the trunk marks `category` `"pending"` (the P0 fact-grounded rule), `isEditableTreeStep` requires `"done"`, so **no jump button exists** — there is no way to choose. Same shape for `facts.category === "unsure"` (the `notSure: {mode:"human-review"}` affordance), where purpose *has* been answered and the case is going to a human, but the rail still says every branch is open.
Corroboration: this diff adds `process.phase_status.pruned` ("not on this branch" / "bukan cabang ini") and never renders it — `getProcessModel`'s phase status can only be `current|done|pending`, so the skipped `intent` phase reads "not started" at the safety-check node.
*Minimal fix:* gate the category section on the `category` trunk step, not on ordinal position (`facts.category !== undefined || thatStep.status === "current"`), and add a "not on this path" state for a phase whose steps are all `pending` while a later phase is `current` — the string is already written.

**5. `flow.ts` (`getProcessModel`) — a post-verdict follow-up resets the rail to "Step 0 / nothing started" and deletes every jump button. *(reachability partly unverified)***
`getTreeSteps` returns `currentIdx === -1` for any node id absent from `order`, and then marks **every** trunk step `"pending"`. `getProcessModel` projects that as `answeredQuestions = 0` and all phases `pending` → "Step 0 of N", five stages "not started", and no `isEditableTreeStep` hits, so the whole jump affordance vanishes at the exact moment an extra question is asked. `ASK_FOLLOW_UP` accepts any registered id not already in history with no on-path constraint (`flow.ts:1198-1219`), and `questionForFact` returns `{followUp: true}` precisely for a collector *not* in `editableQuestionIds` (`engine-adapter.ts:1059-1080`) — i.e. an unasked, possibly off-path question; `flow.test.ts:1550` dispatches `stay_days`, off-path for any recognized category. Also, during a follow-up `atOutcome` is false, so the rail says "The engine is asked once, after you confirm your answers" *after* the engine answered NEEDS_INPUT — the answer that caused the follow-up.
*Unverified:* the mechanism and the test-only dispatch are confirmed; I did not produce a concrete engine NEEDS_INPUT payload whose unique collector is off-path, so production reachability today is unproven.
*Minimal fix:* when `trunk.every(s => s.status === "pending")` but `facts` is non-empty, fall back to fact-derived counts and suppress the stage list rather than reporting "0 / not started"; key the candidates line off "the engine has already been asked", not `current.kind === "verdict"`.
