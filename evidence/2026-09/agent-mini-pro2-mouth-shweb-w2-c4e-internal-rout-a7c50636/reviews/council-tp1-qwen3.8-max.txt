### Findings

**MED – Regex-based source parsing is a second point of fragility the first seat didn't attack**

- **Claim.** `internalRoutes()` extracts the array with `/const INTERNAL_ROUTES = \[([\s\S]*?)\];/` and then pulls every quoted token inside the captured block with `/["']([^"']+)["']/g`. The first seat fixed the single-vs-double-quote gap but left two live problems:
  1. A TypeScript type annotation (`const INTERNAL_ROUTES: string[] = [`) or an `export` keyword breaks the outer regex. The `expect(block).toBeTruthy()` guard makes this *loud*, not silent, so it isn't a correctness hole today — but it turns a refactor into a test-syntax fix that has nothing to do with route coverage, and the next person to hit it may just loosen the regex instead of understanding why.
  2. The inner regex scans *comments* inside the array. Today's comments are quote-free, but a future note like `// don't ship "/billing" yet` would yield the tokens `t ship ` and `/billing`. The first would be harmless noise; the second would silently mark a route as covered.
- **Why it matters.** The whole value of this test is that it is *derived from the filesystem* and therefore can't drift. But the "listed" side is derived from a regex over source text, which is exactly the kind of hand-maintained coupling the test exists to eliminate. The test is only as strong as its weaker half.
- **What to check / condition.** Either (a) import `INTERNAL_ROUTES` directly from `proxy.ts` (the test already resolves the file; a dynamic `import()` or a small re-export would give you the real array, no regex), or (b) at minimum, strip `//`-comment lines from `block[1]` before running the inner regex, and add a type-annotation variant to the outer one. If (a) is blocked by the proxy module pulling in runtime dependencies, say so in a code comment and do (b).

---

**MED – The walk still mishandles two Next.js directory conventions that are one refactor away from biting**

- **Claim.** `entry.name.startsWith("(") && entry.name.endsWith(")")` treats every parenthesised directory as a route group. Next.js intercepting-route markers `(..)`, `(...)`, and parallel-route slots `@name` are not groups:
  - `(..)photos` starts with `(` but ends with `s`, so it is treated as a *literal URL segment* and would produce a phantom route `(..)photos` that the test demands be in `INTERNAL_ROUTES`.
  - `@modal` does not start with `(`, so it is also treated as a literal segment.
  Neither exists in the tree today, but the walk is now the *class* guard; the next person to add an intercepting or parallel route gets a confusing red test instead of a clear "this convention is unsupported" message.
- **Why it matters.** The first seat's resolution correctly fixed route-group descent but did so by pattern-matching the *shape* of the directory name rather than encoding the App Router's actual naming grammar. This is the same category of mistake that caused the original two bugs: a partial mental model of the filesystem convention, written from scratch.
- **What to check / condition.** Add a guard or explicit filter for `@`-prefixed and `(..)`-style directories (even a `continue` with a comment is fine), or add a test fixture that includes one so the behaviour is documented. This is the condition for GO.

---

**LOW – `PAGE_FILES` omits `.mjs` / `.cjs`**

- **Claim.** The list is `page.tsx, page.ts, page.jsx, page.js, page.mdx`. Next.js will also resolve `page.mjs` and `page.cjs`. Unlikely in this codebase, but the test is sold as closing the class.
- **What to check.** Add them, or add a comment explaining why they're excluded. Not blocking.

---

**LOW – `Dirent.isDirectory()` is false for symlinks to directories**

- **Claim.** `fs.readdirSync(…, { withFileTypes: true })` returns `isDirectory() === false` for a symlink pointing at a directory; `isSymbolicLink()` is the separate check. If any part of `(workspace)` is ever symlinked (monorepo shared packages, CI overlays), pages behind the link vanish from the census silently.
- **What to check.** Confirm no symlinks exist under `(workspace)` today. If they do, or if the monorepo tooling could introduce them, use `entry.isDirectory() || entry.isSymbolicLink()` (and `fs.statSync` to confirm the target is a directory). Not blocking given the current tree.

---

**LOW – The `> 10` sentinel is a magic number that will rot**

- **Claim.** `expect(routes.length).toBeGreaterThan(10)` is the "guard the guard" check. If a future refactor legitimately reduces workspace top-level segments below 11, the test fails for the wrong reason and someone will lower the constant without understanding why it exists.
- **What to check.** Derive the expected minimum from a checked-in manifest or at least name the constant (`<REDACTED> = 11`) with a comment tying it to the current count. Not blocking.

### On the structural question

The same two walk bugs appearing in a sibling chunk-guard and in this test within an hour is **structural, not a slip**. The root cause is that there is no shared, tested `walkAppRoutes(dir): string[]` utility. Every consumer independently re-derives the App Router's directory grammar (route groups, dynamic segments, page-file extensions, intercepting routes) from memory, and every consumer independently gets the same edge cases wrong. The fix that was applied here (recursive descent + group transparency) will now need to be applied a *third* time the next time someone writes a route walker, unless the walk is extracted into a single module with its own fixture-based tests. I would not block this PR on that extraction, but I would file it as a follow-up before the next consumer appears, because the pattern says a third one is coming.

---

### Conditions for GO

1. Harden or replace the regex-based `internalRoutes()` (MED above). Minimum: strip comments before token extraction. Preferred: import the array.
2. Guard the walk against `@slot` and `(..)`-style directories, or add a fixture that documents current behaviour (MED above).

Everything else is advisory. The eight route additions are well-evidenced (byte-identical, 200, 0 staff markers, measured sizes), the class test is the right shape of fix, and the "innocence" test is a good counterweight. Ship it once the two conditions are addressed.
