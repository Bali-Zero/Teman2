# LOCALCI-SOVEREIGN — the local gate decides, GitHub is storage

Ruling: `docs/rules/RULINGS.md`, RULED 2026-10-07 (Zero, option 3 of three). Supersedes the end state of
`docs/specs/localci-gate-2026-10-06.md`; that spec's measurements, per-context table and transition shape stay
valid. This document is the plan, with the acceptance of every phase and the order that never leaves `main`
without a gate.

## 1. End state

- Merges to `main` are decided by a gate that runs on our hardware (Pro first; Mini as the second host later).
- A **merger** on Pro, with its own GitHub identity, is the only principal allowed to push to `main`. It takes a
  pull request marked ready, builds the merge candidate (the PR merged into current `main`, as the queue does),
  runs the local gate on it, and merges through the API when green. Agent sessions keep opening PRs; none can
  push to `main` and none holds the merger's credential.
- GitHub keeps the code, the PRs and their history. Required status checks and the merge queue are gone.
  Hosted workflows may remain as advisory scans (CodeQL, Dependabot) if Zero keeps them; none gates.

**Phase C, step C3a-2: the merger enqueues.** After a verdict, `merger.py` evaluates one criterion on the decision it just
made and, only when it holds and the merger is armed, puts the PR in GitHub's merge queue through the GraphQL mutation
`enqueuePullRequest(pullRequestId, expectedHeadOid = the decided head)`. It never merges or pushes itself, and `merge` still
refuses. The sub-criteria, each of which alone refuses and is named in the line's `refused` and `why`:

- no check of its own is FAIL, ERROR, STALE, INTERRUPTED, RUNNING or QUEUED, except `review.independent`, which must be
  QUEUED or PASS;
- every executed required context is OK; a BLOCKED context passes only when its mapping is `blocked` or `not_implemented`, and
  the line names each one with its mapping beside `executed_required: N/M`;
- every context branch protection requires, read live and never hardcoded, is green on the PR head, red-dominant: failure,
  cancelled, timed out, action required, pending or missing refuses, while skipped and neutral pass as they do on GitHub;
- the PR head is still the decided head; the PR is same-repo, not a draft, based on `main`, open and not in the queue (GraphQL
  `isInMergeQueue` / `mergeQueueEntry`); this head was not enqueued by an earlier tick;
- the label `localci:merge-shadow-ok` is on the PR, applied last by an account whose repository role is admin or maintain.

The arm has two halves: that label, and `LOCALCI_MERGER_ARMED=1` in the tick's environment. Without both, the merger stays
shadow and journals `would_enqueue` with the same criterion, every sub-criterion true or false, and the head oid. That line is
the proof read before arming. The flag stays OFF until a proof PR shows `would_enqueue` with every sub-criterion true and only
`armed_env` refused. The proof PR is docs-only, judged by main's code, and NOT armed with `--auto`, so the merger's enqueue is
the only path into the queue. An enqueue journals `enqueued` with the queue entry id, its position and the head oid. A failed
mutation journals `enqueue_error` with GitHub's message, redacted, and is never retried in that tick. `report` prints
`enqueued` and `would_enqueue` on the phase-E line. Every write runs under the ambient `gh` token on Pro until Zero installs
the merger's own credential (§4.1).

**Phase B, step B5: a rewritten judge is no verdict, and a skip is compared as a skip** (RULED 2026-10-08, read from the first tick on B3's code, decision 09:49:54Z on PR #8076).

_The rewritten judge._ A context runs its trusted files from BASE (`trusted_base_required`, `trusted_from_steps`): the candidate never judges itself. When the candidate's diff rewrites one of those files (the plan's `judge_modified`), the BASE judge's run is not a verdict on the candidate in either direction: a green was already not claimed (`steps_verdict` → BLOCKED); from B5 a red is not claimed either — the BASE judge read red against a tool whose contract the same PR changes (#8076: a health state added to the tool, the registry and the test together; the BASE test knew four states, the candidate's tool five; hosted judged with the candidate's test and read green). The rule: a FAIL or ERROR on a step whose trusted inputs the candidate rewrote is `BLOCKED judge_rewritten: <step> read red with the BASE judge while the candidate rewrites <files>; hosted judges with the candidate's copy, which this run did not execute — no verdict (never FAIL, never OK)`; a red on a step whose trusted inputs the candidate did NOT rewrite stays FAIL (the scope is the step, not the context); `hosted_compare` classes it `LOCAL_BLIND`, never `FALSE_RED`; the C3a-2 criterion refuses it (an executed mapping that is not OK). What this does not do: it does not run the candidate's judge. A PR that rewrites a judge is the reviewer's (`review_independent`), and the gate's row says so; running both judges and reporting the pair is a later step if phase D shows judge rewrites are frequent (today: 1 of 60 decisions).

_The agreed skip._ A required context the trusted change_map does not select is NOT_APPLICABLE here and skipped hosted, and GitHub counts a skipped required context as satisfied. The two sides agree on a decision — the classifier's — and that agreement is compared, because a wrong skip would be a false green and must be seen. From B5 the row says what was compared: `local_detail: NOT_APPLICABLE (skip agreed: change_map)` when both sides skipped; `OK (executed; hosted skipped)` when the runner executed what hosted did not (counted full: more was tested here); `NOT_APPLICABLE (skipped here; hosted ran)` when hosted executed what the runner skipped — counted `partial` and named, because the local verdict is a subset of hosted's. The report prints `compared_skip_agreed=N` on the window line, apart from the executed agreements, and the phase-E line names how many of a compared merge's full contexts were skip agreements. The compared-merge rule (≥ 12 compared, ≥ 11 full, ≤ 1 partial) is unchanged: a skip agreement is a full comparison of the decision; it is never silently labelled `OK (executed)`.

**B11 (RULED 2026-10-09): the merger also replays the commit GitHub merged.** Measured on Pro (report of 2026-10-09T06:33Z, window from 2026-10-07T07:37Z): of 26 merged PRs only 9 were merged by GitHub onto the base the local gate decided; 17 (65 %) were merged onto a main that had moved during a 10-48 minute tick, so `compared_merges` stood at 1 after two days and phase D's >= 50 over >= 14 days was unreachable, not slow. The merger therefore also judges, as a _replay_, the exact main commit that merged a PR: candidate = that commit, BASE = its first parent (already on main, trusted), hosted verdict read on the same sha; replays alternate with PR decisions (a replay when the previous decision was not one, or when no PR is waiting), once per merge commit, newest first (B11b, RULED 2026-10-09 after the first live replay: oldest first, the first replay at 09:54Z judged pr8015's merge of 2026-10-07 on a base whose runner executed no context — 14 LOCAL_BLIND, BLOCKED — and 81 more merges of 10-07/10-08 stood between it and the first base on which a PR decision compared 12 contexts, `86b151beec` of 2026-10-08T15:51Z (the decisions before it compared 0-9: the runner gained its contexts step by step, B1-B4, and the VM was full from 15:27Z to 17:27Z); with main taking 31-56 merges a day against about one decision an hour, oldest first never reaches the present, and each old lockfile costs a deps image of its own). Newest first, a merge can be seconds old at the fetch: a commit whose PR GitHub still shows open is asked again on the next replay turn instead of being journalled `replay_unmapped` for good. A replay that meets the unchanged per-merge thresholds (>= 12 contexts compared, >= 11 of them full, <= 1 partial) is a compared merge by the existing definition, a PR counting once. Every other term, `hosted_required_green` and `review_not_blocking` (B29) included, counts; a row whose criterion lacks a term, or carries none, is not mergeable (fail closed).

    if v == "OK":                                                                                    return "OK"
    return "RED"                  # FAIL, ERROR, UNCOVERED, absent, BLOCKED of any other kind

R      = [c for c in required if cls(results.get(c)) == "RESCUE"]

only   = base and not X and bool(R)                                  # the gate is the ONLY reason E could be false
gated  = {c: gate(G1) and base and not X for c in R}                 # record
hosted = lambda H: H == "green"                                      # NEVER substituted by gate(G)

            and L and (E(G1) or only))                               # B19 pending, on RECORDED inputs
ok2    = (pending1 and moved == "none" and local_checks_clean and review_independent and same_repo2
          and (not R or gate(G2)) and hosted(H2) and all(pr_terms2)) # the retry's would_enqueue.ok

### 2b.2 Gate verdict provenance: the Pro ledger

Measured 2026-10-15 (names only, no value read): the combined `commits/{sha}/status` entries carry no creator; every

The ledger is out of the candidate's reach because of facts measured 2026-10-15, each an invariant a later PR must keep:
no self-hosted runner; no public ssh ingress to Pro (cloudflared/Funnel route HTTP app ports only); no secret carries a

**Ledger.** On Pro, `~/.nuzantara-pilots/local-ci-gate/verdicts.jsonl`: directory 0700, file 0600, owner = the merger's
uid; outside the merger state dir, `prune.py`'s scope and every run dir; never in a container argv or env; retention
forever; added to the M5 `~/Backups` set. One JSON line per verdict, exact key set (unknown keys rejected):
`v` (1), `ts` (Pro clock, set by the appender), `repo`, `pr` (a positive int, or null when the gate posts before its PR exists; it is not part of the verification key and is never derived by guessing), `head_sha` (40 lowercase hex), `verdict` (`success` or
`failure`), `gate_session` (str, at most 80), `evidence_sha256` (64 hex or null), `supersedes` (64 hex digest of an earlier
line, or null), `via` (measured from `SSH_CONNECTION` by the appender, never supplied). A line's digest is the sha256 of its bytes without the newline.

**Writer, first.** `scripts/harness_fable_gate.py` appends over `ssh pro` through the tick wrapper's own `gate-append`
mode (so writer and reader are the code the tick runs; superscar #1), and only then posts the GitHub status. The entry
travels as ONE base64 argv, never JSON on a shell line; the appender validates it, refuses a ledger whose last byte is
not `\n`, takes `LOCK_EX`, `O_APPEND|O_CREAT` 0600, one `write()`, `fsync`, and prints the digest; it is idempotent on
(repo, head, verdict, evidence, supersedes) while the head's NEWEST entry carries them (an older twin behind a later verdict is not one). A failed append exits non-zero and posts nothing, so a GitHub-only success is
always an anomaly. `--supersede` (a flag of `gate-append`, success verdicts only; with nothing to supersede it is a plain append, or a no-op when the newest entry is already a success with the same evidence) makes the appender, under the lock, name the digest of the newest UNSUPERSEDED non-success entry of the head, one append per unsuperseded failure (so `F,F,S` takes two). The caller supplies exactly `repo`, `pr`, `head_sha`, `verdict`, `gate_session`, `evidence_sha256`, `supersedes` (null with `--supersede`); `v`, `ts` and `via` are the appender's, and any other key is rejected. `gate_ledger.py verify` reports the first bad line and the mode; `quarantine --line N` moves one
bad line to `verdicts.quarantine.jsonl` and journals it, and REFUSES a line that validates (else it is an override). The
tick journals `gate_ledger_unreadable` once; any session can run both, no human.

**Reader, one rule** `gate_verdict(path, repo, head)`:

1. `lstat` missing, not a regular file, a symlink, any group/other mode bit, or owner not `geteuid()`: false.
2. Under `LOCK_SH` every line must parse and validate, else false for EVERY head. `validate` is the schema alone: a `supersedes` that names no line of the file is valid and supersedes nothing (else `supersede-any-digest` would be equivalent at both sites).
3. `mine` = entries with `repo` equal and `head_sha` equal (exact 40-hex equality); none: false. `repo` is compared byte for byte (the merger binds `lower()`, so P3 must pass `Bali-Zero/Teman2`).
4. The newest of `mine` (the last line in file order, never by `ts`) must be exactly `"success"`; every earlier non-success entry of `mine` must be named by the
   `supersedes` of a later entry of `mine`; otherwise false.

### B36 Mutant rows as append-only fragments

`merger_mutants.py` kept one dict, and every LocalCI PR appended at its tail, so each merge made the others DIRTY and an
armed branch is frozen. New mutants now go in `scripts/localci/tests/mutants/rows/<feature>.py`, one file per change,
defining `ROWS` with the SAME tuple shape as `MUTANTS`. A rows file may `from merger_mutants import` any module-level name the table defines
on main (e.g. `PY`, `SH`, `MERGER_T`, `RD`, `cq`; check the file, a name that exists only in another PR's head is not there yet).
`merge_rows()` runs at import, after every helper and the dict are defined, so a harness that only imports `merger_mutants`
and iterates `MUTANTS` sees the rows too, and again from `main()`: it is idempotent (a row already merged from the same file,
identical, is skipped) and the module registers itself as `merger_mutants` first, so there is no circular import. Files merge
in sorted filename order (`_`-prefixed files are skipped); a duplicate name (across files or against the inline dict), a
missing or non-dict `ROWS`, or a malformed row stops the run (exit message, not a skip). A rows file never writes `MUTANTS`
itself (an AST test over `rows/*.py`). `--list` and `--only` see rows exactly like inline ones. Inline rows stay where they are. Bites: the next LocalCI PR adds
its mutants as a rows file and merges without touching the dict.

## 6. §B35 — the run budget

**Measured (Pro journal, `decisions.jsonl`, 2026-10-08 to 2026-10-15, read-only).** 252 decisions; the 36 with
elapsed >= 3000 s are the full-matrix runs (the rest reuse receipts or stop early). The runner executes the
checks one after another, so the run step costs the SUM of their durations.

| quantity                              | p50         | p95         | max                                            |
| ------------------------------------- | ----------- | ----------- | ---------------------------------------------- |
| full-matrix elapsed (plan+run+status) | 3848 s      | 4878 s      | 5486 s (= the 5400 s cap + the plan; censored) |
| ctx.backend-tests                     | 1451 s      | 2252 s      | 2511 s                                         |
| ctx.e2e-tests / frontend-mouth        | 423 / 352 s | 547 / 595 s | 608 / 708 s                                    |
| ctx.visa-oracle-smoke (late check)    | 153 s       | 193 s       | 203 s (job budget 1800 s)                      |

One run ended `run_rc 124`: #8523, 2026-10-15T02:16Z, 5486 s. Its twelve first contexts had used about 5400 s; `ctx.visa-oracle-smoke`
was SIGTERMed 88 s after it started and read INTERRUPTED, the later checks never ran. Three other runs of the last 14 h took
4406 to 5077 s (and 4878 s a day before): the margin under the cap was down to 6%. The 5486 s is censored by the cap, so the true need of #8523
is its 5400 s plus the rest of visa-oracle-smoke (about 65-115 s) and the checks after it: about 5600 s.

**New budget: `RUN_TIMEOUT_S = 7200`** (named constant in `merger.py`, default of `--run-timeout`). 7200 = the censored need
(5600 s) x 1.28. It is not "p99 + the 1800 s job budget of visa-oracle-smoke" (7400+): that job budget is a hosted
ceiling, the check itself measured 153-203 s, and a budget sized on ceilings would keep an hour of dead air before a hung
run is cut. The growth that matters is backend-tests (the largest check); 28% covers about 700 s of it plus the late checks.

**Every dependent bound, updated together.**

| bound                                         | before | after | rule                                                                                                                      |
| --------------------------------------------- | ------ | ----- | ------------------------------------------------------------------------------------------------------------------------- |
| `--run-timeout` default (README, `merger.py`) | 5400   | 7200  | `RUN_TIMEOUT_S`                                                                                                           |
| `TICK_TIMEOUT_S` (tick watchdog)              | 14400  | 16200 | >= plan 7500 + run 7200 + status 900 + 600 margin (was margin 300+300)                                                    |
| `expected_hb_seconds` of `pro.localci_merger` | 5400   | 6000  | 3 x it must exceed `TICK_TIMEOUT_S` + 600 (the healer's dead window), with slack for the 60 s kill grace, fetch and prune |

Unchanged on purpose: `PLAN_TIMEOUT_S` 7500 (cold deps build, not the run), the status step 900, the launchd `StartInterval`
600 and the plist (it passes no `--run-timeout`; the default is read from the merger at the tick's sha), the lease and its
reclaim (pid liveness, `take_lease`: they follow the process, not a run budget), and the B33 chain: each chained tick writes its own heartbeat before it
re-execs, so the chain cap of 12 never stretches the per-tick bound above.

**Why it cannot make a verdict greener.** The budget only decides when the runner stops waiting. A check that finishes inside
7200 s gets the PASS or FAIL its own steps earn; a check that was cut at 5400 s read INTERRUPTED (never PASS). Nothing about
which checks run, their order, their per-job `timeout-minutes` (kept as hosted's ceiling), the tolerance, the seal or the
status binding changes. A run that really hangs is still cut, now at 7200 s, and reads INTERRUPTED as before.

**A run that still exceeds 7200 s.** It is cut as before: the run step is SIGTERMed, the check in flight reads INTERRUPTED,
the later ones never start, and the decision is not green. Post-flip an INTERRUPTED run is not re-decided on the same base
(B30 excludes that class; gate-b30 verified it on the candidate tree), only when the base moves, about 90 minutes of lane each
time. That is why the budget is sized on the need plus 28% rather than on the median: at p50 3848 s, p95 4878 s and a
censored max of about 5600 s, a normal full-matrix run now has about 1600 s of headroom, and an INTERRUPTED means a hang or a
host fault, not an honest slow run. Nothing watches the drift automatically: the evidence is `merger.py report`'s `ticks.longest_s` and
`ticks.check_max_s` (and each decision row's `elapsed_s`), and the review threshold is a human one: when a full-matrix run
reaches 6500 s (90% of the budget), whoever reads the report re-derives the budget from the new journal, by the same table,
before it is hit.

**READY's age and a long run (B20 R6).** `READY_MAX_AGE_S` is 7200 s. The cache is refreshed when it is
older than `READY_REFRESH_S` (3600 s), so at the start of a decision tick it is already up to about 3600 s old. READY is
therefore stale at the merge when the tick's elapsed time exceeds 7200 s minus that age at the tick's start: a run of about
3600 s (the p50 is 3848 s) can already end READY-stale (a run of 7200 s minus a fresh cache age always does). The merge is then refused as `READY stale`, B19 keeps
the PASS pending, and the retry merges after the next refresh tick has renewed the cache (one refresh tick, then the retry
tick). The cost is a delay of a few ticks, never a wrong merge; raising `READY_MAX_AGE_S` is not part of this change.

**Why not an ordering change.** The sum of the checks is the same in any order; moving the long late checks first would only
move which check is cut when the budget is short, not whether the run fits. The smaller safe change is the budget.

**Pinned** by `test_the_timeouts_hold_a_cold_build_inside_one_tick` (the default equals `RUN_TIMEOUT_S`; tick >= plan + run + 900 +
600; `RUN_TIMEOUT_S` >= 1.25 x the 5600 s need; 3 x `expected_hb_seconds` > tick + 600), by `test_the_plan_step_outlasts_a_cold_deps_build`
(the run step is handed `RUN_TIMEOUT_S`) and by the `b35-*` mutants.
