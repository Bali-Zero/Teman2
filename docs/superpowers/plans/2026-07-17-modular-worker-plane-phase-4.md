# Modular Worker Plane Phase 4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move notification scheduling, then WhatsApp outbox processing, from API/RAG lifespan ownership to the companion worker application without changing their business identities or rollback ability, while encoding their real provider delivery limits instead of overstating exactly-once/idempotent guarantees.

**Architecture:** Phase 4 is an adapter migration. Phase 0/1 `WorkloadSpec`/`WORKLOAD_CATALOG`, `SideEffectCapability`/`SIDE_EFFECT_CATALOG`, `OwnershipGrant`, `ClaimContext`, job envelope, lease/fence guard, and schedule-run identity are the control plane; the durable effect ledger is introduced by Phase 3. Existing `NotificationScheduler` and `WAOutboxWorker` remain domain primitives behind worker-plane adapters; neither is duplicated. One ownership generation is authoritative at a time. Compatibility/cutover is one release; legacy-lifespan deletion is a later release after production observation and a reverse-cutover proof.

**Tech Stack:** Python 3.11, FastAPI lifespan, PostgreSQL/asyncpg, APScheduler adapter, existing WA outbox table/Graph adapter, pytest, Fly process groups, GitHub Actions.

## Global Constraints

- This plan starts only after Phase 0–3 evidence shows G2–G6, G13–G17, and the worker companion `/ready` endpoint passing. Record the evidence bundle path in each PR description; do not recreate Phase 0/1 contracts with parallel names.
- Treat `BusinessContext`/`business_context`, `RuntimeOwner`/`runtime_owner`, `WorkloadSpec`, `WORKLOAD_CATALOG`, `get_workload_spec`, `SideEffectCapability`, `SIDE_EFFECT_CATALOG`, `OwnershipGrant`, `ClaimContext`, workload modes (`off`, `shadow`, `draining`, `active`), `ownership_generation`, job envelope, lease guard, and effect-ledger states as the canonical Phase 0/1 contracts. Business/data ownership never changes merely because execution moves; grants, claims, heartbeats, leases, and CAS transitions use only `runtime_owner`. Their only homes are `backend/architecture/catalogs/{models.py,workers.py,events.py,effects.py,tables.py}` and `backend/worker_plane/{models.py,repository.py,ownership_service.py,liveness.py}`; import them rather than adding an alias, second registry, or second service.
- Every table touched by this phase uses the Phase 1 `TableOwnership` contract: one `business_context`, sorted repeatable `writer_bindings`, and `migration_sources`. No migration, JSON catalog row, model, or test may use a legacy singular writer field. Shared effect-ledger tables receive distinct notification/WA workload-specific grant-fenced bindings for automatic prepare/begin/finish/reconcile mutations and distinct static `api` bindings for operator resolution; no public or private mutation API accepts a caller-selected workload, and shared helpers are pure/read-only.
- Workload identity is stable: `notification_scheduler` and `wa_outbox`. The scheduled notification run identity is exactly `(workload_name, originating_scheduled_for_utc)`; the originating daily business instant is persisted and normalized to UTC, and an hourly poll/retry instant never replaces it. Notification email effect identity is exactly the canonical tuple `(notification_scheduler, originating_scheduled_for_utc, email:<alert_type>, client:<client_id>)`, HMAC-SHA-256 encoded as `notification:v1:<hex>` with the dedicated stable `EFFECT_KEY_HMAC_SECRET_V1`. Only the opaque key/reference is persisted or logged. Email address, To/BCC envelope, subject/body, randomized content, alert row ID, poll/retry time, attempt, claim token, runtime owner, and ownership generation are never key components. The resolved To/BCC envelope is frozen and versioned separately from the effect key so a retry cannot silently change recipients.
- The existing notification service retains SMTP/SendGrid compatibility for legacy callers, but the Phase 4 worker path is pinned to one exact provider: it constructs `backend.app.modules.notifications.service:SendGridProvider` with the injected `SENDGRID_API_KEY` and passes it as `NotificationService(..., email_provider=provider)`. The worker never calls `NotificationService._create_provider`, never reads `EMAIL_PROVIDER`, and never auto-detects SMTP credentials. `notification_scheduler` allows exactly the secret symbols `EFFECT_KEY_HMAC_SECRET_V1` and `SENDGRID_API_KEY`; `EMAIL_PROVIDER`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, and `ZOHO_SMTP_PASSWORD` are absent from its capability. The shipped SendGrid contract remains exactly `non-reconcilable`: it exposes neither a deterministic provider idempotency key nor a destination lookup by stable effect reference. A timeout, cancellation, transport break, process death after dispatch, or provider-accepted/database-confirmation crash records `outcome_unknown` and forbids automatic resend. Changing this to `provider-idempotent` or `reconcilable` requires a separate catalog-contract change with real provider proof, tests, and panel review. Scheduler dispatch, the existing request-facing send-pending route, and admin retry must all enter through the same claim/effect-ledger fence; no endpoint may call the provider directly.
- Preserve the WA worker’s per-thread ordering, claim-token/lease heartbeat, retry/backoff, and Graph-send behavior. The Phase 4 catalog pins the Graph send contract to `non-reconcilable` unless this task produces and independently reviews a real provider reconciliation implementation. For an ambiguous external WA result, record `outcome_unknown`; automatic retry is forbidden (G15). A later change to `reconcilable` is a separate catalog-contract change with provider proof, tests, and panel review, not an implementation-time assumption.
- Every ownership move uses the same ordered protocol. Forward: target observes in `shadow` while the source remains `active`; source transitions `active -> draining` without changing generation; the drain barrier proves no live source lease, no `attempting` effect, and no unresolved non-reconcilable `outcome_unknown`; only then does one CAS activate the target at generation N+1. Reverse: the current worker owner transitions `active -> draining`; the same barrier passes; only then does one CAS activate the legacy owner at generation N+1. No transaction or command makes the target active while the source is still active.
- Never put client content, Graph/email credentials, email addresses, phone numbers, business-recipient identifiers, or raw payloads in logs, metrics labels, review packages, or rollout evidence (G10). Use versioned opaque HMAC references/hashes only; never persist the HMAC input or secret.
- Notification and WA inherit the Phase 3 automatic-effect fence without weakening it. Every workload-bound `prepare`, `begin`, `finish`, and `reconcile` Python wrapper requires the fixed domain-claim locator, `claim: ClaimContext`, `expected_claimed_at`, and the current expected lease-expiry stamp. Its matching workload-specific SQL function receives the scalar runtime owner, generation, build epoch, token, claimed-at stamp, and lease-expiry stamp; in one transaction it locks grant -> domain claim -> effect projection -> current began-attempt event when applicable and validates the live grant, immutable domain-claim stamp, unexpired lease, exact expected attempt ID/state, and the attempt's recorded immutable stamp before DML. Finish additionally requires the attempt creator stamp to equal the current claim stamp. Reconcile may classify an exact locked older attempt after timeout plus margin, but only through a different current live claim; the stale caller's old claim fails the live fence. Prepare therefore cannot race a cutover, and a stale finish/reconcile cannot overwrite a later attempt. A pre-transaction ownership check is never authority.
- `resolve-unknown` is never part of those grant-fenced bindings. Notification and WA each receive distinct projection and attempt static `api` resolution bindings, backed by workload-specific Python/SQL wrappers that accept no `ClaimContext` or caller-selected workload. Resolution requires the exact effect key, expected attempt ID, expected `outcome_unknown` state, actor, reason, terminal result, and provider reference when confirmed. The protected static API management database role has `EXECUTE` only on the named resolution functions and no direct ledger/attempt DML; normal API request roles and worker roles are denied. Resolution remains available while the workload is `off` or completely drained.
- No new public Fly service, no Kafka/Kubernetes, no service/database split, no embedding-model change, and no direct `asyncpg` added to routers. The companion is a private worker process with `:9091/ready`.
- Tasks 1–4 and their compatibility panel are pre-merge work. They may use CI, a disposable real PostgreSQL instance, and simulated ownership/transition fixtures, but they must not mutate live staging or claim live staging cutover evidence. All live staging deployment, shadow observation, drain/CAS activation, reverse-cutover, and evidence capture starts only after the protected merge in production-rollout Task 2.
- Every task below ends with the specified SDD review package, independent spec review, independent quality review, and an atomic conventional commit. A review may not approve its own implementation.
