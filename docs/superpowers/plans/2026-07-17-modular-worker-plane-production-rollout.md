# Modular Worker Plane Production Rollout Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Safely ship worker-plane/receipt compatibility Release A from the current feature branch, prove its fleet-wide bridge behavior, ship a separate receipt-activation Release B only after build-floor/backfill/binary-matrix proof, then cut over `workflow_queue`, `legal_full_ingestion`, `notification_scheduler`, and `wa_outbox` one at a time, observe and reverse-prove them in production, and finally ship a separate legacy-lifecycle deletion release after every rollback window closes.

**Architecture:** The companion worker app runs the same image digest as the API/RAG processes but exposes no public service; API/RAG remain request-serving during the compatibility/cutover releases. Release A installs the additive receipt schema and runs only `legacy-global-bridge`; Release B remains bridge-compatible during its rolling deploy and changes receipt authority only through a post-build-floor audited CAS after exact-digest staging proof. PostgreSQL ownership generation is the only authority for which runtime may execute durable work. Forward and reverse moves use one protocol: drain the current source, pass the lease/effect/unknown barrier, then activate the target at a newer generation. A reverse cutover never restores legacy authority while the companion can still claim. Only a separate later PR/release removes legacy lifespan wiring after live rollback windows and reverse/re-cutover proofs have closed.

**Tech Stack:** GitHub PR/Actions, Fly.io process groups, PostgreSQL, Redis, `/ready` health endpoint, worker-plane ownership/effect/receipt observability, pytest and production-safe probes.
