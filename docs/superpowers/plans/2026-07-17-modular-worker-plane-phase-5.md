# Modular Worker Plane Phase 5 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Introduce a rolling-compatible bridge from the legacy global outbox acknowledgement to independent durable subscription receipts, activate durable fan-out only in a second protected release after fleet and backfill proof, establish a normalized contract registry across PostgreSQL outbox and Redis Streams without merging them, and ratchet architecture gates so old direct/unsafe paths cannot return.

**Architecture:** PostgreSQL `events_outbox` remains the durable cloud event truth and Redis Streams remains local/low-latency transport. The systems share envelope, event catalog, ownership, and compatibility registries; they do not share storage, offsets, acknowledgements, retention, or replay semantics. Phase 5 ships in two protected binary releases. Release A adds the receipt schema and a resumable dual-read/dual-write bridge while global `consumed_at` remains authoritative and durable fan-out remains rejected. Release B retains that bridge as rollback compatibility, but may make named receipts authoritative and admit fan-out only after the complete RAG census is at the activation build floor, deterministic backfill is complete, and the old/new binary matrix is green. In receipt-authoritative mode a delivery is complete only when its named subscription receipt is terminal; global `consumed_at` remains writable only for catalog-declared single-consumer compatibility traffic.

**Tech Stack:** PostgreSQL/asyncpg, Redis Streams, Python 3.11 async services, pytest, GitHub Actions architecture guards.

## Global Constraints

- Begin only after the formal Phase 4 Tasks 1–4 compatibility checkpoint is `GO` or `GO-WITH-CHANGES`, its integrity validator reports no unresolved Blocking/Important finding, and record its commit SHA/evidence bundle in the Phase 5 PR. Production cutover and the later Phase 4 Task 5 deletion are not prerequisites for Phase 5 implementation. Preserve the Phase 0/1 names: `BusinessContext`/`business_context`, `RuntimeOwner`/`runtime_owner`, `WorkloadSpec`, `WORKLOAD_CATALOG`, `get_workload_spec`, `SideEffectCapability`, `SIDE_EFFECT_CATALOG`, `OwnershipGrant`, `ClaimContext`, ownership generation/fence, stale-event quarantine, and capability contracts. Business/data ownership and runtime execution remain independent; no compatibility alias may collapse the two.
- Every table added or changed in this phase uses the canonical Phase 1 `TableOwnership` shape: one `business_context`, sorted repeatable `writer_bindings`, and `migration_sources`. Legacy singular writer metadata is forbidden. Grant-fenced mutation interfaces bind one exact catalog workload and its bounded candidate owners; no caller selects a workload at runtime, and common helpers are pure/read-only.
- No bus merge: do not move cloud outbox traffic to Redis, move Redis offsets to PostgreSQL, introduce Kafka, or create a “universal consumer” that hides different delivery semantics.
- Subscriber identity is an explicit stable catalog key, not a process PID. A receipt uses `(event_id, subscription_name)` and independently records state, attempts, lease owner/expiry, consumer identity, timestamps, and diagnostic/error class. PII payload is never copied into receipts.
- Unknown event/schema/subscription, expired retention, or incompatible consumer version is quarantined/DLQed with alert evidence. It is never silently acknowledged as stale (G17).
- Preserve the inbound-webhook queue wake-up behavior only as explicitly cataloged best-effort wake-up; the underlying durable table remains the truth. Do not claim it has durable fanout semantics.
- Phase 5 extends but does not reimplement Phase 0 durability. PostgreSQL stale/unknown/incompatible events must delegate to `backend.services.events.quarantine.quarantine_outbox_event` and its existing post-commit alert path. Redis consumers must reuse Phase 0 `EventSubscriber` reclaim, PEL, idempotency-outage, and failure-before-ack behavior. Keep the complete Phase 0 quarantine and Redis reclaim suites green as named regressions in every affected task.
- Phase 5 implementation and its panel are pre-merge. They may use CI, disposable real PostgreSQL, and simulated fixtures, but they must not mutate live staging or present live staging evidence. All live staging deployment/mutation/evidence starts only after protected merge in production-rollout Task 2.
- The first protected compatibility merge is Release A and must remain in `legacy-global-bridge` mode throughout its rolling deploy: no second durable subscriber is registered, global `consumed_at` remains authoritative, and receipt rows are only a mirrored compatibility projection. Receipt authority and the first fan-out subscriber require a separate protected Release B, an exact-digest staging activation/reversal proof, and the production activation gate in the rollout plan. No old Release-A-or-earlier binary may coexist with receipt-authoritative mode.
- Every task must include the review package, independent spec review, independent quality review, fixes, tests, and one atomic commit before the next task.
