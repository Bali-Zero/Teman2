# Verdict

**NO-GO — confidence 72.**

The spec is honest about many scars and the incremental-hardening direction is sound. But three load-bearing invariants are false as written: the fencing-generation model cannot prevent duplicate irreversible side effects during cutover; the `events_outbox` cannot carry multi-subscriber fan-out in the Phase 3→5 window; and the "least-privilege worker" claim is unenforceable in the proposed Fly topology. These are not wording issues — they are shared assumptions that propagate into G2/G3/G10/G11/G12, making those gates green-but-dead.

# Blocking findings

**B1 — Cutover duplicates irreversible side effects for channels without provider-side idempotency.** Spec §7.2 (line 387-391), §7.3 (line 413-416), §13 (line 601-616). The cutover sequence is `old=off → drain/expire leases → advance generation → new=active`. The fencing generation is checked only at "the next claim or side-effect checkpoint" — it does not abort an in-flight provider HTTP call. Concrete failure: old owner holds a WhatsApp/Instagram/Brevo send in flight (provider latency > lease*seconds); step 3 reads the lease as expired; step 4 advances the generation and the new owner reclaims the job and re-sends. The spec's mitigation (§16 risk table: "provider-side idempotency key plus local side-effect ledger") presupposes a provider capability the spec never inventories. §7.3's "records the provider request key and result before acknowledging the job" is SEND→RECORD→ACK ordering — a crash between SEND and RECORD still duplicates. G12 ("no duplicate external side effect") is unfalsifiable for any channel whose API offers no idempotency header.
\_Falsifiable correction:* require a pre-flight dedup INSERT (`INSERT … ON CONFLICT (channel, thread_id, outbound_seq) DO NOTHING` returning `xmax=0`) gated ahead of the provider call, OR forbid generation advance until `max(provider_call_latency)` after old-owner lease expiry, with the new owner refusing any job whose `not_before` is within that window.

**B2 — `events_outbox` is single-consumer-summed; Phase 3 moves durable consumers before Phase 5 introduces per-subscription receipts.** Spec §8.2 (line 452-456) admits the global `consumed_at` models single-consumer completion; §12 Phase 3 (line 570-580) moves workflow queue + legal ingestion to `worker`; Phase 5 (line 592) adds receipts. Verified: `apps/backend-rag/backend/services/events/outbox.py:258-268` `acknowledge()` sets `consumed_at` globally; `replay_unconsumed()` (line 408) acks each row after the single `dispatch_fn` returns. If a second durable subscriber is added to any existing channel between Phase 3 and Phase 5 (§8.2 explicitly permits multi-subscriber events), the first ack removes the row from the unconsumed set and the second subscriber silently misses every event that arrived during a listener disconnect. Silent work loss; `get_unconsumed_count` reports zero. Green-but-dead.
_Falsifiable correction:_ make "no new multi-subscriber event type until Phase 5 receipts table lands" a Phase 3 precondition, with a CI check rejecting a second `subscription_name` on any outbox channel lacking a receipts table.

**B3 — "Least-privilege worker credentials" (§11.2) is unenforceable; the worker runs with full DB privileges.** Spec §4 (line 257-260): same image and release as `api`/`rag`. Verified `apps/backend-rag/fly.toml:21-49`: one app, three process groups sharing `[env]`; Fly secrets are app-scoped, not process-group-scoped — all groups receive the same `DATABASE_URL`. No per-workload Postgres role exists (roles in scope: `nuzantara_rag`, `nuzantara_readonly`, dev variants). The worker catalog declares `owner_context` per workload (§7.1) but nothing enforces it at the DB grant level — a worker bug can write any kernel table §5.3 forbids it from touching. This is the spec's own scar #2 (Esiste ≠ Armato) reproduced inside the design: the catalog "checks" ownership but does not "generate" the enforcement.
_Falsifiable correction:_ require per-workload PG roles derived from the catalog, with a startup claim that fails if the role lacks `GRANT` on catalog-declared tables; or strike §11.2 and document the worker as full-privilege.

# Important findings

**I1 — `replay_unconsumed` acks-and-drops events older than 60 minutes.** Verified `outbox.py:334` (`created_at > NOW() - INTERVAL '60 minutes'`) and line 383-393 (stale in-payload rows acked to "suppress further replay"). A deploy + rolling restart + 7-min cold-start + migration can exceed 60min; on reconnect every older `compliance.critical_alert`/`crm.client_created` is silently acked, not DLQd. Sovereignty-adjacent: regulatory notifications lost, not deferred.

**I2 — Redis reclaim defect is live today but sequenced into Phase 5.** Verified `infra/eventbus/subscriber.py:82` (`consumer_id = f"{agent_name}-{os.getpid()}"`) and line 117-129 PEL drain via `xreadgroup(..., self.consumer_id, {stream:"0"})` — returns only the current consumer's pending, not a dead sibling's. `is_seen()` line 218 fails open (`except: return False` → process anyway → duplicate side effects when Redis is flaky). No `XAUTOCLAIM`/`XCLAIM` in file. Spec §8.3 + G6 defer the fix to Phase 5, but §8.1 says this bus carries live Pro/Mini automation today — a crashed daemon's entries are stranded now, not in Phase 5.

**I3 — G7 baseline is not ground-truth-anchored.** `rg 'import asyncpg|from asyncpg' apps/backend-rag/backend/app/routers/` returns 67 files; spec §1.2/G7 says 61. Either counter differs or baseline is stale; either way the `new_count <= 61` ratchet either fails on first run or is gameable by counter choice (scar #3 family).

# What survives review

- Decision D1 (one image/repo) and the rejection of Kafka/K8s/db-per-service (D10) — proportionate to current scale.
- §13 per-workload cutover granularity and shadow/off/active modes — correct in principle.
- §6 catalog-driven route topology and the G1 mutation test — directly addresses the §1.2 multi-source routing scar; `ROUTER_MANIFEST` parity tests already exist as precedent.
- §10 behavioral liveness (heartbeat + oldest-pending-age, not process presence) — correctly targets scar #2.
- §14 extraction gate with 30-day evidence requirement — a genuine firewall against premature services.
- I2 transactional-outbox principle (NOTIFY as wake-up, row as truth) — matches `outbox.py` as-shipped.

# Required amendments

1. Add a pre-flight side-effect dedup contract (B1) — mandatory before any irreversible-channel workload moves to `worker`.
2. Forbid new multi-subscriber event types until a per-subscription receipts table exists; make it a Phase 3 precondition (B2).
3. Either implement per-workload DB roles with a startup grant check, or strike §11.2 (B3).
4. Raise the replay window for declared-irreversible event types to their SLO and route stale-skips to DLQ, not ack-and-drop (I1).
5. Move G6 (Redis reclaim) to Phase 0 — the defect is live, not future (I2).
6. Re-anchor G7 baseline with a checked-in counter output committed at Phase 0 (I3).
7. Phase 2 exit gate must include a measured worker cold-start + memory budget and a lint forbidding the worker entrypoint from importing `app_factory`/routers (§16 risk "same-image worker still imports too much" is currently unverified — `backend/workers/` has no generic entrypoint to measure).

# Falsification test

The strongest single scenario that would flip this to GO: **a staging run of the §13 cutover on the WhatsApp outbox workload where (a) the old owner is killed mid-send (after the Meta POST leaves the process, before the response returns), (b) the lease is allowed to expire, (c) the generation advances and the new owner activates, and (d) telemetry proves exactly one WhatsApp message reached the recipient.** If the design can demonstrate (d) without a provider-side idempotency key — via the pre-flight dedup INSERT of amendment 1 — B1 is refuted and the cutover model survives. Until that evidence exists, every other gate is downstream of an unproven assumption.
