# Revised verdict

**GO-WITH-CHANGES — confidence 85.**

The revised design genuinely closes all sixteen accepted findings from the three-seat panel, and the closures are grounded in repository reality I re-verified independently this turn. However, one revision-introduced defect in the schedule idempotency contract (§7.3) constitutes a new concrete blocker in the "ambiguous side effects and idempotency" area, and three smaller revision gaps need amendments. None of them invalidates the architecture direction, the companion-app boundary, or the fencing model; all are text-level corrections, which is why this is GO-WITH-CHANGES rather than NO-GO.

# Remaining blockers

**RB1 — The schedule run key includes `ownership_generation`, which structurally permits duplicate execution of the same logical scheduled run across a cutover or rollback.** (Spec §7.3 final paragraph; interacts with §13 steps 3–5 and Phase 4.)

- _Verified basis:_ §7.3 specifies the deterministic run key "such as `(workload_name, scheduled_for, ownership_generation)`" and states its purpose is to prevent "enqueuing the same logical run twice." The §13 drain barrier covers leased work and `attempting` effects only — not pending, unclaimed, future-dated scheduled runs.
- _Concrete failure mode (no zombie process required):_ the legacy notification scheduler at generation N enqueues the run for `scheduled_for = T` where T is in the future. Cutover completes before T; the pending run is neither leased nor `attempting`, so the barrier passes. The new owner's scheduler at generation N+1 enqueues `(workload, T, N+1)` — the unique key differs from `(workload, T, N)`, so both rows insert. The new owner then legitimately claims both (its claims carry the _current_ generation, satisfying the database guard), and the same logical notification is sent twice. Every specified gate — G2 (single owner: one owner executed both), G3, G12, G15 (both sends confirmed, no ambiguity) — passes green. The named "schedule dedupe" precondition in §7.2 would catch this only if it happens to test dedupe _across a generation change_, which is nowhere required. The same mechanism fires on rollback (reverse cutover increments the generation again).
- _Falsifiable correction:_ (a) define the uniqueness key as `(workload_name, scheduled_for)` with the generation stored as an attribute, not part of the key — or require cutover/rollback to cancel or adopt pending unclaimed runs of the old generation before the new owner may schedule; (b) require the side-effect `effect_key` to be derived from business identity (e.g., notification ID + scheduled period), not from `job_id`/attempt, so a duplicated run still converges to one effect; (c) add an explicit cross-generation leg to the schedule-dedupe precondition (or to G12): execute cutover between enqueue and execution of a future run and prove exactly one execution.

# Regression findings

These are gaps introduced or exposed by the revision itself; RB1 above is the only one at blocker severity.

1. **Guard-arming order inside Phase 1 is unpinned.** The database claim guard (§7.2, Phase 1 "arm a database claim guard") rejects claim SQL that omits owner/generation. I verified the current pilot claim SQL has no such fields (`apps/backend-rag/backend/services/workflow/queue.py:65-80`: `FOR UPDATE SKIP LOCKED` + `visible_at`, no lease owner or generation). If the guard is armed while any machine still runs that pre-compatibility binary (a rolling deploy in progress, or a stale runtime — the spec's own scar class in §1.5), the _legitimate active owner's_ claims are rejected and the workload stalls. This is fail-closed and self-healing once the rollout completes, so it is amendment-level, not a blocker — but the spec gates only _cutover_ on the compatibility heartbeat floor, not guard arming.
2. **The second-durable-subscriber guard is specified as CI-only, but subscription is a runtime act.** §8.2 says "a checked catalog and CI rule reject a second durable subscriber" and "no naming convention or in-process handler list may bypass this guard," yet the enforcement mechanism named is CI. Verified: `backend/services/events/event_bus.py:244` exposes a runtime `subscribe(event_type, handler)` and the file's own comment (lines 170–171) lists at least five in-process handler modules. A durable consumer added through code that never touches the catalog is invisible to a catalog-diff CI check — reproducing GLM B2's silent event loss and the repository's scar family #2 ("green because it never ran"). Needs a runtime enforcement point.
3. **The companion Fly app contradicts a checked-in infrastructure rule.** `.claude/rules/infrastructure.md` states "Fly.io: ONLY 3 apps (nuzantara-rag, nuzantara-qdrant, nuzantara-postgres)" (itself internally drifted — `apps/backend-rag/fly.toml:40` says Qdrant is Qdrant Cloud via secrets, and project CLAUDE.md §11 says "Fly.io 2 apps"). D2 adds a fourth app without amending these governance artifacts, which will produce agent/CI friction and doc-drift the spec's own §1.5 warns about. Alignment change required in the approval commit.
4. **Companion-app release mechanics are unaddressed at spec level (minor).** The existing app runs migrations in `[deploy] release_command` (`fly.toml:13-19`). A same-image companion app must either skip that command or rely on the advisory-lock-hardened runner, and deploy ordering (primary app first) is implied by "coordinated release" but never stated. Acceptable to defer to the Phase 2 implementation plan, but it should be named there.

# Findings closed

All originally accepted blocking findings are closed in the revised text. Verified facts are marked; the rest is judgment on spec text.

- **Fable B1 (fencing does not bind the legacy claim path) — CLOSED.** §7.2 now requires a compatibility release that installs fencing/kill-switch checkpoints in the existing workflow, legal, notification, and WhatsApp claim paths one release before cutover, a heartbeat build floor blocking cutover, and — decisive for the zombie-binary case — a database-level claim guard (trigger/claim function) that rejects state transitions omitting owner/generation. G2 explicitly tests both the compatibility-release legacy path _and_ raw pre-compatibility SQL. Verified: the pilot's current claim SQL indeed carries no ownership fields, so the guard has a concrete rejection target (`queue.py:65-80`).
- **Fable B2 / Gemini B1 (rollback reactivates a fenced-out stale generation) — CLOSED.** §13 defines rollback as a reverse cutover: worker drains, same lease/effect barrier, one transaction increments the generation and assigns the legacy owner, which reads the grant dynamically (§7.2: "a generation is never a startup-only environment value") and must claim and complete a canary within SLO (G12). A hung new owner delays rollback behind the provider-timeout barrier but cannot produce a zero-owner state or a stale-generation owner.
- **Fable F1 / GLM I3 (irreproducible 61-file ratchet) — CLOSED.** Verified this turn: the pinned regex from §1.2 produces exactly **67** files under `apps/backend-rag/backend/app/routers/` at this checkout, matching §1.2 and G7. The SHA-256 in the spec I could not recompute (no execution in this read-only gate); G7's requirement that the checked-in repository check regenerate it makes that acceptable.
- **Fable F2 (table ownership had no gate) — CLOSED.** §5.3 adds a schema-introspected ownership manifest with expiring exceptions, migration lint, and G16; the worker role is additionally checked against the cataloged grant profile before activation.
- **Fable F3 (one-owner vs. legitimate internal concurrency) — CLOSED.** I1 now defines the owner as the database-backed grant for one runtime profile and generation, with catalog-governed `concurrency` inside it; G2 telemetry explicitly excludes same-grant concurrency. Verified the motivating fact: `main_api.py` spawns `WA_OUTBOX_WORKERS` (default 2) concurrent loops (`main_api.py:42-49, 163-167`).
- **Fable F4 / Gemini I3-budget (no absolute worker budget) — CLOSED.** Phase 2, G9, and G14 fix absolute ceilings: 1 GB VM, 60 s readiness, 750 MiB steady / 850 MiB peak RSS over a 30-minute shadow cycle, ≤ 8 worker DB connections; raising any requires a recorded amendment. These are coherent with the existing per-process VM reality I verified (`fly.toml:87-106`: api 3 GB, rag 2 GB, drive 1 GB).
- **Gemini B2 (Fly-visible worker health) — CLOSED.** §10/G13: internal `:9091/ready` served by the worker entrypoint, a Fly top-level (non-service) check, build-SHA database heartbeat, and a CI promotion gate that keeps workloads `off` on failure; G13 also kills the event loop under a live probe process. The synthesis's partial-acceptance reasoning (Fly does not universally _require_ a check; the operational need still stands) is sound. That top-level checks work for non-public processes and that app secrets are app-scoped are _externally sourced_ facts (Fly documentation, cited in the synthesis), not repository-verified — flagged as such.
- **Gemini I1 (generation change during in-flight external call) — CLOSED.** §7.3 adds the late fence (lease + owner + generation check immediately before the external call), `draining` mode, the provider-timeout-plus-clock-margin barrier, the `prepared/attempting/confirmed/failed/outcome_unknown` effect ledger, and G15's kill-after-dispatch test. The spec honestly states the fence cannot cancel an already-in-flight HTTP request and routes that residue into the ambiguity contract instead of claiming it away.
- **Gemini I2 (XAUTOCLAIM contention) — CLOSED.** §8.3 requires one designated reclaimer per group or a leader lock with jitter.
- **GLM B1 (universal exactly-once is false) — CLOSED.** The revised §7.3 withdraws the promise entirely: per-handler `provider-idempotent` / `reconcilable` / `non-reconcilable` contracts, `outcome_unknown` with audited operator resolution, no automatic retry for non-reconcilable ambiguity, and Phase 4's rule that a non-reconcilable handler cannot move while G15 depends on automatic retry. The synthesis's rejection of GLM's pre-flight-INSERT as _sufficient_ is technically correct (a unique row cannot distinguish crash-before-send from crash-after-send); the ledger is retained for what it can do. This closes the finding by changing the claim to a true one rather than by pretending to meet the false one — the right resolution.
- **GLM B2 (global-ack outbox cannot carry fan-out) — CLOSED with the runtime-enforcement amendment above.** Verified the underlying facts: `events_outbox.acknowledge()` sets a single global `consumed_at` (`outbox.py:261-264`); §8.2 confines it to declared single-consumer channels, blocks a second durable subscriber until per-subscription receipts exist, and G5 tests both the guard and later receipts.
- **GLM B3 (same-app least privilege unenforceable) — CLOSED.** This is the revision under special scrutiny and it holds: verified that the current topology is one Fly app with three process groups sharing `[env]` (`fly.toml:21-53`), so app-scoped secrets genuinely cannot give a worker a narrower `DATABASE_URL`. The companion app (§4.1, §11.2, alternative E) with the same immutable digest, coordinated release, dedicated scoped PostgreSQL role, effective-grant audit failing closed, and no public service is the smallest honest boundary; the release-skew risk is covered by digest-equality and build-SHA gates (§16, G13). Cross-app reachability of the worker→RAG path over the org 6PN is inference from Fly platform behavior, consistent with the existing `rag.process.nuzantara-rag.internal` addressing (`fly.toml:29-31, 42`), not something I could verify read-only.
- **GLM I1 (stale durable events acked away) — CLOSED.** Verified the live defect: replay filters `created_at > NOW() - INTERVAL '60 minutes'` and acks stale payloads "to suppress further replay" (`outbox.py:332-334, 383-393`). Phase 0 replaces this with per-event replay SLOs and quarantine/DLQ; G17 proves it; §8.2 explicitly brands the current behavior legacy-to-remove.
- **GLM I2 (Redis reclaim defect is live, not Phase 5) — CLOSED.** Verified: `subscriber.py` drains only the current PID-scoped consumer's PEL (`subscriber.py:82, 102-105, 119-122`), contains no `XAUTOCLAIM`/`XCLAIM`, and `is_seen()` fails open (`subscriber.py:204-219`). The fix — reclaim plus fail-closed idempotency for irreversible handlers — is moved to Phase 0 and G6.
- **Verified-ground integrity generally.** The revision's §1 factual base checks out at this checkout: 157 router files, manifest/registration/app_factory/service_initializer/main_api line counts (474/979/724/1805/253), `HEAVY_PREFIXES` at `rag_proxy.py:32`, `backend/workers/` containing only the Drive worker.

# Required amendments

1. **(Closes RB1)** §7.3: make the schedule-run uniqueness key generation-independent — `(workload_name, scheduled_for)` — or require cutover/rollback to cancel or adopt the old generation's pending unclaimed runs before the new owner may schedule; pin `effect_key` derivation to business identity rather than job attempt; add a cross-generation dedupe leg (cutover between enqueue and execution of a future run must yield exactly one execution) to the §7.2 schedule-dedupe precondition and G12.
2. §12 Phase 1: gate _arming_ of the database claim guard on the same compatibility heartbeat floor that gates cutover, so a pre-compatibility binary that is still the legitimate active owner is never fail-closed out of its own workload mid-rollout.
3. §8.2: specify runtime enforcement of the second-durable-subscriber guard — the dispatcher/`subscribe()` path consumes the event catalog at startup and fails closed on an uncataloged durable subscription to a global-ack channel. A CI-only catalog diff cannot see `event_bus.subscribe()` calls added in code (`event_bus.py:244`), and a guard that exists but never runs is the repository's scar family #2.
4. Approval commit must reconcile governance artifacts with D2: `.claude/rules/infrastructure.md` ("ONLY 3 apps") and project CLAUDE.md §11 ("Fly.io 2 apps") both contradict the companion app; while touching it, correct the stale `nuzantara-qdrant` entry against the Qdrant Cloud reality in `fly.toml:40`.
5. Phase 2 implementation plan (may stay out of the spec body, but must be named in §12 Phase 2): companion-app `release_command` policy (skip or rely on the advisory-locked migration runner) and deploy ordering relative to the primary app.
