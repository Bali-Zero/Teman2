## Q1 — PostgreSQL Job Queue senza broker

**Risposta NB-9:**

Il pattern corretto per Fly.io `auto_stop` è **SKIP LOCKED + visibility timeout** (NON advisory locks).

### Perché NON advisory locks

Gli advisory lock richiedono una connessione DB aperta per tutto il processing. Quando Fly.io stoppa la macchina, la connessione viene tagliata e il lock si perde senza recovery automatico.

### Pattern raccomandato: visibility_at timeout

```sql
-- Schema
CREATE TABLE workflow_jobs (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    chain_id    TEXT NOT NULL,
    thread_id   TEXT,                    -- LangGraph thread_id per resume
    status      TEXT DEFAULT 'pending',  -- pending | in_progress | done | failed
    payload     JSONB,
    visible_at  TIMESTAMPTZ DEFAULT NOW(),
    retry_count INT DEFAULT 0,
    max_retries INT DEFAULT 3,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX ON workflow_jobs (status, visible_at);
```

```sql
-- Dequeue atomico (worker loop)
WITH claimed AS (
    SELECT id FROM workflow_jobs
    WHERE status = 'pending'
      AND visible_at <= NOW()
    ORDER BY visible_at
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
UPDATE workflow_jobs
SET status = 'in_progress',
    visible_at = NOW() + INTERVAL '10 minutes',  -- visibilità timeout
    retry_count = retry_count + 1
WHERE id = (SELECT id FROM claimed)
RETURNING *;
```

**Flusso critico:**

1. Fast transaction: claim job → imposta `visible_at = now() + timeout` → commit subito
2. Processa in async
3. ACK su completamento: `UPDATE SET status='done'`
4. Se macchina muore → job diventa disponibile dopo timeout → prossima macchina riprende

### Librerie consigliate

- **PgQueuer** (minimalist, LISTEN/NOTIFY + SKIP LOCKED, asyncpg-native) — raccomandato per il nostro stack
- **Procrastinate** (feature-rich, Django-inspired, async-native) — per use case più complessi

### Nota per il nostro stack

`auto_stop='stop'` + `min_machines=1` → la macchina viene fermata (non suspended). Fly manda SIGTERM, poi dopo `kill_timeout=300s` SIGKILL. Il visibility timeout deve essere > 300s per i workflow lunghi (es. 10-15 min per workflow da 8 step).

## Q2 — Idempotency Keys FastAPI (exactly-once delivery)

**Risposta NB-9:**

L'exactly-once delivery pura è impossibile a livello di rete (Two Generals Problem). La soluzione è **exactly-once processing** lato server tramite idempotency keys.

### Schema PostgreSQL

```sql
CREATE TABLE idempotency_records (
    idempotency_key VARCHAR(255) PRIMARY KEY,
    request_hash    VARCHAR(64) NOT NULL,      -- hash del payload per detect key reuse
    response_status INTEGER NOT NULL,
    response_body   JSONB,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    expires_at      TIMESTAMPTZ NOT NULL
);
CREATE INDEX idx_idempotency_expires ON idempotency_records(expires_at);
```

### Pattern implementazione FastAPI

```python
# 1. Client invia Idempotency-Key header (UUID v4)
# 2. Server: check esistenza chiave
# 3. Se nuova → processa → salva risultato (con INSERT ... ON CONFLICT DO NOTHING)
# 4. Se duplicata → restituisci risposta cached (SEMPRE 200, mai 409!)

async def handle_with_idempotency(key: str, payload: dict, process_fn):
    async with pool.acquire() as conn:
        async with conn.transaction():
            # Guarded upsert atomico
            existing = await conn.fetchrow(
                "SELECT response_status, response_body FROM idempotency_records WHERE idempotency_key = $1",
                key
            )
            if existing:
                return existing["response_body"]  # cache hit

            # Processa
            result = await process_fn(payload)

            # Salva con INSERT ON CONFLICT DO NOTHING
            await conn.execute("""
                INSERT INTO idempotency_records
                    (idempotency_key, request_hash, response_status, response_body, expires_at)
                VALUES ($1, $2, $3, $4, NOW() + INTERVAL '7 days')
                ON CONFLICT DO NOTHING
            """, key, hash_payload(payload), 200, json.dumps(result))

            return result
```

### Punti critici per il nostro stack

1. **Nessun Redis necessario** — asyncpg su PostgreSQL existente regge il carico
2. **auto_stop silent kill** — FastAPI BackgroundTasks rischiano di essere killati da Fly.io se la HTTP response è già stata inviata (zero active connections = machine idle). Per workflow lunghi, usare il job queue (Q1) invece di BackgroundTasks
3. **TTL**: 7 giorni copre la maggior parte delle retry window dei webhook provider
4. **Cleanup**: `DELETE FROM idempotency_records WHERE expires_at < NOW()` via background job periodico

## Q3 — LangGraph checkpoint-postgres per produzione

**Risposta NB-9:**

### Setup AsyncPostgresSaver

⚠️ **CRITICO**: `langgraph-checkpoint-postgres` usa **psycopg3** (NON asyncpg).

```python
# Installazione
# pip install langgraph-checkpoint-postgres psycopg[binary]

from psycopg_pool import AsyncConnectionPool
from psycopg.rows import dict_row
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver

async def create_checkpointer(db_url: str) -> AsyncPostgresSaver:
    pool = AsyncConnectionPool(
        conninfo=db_url,
        kwargs={
            "autocommit": True,       # OBBLIGATORIO per .setup() DDL
            "row_factory": dict_row,  # OBBLIGATORIO — altrimenti TypeError
        },
        min_size=2,
        max_size=10,
        open=False,
    )
    await pool.open()

    checkpointer = AsyncPostgresSaver(pool)
    await checkpointer.setup()  # crea tabelle al primo avvio
    return checkpointer
```

### Tabelle create da .setup()

| Tabella                 | Scopo                                                   |
| ----------------------- | ------------------------------------------------------- |
| `checkpoints`           | Snapshot stato per ogni super-step (INSERT append-only) |
| `checkpoint_blobs`      | Payload serializzati grandi (separati per performance)  |
| `checkpoint_writes`     | Scritture pendenti (fault-tolerance)                    |
| `checkpoint_migrations` | Schema versioning (compatibilità futura)                |

### Come abilita il resume dopo restart

```python
# Ogni super-step → INSERT in checkpoints con (thread_id, checkpoint_id)
# Alla ripresa: fornisci lo stesso thread_id → LangGraph ricarica l'ultimo stato

config = {"configurable": {"thread_id": "mcp_chain_xyz_123"}}
# Resume automatico — bypassa i nodi già completati
result = await graph.ainvoke(None, config)
```

### ⚠️ CRITICO: Checkpoint Bloat (2GB RAM)

LangGraph usa INSERT per ogni step (append-only, mai UPDATE). Se lo stato contiene payload grandi (documenti RAG, array LLM responses), si innesca PostgreSQL TOAST compression → write amplification.

**Soluzione: Pointer State Pattern**

```python
# ❌ SBAGLIATO — salva 100KB di documenti nello stato
state = {"retrieved_docs": [doc1, doc2, doc3, ...], "thread_id": "xyz"}

# ✅ CORRETTO — salva solo puntatori
state = {
    "docs_ptr": "pg:retrieval:uuid-1234",  # ID in tabella separata
    "thread_id": "xyz"
}
# I documenti pesanti vanno in Qdrant o in una tabella PostgreSQL separata
```

## Q4 — FastAPI lazy init ML models (CrossEncoder ~400MB)

**Risposta NB-9:**

### Pattern raccomandato: lifespan + asyncio.to_thread()

La documentazione FastAPI ufficiale raccomanda il caricamento nel `lifespan` (prima delle richieste). Il pattern sentinel/on-first-request NON è documentato nelle fonti NB-9.

```python
from contextlib import asynccontextmanager
import asyncio
from fastapi import FastAPI

_model_state = {"cross_encoder": None}

def _load_model_sync():
    """Caricamento bloccante in thread separato."""
    from sentence_transformers import CrossEncoder
    return CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Offload a thread pool — non blocca l'event loop
    _model_state["cross_encoder"] = await asyncio.to_thread(_load_model_sync)
    yield
    # cleanup
    _model_state["cross_encoder"] = None

app = FastAPI(lifespan=lifespan)
```

### ⚠️ Vincoli critici per il nostro stack

1. **UN solo worker** — 400MB × 4 worker = 1.6GB → OOM crash su macchina da 2GB. Configurare Uvicorn con `--workers 1`.

2. **grace_period nel fly.toml** — il caricamento del modello dura ~10-30s. Senza grace_period sufficiente, i health check falliscono e il deploy fallisce.

```toml
# fly.toml
[[services.http_checks]]
  grace_period = "30s"
  interval = "15s"
  timeout = "5s"
  path = "/health"
```

3. **Volume mount per il modello** — NON baked nell'immagine Docker (gonfia l'immagine di 400MB, rallenta i deploy):

```toml
[mounts]
  source = "ml_models"
  destination = "/app/models"
```

## Q5 — Granian vs Uvicorn per SSE

**Risposta NB-9:**

### Supporto SSE e asyncpg

- **SSE**: Granian supporta pienamente ASGI/3 → SSE è una HTTP response chunked = nativo ✅
- **asyncpg**: nessun conflitto — benchmark reali (Jan 2026, r/Python) confermano compatibilità ✅

### Rischi di migrazione

| Aspetto                              | Rischio  | Valutazione                                    |
| ------------------------------------ | -------- | ---------------------------------------------- |
| Debugging cross-boundary Rust/Python | Medio    | Community più piccola                          |
| Process management                   | Basso    | Granian autonomo (no Gunicorn wrapper)         |
| CPU limiting su Fly.io               | **ALTO** | Work-stealing Rust peggiorato da 1-vCPU shared |
| Memory baseline                      | Positivo | ~15MB vs ~20MB Uvicorn                         |

### ⚠️ Raccomandazione per il nostro stack

**Non migrare a Granian su Fly.io con `shared-cpu-2x`** a meno che non si passi a macchine `performance-2x` con CPU dedicate. Il work-stealing scheduler di Granian è penalizzato da CPU condivise. Su Fly.io shared, Uvicorn + uvloop resta l'opzione migliore.

Granian vale la pena se in futuro si passa a `performance-2x` (dedicated CPU).

## Q6 — asyncpg pool settings per Fly.io idle/resume

**Risposta NB-9:**

### Configurazione raccomandata

```python
# SQLAlchemy 2.0 + asyncpg (pattern attuale nostro stack)
engine = create_async_engine(
    DATABASE_URL,
    pool_size=5,           # 1 worker → max 5 connessioni simultanee
    max_overflow=2,
    pool_timeout=30,
    pool_recycle=3600,     # Ricicla connessioni dopo 1h
    pool_pre_ping=True,    # CRITICO: verifica connessione prima dell'uso
    connect_args={
        "timeout": 10,
        "command_timeout": 30,
    }
)
```

### Problema post-resume/restart

Dopo `auto_stop='stop'` e riavvio: il pool pensa che le connessioni siano vive, ma PostgreSQL le ha già chiuse → prima query fallisce con `ECONNRESET`.

**Soluzione**: `pool_pre_ping=True` emette una query leggera prima di ogni checkout → sostituisce automaticamente connessioni morte.

```python
# Pattern per raw asyncpg (se non usi SQLAlchemy)
async def execute_with_retry(pool, query, *args):
    try:
        async with pool.acquire() as conn:
            return await conn.fetch(query, *args)
    except (asyncpg.ConnectionDoesNotExistError, asyncpg.TooManyConnectionsError):
        await pool.expire_connections()  # già implementato nel nostro DB pool recovery
        async with pool.acquire() as conn:
            return await conn.fetch(query, *args)
```

### Clock-skew JWT dopo resume

Fly.io `auto_stop='stop'` fa cold boot → clock preciso da NTP ✅ (il problema del clock-lag vale solo per `suspend`, che usiamo NON usiamo).

Ma per sicurezza, aggiungere leeway al JWT decoder:

```python
# python-jose / PyJWT
jwt.decode(token, key, leeway=10)  # 10 secondi di tolleranza
```

### Configurazione attuale già corretta

Il nostro `max_inactive_connection_lifetime=300` e `expire_connections()` in recovery (commit `2026-03-22`) sono già la soluzione giusta per Fly.io auto_stop.

**Risposta NB-9 — Architettura raccomandata:**

### PARTE 1: MCP workflow chains resumable (PostgreSQL only)

**Architettura: PG Job Queue + LangGraph AsyncPostgresSaver**

```
MCP Tool call
    ↓
POST /api/workflow/start
    → INSERT workflow_jobs (status=pending, visible_at=now())
    → return job_id + thread_id
    ↓
Background worker (asyncio.create_task in lifespan)
    → SKIP LOCKED dequeue
    → claim: visible_at = now() + 10min
    → graph.ainvoke(input, {"configurable": {"thread_id": thread_id}})
        → LangGraph AsyncPostgresSaver → checkpoint ogni super-step
    → ACK: UPDATE status='done'
```

**Se macchina viene killata:**

- visibility_at scade → job torna disponibile
- Prossimo avvio → worker dequeue lo stesso job → stessa thread_id → LangGraph riprende dall'ultimo checkpoint

**Tabelle PostgreSQL necessarie:**

1. `workflow_jobs` — job queue con SKIP LOCKED
2. `checkpoints` + `checkpoint_blobs` + `checkpoint_writes` + `checkpoint_migrations` — create da `AsyncPostgresSaver.setup()`
