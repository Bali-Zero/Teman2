# Change-map coverage reports

Weekly, **measure-only** reports on how `.github/workflows/tests.yml`'s
path-aware "Change map" gate (`scripts/ci/change_map.py`) actually behaved
over the trailing 7 days, generated by `scripts/ci/change_map_coverage.py`
(cron wrapper: `scripts/change_map_coverage_cron.sh`, weekly on Mini).

Each report covers `merge_group` runs (post-queue) and `pull_request` runs
(pre-merge) separately and answers, for each:

1. How many batches landed in each classifier `reason` bucket
   (`classified` / `unclassified_paths` / `enumeration_failed` /
   `empty_changed_set`), plus how many this script itself could not read.
2. For each of the six required heavy suites: how many batches ran it, how
   many skipped it, and the skip rate.
3. Which batches ran a suite that the classifier's own domain routing
   (`change_map.py::_suggested_jobs`) would NOT have selected — i.e. it ran
   only because the batch fell back to `run_all` for a non-domain reason —
   with a frequency table of the `unknown_paths` responsible and the PR
   numbers (from the merge-queue branch name) that carried them.
4. Which domains legitimately forced each suite to run, and how often.

**This is measurement, not a proposal.** No report here changes the
allowlist in `scripts/ci/change_map.py`, the job gating in `tests.yml`, or
any other CI behavior. It exists so a human can look at real 7-day evidence
before deciding whether a narrower rule is warranted — see item 3 above for
the concrete candidates that evidence would rest on.

Data scope: run ids, job conclusions, PR numbers, and the classifier's own
JSON (domains/reason/file paths) — CI metadata only. No client data or OSINT
ever appears here.
