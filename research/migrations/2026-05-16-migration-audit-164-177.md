## Findings

### F1 — Cicatrix archive entry "registry split" è imprecisa (DOC-DRIFT, NOT a code bug)

**Cicatrix `cicatrix-scars-archive.md`** dichiara:

> "\_schema_versions vs schema_migrations registry split: runner attivo legge schema_migrations (88 rows, latest 144), legacy \_schema_versions ferma a 6 rows max=129"

**Realtà 2026-05-16** (verificata su `apps/backend-rag/backend/db/migration_manager.py` + `migration_base.py` + `schema_audit.py`):

| Tabella             | Scrittore                                                   | Letta da                     | Status                                               |
| ------------------- | ----------------------------------------------------------- | ---------------------------- | ---------------------------------------------------- |
| `_schema_versions`  | `MigrationManager.apply_migration()` (legacy runner Python) | Same                         | LIVE — 10 query references in `migration_manager.py` |
| `schema_migrations` | `migration_base.py:387` (runner v2, asyncpg)                | Same + `schema_audit.py:182` | LIVE — usata da migrations v2 (164-177 inclusi)      |

`schema_audit.py:18-22` esplicita: "we have two tables in flight: `_schema_versions` (legacy) and `schema_migrations` (canonical, written by migration v2 runner)". L'audit periodico **confronta entrambe** e flagga divergenze. Migration 165 stessa è il fix per duplicati storici nella tabella `schema_migrations` (non `_schema_versions`).

**Implicazione operativa**: future debug "did migration N apply?" deve query `schema_migrations` per migrations v2, **non** `_schema_versions` come dice la cicatrix. La cicatrix entry data 2026-04-29 — è stata ribaltata da 165 (2026-05-10) ma mai aggiornata.

### F2 — DROP TRIGGER in sezione UP di 168 è idempotency safe (NON è bug)

`168_intel_lake_schema.sql:130` ha `DROP TRIGGER IF EXISTS trg_notify_intel_lake_event ON intel_items;` **prima** del COMMIT (sezione UP, non ROLLBACK). Pattern standard per trigger PG: PG non ha `CREATE OR REPLACE TRIGGER`, quindi `DROP IF EXISTS + CREATE` è il pattern idempotente per re-runs sicuri. **Non è un bug**, ma future audit AST-based potrebbero falsely-positive — annoto qui.

### F3 — Header migration 170 e 175 documentano collisioni P0-7 risolte

- **170** ("Numbered 170 because 169 was concurrently claimed by 169_crm_workspace_ai_snapshots.sql on main — cicatrix STRUCTURAL 2026-04-29 P0-7")
- **175** ("Renumbered 174 → 175 to resolve a prefix collision with 174_intel_lake_jsonb_double_encoding_repair.sql merged to main in parallel — cicatrix STRUCTURAL 2026-04-29 P0-7")

Conferma che il **runtime check uniqueness in `migration_manager.discover_migrations`** + il workflow `.github/workflows/lint-migration-numbers.yml` stanno funzionando come antibody: 2 collision in 14 migrazioni intercettate e risolte rinominando, zero collisione applicate in prod.

### F4 — Squawk warnings raw (95% style, 5% ban-drop in ROLLBACK)

Squawk raw verdict (no exclude) ha 11 file con warnings. Ma analisi UP-vs-ROLLBACK section classifier mostra che **tutti i `DROP TABLE` / `DROP COLUMN` / `DROP INDEX` flagged sono in sezione ROLLBACK** (linea > rollback marker), quindi sono **intenzionali e mai eseguiti dal runner forward** (`migration_base.py:493` esegue solo la sezione pre-marker). Gli warning rimanenti sono pure style (`prefer-bigint-over-int`, `prefer-text-field`, `prefer-identity`, `require-timeout-settings`, `require-concurrent-index-creation`) — tutti già in CI exclude list con justification scritta.

L'unica statement DROP in sezione UP è il `DROP TRIGGER IF EXISTS` di mig 168 (cf. F2 — pattern intenzionale).

### F5 — `CREATE INDEX` non-CONCURRENTLY è il pattern strutturale del runner

Tutti gli `CREATE INDEX` nelle 14 migrazioni sono non-CONCURRENTLY. Verificato su `migration_base.py:493`: il runner avvolge l'intera migrazione in un'unica `conn.transaction()` asyncpg. PG **non permette CONCURRENTLY dentro una transazione** (richiede autocommit). Quindi è un'invariant del runner v2, non una scelta per-migration. Squawk exclude `require-concurrent-index-creation` è già in CI con justification "the migration_base.py runner already wraps the whole file in a single asyncpg conn.transaction()".
