## NEW KILLER HUNT RESULTS

### FOR UPDATE lock: does it survive between F1.3 and F9?

The plan states: "This serializes any other writer (e.g. accidental Antonello use of mode-change UI) until our transaction commits, then releases. NOT a value change."

The plan itself answers the question. The transaction is: `BEGIN; SELECT ... FOR UPDATE; COMMIT;`. The lock holds for the duration of the transaction — milliseconds — and releases at `COMMIT`. F2 through F9 run for approximately 6 hours with NO row lock on `federation_alert_mode`. The advisory protection advertised ("serialize any other writer during cleanup") does not exist.

This is a semantic mismatch, not a functional break: the trap on EXIT is the actual protection mechanism (re-asserts `$PRIOR_FAM` on exit). The FOR UPDATE adds zero value. But the design is architecturally misleading and the "observe-lock" label in the heading is false advertising. Not a KILLER because no damage occurs — the trap is real. Downgraded to MEDIUM.

### PRIOR_FAM trap: unset or empty path?

`PRIOR_FAM` is interpolated at trap-set time (F1.3 Step 3, double-quoted string). F0.4 saves it to `$DATED_BACKUP/state/federation_alert_mode.prior`. F1.3 does NOT re-source that file — it relies on the shell variable persisting from F0.

If the operator runs each fase as copy-pasted chunks in separate terminals (common with 6h multi-window ops), `PRIOR_FAM` is unset in F1.3. The F1.3 Step 2 check (`if [ "$CURRENT_FAM" != "$PRIOR_FAM" ]`) fires: `CURRENT_FAM="observe"`, `PRIOR_FAM=""` — mismatch → `exit 1 (ABORT)`. The abort is a false positive, not corruption. This blocks progress but does not damage state.

If somehow the enum check at F0.4 was bypassed and `PRIOR_FAM=""` reached the trap, the trap executes `SET value='' WHERE value != ''` — writing an empty string to the enum column. The enum case guard at F0.4 prevents this path entirely (`*) echo FATAL; exit 1`).

Verdict: chunk-execution causes a false-abort. Not a KILLER. Medium severity. Mitigation: add `[ -z "$PRIOR_FAM" ] && PRIOR_FAM=$(cat $DATED_BACKUP/state/federation_alert_mode.prior)` at start of F1.3.

### LaunchAgent runOnce: fires once or re-fires?

`StartCalendarInterval` with `Year+Month+Day+Hour+Minute` all specified matches exactly one calendar instant. When that instant passes, launchd will not find another matching instant in future years (Year=2026 will not match 2027). The LaunchAgent fires once.

The restore script also self-destructs: `launchctl bootout ... && rm -f ~/Library/LaunchAgents/...plist`. If the machine reboots before firing, launchd re-evaluates on load; if the deadline is still in the future it fires; if past, the spec's date (2026-specific Year) will not match in 2027+ so it silently skips. The plist is still on disk until it fires. On a reboot after the deadline has passed with no fire, the sentinel becomes a permanent resident that launchd loads but never fires — effectively inert, but not cleaned up. This is a LOW residual: add a `RunAtLoad=true` guard or document that reboot-before-fire leaves an inert plist.

Verdict: single-fire behavior confirmed correct. Residual reboot-after-deadline case is LOW.

### lint_symbiosis_promises.py: does it accept @pytest.mark.skip?

The linter (`scripts/lint_symbiosis_promises.py`) scans `SYMBIOSIS.md` for durability-promise keywords and checks for test path citations in the surrounding 15-line window. It does NOT open or read test files. It does NOT check `@pytest.mark.skip` status. It does NOT verify file existence on disk.

The F2.3 Step 4 claim — "Symbiosis lint check (gate: file must exist before deploy)" — is incorrect on two counts:
1. The linter does not check file existence at all.
2. SYMBIOSIS.md has no entry for `pg-organism-bridge-watchdog` (confirmed: `grep -n "pg-organism-bridge-watchdog" SYMBIOSIS.md` returns 0 lines). The linter has nothing to evaluate for the watchdog. The `grep -E "(pg-organism-bridge-watchdog|polling)" | head -3` on the linter's output returns empty. The step passes vacuously — not because the gate was satisfied, but because the gate never evaluated the relevant claim.

The `@pytest.mark.skip` stubs therefore DO satisfy the linter — because the linter never reads them. The actual L4 audit-trail gate relies on the path string being cited in SYMBIOSIS.md, which is deferred to the follow-up PR. The Step 4 in F2.3 is a false gate.

Verdict: functional risk is LOW (no breakage). Documentation mislabeling is MEDIUM.
