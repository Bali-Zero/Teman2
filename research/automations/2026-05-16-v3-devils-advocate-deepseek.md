| 6 | HIGH | F1.3 CTE result capture | `PRIOR_FAM=$(psql "$DATABASE_URL_LOCAL" -tA <<'SQL' BEGIN; WITH ... SELECT value FROM prior; COMMIT; SQL)`. The heredoc sends multi-statement SQL to psql. While `BEGIN` and `COMMIT` produce no output rows under `psql -tA`, the CTE itself `WITH prior AS (SELECT ... FOR UPDATE), swap AS (UPDATE ...) SELECT value FROM prior` is a single statement. PostgreSQL requires that DML inside a CTE (`UPDATE`) be in the same transaction as the outer query. When sent via a heredoc that includes explicit `BEGIN`/`COMMIT`, the `WITH ... UPDATE` CTE executes inside an explicit transaction block, but psql command-line sends statements sequentially. The CTE SELECT and UPDATE ARE atomic. However, `PRIOR_FAM` will capture the SELECT output including any trailing newline from psql. When used in the trap: `value='$PRIOR_FAM'`, the SQL becomes `value='observe\n'` — a value with a trailing newline. This will NOT match `WHERE key='federation_alert_mode'` row lookup downstream if compared, but the UPDATE itself writes the literal `observe\n` back. The daemon's `get_db_mode()` then returns `'observe\n'`, which fails all FederationAlertMode string comparisons (`'observe\n' != 'observe'`), causing the daemon to silently fall into the same unhandled-mode trap as finding #1. | `PRIOR_FAM=$(psql "$DATABASE_URL_LOCAL" -tA <<'SQL' ... ## Verdict

**BLOCK**

Reason: 4 KILLER findings, any one of which causes irreversible damage or failed safety net:

1. Writing `'silent'` to `federation_alert_mode` puts the FAD daemon into a permanently stuck state where all proposals silently rot in `received` — the daemon stays running but processes nothing, no alerts, no logs, no failures. This persists until manually fixed and is not reversed by the trap (the trap restores `'silent'` → `'observe'` correctly, but the window of damage is the entire cleanup session).

2. `atrun` not loaded means the TTL sentinel is a queued job that will never execute. The only safety net surviving a SIGKILL or power-loss is the shell trap — which does not survive either.

3. Symlink plist will silently fail to load the watchdog. F2.3 is the fix for a production SPOF monitoring gap — if the watchdog does not load, the gap is not closed.

4. F3.1 body omitted — unverifiable K1 crontab fix. If the v2 K1-broken crontab command runs, 90 Pro cron jobs are deleted.
