2. **Index-letter confusion — RESOLVED for production, not for NB-2 sourcing.** Two independent
   NB-2 answers (`E2B2-T1-E31BC`, `E2B2-T1-E31DE`) disagree with each other AND with the production
   catalog on what "E31C" means: primary-law reading (per those answers) = "child of a WNA-WNI
   mixed marriage" OR "child born of a marriage between a foreign national and a WNI" (the two

   (`nb2_visa_types_final.txt`) instead labels E31C = "parent of KITAS/KITAP holder" — `CL-E31BCDEF-
   01`, **CONFLICTING** (NB-2-source-only, production unaffected — this is the fourth/fifth
   recurrence of the CF-5/CF-9 pattern, not re-litigated as a new CF here).
3. **Sponsor.** `family.relation_to_sponsor = "PARENT"` in the live pack — meaning E31C's applicant
   is treated as the CHILD and the sponsor as the PARENT (the field encodes what the SPONSOR is to
   the applicant, not the applicant's relation to the sponsor — the field name's literal English
   reads the opposite direction, a naming trap). **Confirmed by pack-internal cross-rule consistency,
   not a GAP**: `el.e31g-parent-wni-child-support` and `el.e31h-parent-itas-child-support` (both
   "parent joining a child sponsor" products) use `relation_to_sponsor = CHILD`, and the E31A-family
   spouse rules use `SPOUSE` — if the field meant "applicant's relation to sponsor," E31G/E31H would
   read `PARENT`, not `CHILD`. Neither `models.py` nor `contract.schema.json`'s property definition
   documents this direction explicitly, so the CONTRACT itself is undocumented even though the
   ENCODING is internally consistent and now cross-verified.
4. **Permitted/prohibited activities, entry pattern, duration.** **GAP** — no dedicated E31C claim
   covers these; only the identity claim (§3.1) exists.
5. **Rule 2's reason_code is not backed by its own when-clause — a real defect, not a claim gap.**
   `el.e31c-mixed-marriage-parents` fires `REQ_MIXED_MARRIAGE_PARENTS` but its `when` clause never
   tests `family.marriage_registered` or `family.sponsor_nationalities` — only the same
   `purposes ∩ FAMILY` + `relation_to_sponsor = PARENT` predicate as rule 1 (nested/duplicated, not
   syntactically identical, but testing the identical two facts). Contrast E31A's spouse rules, which
   DO test `family.marriage_registered`/`family.sponsor_nationalities`, and E31F's own PARENT rule,
   which tests `sponsor_nationalities ∩ {ID}`. The rule fires for ANY FAMILY+PARENT applicant, mixed
   marriage or not — `CL-E31C-01` (identity: "child of mixed marriage") cannot actually back a rule
   that never checks mixed marriage. Flagged §7 for E5/rule-authoring, not resolved here.
6. **Undeclared cross-product overlap.** E31C rule 1 (`FAMILY` + `PARENT`, no nationality check) is
   strictly broader than E31F's own support rule (`FAMILY` + `PARENT` + `sponsor_nationalities ∩
   {ID}`) — E31C's rule 1 fires on E31F's fact pattern too. Not resolved here; flagged §7.

## Adversarial review

Real cross-family review run this session via `kimi -m kimi-code/k3` (generator≠grader), independently
re-deriving the pack's `when` clauses byte-for-byte rather than trusting this card's prose.

Findings and disposition:

1. **[P1, CONFIRMED, cured]** The two E31C rules are **semantically** equivalent but NOT syntactically
   identical (rule 2 nests the same 2-fact conjunction, duplicated) — the original draft's "when
   clauses match" framing glossed over this. More substantively: rule 2's `REQ_MIXED_MARRIAGE_PARENTS`
   reason_code is not backed by any tested fact — the rule fires on the same bare FAMILY+PARENT
   predicate as rule 1, never checking marriage registration or sponsor nationality (contrast E31A's
   spouse rules and E31F's own PARENT rule, both of which test additional facts). This means the
   "one claim genuinely covers both" framing in the original §6 was too comfortable — `CL-E31C-01`
   backs the category IDENTITY, but rule 2's specific reason_code asserts something the rule never
   verifies. Added §3.5 and reworked the rule table + gap list to state this precisely.
2. **[P2, CONFIRMED, cured]** §3.3's original framing declared the `relation_to_sponsor=PARENT`
   reading a GAP requiring independent confirmation — but the pack itself already cross-confirms it:
   E31G/E31H (parent-joins-child products) use `relation_to_sponsor=CHILD`, and E31A-family spouse
   rules use `SPOUSE`, which is only consistent if the field encodes what the SPONSOR is to the
   applicant. Reworded §3.3 to state this is confirmed by pack-internal consistency, not an open GAP
   — while still noting the schema itself does not document the direction.
3. **[P2, CONFIRMED, new]** Undeclared cross-product overlap: E31C's rule 1 is strictly broader than
   E31F's own support rule (E31C tests no nationality; E31F requires `sponsor_nationalities ∩ {ID}`)
   — E31C's rule fires on E31F's fact pattern too. Added §3.6 and gap #4.

Net: 3 real findings, all substantive (not cosmetic), all reflected above. Disposition
(REACHABLE_AND_SUPPORTED) unchanged — the OD-3 criterion is about claim-backing, and `CL-E31C-01`
