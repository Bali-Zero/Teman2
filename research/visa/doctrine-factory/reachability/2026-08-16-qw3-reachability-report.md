# QW-3 — reachability/gap report against the ACTIVE pack (sequence 7)

Before this report, the only reachability measurement on record was three
asserts in `test_seq6_refuter_witnesses.py`, pinned against
`rulepack-prod-006.source.json` — a pack sequence-7 has since superseded in

## The persona-corpus caveat (do not skip this)

The 20-gold-persona corpus replays against a **hand-written fixture pack**
(`_gold_fixtures.py::build_gold_compiled_pack`), never the signed pack this
report inspects — a known gap the visaoracle skill's 2026-08-12 LIVE STATE
entry already flagged in prose ("G-b replays against a HAND-WRITTEN FIXTURE
pack, never the active signed one"). This report is the first to *measure*
that gap concretely against sequence 7 specifically, rather than merely
asserting it exists:

- The persona corpus positively supports 5 distinct product codes:
  `C1`, `E23`, `E28A`, `E31`, `E33G`.
- **`E31` does not exist in this pack at all.** The real pack uses
  `E31A`..`E31J` (10 sibling codes); the fixture's `E31` is fixture-only
  vocabulary. This single mismatch already explains why a naive code-match
  against the persona corpus under-counts coverage — it is not that `E31A`
  through `E31J` have never been exercised by *any* persona-shaped
  scenario, it is that the one persona corpus in this repo that could
  exercise them uses a name none of them carry.
- Of the 4 remaining persona codes that DO exist in this pack (`C1`, `E23`,
  `E28A`, `E33G`), all 4 are counted as covered — the 34-uncovered figure
  above already excludes them.

**Conclusion:** "34/38 products lack a positive persona" measures the
persona corpus's vocabulary coverage against this specific pack for the
first time — it is real signal (most of this pack's 38 products genuinely
have no persona-level positive test anywhere in the repo), but it should
not be read as "34 products are broken" or "34 products are unreachable" —
27 of those 34 ARE statically reachable per the reachability section above,
they simply have no persona asserting so.

## Adversarial review

Reviewed by Codex (`gpt-5.6-terra`, `--sandbox read-only`, reasoning effort
`ultra`, `132,358` tokens) against the full content of both new files
(`reachability_report.py` + `test_reachability_report.py`), invoked via a
dedicated subagent (generator≠grader — the review ran independently of the
implementer). The run took two attempts: the first hit a 5-minute Bash
timeout mid-review (it was cross-checking the pasted diff against the real
`compiler.py`/`models.py` source rather than reasoning from the pasted text
alone); the retry with a longer budget completed with exit 0.

**10 findings, verbatim verdict summarized, with dispositions** (all
verified against the real `compiler.py`/`models.py` source by a second,
independent read-only investigation before curing — never taken on the
reviewer's word alone):

1. **[DISPOSITION: documented, not a defect] "The signed-pack contract
   isn't implemented" (P1).** True as stated — this script parses
   `RulePackPayload` (the unsigned content), never a full signed `RulePack`
   envelope. **Not a defect for this report's purpose**: the payload
   content is byte-identical to what gets signed (`sign_pack.py` signs the
   canonical JSON of the same payload), and `compile_pack.py` — the
   existing, established tool this script's docstring explicitly models
   itself on — makes the identical scope choice for the identical reason.
   Made explicit in the module docstring rather than silently assumed.

2. **[FIXED — real bug, changed a reported number] "A GLOBAL-scope
   SUPPORT rule would be invisible to reachability" (P1).** Confirmed and
   fixed — but the actual defect was WORSE than the finding named: the
   bug wasn't SUPPORT-specific, it silently dropped **every** GLOBAL-scope
   rule (`EXCLUDE`, `REQUIRE_REVIEW`, `ADD_SCORE` too) from per-product
   attribution, because the rule-scoping helper returned an empty tuple
   for `product_version_ids: null` instead of "every product". This did
   NOT move the 27/11 reachability split (no `GLOBAL SUPPORT` rule exists
   in the live pack), but it DID make one line of this report's first
   draft **false**: "4 blocked products have zero scoped rules at all"
   (`E23U`, `E23V`, `E30E`, `E30F`) — those four are in fact touched by
   six `GLOBAL` `EXCLUDE`/`REQUIRE_REVIEW` rules each, just never
   individually named. Fixed with a new `_rule_effective_product_ids`
   helper (GLOBAL → every known product_version_id) used for all four
   effect types; `_rule_scoped_product_ids` (explicitly-named ids only)
   kept separately for orphan-reference detection, which is meaningless
   for a rule that names nothing. New tests:
   `test_global_scope_support_rule_grants_reachability`,
   `test_global_scope_rule_is_never_flagged_orphan`.

3. **[FIXED] "product_code aggregation could conflate two distinct
   product_version_ids sharing one code" (P2).** Confirmed real (the
   model only guarantees `product_version_id` uniqueness, and the
   evaluator's bitemporal design intentionally allows multiple versions
   per code — see the visaoracle skill's PR1b history). Investigated: **0
   duplicate codes exist in the live pack**, so this did not affect any
   number above. Fixed by failing loud (`ValueError`) the moment a
   duplicate is detected, rather than silently reporting a number that
   would mean something narrower than it claims. New test:
   `test_duplicate_product_code_raises_value_error`.

4. **[FIXED] "used_facts is declared (`required_facts`), not what the AST
   actually reads" (P2).** Confirmed: the Pydantic schema does not itself
   enforce `required_facts == collect_fact_paths(when)` — only the
   compiler does, as a separate invariant. A schema-valid-but-uncompilable
   pack could carry a stale `required_facts`. Swapped the authoritative
   source to `ast.collect_fact_paths(rule.when)`, kept `required_facts` as
   a cross-check reported via `required_facts_ast_mismatches` (0 on the
   live pack, confirming the compiler invariant holds there).

5. **[FIXED] "`has_any_scoped_rule` ignores `ADD_SCORE`/`RANKING` rules"
   (P2).** Confirmed: a product named only by a ranking rule would have
   been falsely reported as having zero scoped rules. Added
   `add_score_rule_ids` tracking, included in `has_any_scoped_rule`. New
   test: `test_add_score_rule_counts_as_a_scoped_rule`.

6. **[FIXED] "The orphan-rule docstring's 'silent no-op / compiles
   clean' claim is false" (P2).** Confirmed by direct read of
   `compiler.py::_check_product_reference_integrity`: a dangling
   `product_version_id` reference is collected as an
   `UNKNOWN_PRODUCT_REFERENCE` `CompilationError`, and the higher-level
   compile entry point raises `RulePackCompilationError` on any non-empty
   error list — the pack is schema-valid (loadable here) but
   compilation-invalid (never signable). Docstring and markdown output
   corrected to say so precisely. Added
   `test_orphan_rule_with_mixed_valid_and_dangling_ids` (a rule naming
   both a real and a dangling id must flag the dangling one while still
   crediting SUPPORT to the real target — the finding's own "mixed case
   untested" sub-point).

7. **[FIXED] "The NOT_ASKED regex scans the whole file, so a comment
   could false-positive" (P2).** Confirmed as a real (if narrow) gap.
   Scoped extraction to the `const data: ApplicantFactsDataWire = { ...
   };` object literal specifically, with a loud `ValueError` if that block
   can't be located (never a silent empty result). New tests:
   `test_not_asked_extraction_ignores_a_comment_outside_the_data_literal`,
   `test_not_asked_extraction_raises_on_missing_data_literal`.

8. **[FIXED] "The persona-code regex `[A-Z0-9]+` drops hyphenated codes"
   (P2).** Confirmed against `models.py`'s real
   `PRODUCT_CODE_PATTERN = r"^[A-Z][A-Z0-9-]{0,31}$"` — hyphens ARE legal.
   Widened the regex to match. New test:
   `test_persona_code_regex_accepts_hyphenated_product_codes`.

9. **[FIXED] "The 'without positive persona' test is innocence-only" (P2).**
   Confirmed: an implementation always returning `()` would have passed
   the original test. Added
   `test_products_without_positive_persona_includes_a_known_uncovered_code`
   (asserts `A1`, not in the persona corpus, appears in the without-list).

10. **[DISPOSITION: documented, not a live bug] "Path-base inconsistency
    between defaults (repo-root-relative) and user overrides
    (CWD-relative)" (P3).** Codex explicitly confirmed no current
    off-by-one (`_REPO_ROOT = parents[5]` is correct for this file's
    depth). The residual risk — a user-supplied `--fact-mapper`/
    `--gold-persona-test` override resolving against CWD while the default
    resolves against repo root, or a pack from a different worktree being
    silently compared against the current worktree's mapper/personas — is
    real but low-severity and not exercised by any test. Left as a
    documented limitation rather than adding cross-worktree path
    reconciliation, which would meaningfully widen this PR's scope for a
    P3 with no live-pack impact.
