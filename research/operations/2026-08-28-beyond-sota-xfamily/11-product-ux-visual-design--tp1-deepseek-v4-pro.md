## 0. TL;DR

**Position vs SOTA:** Nuzantara is **AHEAD** in automated editorial design pipelines (WR2), **BEHIND** in design-system token governance and quantitative UX measurement, and **AT** industry average in accessibility and performance.  
**Biggest gap:** No single source of truth for design tokens; three competing token systems exist, and ~600+ hardcoded hex values drift across the product, creating a fragile, inconsistent user experience.  
**Top‑3 moves:** (1) Build a CI‑enforced design‑token pipeline that generates CSS, Tailwind config, and component props from a single token specification, eliminating drift. (2) Deploy an LLM‑as‑critic gate that screens every PR for UX regressions (visual, copy, interaction) using the scar corpus as ground truth. (3) Create a continuous UX measurement fabric that runs synthetic journey tests on production and surfaces the five known public‑surface defects automatically, converting them into regression tests.

## 5. Beyond‑SOTA recommendations

Ranked by (impact × confidence) / cost. All respect the hard rules (no paid Anthropic API, CLI‑only, PII boundary, Fable not auto‑routed).

### 5.1 **LLM‑based design critic gate for all PRs** (Rank 1)

- **What:** A CI gate that runs a multimodal LLM (e.g., Gemini, Claude, or local model) on Playwright screenshots of every PR that changes the UI. The critic compares the screenshots against a design rubric derived from the brand cortex, the scar corpus, and WCAG 2.2. It comments on the PR with a pass/fail and a severity‑ranked list of violations.
- **Why it beats SOTA:** No surveyed system uses a scar‑corpus‑trained LLM critic in CI. Current tools (Chromatic, Percy) do pixel‑diff only; they don’t understand design intent, copy, or accessibility. The asymmetry is that Nuzantara already has a rich scar corpus (the very failures the critic would catch) and a multi‑LLM fleet that can act as the critic (Gemini for vision, DeepSeek for copy, Kimi for code). This composes known pieces into a unique whole.
- **Cost:** Flat subscription tokens only (the critic would run on an existing seat, e.g., Gemini 3.1 Pro). Each run takes ~10 screenshots × 30s LLM time ≈ 5 minutes of compute. At 10 PRs/week, ~50 minutes/week of seat time.
- **Gear:** 2 (significant automation, but the critic’s judgment is advisory; the human still decides).
- **Risk:** Scar family #4 (false positives) — the critic may flag acceptable changes, causing friction. Kill criterion: if the critic’s false positive rate exceeds 20% over 20 PRs, downgrade to advisory only.
- **Metric:** Number of design defects caught pre‑merge vs post‑merge. Before: 5 defects discovered in one day (2026‑08‑28). After: aim for 0 public‑surface defects in the first 30 days.
- **Measurement method:** Count defects reported after each production release; compare to the critic’s PR comments.
- **First PR:** Add a script `scripts/design-critic.sh` that takes a PR number, captures screenshots via Playwright, and sends them to an LLM with a prompt seeded from `cicatrix-scars.md` and `bali-zero-brand` constitution. Wire it into a new GitHub Actions workflow `design-critic.yml` triggered on PRs touching `apps/mouth/src/`. Net lines: ~300.

### 5.2 **Unified design token pipeline (DTCG → Style Dictionary → CI enforcement)** (Rank 2)

- **What:** Define all design tokens in a single DTCG‑compliant JSON file (`tokens.json`). Use Style Dictionary to generate CSS custom properties, Tailwind config, and TypeScript types. A CI gate ensures that no hardcoded color, spacing, or typography value exists in the codebase — every PR must use the generated tokens.
- **Why it beats SOTA:** Most design systems have a token pipeline, but few enforce token immutability in CI with a scanner that can detect hardcoded values in JSX, CSS, and inline styles. Nuzantara’s existing `brand_token_lint.py` can be extended to cover the entire app, not just the component library. The asymmetry is the existing CI infrastructure (106 workflows) and the merge‑queue discipline that can enforce this.
- **Cost:** ~1 week of engineering time to set up the token pipeline and migrate the ~600 hardcoded hexes. No additional subscription cost.
- **Gear:** 1 (foundational — everything else builds on it).
- **Risk:** Scar family #2 (exists ≠ armed) — the lint may be bypassed or ignored. Mitigation: make it a required check.
- **Metric:** Number of hardcoded hex values in the codebase. Before: ~600. After: 0, with a CI gate blocking any new ones.
- **Measurement method:** `brand_token_lint.py` scan across the entire `apps/mouth/src` directory.
- **First PR:** Create `design-tokens/tokens.json` with the existing semantic tokens from `packages/core/tokens`, add a `scripts/generate-tokens.sh` script, and a CI workflow `token-lint.yml` that runs the lint on all source files. Net lines: ~400.

### 5.3 **Continuous UX measurement fabric (synthetic journeys + real‑user monitoring)** (Rank 3)

- **What:** Deploy synthetic user journeys (using Playwright) that run against production every 15 minutes, simulating the five most critical flows (visa check, purchase, portal login, document upload, WhatsApp handoff). These journeys measure not just functionality but UX quality: time to complete, error rates, visual consistency. Combine with real‑user monitoring (RUM) via the `web-vitals` library to capture actual CWV. Surface all metrics in a single dashboard with paged alerts on degradation.
- **Why it beats SOTA:** Most organizations have synthetic monitoring OR RUM, not both fused into a single UX quality score. The asymmetry is the ASSEMBLY‑LINE’s mandate for synthetic probes and the existing frontend‑live‑sentinel pattern. This extends the sentinel from “is the commit live?” to “is the experience good?”.
- **Cost:** ~2 weeks of engineering to build the probes and dashboard. Uses existing Playwright and `web-vitals` libraries. No new subscription (can use a free tier for the dashboard).
- **Gear:** 2 (proactive monitoring).
- **Risk:** Scar family #8 (alert fatigue) — too many alerts. Kill criterion: if the pager fires more than once per day on average, re‑tune the thresholds.
- **Metric:** Before: no continuous UX measurement. After: detect any UX degradation within 15 minutes and correlate with deployment.
- **Measurement method:** The synthetic journeys themselves produce the metric.
- **First PR:** Add a GitHub Actions workflow `ux-synthetic-probe.yml` that runs a Playwright script against production, checks the five critical flows, and posts a failing status if any flow is broken or slow. Net lines: ~250.

### 5.4 **Experimentation framework (GrowthBook + CUPED)** (Rank 4)

- **What:** Integrate GrowthBook (or a similar feature‑flag/experimentation tool) into the frontend to enable A/B testing of design changes. Use CUPED (Controlled‑experiment Using Pre‑Experiment Data) to reduce variance and increase sensitivity. All product changes behind a flag are measured against the primary metric (e.g., check→purchase conversion).
- **Why it beats SOTA:** The ASSEMBLY‑LINE already mandates flag‑off deployment and progressive rollouts. Adding an experimentation layer closes the loop from “ship dark” to “learn from data”. Most startups use GrowthBook; the unique aspect is the CUPED integration, which reduces the sample size needed for statistical significance — critical for a low‑traffic service like VOA.
- **Cost:** GrowthBook is open‑source; self‑hosting on Fly.io would cost ~$5/month. Engineering time ~1 week.
- **Gear:** 2 (measurement).
- **Risk:** Scar family #9 (experiment interference) — overlapping experiments may corrupt results. Mitigation: strict namespace isolation.
- **Metric:** Number of design changes validated by experiment before full rollout. Before: 0. After: >50% of design changes.
- **Measurement method:** GrowthBook dashboard.
- **First PR:** Add `@growthbook/growthbook-react` to `apps/mouth`, create a simple feature flag provider, and wire it to a self‑hosted GrowthBook instance. Net lines: ~200.

4. **Visual identity for the GARUDA VOA surfaces** — the Mandate §3 lists 5 owner decisions, including the visual identity pick from 3 concepts. This is a design‑level decision that the owner must make.

## 8. §Meta‑pattern

The single defective belief that repeats across the product, UX, and visual design craft is:

**“The design system is a side effect of implementation, not an intentionally governed asset.”**

This manifests in:
- Three competing token SSOTs — because tokens were added ad‑hoc by different sessions.
- 600+ hardcoded hexes — because there was no enforcement mechanism.
- Two ThemeProviders — because the migration was never completed.
- A component catalog that is generated but not visually tested.
- A funnel audit that revealed a website that was never designed to convert.

The root cause is the organism’s strength turned pathological: the extreme autonomy of sessions (each session owns its worktree, its model, and its decisions) leads to design decisions being made locally without a global governance layer. The cure is to **invert the relationship**: make the design system the *source of truth* that sessions consume, and make any deviation a CI‑enforced violation. The token pipeline and the design critic are the mechanical embodiment of this inversion.
