### 3.1 The 3–5 that matter most

**1) WCAG 2.2 + axe-core + manual audits.** The organism already uses axe-core through Playwright, which is SOTA for automated gating. The missing part is the well-known limitation: automated tools do not catch all accessibility failures. WebAIM Million repeatedly shows that automated detection is useful but incomplete. The organism should keep the automated gate but add keyboard-only journeys, target-size checks, focus-order checks, and periodic assistive-technology smoke tests.

**2) GOV.UK Service Manual.** For high-stakes services such as visas, company setup, tax compliance, and immigration, GOV.UK-style service design is the most relevant SOTA. It emphasizes task clarity, plain language, evidence-based content, accessibility, and end-to-end transaction success. This is more relevant than generic consumer CRO because the user is often anxious, time-constrained, and dealing with legal/financial consequences.

**3) Design tokens + Storybook + Chromatic.** The ground pack shows logo and layout assertions but not a tokenized brand cortex. World-class product teams make brand executable: tokens, components, visual diffing, and interaction tests. This would turn “brand craft” from a visual review into a continuously verified system.

**4) CLIPScore / VLM alignment for generated assets.** The organism already uses VLM alignment validation for WR2 images. SOTA generative pipelines add provenance, prompt versioning, human rating, and multiple judges: prompt alignment, brand style, textlessness, composition, and safety. This converts WR2 from fallback-based resilience into a learning brand-generation loop.

**5) Experimentation with guardrails.** For conversion, SOTA is not random A/B testing. It is hypothesis-driven experimentation with guardrail metrics: support contacts, error rates, accessibility regressions, refund/complaint proxies, and high-stakes task completion. The organism currently proves price exactness but does not show funnel telemetry or experimentation infrastructure.

## 5. Beyond-SOTA recommendations

Ranking criterion: **(impact × confidence) / cost**.  
Gear definition: **1** = repo-only/local; **2** = cross-app/pipeline; **3** = product/org-level.

### Rank 1: Journey-level UX receptors for high-stakes funnels

- **What:** Add Playwright journey specs for visa/company/tax funnels: discover service → view exact price → open details → start booking → encounter validation failure → recover → continue. Keep API mocking, but assert state, focus, error messaging, and no overflow across the journey.
- **Why it beats SOTA:** Most teams test routes or components. Testing task completion and recovery under synthetic failure conditions is closer to real high-stakes usage.
- **Cost:** 2–4 engineer-days for first funnel.
- **Gear:** 1/2.
- **Risk:** Mock drift; flaky asynchronous UI.
- **Metric + measurement:** Journey pass rate; number of unique UX defects found before production; task-success assertions; front-end funnel event emission.
- **Kill criterion:** If after 4 weeks flake rate >15% or zero unique defects are found beyond existing route tests, reduce scope to critical paths only.
- **First PR:** `test(mouth): add booking funnel journey receptor`  
  Files: `apps/mouth/e2e/book-funnel.spec.ts`, `apps/mouth/e2e/fixtures/book-funnel.ts`  
  Net lines: <=400.  
  Acceptance: one happy path and one failure-recovery path pass with mocked APIs; no serious/critical axe violations; no horizontal overflow.

### Rank 2: Executable brand cortex: tokens + visual regression + WR2 prompt grammar

- **What:** Create a small token package: color, spacing, type scale, radii, motion duration, reduced-motion rules, and brand voice constraints. Generate CSS variables. Add lint for off-token values. Add visual baseline screenshots for critical routes. Feed token constraints into WR2 prompt grammar.
- **Why it beats SOTA:** Design tokens are SOTA; making them enforceable in E2E, visual diff, and generative prompts moves beyond static brand PDFs.
- **Cost:** 5–8 engineer-days.
- **Gear:** 2.
- **Risk:** Initial churn; false positives in visual diff.
- **Metric + measurement:** off-token lint violations; visual diff count; review time; WR2 prompt adherence score.
- **Kill criterion:** If token lint is bypassed >10% of the time or visual diffs are ignored for 2 consecutive weeks, pause and simplify.
- **First PR:** `feat(ui): seed executable brand tokens`  
  Proposed new files: `packages/ui/tokens/tokens.json`, `packages/ui/tokens/build.css`, `apps/mouth/src/styles/tokens.css`, `scripts/lint-tokens.mjs`  
  Net lines: <=400.  
  Acceptance: build emits CSS variables; lint fails on a deliberate off-token color; critical page screenshot uses token-driven styles.

### Rank 3: High-stakes conversion UX + front-end funnel event contract

- **What:** Build conversion patterns for high-stakes services: eligibility checklist, all-inclusive price explanation, next-step timeline, required documents, consent language, human support affordance, and error recovery. Add typed front-end events such as `view_price`, `open_details`, `start_booking`, `validation_error`, `recover_from_error`. Backend storage is lane 12; this lane owns UX event contract and emission.
- **Why it beats SOTA:** SOTA CRO often optimizes clicks. High-stakes services need trust, comprehension, and error recovery. Combining content design with typed front-end events is stronger than generic A/B testing.
- **Cost:** 5–10 engineer/product days.
- **Gear:** 2/3.
- **Risk:** Event schema becomes PII-sensitive if over-collected; experiments underpowered.
- **Metric + measurement:** CTA start rate, qualified inquiry rate, validation error rate, recovery rate, support-contact proxy, accessibility guardrail.
- **Kill criterion:** If two sequential experiments show no improvement and guardrails worsen, stop the variant and return to qualitative research.
- **First PR:** `feat(mouth): front-end funnel event contract`  
  Files: `apps/mouth/src/lib/ux-events.ts`, `apps/mouth/e2e/events/book-events.spec.ts`

### Rank 4: Accessibility beyond automated axe: WCAG 2.2 + keyboard-only + AT smoke

- **Why it beats SOTA:** Many teams stop at automated Axe. Task-level accessibility under keyboard and assistive technology is closer to real inclusion.

- **Gear:** 1/2.
- **Risk:** Manual tests are slow; assistive-tech environments can be flaky.
- **Metric + measurement:** zero serious/critical automated violations; keyboard task success rate; AT smoke pass/fail; time to complete core task without pointer.

Add automated judges: prompt alignment, brand style, no unwanted text, composition, and safety. Use the same eval contract for WR3 when it appears.
- **Why it beats SOTA:** Most generative pipelines only check “did it generate?” or “did a VLM score pass?” A provenance + human-rating loop learns what brand quality means over time.
- **Cost:** 5–10 engineer-days.
- **Gear:** 2.
- **Risk:** Automated score may not match human taste.
- **Metric + measurement:** human/auto agreement; off-brand rejection rate; time from draft to approved asset; operator intervention rate.
- **Kill criterion:** If human/auto agreement stays below ~0.6 after prompt calibration, keep VLM only as pre-filter and require human approval.

### Rank 7: Funnel UX defect ledger

- **What:** Create a UX defect taxonomy tied to journey steps: `discovery`, `price_comprehension`, `eligibility`, `booking_start`, `document_upload`, `payment`, `confirmation`, `support_handoff`. Frontend emits typed defects for validation failures, inaccessible errors, overflow, dead ends, and retry loops. Lane 12 owns backend persistence; lane 11 owns UX meaning.

- **Cost:** 2–4 engineer-days for contract and local emitter.
- **Gear:** 2.
- **Risk:** Noise if every warning becomes a defect.
- **Metric + measurement:** defects per journey step; mean time to triage; repeat-defect rate; funnel drop-off correlation.
- **Kill criterion:** If ledger is not triaged weekly for 3 weeks, pause and reduce to critical severity only.
- **First PR:** `feat(mouth): ux defect emitter contract`

### Rank 8: Design study loop / design canvas evaluation spike

- **Cost:** High; 1–2 weeks for credible spike.
- **Gear:** 3.
- **Risk:** Researchy; may not predict real user behavior.
- **Metric + measurement:** variant win rate against human review; automated defect reduction; time to produce testable design alternative.
- **Kill criterion:** If variants do not produce any approved improvement over current baseline after 3 studies, stop and return to human-led design studies.

## 7. Needs-ruling

Only true business/consent/credential/GUI/physical items.

1. **Business owner for high-stakes conversion KPI.** Need a named owner to define what counts as a qualified lead, booking start, or successful handoff. Without this, conversion experiments cannot be judged.
2. **Consent mechanism for user research and session evidence.** If real-user journey evidence, surveys, accessibility interviews, or session replays are introduced, explicit consent and retention rules are required.
3. **Non-production credentials for role-based GUI testing.** Need sandbox accounts for `user`, `admin`, `founder`, or equivalent roles to test gates and journeys without touching production. No credential values should be stored in repo or logs.
4. **GUI access to staging `apps/mouth` and WR2 operator surface.** Needed for visual regression baselines, WR2 eval calibration, and journey testing. This is GUI access, not backend data access.
5. **Physical/device access for realistic locale and accessibility testing.** At minimum: one low/mid-range Android device and one iOS device. For accessibility, access to a screen-reader-capable device or environment is needed.
6. **Design-source access if a design canvas or Figma source exists.** This is optional but necessary to build a true brand cortex. If it does not exist, the roadmap should proceed with repo-derived tokens.

## 8. Meta-pattern

The single defective belief generating most findings is:

**“Passing automated UI guards is proof of product quality.”**

This belief produces strong guards — axe gates, viewport checks, exact price assertions, RBAC redirect tests — but it does not prove that a user can understand a high-stakes service, recover from an error, complete a booking, trust the price, or use the product under locale, assistive, or network constraints. The organism has excellent receptors for **UI states**; it lacks a closed loop for **user outcomes**.
