## 1. How the organism does it today for THIS part

Every claim below cites a ground‑pack path or is explicitly marked as inferred (not verified).

### Secrets hygiene (family #4)
- **`scripts/secrets_permissions_audit.py`** (superscar #4 auditor) scans for credential‑like files with overly permissive permissions. It uses only name/path patterns, **never** reads file contents. It strips backup suffixes (`.bak`, `.bak‑*`, `.orig`, `~`) so a backup inherits the sensitivity of the base file. The `reachable_by()` function checks every directory ancestor for group/other traversal bits, so a file inside a `0700` directory is NOT reported as “in the clear”. A “blind scan” guard (exit code 2) prevents a scan that traversed zero files from certifying “clean”.
- **`scripts/detect_secrets_auto_triage.py`** auto‑triages `.secrets.baseline` findings. It uses two rule classes:
  - **Path‑only rules** for definitionally non‑sensitive files (e.g., `.env.example`), gated by production‑path blocks.
  - **Content‑keyed rules** that require the exact source line at the finding’s line‑number to match a narrow regex (e.g., a SHA256 pin must be `"<64‑hex>"` with end‑anchor). This enforces the “guard‑over‑match” principle (superscar #3): a real secret on a neighbouring line or a different shape is still left `unaudited` for human review.

### PII redaction & Law 2 output boundary
- **`scripts/_redact_pii.py`** is a four‑pass redactor loaded before any text is sent to an external LLM:
  - Pass 1: identifier + internal patterns (NPWP, KITAS, OSINT block, etc.)
  - Pass 2: team emails/phones (runs before generic email so team tokens are redacted with a specific label)
  - Pass 3: generic email, IBAN, SWIFT, bank account
  - Pass 4: dynamic client/company names loaded from Postgres (`clients.full_name`, `companies.name`)
  - Fail‑closed: any rule error, or output shorter than `gate.min_remaining_chars`, aborts the run.
  - Dynamic‑name loading distinguishes “PG out of scope” (env not set → degrade gracefully) from “PG expected but down” (raise `DynamicNameLoadError` so the caller can fail‑closed).
- **`SYMBIOSIS.md` lines 174‑277** codifies Law 2: “nessun LLM, agente, skill, memoria, report, log, alert, … deve trascrivere o persistere in chiaro dati cliente o OSINT”. The output boundary is a non‑negotiable internal security policy. A derogation for internal digest delivery on WhatsApp is narrowly scoped with payload restrictions.

### RBAC / CODEOWNERS
- **`.github/CODEOWNERS`** uses last‑matching‑rule semantics to require `@Balizero1987` review for 40+ critical paths: CI workflows, deploy config, DB migrations, auth, billing, the meta‑verifier, and the change‑map / impact‑map / shard‑tests that decide which CI checks run. The explicit threat model is “agentic workflow injection” (arXiv 2605.07135). Forward‑declared paths (e.g., `services/auth/`) are listed so they auto‑inherit protection if created later.

### Hooks / guardrails as backstop
- The redactor is a pre‑LLM guard. The auto‑triage script is a CI guard. The permissions audit is a post‑hoc scan. The CODEOWNERS file is a merge‑time guard. Each operates independently; there is no shared policy engine.

## 2. Scars & ledger evidence in this area

The ground pack contains explicit references to past incidents and their subsequent fixes:

- **Superscar #4 – “Secret in the clear”:** Production credentials (DB passwords, API keys) ended up world‑readable, especially backup files (`.bak`, `.orig`, `~`). A P0 on 2026‑05‑21 placed a Postgres password in 32 files. The `secrets_permissions_audit.py` script was created to detect this pattern (W65 skills‑bridge `.bak` cited).
- **Superscar #2 – “Guard that outputs false positives stops being read”:** The permissions audit tool’s blind‑scan guard and directory‑traversal reachability check were added to prevent a permanent stream of findings that would be ignored.
- **Superscar #3 – “Guard‑over‑match”:** The auto‑triage rules were redesigned to match entity/intent (content‑keyed), not bare path, after a blanket path‑rule would have approved a future real secret in the same file.
- **P2 §7.1 BUG #1 & #2:** The redactor had a fail‑open trap (dynamic CRM names silently skipped on PG outage) and a case‑sensitivity bypass (lowercase names leaked). Both were fixed in `_redact_pii.py`.
- **PR #3927 (closed, non‑merged):** A session attempted to over‑ride Law 2 boundaries; it was rejected, and `SYMBIOSIS.md` was updated with explicit constraints.
- **Scar family #1 (HOME‑fork drift):** The VCR pilot’s `certified_hash` is an integrity anchor to detect unauthorised modifications of the prober script.

### The 3‑5 that matter most

1. **OPA (Open Policy Agent):** The SOTA in policy enforcement is to decouple rules from application code. OPA allows a single sidecar to enforce PII redaction, token validity, egress allow‑listing, and rate limits across all external calls. For an organism with multiple independent guardrails, OPA provides the missing orchestration layer — every decision is logged, versioned, and testable. This beats the current “string of point checks” approach.

2. **SLSA + Sigstore:** Supply‑chain integrity is critical for a system that agentically auto‑fixes code. SLSA provides a graduated framework; L3 ensures auditable, non‑falsifiable provenance. Sigstore makes signing frictionless. The organism’s current SHA256 pins are a good start, but they are manual and not systematically generated. Achieving L3 would place the organism ahead of most adopters (many are at L2) and directly address the “HOME‑fork drift” scar family.

3. **Prompt Injection Firewall:** As LLM usage grows, prompt injection is the top threat. The SOTA includes dedicated ML classifiers that can be integrated into the request path. The organism’s redactor already processes every prompt; adding a classifier would close the injection surface without a new hop. This is a direct extension of the existing pre‑LLM guard.

4. **HashiCorp Vault for dynamic secrets:** Standing secrets (env files) are the root cause of superscar #4. Vault generates short‑lived, dynamic credentials, eliminating the long‑lived secret problem. Many organisations still use static secrets; moving to dynamic is a clear SOTA advantage.

5. **Tailscale / WireGuard for zero‑trust tailnet:** The organism’s infrastructure (Fly, local machines, CI) likely communicates over the public internet or basic VPCs. A tailnet with device‑identity‑based ACLs reduces the attack surface and aligns with zero‑trust principles. SOTA is moving away from perimeter‑based VPNs.

## 5. Beyond‑SOTA recommendations

Ranked by (impact × confidence) / cost. Each states: what, why it beats SOTA, cost, gear (1/2/3), risk, metric + measurement method, kill criterion, first PR (≤400 net lines).

### R1: Deploy an OPA‑based policy sidecar for all external calls
- **What:** An OPA proxy that intercepts every outbound request (LLM, cloud, email) and enforces Rego policies: PII redaction status, token validity, allowed endpoints, rate limits. It re‑uses the existing `Redactor` class and adds a prompt‑injection check.
- **Why it beats SOTA:** Unifies the current scattered guardrails into a single policy‑as‑code engine with centralised audit. Typical OPA deployments handle only authorisation; this would also enforce data‑privacy rules, which is novel.
- **Cost:** Medium (2‑3 weeks).
- **Gear:** 2 (process change).
- **Risk:** Added latency. Mitigation: OPA is fast (<1 ms per decision); start in dry‑run mode.
- **Metric:** % of external calls passing through the proxy; policy violations blocked; false positive rate. Target: 100% coverage in 90 days, <1% false positive.
- **Kill criterion:** If p95 latency exceeds 100 ms and cannot be optimised, or false positive rate remains >5% after 2 weeks of tuning, revert to direct calls.
- **First PR:** `Add OPA sidecar for LLM egress with PII and prompt-injection policies` — files: `infra/opa-policies/pii-redaction.rego`, `infra/opa-policies/llm-egress.rego`, `scripts/opa_sidecar_proxy.py` (≤400 lines). The proxy calls OPA before forwarding to LLM endpoints, initially dry‑run.

### R2: Adopt SLSA L3+ supply‑chain attestation with Sigstore
- **What:** Generate SLSA provenance for all production artefacts (Docker images, Python packages) using in‑toto. Sign with Sigstore; store in a transparency log. Verify before deployment.
- **Why it beats SOTA:** Most adopters are at L2. L3 provides auditable, non‑falsifiable provenance, critical for an agentic auto‑fix pipeline. Directly addresses scar family #1.
- **Cost:** Medium‑high (3‑4 weeks).
- **Gear:** 2 (process) + 1 (tooling).
- **Risk:** Build pipeline complexity. Mitigation: start with a single service.
- **Metric:** SLSA level (Scorecard); time to detect tampering. Target: L3 in 90 days, detection <1 min.
- **Kill criterion:** If build failures increase >10% due to attestation issues, simplify to L2.
- **First PR:** `Add SLSA provenance generation for backend-rag Docker image` — files: `.github/workflows/provenance.yml`, `scripts/generate_provenance.sh`, `infra/policy/slsa-policy.rego`. Uses `slsa-github-generator`.

### R3: Build a prompt‑injection firewall with a dedicated classifier
- **What:** Integrate a lightweight ML classifier (e.g., fine‑tuned DeBERTa) into the redactor pipeline. The classifier assigns a score to each prompt; “suspicious” prompts are flagged and can be blocked.
- **Why it beats SOTA:** Tailored to the organism’s domain (legal/tax/visa), it can be more accurate than generic commercial APIs. Integrating with the existing redactor avoids an extra hop. Most organisations use separate, external services.
- **Cost:** Medium (2‑3 weeks).
- **Gear:** 2 (process) + 1 (training).
- **Risk:** Adversarial bypass. Mitigation: ensemble approach, regular retraining. False positives blocking legitimate queries: start with “suspicious” flag only.
- **Metric:** Detection rate on known injection test set; false positive rate on legitimate prompts. Target: >95% detection, <1% false positive.
- **Kill criterion:** If detection <90% or false positive >5% after 1 month of tuning, abandon custom model and use a commercial API.
- **First PR:** `Add prompt-injection classifier to redactor pipeline` — files: `scripts/_redact_pii.py` (modify), `scripts/prompt_classifier.py` (≤400 lines, baseline logistic regression on TF‑IDF). Includes a test set of injection examples.

### R4: Introduce a secrets gateway (Vault) with dynamic secrets
- **What:** Deploy HashiCorp Vault to manage all production secrets. Modify the application to fetch secrets at runtime via the Vault agent, enabling dynamic database credentials and automatic rotation.
- **Why it beats SOTA:** Eliminates the standing‑secret problem (superscar #4). Many orgs still use static secrets; dynamic secrets is a direct SOTA upgrade.
- **Cost:** Medium (2‑3 weeks).
- **Gear:** 2 (process) + 1 (infrastructure).
- **Risk:** Vault as a single point of failure. Mitigation: HA mode, fallback cache.
- **Metric:** % of dynamic secrets; time to rotate a compromised secret. Target: 100% dynamic for DB creds in 90 days, rotation <1 min.
- **Kill criterion:** If Vault causes >2 production incidents in the first month, revert to static secrets with improved audit.
- **First PR:** `Add Vault agent sidecar and dynamic DB credentials for backend-rag` — files: `infra/vault/vault-policy.hcl`, `apps/backend-rag/Dockerfile`, `apps/backend-rag/backend/app/core/config.py` (modify). Proof‑of‑concept with a single DB credential.

### R5: Implement gVisor‑based sandboxing for agent‑executed code
- **What:** Run any code generated or modified by an agent (e.g., Codex autofix) inside a gVisor sandbox with a restrictive seccomp profile, limiting syscalls, network, and filesystem writes.
- **Why it beats SOTA:** Adds defence‑in‑depth to the agentic workflow. While containerisation is common, full sandboxing with gVisor is stronger and still rare in CI pipelines.
- **Cost:** Low‑medium (1‑2 weeks).
- **Gear:** 1 (tooling).
- **Risk:** Performance overhead, compatibility issues. Mitigation: use only for untrusted steps.
- **Metric:** Syscalls blocked; time overhead. Target: <10% overhead, 100% of agentic runs sandboxed.
- **Kill criterion:** If sandboxing breaks the autofix pipeline and cannot be tuned within 1 week, revert to non‑sandboxed with enhanced monitoring.
- **First PR:** `Add gVisor runtime for Codex autofix test execution` — files: `.github/workflows/codex-autofix.yml`, `scripts/run_sandboxed.sh`. Modifies a single job to use `runsc`.

### R6: Adopt Zero‑Trust tailnet with Tailscale
- **What:** Connect all infrastructure (CI, production, developer machines) via Tailscale, with ACLs based on device tags and identity. Enforce device posture checks.
- **Why it beats SOTA:** Replaces broad‑access VPNs with zero‑trust, identity‑based networking. SOTA is moving this way; many orgs still use legacy VPNs.
- **Cost:** Low (1 week).
- **Gear:** 1 (tooling).
- **Risk:** Dependency on Tailscale control plane; connectivity issues. Mitigation: Headscale as fallback.
- **Metric:** % of infrastructure on tailnet; open ports reduced. Target: 100% of production traffic on tailnet, 0 open public ports except ingress.
- **Kill criterion:** If connectivity issues persist >2 weeks, fall back to existing VPN.
- **First PR:** `Add Tailscale to CI runners and production services` — files: `infra/tailscale/docker-compose.tailscale.yml`, `scripts/join_tailnet.sh`. Adds Tailscale to the local dev/CI Docker Compose.

## 7. Needs‑ruling

The following items require explicit business, consent, credential, GUI, or physical decisions that cannot be automated:

1. **Consent‑collection mechanism for Law 2 PROD:** The `SYMBIOSIS.md` consent decision (Zero, 2026‑08‑09) mandates that consent be collected per client. 2. **Choice of secrets manager (Vault vs. AWS Secrets Manager vs. cloud‑agnostic):** A credential/architectural decision that depends on cost, operational maturity, and the existing cloud footprint. The team must decide whether to self‑host Vault or use a managed service.

3. **Physical/network access for tailnet deployment:** If on‑premise machines or physical CI runners exist, joining them to a tailnet may require physical access or network configuration changes (firewall rules, router settings). This is a physical/network decision.

4. **Prompt‑injection firewall threshold:** The acceptable false‑positive rate for blocking legitimate user queries is a business decision that directly impacts user experience. The product owner must set the risk tolerance.

5. **Sandboxing performance vs. security:** The acceptable CI pipeline slowdown for gVisor sandboxing is an operational decision that must balance security with developer productivity.

6. **Public‑repo sensitivity boundary:** While the repo is public, some configuration files (e.g., Vault policies, Tailscale ACLs) may contain non‑secret but sensitive information. A human must judge what is safe to expose.

## 8. Meta‑pattern

**The single defective belief that generates the most findings above is:**  
*“A security posture is the sum of its point defences; each guard, if individually correct, collectively secures the system.”*

This belief is visible in the organism’s architecture: they have built an exceptionally sophisticated permissions auditor, a content‑keyed triage engine, a four‑pass redactor, and a detailed CODEOWNERS file — each is excellent in isolation. But they lack a unifying policy orchestration layer. The guards do not share context, their outputs are not aggregated into a coherent dashboard, and there is no runtime enforcement point that can answer “should this request proceed?” by consulting all relevant policies at once.

The superscars themselves betray the pattern: #2 (guard that outputs false positives stops being read) is a symptom of uncoordinated alerts; #3 (guard‑over‑match) is a symptom of a rule engine that was too permissive until a narrower rule was hand‑crafted. Each time a gap is found, a new feature is added to the specific guard, rather than stepping back to design a system where a single policy change can close the class of gaps.

The beyond‑SOTA recommendations are all about replacing this belief with its opposite: **security is a continuous, orchestrated function, not a checklist.** The OPA sidecar is that orchestration layer. SLSA is about making integrity a pipeline property, not a one‑off check. The prompt‑injection firewall makes LLM safety a runtime service, not a pre‑redaction step. The defective belief is that complexity can substitute for integration; the cure is to treat security as a system, not a set of parts.
