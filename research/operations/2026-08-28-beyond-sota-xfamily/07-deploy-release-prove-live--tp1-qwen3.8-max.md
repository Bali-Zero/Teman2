## 0. TL;DR

The organism is strong at **machine-level deploy safety** — rolling Fly deploys, migration re-application on the fresh image, image-tag convergence checks, and anti-split-brain guards — but it is **behind world SOTA on user-facing proof-live, progressive exposure, cross-platform flag control, and automated rollback**.

Biggest gap: **there is no supplied evidence of a closed-loop PROVE-LIVE stage that independently verifies the deployed system from the outside and can halt/rollback a release**.

Top-3 moves:
1. Add a **PROVE-LIVE attestation** stage with synthetic post-deploy probes for Fly and Vercel.
2. Build a **deploy ledger + consumer-map** that reconciles Fly image tag, migration version, Vercel promotion, flag state, and runtime checkout.
3. Introduce **dark → synthetic → 5% → 100% release rings** with automatic hold/rollback backed by flags and snapshots.

## 1. How the organism does it today for THIS part

### 1.1 Fly backend deploy pipeline

The backend Fly deploy is triggered on push to `main` for backend paths, with explicit exclusions for docs/tests and a manual dispatch escape hatch (`.github/workflows/fly-deploy.yml`). Concurrency is serialized: one Fly deploy at a time, no cancellation of an in-flight deploy (`.github/workflows/fly-deploy.yml`).

Before deployment, a `pre-deploy-gate` job runs:
- installs backend dependencies;
- performs an import-chain gate described as blocking rogue refactor damage (`.github/workflows/fly-deploy.yml`);
- runs a deploy-critical Ruff subset (`F401`, `F821`, `F822`, `F823`) while keeping full lint informational (`.github/workflows/fly-deploy.yml`);
- runs a small core test gate (`.github/workflows/fly-deploy.yml`);
- checks CVE exception staleness and filters dependency vulnerability findings through an exception policy (`.github/workflows/fly-deploy.yml`);
- sends a Telegram alert on gate failure (`.github/workflows/fly-deploy.yml`).

This is a deploy gate, not just CI: the deploy workflow itself refuses to continue unless these checks pass (`.github/workflows/fly-deploy.yml`).

### 1.2 Migrations at deploy

The workflow has an explicit two-phase migration story:

1. **Pre-deploy migration job** runs `python -m backend.db.migrate apply-all` via `flyctl ssh console` against the currently running container, i.e. the old image (`.github/workflows/fly-deploy.yml`).
2. **Post-deploy SQL v2 migration job** re-runs migrations on the fresh image because new SQL files are only present after the new image lands (`.github/workflows/fly-deploy.yml`).

The post-deploy migration job contains a sentinel step that waits for all started machines to share one image tag, then pins migration execution to a started machine in the API process group (`.github/workflows/fly-deploy.yml`). The comments explicitly say this resolves a structural scar where SQL v2 migrations applied on the old image (`.github/workflows/fly-deploy.yml`).

### 1.3 Rolling deploy and lease retry

The deploy step uses `flyctl deploy --strategy rolling`, with retry logic for lease-contention errors. It retries up to three times when logs indicate lease acquisition problems (`.github/workflows/fly-deploy.yml`). This shows awareness that platform-level contention can strand a deploy.

### 1.4 Fly token health and deadman’s switch

A separate weekly workflow validates that the Fly API token is still valid using `flyctl auth whoami`, then alerts through Telegram on failure (`.github/workflows/fly-secrets-check.yml`). The comments describe a deadman’s-switch concept: if the workflow fails, GitHub notification still exists even if Telegram fails (`.github/workflows/fly-secrets-check.yml`). This is deploy-credential hygiene, not application observability.

### 1.5 Fleet restart detection and anti-split-brain recovery

The 15-minute Fly restart detector workflow checks fleet state for two Fly apps and classifies machines: started, expected stopped, unexpected stopped, crashed-stopped, clean stopped, OOM events, and unhealthy checks (`.github/workflows/cron-fly-restart-detector.yml`).

It has recovery logic:
- force-start machines that are stopped after a crash where the last exit code is non-zero (`.github/workflows/cron-fly-restart-detector.yml`);
- for one specific backend app, force-start a stopped non-standby machine when its whole process group has no started member (`.github/workflows/cron-fly-restart-detector.yml`);
- avoid starting a stopped leftover beside a live replacement because that would create an old-image/new-image split-brain (`.github/workflows/cron-fly-restart-detector.yml`);
- allow pausing autoheal with a repository variable while keeping detection active (`.github/workflows/cron-fly-restart-detector.yml`).

This is post-deploy self-healing and split-brain prevention, not full release verification.

### 3.1 The 3–5 that matter most here

**Google canarying + Netflix Kayenta.** The core lesson is not “canary exists”; it is that a release should have an automated judgment function. The organism currently verifies image convergence and migration application, but not whether the new release behaves correctly under live conditions. A Kayenta-style judge would compare probe results, error budgets, and critical journey outcomes between old and new, then pass/fail the rollout.

**Argo Rollouts / Flagger.** These systems formalize rollouts as state machines: `stable → progressing → analyzing → promoted/aborted`. The organism’s Fly deploy is closer to “run deploy command, retry lease errors, then re-run migrations.” A rollout state machine would make dark, 5%, and 100% explicit states with gates.

**LaunchDarkly / OpenFeature.** Feature flags are the cleanest way to implement dark launch and partial exposure without changing infrastructure topology. For this organism, the key SOTA idea is not a vendor but a **flag manifest**: one source of truth for flag state across backend, worker, frontend, and local organs.

**Vercel immutable deployments + instant rollback.** For frontend, SOTA is simple: every build is immutable, production is an alias, rollback is promotion of a known-good artifact. The organism’s auto-promote organ should therefore record both promoted deployment and previous deployment, enabling one-step rollback.

**DORA metrics.** The lane should measure failed deploy recovery time, not just deploy success. The organism’s scar ledger already contains MTTR-like evidence: 2h of 503s before human notice (`.github/workflows/cron-fly-restart-detector.yml`). SOTA release engineering treats that as a metric to drive automation, not just a story.

### 5.1 PROVE-LIVE attestation with synthetic probes

**What.** Add a post-deploy verifier that runs after Fly migration re-run and after Vercel promotion. It should check:
- Fly health endpoint and at least one authenticated critical API journey;
- migration version endpoint or equivalent DB schema marker;
- Vercel production alias resolves to expected deployment;
- critical frontend route returns expected status and marker metadata;
- results are written as a signed/attested deploy report artifact.

**Why it beats SOTA.** SOTA often checks platform health or passive metrics. This organism needs **active proof** because its scars show platform success without live service: stopped worker after deploy, group down with exit code 0, fixed image not serving (`.github/workflows/cron-fly-restart-detector.yml`). PROVE-LIVE converts “deploy command succeeded” into “the system demonstrably serves the required journeys.”

**Cost.** 2–4 dev-days for first version.

**Gear.** 2.

**Risk.** Flaky probes causing false release failures. Mitigate with bounded retries, probe idempotence, and separate “warn” mode for the first week.

**Metric + measurement.**
- `prove_live_success_rate`;
- `time_from_deploy_success_to_live_proof`;
- `bad_release_detection_time` measured from deploy completion to probe failure.
Measurement source: workflow artifacts and probe logs.

**Kill criterion.** If false-positive probe failure exceeds 5% over 20 production deploys, demote probe to warning and fix probe contract.

**First PR.** Add `scripts/release/prove_live_smoke.py`, a post-deploy job in `.github/workflows/fly-deploy.yml`, and a minimal Vercel probe hook. Target <=400 net lines.

### 5.2 Deploy ledger + consumer-map

**What.** Create a release manifest per deploy:
- git SHA;
- Fly image tag;
- Fly process groups and machine counts;
- migration version before/after;
- Vercel deployment ID and alias state;
- flag state hash;
- Pro runtime checkout SHA where relevant.

Then build a consumer-map: which consumers require which artifacts. Examples: API machines need image tag + migration version; RAG worker needs image tag + process-group liveness; frontend needs Vercel deployment alias; local organs need runtime checkout SHA.

**Why it beats SOTA.** Most SOTA systems assume one deployable unit. This organism has at least three planes: Fly backend/worker groups, Vercel frontend, and local launchd/runtime checkout. A consumer-map lets the release system ask: “Are all consumers on compatible versions?” That is stronger than single-service canary analysis.

**Cost.** 3–5 dev-days.

**Gear.** 2.

**Risk.** Ledger becomes stale if written manually. Mitigate by writing ledger entries only from workflows/scripts, not by hand.

**Metric + measurement.**
- `consumer_divergence_count` per release;
- `time_to_detect_consumer_mismatch`;
- `ledger_coverage` = percentage of deploy events with complete manifest.
Measurement source: ledger artifacts and reconcile jobs.

**Kill criterion.** If ledger misses >2% of deploy events or adds >15 minutes median deploy time without reducing incidents, simplify scope.

**First PR.** Add `scripts/release/deploy_ledger.py`, `release/consumers.yaml`, and artifact upload in Fly/Vercel workflows. Target <=400 net lines.

### 5.3 Automated rollback snapshot

**What.** Before promotion, snapshot the last known-good state:
- Fly previous image tag or machine configuration reference;
- Vercel previous production deployment ID;
- flag state hash;
- migration compatibility status.

If PROVE-LIVE fails or a post-deploy crashloop is detected, either automatically rollback or generate a one-command rollback instruction.

**Why it beats SOTA.** Many teams have rollback as a documented procedure. Beyond-SOTA is making rollback a **machine-executable artifact** tied to the exact release ledger. This is especially important because the organism already has autoheal for stopped machines; rollback should be another bounded recovery action, not an improvisation.

**Cost.** 3–5 dev-days for snapshot + manual rollback command; more if fully automatic.

**Gear.** 3 if automatic, 2 if one-command.

**Risk.** Rolling back after a non-backward-compatible migration can fail. Therefore rollback must know migration compatibility state and prefer forward-fix if schema is not rollback-safe.

**Metric + measurement.**
- `rollback_time` from decision to restored previous state;
- `rollback_success_rate`;
- `failed_deploy_recovery_time` aligned with DORA [13].

**Kill criterion.** If rollback fails twice in staging due to migration incompatibility, block automatic rollback until expand/contract gate exists.

**First PR.** Add `scripts/release/snapshot_good_state.py` and a rollback runbook command. Target <=400 net lines.

### 5.4 Two-platform flag manifest and parity

**What.** Define flags in a repo manifest, for example `release/flags.yaml`. For each flag, declare:
- default state;
- backend consumer keys;
- worker consumer keys;
- frontend/Vercel consumer keys;
- rollout ring;
- kill-switch behavior.

The sync checker compares desired flag state to actual platform state using key names and hashes, not secret values.

**Why it beats SOTA.** SOTA flag systems often live in one vendor plane. This organism needs flag parity across Fly backend, Vercel frontend, and possibly local organs. A declarative flag manifest with parity checks prevents “backend flag on, frontend flag off” split-brain.

**Cost.** 4–7 dev-days.

**Gear.** 2.

**Risk.** Accidental secret leakage. Mitigate by storing only flag keys, environments, and hashes; never store credential values.

**Metric + measurement.**
- `flag_drift_events`;
- `flag_parity_check_success_rate`;
- `time_to_detect_flag_mismatch`.

**Kill criterion.** If parity checks require manual correction in more than 10% of releases, redesign the flag provider contract.

**First PR.** Add `release/flags.yaml`, `scripts/release/flag_sync.py`, and a dry-run workflow. Target <=400 net lines.

### 5.5 Migration expand/contract compatibility gate

**What.** Require migrations to be deploy-safe in both directions:
- old code can run against new schema (expand);
- new code can run against old schema until migration completes (contract later);
- destructive changes require an explicit two-release plan.

Add a pre-deploy check that inspects migration SQL for dangerous operations and runs compatibility tests against a throwaway database.

**Why it beats SOTA.** The organism already has a strong migration timing fix (`.github/workflows/fly-deploy.yml`). The next level is proving that migration timing is safe under partial rollout and rollback. Many SOTA pipelines still apply migrations without proving bidirectional compatibility.

**Cost.** 5–8 dev-days, depending on migration tooling.

**Gear.** 2.

**Risk.** Slows schema changes. Accept this for destructive operations; allow fast path for additive migrations.

**Metric + measurement.**
- `migration_incident_count`;
- `migration_gate_false_block_rate`;
- `rollback_blocked_by_schema_incompatibility`.

**Kill criterion.** If the gate blocks >10% of safe additive migrations incorrectly, relax heuristics and move checks to advisory mode.

**First PR.** Add `scripts/release/migration_compat_lint.py` and a test fixture migration. Target <=400 net lines.

### 5.6 Dark → synthetic → 5% → 100% release rings

**What.** Model releases as rings:
1. **Dark**: code deployed, feature off, no user exposure.
2. **Synthetic**: PROVE-LIVE probes exercise the feature with test tenant/data-free payloads.
3. **Internal/consented**: limited to operator or test cohort.
4. **5%**: small user cohort if business approves.
5. **25%/100%**: full rollout if gates remain green.

Each ring requires:
- deploy ledger entry;
- flag state;
- probe result;
- rollback snapshot;
- optional human approval for user-facing percentage increases.

**Why it beats SOTA.** SOTA canarying usually begins with live traffic. A mandatory synthetic ring before human exposure is stronger for a small team because it catches wiring errors without user blast radius. It also matches the organism’s existing scar awareness: “exists != armed” and “deployed != serving” (`.github/workflows/vercel-autopromote-tests.yml`, `.github/workflows/cron-fly-restart-detector.yml`).

**Cost.** 1–2 weeks for full controller; can be delivered in slices.

**Gear.** 3.

**Risk.** Over-engineering. Start with two rings: dark/synthetic and 100%. Do not build percentage traffic splitting until flag/ledger foundations exist.

**Metric + measurement.**
- `escaped_defects_per_release`;
- `percent_releases_auto_promoted`;
- `blast_radius_exposure_time` at 5%;
- `failed_deploy_recovery_time`.

**Kill criterion.** If median release delay exceeds 2 hours without reducing escaped defects or incident count, collapse rings to dark/synthetic + 100%.

**First PR.** Add `release/rings.yaml` and `scripts/release/ring_gate.py` with dark/synthetic/100% only. Target <=400 net lines.

## 7. Needs-ruling

Only true business/consent/credential/GUI/physical items.

### Business / consent
- Approval to define production release rings and to hold/rollback releases automatically based on PROVE-LIVE failures.
- Approval before any real user traffic is exposed at 5% or any percentage ring.
- Approval for synthetic probes to use a dedicated test tenant or test-only routes; no real user data or PII may be used.
- Approval for maintenance pause flag semantics, equivalent to the existing autoheal pause concept (`.github/workflows/cron-fly-restart-detector.yml`).

### Credentials / secrets mechanisms
- Scoped Fly API token usable by deploy and verify workflows; secret stored in GitHub Actions, value never logged (`.github/workflows/fly-deploy.yml`, `.github/workflows/fly-secrets-check.yml`).
- Scoped Vercel token or equivalent deployment API credential for promotion, inspection, and rollback.
- Telegram bot token/chat secret mechanism for alerts; values must remain secret references only (`.github/workflows/fly-deploy.yml`, `.github/workflows/fly-secrets-check.yml`).
- Rotation procedure for deploy tokens; weekly token validity check is a good base (`.github/workflows/fly-secrets-check.yml`).

### GUI
- Prefer API-only. GUI access is not required unless Vercel project linkage or initial OAuth consent cannot be completed via API.

### Physical
- The existing Pro/Mini host(s) for launchd-based Vercel auto-promote and runtime checkout operations, because the pack describes local wrappers/plists and runtime checkout split (`.github/workflows/vercel-autopromote-tests.yml`, `docs/runbooks/runtime-dev-checkout-split.md`).
- Sufficient disk space if the runtime checkout later moves from worktree to full clone, as the runbook explicitly defers clone until free disk is adequate (`docs/runbooks/runtime-dev-checkout-split.md`).

## 8. Meta-pattern

The single defective belief generating most findings is:

**“A green platform operation is proof of live correctness.”**

The ground pack shows repeated corrections to this belief: migrations had to be re-run on the fresh image (`.github/workflows/fly-deploy.yml`); a fixed image could sit stopped while users saw 503s (`.github/workflows/cron-fly-restart-detector.yml`); a process group could be down even with exit code 0 (`.github/workflows/cron-fly-restart-detector.yml`); an organ that exists is not armed if nothing gates it (`.github/workflows/vercel-autopromote-tests.yml`). The organism already knows this intellectually through scars. The beyond-SOTA move is to encode it structurally: no release is complete until an independent verifier produces a PROVE-LIVE attestation and all consumers in the release ledger converge.
