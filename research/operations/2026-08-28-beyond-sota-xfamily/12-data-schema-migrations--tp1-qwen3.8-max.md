## 0. TL;DR

- Position vs SOTA: the organism is at or ahead of SOTA in scar-driven migration linting and prod-shaped test isolation, but behind SOTA on ownership separation, live schema-state verification, and governed vector/JSONB/outbox schema surfaces.
- Biggest gap: the system often treats migration bookkeeping — discovered file, lint pass, applied row, idempotent no-op — as proof that the live database has the intended schema, ownership, and invariants.
- Move 1: make Postgres ownership a first-class migration invariant: dedicated migration/owner roles, explicit grants, runner role switching or preflight, and CI ownership tests.
- Move 2: add schema-contract snapshots and drift detection so CI, prod-shaped test DBs, and production are compared by catalog state, not by migration history alone.
- Move 3: extend the migration discipline to Qdrant collections, frozen embeddings, JSONB codecs, and outbox durability with versioned manifests, DB-side checks, and operational tripwires.

### 1.1 Migration authoring: `migrations_v2`, forward-only SQL, no Alembic

The organism uses a SQL migration series under `apps/backend-rag/backend/db/migrations_v2/`. The legacy-promotion README explicitly says “No Alembic” and points to a v2 SQL runner, referenced as `backend/db/migration_manager.py` (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`). The same README describes the v2 series as the replacement for an older Python migration series that the v2 runner does not discover (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).

Legacy promotion migrations are deliberately idempotent: `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `DROP NOT NULL`, and `SET DEFAULT` are used so the same file can be a no-op in prod and safe in CI (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`). They are explicitly not data migrations: no `INSERT`, no `UPDATE`, no data movement (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).

The pack also shows a deliberate policy against silently tightening legacy columns: nullable columns remain nullable, and a test is named as guarding against accidental `NOT NULL` promotion (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).

### 1.2 The CI/prod schema recipe gap and strangler-fig cutover

The README identifies a structural defect: CI bootstrapped schema from a different recipe than prod. The bootstrap script, referenced as `apps/backend-rag/scripts/ci_bootstrap_schema.py`, used `SQLModel.metadata.create_all()` on top of raw DDL; the README says this gap is the root cause of several schema drifts (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).

The cutover plan is strangler-fig: merge idempotent legacy promotion migrations, then add `SCHEMA_AUDIT_REQUIRED_TABLES`, run a schema audit, remove the bootstrap step, and finally delete or stub the bootstrap script; each step is a separate PR (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).

### 1.3 DDL safety gates: Squawk, required-safe workflows, documented exclusions

The Squawk workflow lints changed migrations under `apps/backend-rag/backend/db/migrations_v2/` using `squawk-cli` (`/.github/workflows/migration-lint.yml`). It is designed to be required-safe: no top-level `paths:` trigger, with relevance decided inside a job step, because a required check with a path filter can hang forever on path-miss PRs (`/.github/workflows/migration-lint.yml`).

The workflow contains detailed exclusions: for example, `prefer-robust-stmts` is excluded because the migration runner wraps each file in one asyncpg transaction; `disallowed-unique-constraint` can fire on the rollback section even though only forward DDL executes; and several style rules are suppressed for small integer or fixed-length text choices (`/.github/workflows/migration-lint.yml`). The workflow also notes that Squawk complements, rather than replaces, runtime rollback-marker validation (`/.github/workflows/migration-lint.yml`).

### 1.4 Migration numbering and rollback-marker lints

A separate workflow detects duplicate migration-number prefixes. The rationale is that two files with the same numeric prefix make discovery order undefined, so the runner may apply one and silently skip the other later (`/.github/workflows/lint-migration-numbers.yml`). The workflow triggers on both `pull_request` and `push` to main because direct-push commits can bypass PR-only checks (`/.github/workflows/lint-migration-numbers.yml`).

Another workflow enforces inline `-- === ROLLBACK ===` markers. The pack states that `BaseMigration.__init__` requires every migration number greater than 111, except a legacy whitelist, to declare rollback SQL inline; missing markers raise `ValueError` at import time and block all pending migrations (`/.github/workflows/lint-migration-rollback.yml`).

### 1.5 Runtime-DSN migration runner and transaction boundary

The Squawk workflow states that the migration runner wraps the whole SQL file in a single asyncpg transaction, referencing `apps/backend-rag/backend/db/migration_base.py` (`/.github/workflows/migration-lint.yml`). The migration 289 file states that migrations connect with `settings.database_url`, referenced as `migration_manager.py:96`, and that this is the same DSN the runtime uses, with no `SET ROLE` anywhere in the chain (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).

That means migration execution privilege and runtime application privilege are not separated in the evidence shown. This is not a style issue: it directly determines whether a migration can replace owned functions or other owner-restricted objects (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).

### 1.6 Postgres roles, ownership, SECURITY DEFINER, and guard blocks

Migration 289 is highly explicit about ownership. Two trigger functions are owned by `visa_ledger_owner` and are `SECURITY DEFINER`; `CREATE OR REPLACE FUNCTION` preserves owner and ACL, but security/volatility/search-path attributes come from the new statement, so omitting `SECURITY DEFINER` would silently demote the function (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).

The same file records that the runtime role `backend_rag_v2` is not a member of `visa_ledger_owner`, and that a bare `CREATE OR REPLACE` would raise `must be owner of function` inside the release command, aborting deploys (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`). It also states that migrations 281/284-287 required out-of-band superuser application because of this class of failure (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).

The migration therefore wraps replacements in `DO` guard blocks. If the current role is not owner/member/superuser, it emits a loud `NOTICE` and returns instead of failing (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`). The file also acknowledges the danger of this shape: a declined dynamic SQL body may never be parsed, so syntax errors can be unseen on the decline path; it mitigates this by requiring CI tests that apply the migration as an able role (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).

### 1.7 Invariants, tripwires, and catalog-level preflight

Retention-policy authority is enforced by an exclusion constraint. Migration 264 created one active row per environment; migration 281 widened the invariant to one active row per `(environment, policy_scope)` (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`). The 289 incident shows the organism uses tripwires at multiple levels:

- Database constraint: exclusion constraint prevents multiple active rows per scope (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).
- Trigger-level enforcement: binders use `SELECT ... INTO STRICT`, reject missing policies, reject ambiguous policies, validate retention deadline, reject legal hold on insert, and require `created_at` to equal the database transaction clock (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).
- Operational preflight: the migration states that `operational_preflight.py` has a binder check that reads live function bodies from `pg_proc` and fails while the binder still resolves policy by environment alone (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).
- Test-level guard: legacy promotion is guarded by a test against accidental `NOT NULL` promotion (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).

This is a strong pattern: invariants are not only declared, they are checked by the database, by preflight, and by tests.

### 1.8 Prod-shaped test DBs, worker isolation, and DSN fail-closed guards

The root test configuration builds a strong prod-shaped test-database story. CI migrates `nuzantara_test` once before tests run, and each xdist worker receives its own throwaway Postgres database cloned from a dedicated, connectionless template using `CREATE DATABASE ... TEMPLATE` (`apps/backend-rag/backend/tests/conftest.py`).

The conftest records two hard-won lessons:

1. Ownership matters when cloning. The DSN guard is also notable. ### 3.1 The 3-5 that matter most for this organism

The most relevant SOTA patterns are not generic “use a migration tool” ideas; they address the organism’s exact failure modes.

**1. Ownership as a first-class schema invariant.** PostgreSQL’s ownership model is the root mechanism behind the migration 289 incident: function ownership, role membership, and `SECURITY DEFINER` attributes determine whether DDL can run at all [1]. World-class systems treat ownership not as an operational afterthought but as part of the schema contract: who owns tables, functions, triggers, sequences, and schemas; which role applies migrations; which role the app uses; and how CI reproduces the split. The organism already discovered this painfully, but has not yet institutionalized it beyond guarded migrations.

**2. Schema state contracts and drift detection.** Atlas-style desired-state diffing and pgroll-style versioned migrations matter because the organism’s biggest structural risk is “migration history says applied, but shape is wrong” [7][8]. The legacy bootstrap gap shows this is not hypothetical: CI built one shape, prod had another, and the README names that as a root cause of drift (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`). A catalog snapshot contract would make the README’s `SCHEMA_AUDIT_REQUIRED_TABLES` idea into a continuous, automated invariant.

**3. Transactional outbox durability.** For outbox durability, the SOTA pattern is not “send events from request handlers.” It is: write an event row in the same database transaction as the business mutation, then relay via polling/CDC with idempotency keys and DLQs [11]. The pack does not evidence such a lane yet. If the organism needs durable side effects — notifications, audit fanout, downstream indexing — this is the cleanest architecture.

**4. Vector-store schema governance.** Qdrant collections are schema-like objects: vector size, distance metric, payload indexes, quantization, and collection metadata. SOTA vector systems treat collection changes like migrations: aliases/blue-green, snapshots, rebuild/backfill, and embedding-model version pins [13]. The organism currently shows only test mocks and environment guards for Qdrant (`apps/backend-rag/backend/tests/conftest.py`), so this is a major beyond-SOTA opportunity.

**5. Retention as structural partitioning, not row-by-row deletion.** The organism’s retention policy table is sophisticated, but the evidence still centers on row-level triggers and policy lookup [4]. For high-volume tables, SOTA retention uses partitioning, automated drop/detach, legal-hold partitions, and auditable deletion certificates [10][14]. This makes deletion fast, predictable, and provable.

## 5. Beyond-SOTA recommendations, ranked by (impact × confidence) / cost

Gear legend: **1** = low-risk tooling; **2** = runner/service/database changes; **3** = architecture/multi-system changes.

### Rank 1 — Ownership plane: migration owner, app role, and role manifest

- **What:** Introduce explicit Postgres roles: `migration_owner` for DDL, `app_runtime` for DML, and optional `audit_owner`/`ledger_owner`. New objects are created by `migration_owner`; app role receives only needed grants. Migration runner either connects as migration owner or performs controlled `SET ROLE` where platform constraints allow. Add a checked-in role manifest: object class, owner, expected grants, negative privileges.
- **Why it beats SOTA:** Many SOTA linters catch dangerous DDL but do not verify ownership execution paths. This turns ownership into a testable schema contract and eliminates the exact failure in migration 289: runtime role cannot replace owner-held functions (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).
- **Cost:** Medium. Requires role design, grants, CI role emulation, and careful staging.
- **Gear:** 2.
- **Risk:** Permission breakage, failed deploys, locked objects. Mitigate by first running in read-only preflight and staging.
- **Metric + measurement:** Zero `must be owner of function` deploy errors; zero out-of-band superuser applies; CI ownership matrix pass rate 100%. Measure from migration logs, release-command logs, and CI role tests.
- **Kill criterion:** If role separation causes deploy failure rate to rise above baseline by >2% for two consecutive weeks, freeze and simplify to one migration-owned database role while preserving ownership tests.
- **First PR:** `apps/backend-rag/backend/db/roles/001_role_manifest.sql`, `apps/backend-rag/backend/tests/db/test_role_manifest.py`, small runner preflight hook. ≤400 net lines.

### Rank 2 — Schema-contract snapshots and drift detection

- **What:** After each migration, emit a normalized schema snapshot: tables, columns, defaults, nullability, constraints, indexes, triggers, function owners, `SECURITY DEFINER`, `search_path`, sequences, grants. CI applies migrations to a clean DB and compares the resulting snapshot with expected snapshots. A separate preflight compares prod-shaped test DB or staging to expected snapshot.
- **Why it beats SOTA:** This extends Atlas-like drift detection into the organism’s legacy-promotion reality. It directly closes the bootstrap/prod recipe gap and makes `SCHEMA_AUDIT_REQUIRED_TABLES` continuous rather than episodic (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).
- **Cost:** Medium. Snapshot normalization is fiddly but mechanical.
- **Gear:** 2.
- **Risk:** False positives from environment-specific grants/extensions. Use allowlists and environment-specific overlay files.
- **Metric + measurement:** Number of drift findings per deploy; time from drift introduction to CI red; false-positive rate. Target: 100% of schema drift caught before prod.
- **Kill criterion:** If drift check produces >5% false-positive PR blocks after two weeks of tuning, switch to warning-only for low-severity fields while keeping owner/constraint checks blocking.
- **First PR:** `scripts/ci/schema_snapshot.py`, one snapshot for a small migration set, test that mutates schema and fails diff. ≤400 net lines.

### Rank 3 — Invariant tripwire registry with operational preflight

- **What:** Create a registry of named invariants: active-policy uniqueness per scope, binder scope predicate, function ownership, expected `SECURITY DEFINER`, NOT NULL contracts, JSONB envelope validity, outbox monotonicity, Qdrant embedding-model hash match. Each invariant has SQL/Python check, severity, owner, and run stage: CI, predeploy, postdeploy.
- **Why it beats SOTA:** The organism already has tripwires, but they are scattered. A registry makes invariants enumerable and testable. It also turns the 289 lesson — preflight must read live catalog, not just migration history — into a general system (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).
- **Cost:** Medium.
- **Gear:** 2.
- **Risk:** Alert noise. Start with blocking only for P0 invariants.
- **Metric + measurement:** Invariant violation count in CI/predeploy; mean time to detect invariant break; number of invariants covered. Target: zero prod invariant breaks that were expressible in registry.
- **Kill criterion:** If >10% of predeploy runs are blocked by non-actionable invariant noise in 30 days, demote non-P0 invariants to warnings.
- **First PR:** `apps/backend-rag/backend/db/invariants/registry.sql`, `scripts/operational_preflight_invariants.py`, tests for retention scope and ownership. ≤400 net lines.

### Rank 4 — JSONB codec registry with DB-side validation

- **What:** Define versioned JSONB envelopes: `{"v": 1, "codec": "client_fact", "data": {...}}`. Register codecs in a table. Add `CHECK` constraints or generated columns for required envelope fields and payload type. Python codec registry enforces backward-compatible evolution: unknown future versions are readable-only or rejected by policy, not silently stored.
- **Why it beats SOTA:** Most teams treat JSONB as schemaless. This makes JSONB a governed schema surface with versioning, validation, and migration rules. It pairs with schema snapshots: JSONB contracts become part of the schema state.
- **Cost:** Medium.
- **Gear:** 2.
- **Risk:** Insert latency or query complexity. Measure and index generated columns where needed.
- **Metric + measurement:** Invalid JSONB insert count; codec fuzz failures; p99 insert latency delta. Target: zero invalid envelopes in prod.
- **Kill criterion:** If JSONB validation adds >5 ms p99 write latency or >10% query regression for key paths, move validation to application boundary plus sampled DB checks.
- **First PR:** codec registry table migration, one table converted to envelope, Python codec module. ≤400 net lines.

### Rank 5 — Outbox durability lane

- **What:** Add `outbox_events` table: monotonic sequence, aggregate type/id, event type, event version, payload JSONB envelope, created_at, published_at, status, idempotency key, DLQ fields. Business writes insert outbox rows in the same transaction. Relay polls or uses logical decoding; consumers are idempotent. Add gap detection: sequence holes or stale unpublished rows alert.
- **Why it beats SOTA:** It avoids dual-write and makes side-effects auditable. It also connects naturally to JSONB codec governance and retention. The pack does not evidence an outbox today, so this is a clean leapfrog opportunity.
- **Cost:** Medium/high depending on relay choice. Start with poller, not CDC.
- **Gear:** 2.
- **Risk:** Duplicate delivery, poison messages, relay lag. Use idempotency keys and DLQ.
- **Metric + measurement:** Outbox lag p99; unpublished row age; duplicate delivery count; DLQ depth. Target: no event older than 5 minutes without publish or DLQ.
- **Kill criterion:** If relay lag p99 exceeds 10 minutes for 24h or write latency regression exceeds acceptable budget, pause and simplify to synchronous handler with retry only for critical flows.
- **First PR:** outbox migration, repository helper that writes outbox inside transaction, fake relay test. ≤400 net lines.

### Rank 6 — Qdrant collection-as-code and frozen embedding manifest

- **What:** Define collection manifests: collection name, vector size, distance metric, quantization, payload indexes, embedding model ID, embedding model hash, normalization, schema version, rebuild policy. Use aliases or blue/green collections for cutover. Store embedding model/version in point payload and collection metadata. A reconciler diffs live collection against manifest in CI/staging.
- **Why it beats SOTA:** Many teams treat vector stores as mutable runtime config. This treats Qdrant like a schema system: versioned, testable, rebuildable, and observable. Frozen embedding becomes enforceable: if collection manifest says model/hash X, points with model/hash Y are migration candidates or rejects.
- **Cost:** High. Requires collection lifecycle and backfill design.
- **Gear:** 3.
- **Risk:** Recall regression, rebuild downtime, embedding mismatch. Use aliases and staged traffic.
- **Metric + measurement:** Collection drift findings; embedding-model mismatch count; rebuild duration; retrieval recall@k before/after cutover. Target: zero silent model/dimension mismatches.
- **Kill criterion:** If rebuild/alias cutover causes recall@10 drop >1% or query error rate >0.5%, roll back alias and keep old collection.
- **First PR:** manifest schema, dry-run diff script against local/staging Qdrant, test fixture with fake collection info. ≤400 net lines.

### Rank 7 — Retention partitioning and provable deletion

- **What:** For high-volume retention-bound tables, partition by retention anchor or created_at. Retention policy scopes map to partition drop/detach operations. Legal hold moves or blocks rows/partitions. Deletion jobs produce certificates: table, partition, policy ID, scope, row estimate, executed_at, operator/role.
- **Why it beats SOTA:** Row-level deletion is slow and hard to prove. Partition drop is structural, fast, and auditable. This extends the organism’s already-strong policy model into operational deletion engineering.
- **Cost:** High for existing tables; medium for new tables.
- **Gear:** 3.
- **Risk:** Query plan regressions, FK complications, legal-hold mistakes. Pilot with append-only tables first.
- **Metric + measurement:** Retention job runtime; oldest row age by scope; failed deletion count; legal-hold violation count. Target: zero deletion beyond allowed grace, zero legal-hold deletion.
- **Kill criterion:** If partitioned query p95 worsens >20% or retention job fails twice in one week, revert partitioning for affected table and redesign.
- **First PR:** design migration for one append-only table, partition creation script, CI test that detaches/drops a partition. ≤400 net lines.

### Rank 8 — Generic audit/temporal trigger generator

- **What:** Create an opt-in audit generator: for selected tables, triggers write immutable audit rows to separate audit tables. Audit rows include operation, role, transaction timestamp, before/after JSONB envelope, monotonic sequence, and hash chain. Audit tables are owned by an audit role; app role cannot update/delete audit rows.
- **Why it beats SOTA:** It turns audit from ad-hoc triggers into declarative, testable infrastructure. It also aligns with JSONB codec governance because before/after payloads can use versioned envelopes.
- **Cost:** High.
- **Gear:** 3.
- **Risk:** Write amplification, storage growth, trigger ownership issues. Use per-table opt-in and retention for audit tables.
- **Metric + measurement:** Audited-table coverage; audit write overhead p99; hash-chain verification failures. Target: 100% chain validity for audited tables.
- **Kill criterion:** If write overhead exceeds budget or audit storage growth is unsustainable after compression/retention, reduce audited column set or move to sampled audit.
- **First PR:** generator function, one pilot table, hash-chain test. ≤400 net lines.

## 8. Meta-pattern

The single defective belief generating most findings is:

> **“A migration’s bookkeeping — discovered file, lint pass, applied row, idempotent no-op, or green CI — is equivalent to the live database possessing the intended schema, ownership, invariants, and operational truth.”**

This belief explains:

- Legacy bootstrap drift: CI believed it had the schema because bootstrap ran, while prod had a different shape (`apps/backend-rag/backend/db/migrations_v2/LEGACY_PROMOTION_README.md`).
- Duplicate migration numbers: file discovery order threatened to make application state ambiguous (`/.github/workflows/lint-migration-numbers.yml`).
- Missing rollback markers: runner import could fail late because file form was not enforced early (`/.github/workflows/lint-migration-rollback.yml`).
- Ownership failure: a migration could be recorded as applied while live functions remained unmodified because the applying role lacked ownership (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).
- Retention scope outage: the schema’s invariant changed, but readers were not automatically forced to prove they understood the new invariant (`apps/backend-rag/backend/db/migrations_v2/289_visa_retention_binders_scope_to_visa_decision.sql`).
- Missing JSONB/Qdrant/outbox governance: if a surface is not represented in migration/catalog checks, it becomes invisible even while operationally critical.

The corrective principle is: **live database truth must be verified by catalog state, ownership checks, constraint tests, and operational preflight; migration history is only one input.**
