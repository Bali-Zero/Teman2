## 0. TL;DR

- Position vs SOTA: the organism is ahead of typical repo practice on metadata-only secret-permission auditing and fail-closed PII redaction policy, but behind world-SOTA on unified, capability-scoped egress, OAuth token lifecycle, and agent/network containment.
- Biggest gap: security is enforced as scattered file/line/path checks rather than as one authorized flow boundary; new surfaces (external CLIs, OAuth tokens, env inheritance, tailnet, agent actions) inherit default trust.
- Move 1: build a single local Law-2 egress kernel with signed redaction/consent receipts and fail-closed denial.
- Move 2: create an environment firewall for external CLIs: default-deny env inheritance, allowlist-only variables, canary detection.
- Move 3: replace long-lived token/file/env secrets with a short-lived, process-bound token broker plus public token-metadata registry.

## 1. How the organism does it today for THIS part

All claims below are grounded in the supplied excerpts unless explicitly marked inferred.

### Law-2 output boundary and PII redaction

- Law 2 is defined as a non-negotiable output boundary: no LLM, agent, report, log, memory, shared artifact, or public output may persist or transcribe client/OSINT data in cleartext; outputs must use abstract, redacted, or referenced forms such as `client_id`, hashes, or placeholders (SYMBIOSIS.md).
- The policy is two-phase: DEV suspends only the absolute zero-cloud operational constraint for code/test data, while the output-boundary and minimization rules remain in force; PROD re-arm is explicit, not automatic (SYMBIOSIS.md).
- Cloud inference on chat text containing client PII is treated as processing and transfer; until a per-transfer legal basis is demonstrable, the required posture is fail-closed: keep local/off-cloud or abstain (SYMBIOSIS.md).
- A narrow internal digest derogation is allowed only for assigned-team delivery, with forbidden payload classes, HELD behavior, no fallback recipient, and content-level control over free-text pitches because a pitch can leak forbidden fields semantically even if structured fields are clean (SYMBIOSIS.md).
- The redactor implements a four-pass pipeline before external LLM use: internal identifiers, team-contact patterns first, generic email/bank patterns, then dynamic CRM names built from the database (scripts/_redact_pii.py).
- Redaction is fail-closed: rule-application errors, broken regexes, or too-short output abort the run; regexes are compiled at initialization so failures are loud (scripts/_redact_pii.py).
- Dynamic CRM-name redaction distinguishes “database legitimately out of scope” from “database expected but unreachable”; the latter raises a fail-closed error instead of silently skipping names (scripts/_redact_pii.py).
- Dynamic name matching escapes names, sorts longest-first, and is case-insensitive after a prior lowercase-bypass bug (scripts/_redact_pii.py).
- The redactor is explicitly designed for external LLM egress paths and references external LLM surfaces, including an OAuth-based external path (scripts/_redact_pii.py).

### Secrets hygiene, family #4: secret-in-the-clear

- The filesystem secret-permission auditor targets production credentials exposed with group/world-readable permissions and treats backup suffixes as inheriting the sensitivity of the original file (scripts/secrets_permissions_audit.py).
- It deliberately inspects by name/path pattern only and never opens, reads, or prints file contents; the invariant is that a secret audit must not become an exfiltration channel (scripts/secrets_permissions_audit.py).
- It has explicit blind-scan discipline: if roots exist but zero files are traversed due to sandbox/TCC denial, it exits as blind and refuses to certify clean (scripts/secrets_permissions_audit.py).
- It evaluates reachability through the directory chain, not just file mode; a restrictive parent directory can make a permissive file unreachable (scripts/secrets_permissions_audit.py).
- On stat errors, it defaults to “reachable/cannot verify,” not clean (scripts/secrets_permissions_audit.py).
- It declares an honest limit: hard links to the same inode from another permissive directory are outside a pure path-based audit (scripts/secrets_permissions_audit.py).
- Default scan roots include home-directory credential locations and agent/config directories, indicating concern that agent toolchains hold credential-like files (scripts/secrets_permissions_audit.py).
- It supports `--fix` mode where findings can be chmod-repaired, with nonzero exit if repair fails (scripts/secrets_permissions_audit.py).

### Public-repo hygiene and secret-scan triage

- The detect-secrets triage tool marks baseline findings false only under conservative rules; everything else remains unaudited for human review (scripts/detect_secrets_auto_triage.py).
- It refuses blanket auto-approval for production-like paths, live/prod names, and non-example `.env` files (scripts/detect_secrets_auto_triage.py).
- For files that are not definitionally non-sensitive, it uses content-keyed rules requiring both path scope and exact source-line shape at the finding line (scripts/detect_secrets_auto_triage.py).
- Content-keyed approvals are end-anchored and value-shape constrained after review found two bypass classes: real secret assigned to a pin-named variable, and a second statement riding on the same line (scripts/detect_secrets_auto_triage.py).
- The tool explicitly states the honest limit: a live credential with the same hex shape is byte-indistinguishable from a digest; shape rules narrow, not certify (scripts/detect_secrets_auto_triage.py).
- Public-repo hygiene is handled by allowing public integrity anchors—hashes, truncated credential identifiers, public verification keys—while avoiding secret values; the stated intent is that a public repo can name authorized material without holding it (scripts/detect_secrets_auto_triage.py).

### The 3–5 SOTA practices that matter most here

**1. Secret scanning plus push protection is necessary but insufficient.** Modern repo secret controls try to stop secrets before they enter history and validate whether leaked credentials remain active [6][7]. The organism already has baseline triage and a permission auditor, but SOTA increasingly treats secret scanning as one layer in a lifecycle: detection, immediate rotation, validity checks, and history response. The missing piece here is not scanning; it is a token/secret lifecycle that makes leaked material short-lived and non-reusable.

**2. OAuth security has moved from “store tokens carefully” to “make tokens hard to use if stolen.”** RFC 9700 and related OAuth guidance emphasize exact redirect validation, PKCE, refresh-token rotation, sender-constrained tokens, and rapid revocation [3][4]. For local agent CLIs, the strongest extension is a local token broker: the refresh token never appears in env or repo; the broker issues short-lived, scope-limited access tokens to attested processes only. This directly addresses the OAuth gap inferred from the ground pack.

**3. Prompt injection is a design problem, not a filtering problem.** The strongest direction in 2023–2026 work is separating untrusted data from control flow, limiting tool capabilities, and requiring explicit authorization for actions that touch secrets or egress [1][2]. The organism already protects CI files from agentic modification (.github/CODEOWNERS), but the provided excerpts do not show runtime separation of untrusted content from tool invocation or egress. That is the biggest agent-security gap.

**4. Supply-chain integrity is moving from static pins to provenance.** Static hashes are useful but fragile if the build system or distribution path is compromised. SLSA and Sigstore-style provenance provide signed, verifiable build history and transparency, making “this binary/script is the one we expect” a continuously checkable statement rather than a manually updated pin [8][9]. The organism’s pins and public signing keys are strong for their current scale, but below SOTA for automated supply-chain assurance.

**5. Zero trust tailnet and OS sandboxing turn policy into enforcement.** Tailnet ACLs, device identity, and OS sandboxing make it harder for a compromised agent or CLI to move laterally, read unrelated files, or exfiltrate via arbitrary network paths [11][13][14]. The ground pack does not evidence tailnet or sandbox enforcement, so this is an unaudited but high-leverage area.

## 5. Beyond-SOTA recommendations

Ranking uses qualitative `(impact × confidence) / cost`. Gear definitions: **Gear 1** = config/process; **Gear 2** = code/CI; **Gear 3** = architecture/platform.

### 1. Unified Law-2 egress kernel with signed receipts

- **What:** Introduce one local chokepoint for all external LLM/cloud/CLI egress. The wrapper requires redactor success, records a signed receipt (rule-set hash, destination class, consent/legal-basis id, dynamic-name load state, payload hash), and blocks when dynamic names are expected but unavailable. It should support deterministic pseudonymization: raw names become stable local tokens, while re-identification remains local-only.
- **Why it beats SOTA:** Most SOTA DLP/redaction is library-level or gateway-level after the fact. A local kernel makes Law 2 an enforceable capability boundary, not a script convention. Signed receipts create auditability and non-repudiation without storing PII.
- **Cost:** Medium, 2–4 engineer-weeks for pilot.
- **Gear:** 2.
- **Risk:** Developer bypass, latency, false positives. Mitigate with PATH shims, CI detection of direct external invocations, dry-run mode, and an emergency break-glass receipt.
- **Metric + measurement:** Egress coverage (% external calls through kernel), receipt verification pass rate, synthetic-PII canary leak detection, false-block rate. Measure via local append-only receipt log and weekly canary prompts containing synthetic identifiers.
- **Kill criterion:** If coverage cannot exceed 80% of external calls after 30 days, or false-block rate exceeds 2% in pilot without clear fix, stop and redesign the integration surface.
- **First PR:** `Egress gate wrapper with redaction receipt`, files: `scripts/egress_gate.py`, `tests/test_egress_gate.py`, short operator doc. ~380 net lines. Acceptance: synthetic PII blocked when redaction fails; receipt verifies; logs contain no synthetic PII.

### 2. Environment firewall for external CLIs

- **What:** All external CLIs and agent subprocesses are launched through a sanitized-environment wrapper. Default: no inherited env. Allowlist-only variables. Unknown required variables are denied and logged by key name only. Add a synthetic env canary that must never appear in child output or crash reports.
- **Why it beats SOTA:** Env inheritance is a common, boring leak path; most teams only discover it after a secret appears in logs or a child process. Default-deny env is rare and high-leverage.
- **Cost:** Low, 3–5 days.
- **Gear:** 1/2.
- **Risk:** Breaks tools that expect environment variables. Mitigate with explicit per-tool allowlists and a dry-run mode that reports what would be denied.
- **Metric + measurement:** Number of canary detections (target zero), count of denied unexpected env keys, external CLI failure rate. Measure via wrapper logs and test harnesses that print allowed key names only.
- **Kill criterion:** If critical external CLIs fail >5% of runs after allowlist stabilization, or allowlist grows without justification beyond a small threshold, pause and redesign.
- **First PR:** `Sanitized spawn for external CLIs`, files: `scripts/spawn_clean_env.py`, `tests/test_spawn_clean_env.py`. ~250 net lines. Acceptance: canary env var absent from child environment; allowed vars pass; unknown vars denied.

### 3. OAuth token capability broker

- **What:** Replace long-lived OAuth tokens in files/env with a local token broker. Refresh tokens live only in OS keychain or secret manager, ACL-restricted to the broker. External processes receive short-lived, scope-limited access tokens via a local authenticated socket or controlled stdin. The public repo may keep only one-way token metadata (hash/truncated id), extending the existing philosophy of naming authorized material without holding it.
- **Why it beats SOTA:** OAuth BCP already recommends rotation, PKCE, and sender-constrained concepts [3][4]; the broker adds workload/process identity and short local TTL, making stolen tokens less portable and easier to revoke.
- **Cost:** High, 4–8 weeks for a robust pilot.
- **Gear:** 3.
- **Risk:** Broker becomes an availability chokepoint; keychain integration friction. Mitigate with read-only degraded mode for non-egress operations, but fail-closed for external transfer.
- **Metric + measurement:** Count of long-lived token files/env entries, median access-token TTL, time-to-revoke, unauthorized token-use alerts. Measure via broker ledger, provider token metadata where available, and periodic filesystem audits.
- **Kill criterion:** If broker outage or fallback behavior reintroduces long-lived tokens in env/files for >24h, kill the pilot and simplify scope.
- **First PR:** `Token inventory metadata auditor`, files: `scripts/token_inventory_audit.py`, `tests/test_token_inventory_audit.py`. ~350 net lines. Acceptance: undeclared token-like paths fail; declared one-way metadata passes; auditor never reads file contents.

### 4. Sealed-verdict secret content audit + hardlink signal

- **What:** Extend the metadata-only permission auditor with an isolated content-classifier process that returns only sealed verdicts: file hash, line number, rule id, confidence, and verdict. The parent audit process never receives content. Add `st_nlink` hardlink suspicion reporting and a canary harness for blind-scan, permission, and backup-suffix cases.
- **Why it beats SOTA:** SOTA scanners often read and sometimes log secret content. A sealed-verdict design improves recall while preserving the non-exfiltration invariant. Hardlink metadata partially addresses the declared hardlink blind spot without reading content.
- **Cost:** Medium, 2–3 weeks.
- **Gear:** 2.
- **Risk:** False positives from shape-only content rules; sandbox misconfiguration. Mitigate with canary precision/recall tests and no-network sandbox execution.
- **Metric + measurement:** Recall/precision on seeded canaries, blind-scan rate, hardlink-suspicion findings, human triage volume. Measure via canary corpus and audit reports.
- **Kill criterion:** If canary recall <95% or false-positive volume makes human triage unsustainable, stop content extension and keep metadata-only mode.
- **First PR:** `Hardlink warning + canary harness for permission auditor`, files: small delta to `scripts/secrets_permissions_audit.py`, `tests/test_secrets_permissions_canary.py`. ~300 net lines. Acceptance: candidate file with `st_nlink > 1` is flagged; blind root exits non-clean; output contains no file content.

### 5. Guardrail and triage policy ledger with expiry

- **What:** Convert secret-triage approvals and critical guardrail baselines into signed, expiring policy objects. Each approval records owner, justification, approved-surface hash, expiry, and renewal requirement. CI computes an approved-surface diff; rule changes require owner review plus a second reviewer where possible. This should cover triage rules, guardrail hashes, meta-verifier baselines, and hook-related files.
- **Why it beats SOTA:** SOTA often uses static CODEOWNERS and permanent baselines. Time-boxed, signed approvals make the approved surface measurable, reversible, and resistant to silent expansion.
- **Cost:** Medium, 2–3 weeks.
- **Gear:** 2.
- **Risk:** Approval overhead slows routine work. Mitigate with low-risk auto-renewal only when approved surface is unchanged and canaries pass.
- **Metric + measurement:** Average approval age, expired approvals, approved-surface growth rate, unauthorized rule-change detections. Measure via CI policy reports.
- **Kill criterion:** If >10% of findings remain unaudited for >14 days due to process friction, simplify rules or reduce scope.
- **First PR:** `Security policy schema for triage/guardrails`, files: `scripts/security_policy_schema.py`, `tests/test_security_policy_schema.py`, example policy fixture. ~350 net lines. Acceptance: expired or unowned rule rejected; current rules parse; approved-surface diff is deterministic.

### 6. Prompt-injection capability firewall

- **What:** Treat retrieved documents, web content, messages, and any external text as untrusted data. Untrusted content cannot directly satisfy tool invocations, secret access, or egress. Introduce capability tokens: a trusted operator intent or validated plan grants narrow capabilities; the egress kernel checks capability before transfer. Run untrusted-content agents in OS sandboxes with no direct network except through the egress kernel.
- **Why it beats SOTA:** It moves from “hope the model obeys warnings” to enforced data/control separation, aligned with prompt-injection research and LLM risk guidance [1][2].
- **Cost:** High, 4–6 weeks for a first enforceable slice.
- **Gear:** 3.
- **Risk:** Workflow friction; false confidence if capabilities are too broad. Mitigate with narrow default capabilities and red-team canaries.
- **Metric + measurement:** Red-team injection success rate, blocked untrusted-to-action attempts, untrusted-origin egress attempts. Measure via scenario tests and capability logs.
- **Kill criterion:** If critical agent workflows require manual approval >30% of the time after tuning, reduce scope or redesign capability model.
- **First PR:** `Untrusted-context capability wrapper`, files: `scripts/untrusted_context.py`, `tests/test_untrusted_context.py`. ~350 net lines. Acceptance: untrusted text cannot produce a valid capability token; egress denied without capability.

### 7. Supply-chain provenance and tailnet control plane

- **What:** Upgrade from static pins to SLSA/Sigstore-style provenance for production binaries, wrappers, and critical scripts. Publish signed manifests and verify them before execution. In parallel, define tailnet policy-as-code: device approval, key expiry, service-to-service ACLs, no broad subnet access, and continuous exposure scans.
- **Why it beats SOTA:** Pins prove a value at a moment; provenance proves source/build path. Tailnet ACLs turn network trust into identity-based least privilege [8][9][13].
- **Cost:** High, 4–8 weeks.
- **Gear:** 3.
- **Risk:** Signing infrastructure outage or network lockout. Mitigate with offline verification caches and break-glass recovery runbooks.
- **Metric + measurement:** % artifacts with verified provenance, time-to-detect drift, unauthorized tailnet reachability findings, device-key expiry compliance. Measure via verification logs and periodic scans.
- **Kill criterion:** If signing/verification availability falls below operational tolerance or tailnet changes cause repeated lockouts, pause and simplify topology.
- **First PR:** `Tailnet ACL and provenance manifest fixtures`, files: example YAML/JSON schemas, validation tests. ~380 net lines. Acceptance: over-broad ACL fixture rejected; missing signature/provenance field fails validation.

Wave goals:

- **Wave 1:** close the cheapest high-risk gaps: egress chokepoint pilot, env firewall, and policy schema. Exit criteria: external egress pilot covers at least one pipeline; env canary tests pass; triage/guardrail policy schema rejects malformed rules.
- **Wave 2:** begin replacing artifact-centric secret trust with flow-centric trust: token inventory and sealed-verdict audit. Exit criteria: no undeclared token-like paths in scanned roots without exception; canary recall known and measured.
- **Wave 3:** establish beyond-SOTA agent and network boundaries: untrusted-data capability firewall and supply-chain/tailnet policy fixtures. Exit criteria: red-team injection canary fails closed; manifest validation blocks over-broad fixtures.

## 7. Needs-ruling

Only true business/consent/credential/GUI/physical items:

- **Business/consent:** owner/legal decision on PROD re-arm date; per-transfer legal-basis registry; contract clause for consent; per-client consent proof and revocation workflow; DPA/SCC status recording. These are legal/business controls, not code-only.
- **Credential/admin:** GitHub org/admin authority to enforce required reviews/status checks; secret-manager or OS keychain admin authority for token broker; OAuth application/client registration authority; tailnet admin authority if tailnet is adopted; code-signing or Sigstore identity authority if provenance signing is adopted.
- **GUI/interactive:** macOS TCC/keychain prompts may require human approval for full audit coverage or broker keychain access; sandbox or file-access consent prompts may appear during agent containment.
- **Physical:** if high-assurance signing or admin keys are adopted, a hardware security key or equivalent physical factor may be required. No client data, consent records, or production PII is required for engineering tests; synthetic canaries should be used.

## 8. Meta-pattern

The single defective belief generating most findings is:

**Security can be proven at the granularity of artifacts—file names, regex line shapes, owned paths—rather than enforced at the granularity of flows and capabilities.**

This belief produces the OAuth gap, env-inheritance gap, prompt-injection gap, tailnet silence, and the continued reliance on shape-based triage. The organism already knows “cannot verify is not clean,” but the next step is stronger: “absence of a pattern is not authorization.” The safe unit must become the authorized flow: who spawned it, what capabilities it holds, what data class it touches, where it may egress, and how long its tokens remain valid.
