## 1. How Nuzantara does it today

The verification system is a layered defense, grounded in the generator≠grader principle and enforced by CI gates and local hooks.

### 1.1 Generator ≠ Grader (`verify-template.js`)
- Path: `infra/workflows/verify-template.js` (verified in pack).
- Reusable workflow: Gather (multiple angles) → Verify (independent skeptic per finding) → Synthesize (survivors only).
- Schema-enforced findings with evidence, source, confidence.  
- Skeptic count configurable (default 1, up to 5 for high-stakes).  
- Majority voting: a finding survives if not refuted by majority.  
- Encodes the principle “judging < generating” and the lesson W65: “even the refuter hallucinates.”

### 1.2 Final Gate Discipline (`.claude/skills/final-gate-discipline/SKILL.md`)
- Path: verified in pack.
- Non-delegable: the operator (Fable 5) must re-read the diff, verify subagent scope, and check all touched docs.
- Five mandatory questions before declaring “done”:
  1. **Who calls it?** (grep for callers)
  2. **What other surface describes it?** (docs vs reality)
  3. **What did I just write that will expire?** (hardcoded numbers/paths)
  4. **Can my probe actually say yes?** (positive control required)
  5. **Where does the work actually live right now?** (committed, pushed, merged)
- Derived from real failures (e.g., tracking events registered but never called).

### 1.3 Guard Conformance (`check_guard_conformance.py` + `registry.json`)
- Path: `infra/guard-conformance/check_guard_conformance.py` (header verified).
- Enforces superscar #3 antidote: “no guard merges without a guilt AND innocence test.”
- Census (C1): every `_guard_*` in code must be in registry, no stale entries.
- Proofs (C2): every guard must have ≥1 guilt and ≥1 innocence test ref.
- Anti-phantom (C3): every test ref must exist as a `def` in the declared file.
- Armed (C4): every test file must be reachable by at least one workflow.
- Runs in CI via `guard-conformance.yml` (sentinel pattern avoids W69 pending-forever).

### 1.4 Fuzz Harness (`guard_fuzz_harness.py`)
- Path: `infra/claude-hooks/guard_fuzz_harness.py` (header verified).
- Property-based fuzz corpus for command-matching guards (e.g., `worktree_isolation.py`).
- Generates combinatorial shapes: noop wrappers, remote dispatch, text-only, deceptive local, true-compound remote prelude.
- Each case carries expected verdict from grammar rule (property, not memorized example).
- Covers W83, W84, W85, W91, W92, W105, W117 over-match incidents.
- Used in CI via `guard-conformance.yml` step “Property/fuzz corpus”.

### 1.5 Mutation Testing (`p1s2-mutation-incremental.yml`)
- Path: `.github/workflows/p1s2-mutation-incremental.yml` (verified).
- Incremental mutation (AST-diff, changed lines only) with hidden canary mutants.
- Ensures the mutation driver’s own tests pass, and canary mutants are killed.
- Runs on `pull_request` and `push` to main.

### 1.6 Adversarial Review Gate (`adversarial-review-gate.yml`)
- Path: `.github/workflows/adversarial-review-gate.yml` (verified).
- Required check: every research/audit deliverable must have an adversarial review by a seat ≠ author.
- Script `check_adversarial_review.py` verifies presence; includes self-test for guilt+innocence.
- No paths filter – always runs to avoid pending-forever (W69).

### 1.7 Harness Floor (`harness-floor.yml`)

### 3.1 Most relevant SOTA to our part

1. **Google’s mutation testing integration** is the closest analogue to our `p1s2` gate, but they run it on every change, not just changed files. Our incremental approach is similar, but the canary mechanism is our unique addition.

2. **LLM-as-Judge biases** directly threaten our generator≠grader architecture. If our skeptics are sycophantic or biased, the whole verification pipeline is compromised. We should implement debiasing techniques (e.g., position randomization, multiple model families).

3. **Differential testing** is under-exploited. We have a fleet of models capable of generating alternative implementations of small functions. Running them on the same inputs and comparing outputs could catch semantic bugs that unit tests miss.

4. **Property-based testing** is a natural fit for our guard conformance. The fuzz harness already does this for command guards; we could generalize to data invariants, API contracts, and UI states.

5. **Formal verification** is still too heavy for our organism, but lightweight invariant checking (e.g., using Python’s `assert` or `pydantic` validators) could be enforced by a new CI gate.

## 5. Beyond-SOTA recommendations

### 5.1 Scar-to-Test Compiler (S2TC) — rank 1

**What:** A tool that reads the scar corpus (`cicatrix-scars.md`, `cicatrix-superscar.md`) and generates executable regression tests (property-based, differential, or metamorphic) for each scar. The compiler uses an LLM (e.g., local Ollama for PII-free) to parse the scar narrative and produce a test skeleton, which is then reviewed by a human or a different model before being armed.

**Why it beats SOTA:** No surveyed system automatically generates regression tests from an organization’s own failure log. Google’s mutation testing and Meta’s Getafix mine code changes, not incident narratives. This exploits our unique scar corpus (296 KB) and the generator≠grader principle (the compiler generates, a separate system verifies the tests).

**Cost:** Flat-sub token usage (Ollama local for initial generation, then a review pass with Opus). Estimated 50K tokens per scar, ~3M tokens for 60 scars.

**Gear:** 3.

**Risk:** Scar descriptions may be ambiguous; generated tests might be incorrect or tautological. This could trigger superscar #3 (over/under-match) if tests are too broad/narrow. Mitigation: mandatory review by a different model, and the test must pass against the current codebase (if it fails, either the scar is not fixed or the test is wrong).

**Metric:** Number of armed scars (from 2/66 to 50/66). Measurement: `jq '[.gates[] | select(.prose_only==false)] | length' infra/scar-gates/MANIFEST.json`.

**Kill criterion:** If the generated tests take more time to fix than to write manually, after 10 scars.

**First PR:** `scripts/scar_to_test.py` (≤400 lines): takes a scar ID, reads the scar block, prompts an LLM to generate a test file, and writes it to `infra/scar-gates/test_W<N>_<slug>.py`. Includes a dry-run mode.

### 5.2 Cross-Model Verification Tournament (CMVT) — rank 2

**What:** For high-stakes Gear 3 tasks, instead of a single skeptic (or N homogeneous skeptics), run a tournament of refuters from different model families (Opus, Sonnet, Gemini, Codex, DeepSeek, local Ollama). Each refuter independently attacks the claim; then the refuters’ arguments are cross-evaluated by a different set of models. The final verdict is a synthesis of the strongest counterarguments that survived cross-evaluation.

**Why it beats SOTA:** Debate frameworks (Irving, Khan) use two homogeneous agents; our tournament uses heterogeneous models, exploiting the organism’s 6 OAuth seats. It also combats LLM-as-Judge biases (Zheng et al.) by diversifying the judge pool. The cross-family council is already a seed of this, but it’s ad-hoc; we make it a structured workflow.

**Cost:** High token usage: 6 refuters + 3 cross-evaluators per claim. For a typical Gear 3 task with 5 findings, ~45 LLM calls. Flat-sub quotas may be strained.

**Gear:** 3 (opt-in, for tasks where error cost >15× tokens).

**Risk:** Cost and latency; may be overkill for low-stakes. Scar family: #6 (wrong scar propagated) if the tournament reinforces a false consensus.

**Metric:** Reduction in false-positive findings (measured by tracking retractions of findings within 30 days). Baseline: current retraction rate (from retracted-claims registry).

**Kill criterion:** If the tournament’s verdicts are no better than a single strong skeptic after 10 trials.

**First PR:** `infra/workflows/verify-tournament.js` (≤400 lines): extends `verify-template.js` to accept a `tournament: true` flag, which fans out refuters to a configurable model roster and adds a cross-evaluation phase.

### 5.3 Continuous Differential Fuzzing (CDF) — rank 3

**What:** For every function with a clear specification, use the fleet to generate alternative implementations (e.g., Sonnet, Codex, DeepSeek each write their own version of a pure function). Then run the same inputs through all implementations and compare outputs. Any discrepancy is flagged as a potential bug in the original or in the alternatives.

**Why it beats SOTA:** Differential testing is known, but no system uses LLMs to generate the alternative implementations on the fly. Our organism has multiple coding-capable models and a culture of “always have a second opinion”—this extends that to code.

**Cost:** Moderate token usage: generate 2-3 alternative implementations per function, then run tests. Can be limited to hot-zone files.

**Gear:** 3 (or 2 for non-critical).

**Risk:** Non-deterministic functions (e.g., time, random) will produce false positives. Mitigation: only apply to pure functions or those with mocked side effects. Scar family: #3 (over-match if the fuzzer flags too many false positives).

**Metric:** Number of bugs found that were not caught by existing tests. Measurement: count of issues filed by CDF.

**Kill criterion:** If signal-to-noise ratio is below 10% after 4 weeks.

**First PR:** `scripts/differential_fuzz.py` (≤400 lines): takes a function name, generates 2 alternative implementations via Codex and Sonnet, runs a set of inputs, and reports differences.

### 5.4 Self-Verifying Invariants — rank 4

**What:** Instrument critical functions with runtime invariant checks (e.g., `assert balance >= 0`). A CI gate (`invariant-conformance.yml`) ensures that every invariant has a corresponding test that triggers it (guilt) and a test that doesn’t (innocence), similar to guard conformance. This extends the guard conformance pattern to data invariants.

**Why it beats SOTA:** Amazon uses automated reasoning, which is heavy; this is a lightweight, executable approach that exploits the existing guard-conformance infrastructure. It makes invariants visible and enforceable.

**Cost:** Low: extending `check_guard_conformance.py` to a new surface.

**Gear:** 2.

**Risk:** False positives if invariants are too strict; false negatives if they’re not comprehensive. Scar family: #3.

**Metric:** Number of invariants with both guilt and innocence tests. Measurement: `grep -c "assert" --include="*.py" -r apps/ | wc -l` vs registry count.

**First PR:** Extend `registry.json` with an `invariants` section, and add a checker in `check_guard_conformance.py` for `assert` statements.

## 8. §Meta-pattern

The single defective belief that generates the majority of verification failures is:

**“A guard that exists is a guard that works.”**

This manifests as:
- Scar gates written as prose, never armed (64/66).
- AI PR review workflow that ran green but delivered zero (W64).
- Canary test that was a tautology (catC).
- Guard conformance checker that didn’t run its own tests (W81, later fixed).
- The assumption that a comment promising visibility is a caller (memory lesson).

The antidote, already encoded in the final gate discipline’s question 4 (“Can my probe actually say yes?”), is: **probe the work, not the proxy.** Every verification mechanism must prove its own effectiveness on a known-positive case, and that proof must be re-executed by CI, not just asserted in a comment.
