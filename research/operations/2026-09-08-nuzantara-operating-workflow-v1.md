## Authority and staffing

Zero and Subhi supply user needs, business behavior, scope decisions and UX acceptance. They do not code, carry patches or review code. Zero owns spending and changes in authority. Do not infer Todoist contact identities from names.

| Role | Responsibility and communication |
|---|---|
| **Imperators Fable 5.1 and Astra, equal peers** | Strategic direction, constraints and appointment of a temporary Dux. Communicate with each other and the generals; intervene on material decisions and exceptions rather than managing every builder. No dual imperial approval is required for each small change. An Astra session opened by the user is a strategic entry point, not an automatic promotion to general or implementer. |
| **Generals Opus and Sol, equal peers** | One is appointed **Dux** for the mission, owning planning, assignments, coherence, integration, evidence and Todoist reconciliation through one operational base. Dux is a temporary responsibility, not a new model, permanent rank or coordinator software. The other general serves a separate front of the same objective, or verification, only when useful and eligible. Opus is not assigned permanent reviewer status by this hierarchy. |
| **Optional specialists** | Own a domain or technical contract, communicate with their general and, when necessary, their assigned builders. |
| **Builders** | Implement bounded file ownership and proof criteria; report to the assigned general or specialist. |
| **Optional supports** | Perform narrow work for a builder, such as tests, cleanup or mechanical checks, with bounded inputs and outputs. |

A small mission may consist of its Dux, also implementing, plus independent verification. These are responsibilities, not five mandatory recursively nested runtime levels. There is no additional workshop-agreed numerical agent limit or requirement to occupy every rank. The Dux chooses one available qualified operational base for the mission; Opus/Claude-native and Sol/Codex-native are peer choices, not a permanent default ordering. Record the appointment, executor, independent verifier and authorized release owner, with actual session identifiers, effective models and verified availability before relying on them. Unavailable or unobserved fields remain explicit; a roster label never proves an executed launch.

**Independent verification is an assignment outside the contribution chain for the evaluated artifact, not a permanent rank.** General parity does not confer new merge, arm or deploy authority on Astra or Sol. Under the current external-builder contract, a Sol/Codex external builder prepares; a separate noncontributing Claude session verifies, and an authorized Claude owner releases. The Dux may not grade its own contribution or bypass that fence.

Add builders, specialists or supports only for a concrete need, with explicit ownership, reporting and integration boundaries. Use qualified available subscription routes; this document grants no paid API authorization or claim that those routes are currently running.

PRE-review should provisionally use a session separate from the plan author. It may also perform POST-review if it remains independent of implementation. A reviewer who edits or contributes implementation becomes a contributor and cannot grade that result. Changing skills inside a builder session is not independence. A separate session from the same model family can be independent, but applicable repository Gear, family/model and external-builder release requirements still bind; this pilot cannot waive them.

## State contract

Exactly one complete user objective is active. Each transition records its input, output, owner and evidence. State names below are logical record fields, not a claim that custom Todoist statuses exist.

| State | Required input and output / exit condition |
|---|---|
| `NEED` | Zero/Subhi supplies need and acceptance. Strategic entry obtains the Dux appointment; Dux reconciles prior work and records one objective, journey and exclusions. |
| `PLAN` | The general acting as Dux produces technical scope, affected components, alternatives, risks, checks, consumer proof and rollback approach. Material strategic questions go to imperators. |
| `PRE_REVIEW` | Dux assigns and obtains completed AI plan review. Resolve technical objections; identify remaining business choices before human decision. Merely requesting review is insufficient. |
| `HUMAN_DECISION` | Present plan and review to Zero/Subhi. Record explicit scope, intended behavior and authorization to implement. Silence is not consent. |
| `BUILD` | Assigned builder, or Dux for a small mission, implements authorized scope in an isolated worktree. Run relevant checks and return a concern-scoped diff with evidence to the general or specialist. |
| `POST_REVIEW` | Dux freezes and identifies exact revision and contribution chain. An eligible reviewer outside that chain completes review and returns `PASS`; otherwise correct or block. |
| `TEST_ACCEPTANCE` | Dux establishes that required tests and acceptance evidence are completed and passed for the reviewed result. Earlier runs are reusable only if still applicable to that exact result. |
| `READY_FOR_RELEASE` | Dux delivers the complete evidence package to an authorized Claude release owner. External Codex builders never merge, arm or deploy their own work. |
| `VERIFY_LIVE` | Authorized owner releases through existing gates. Observe the agreed behavior in the actual consumer; merged or deployed alone does not satisfy this state. |
| `CLOSED` | Dux closes only after acceptance and live proof pass, residuals are recorded, and the final Todoist update is read back successfully. |

Documentation-only work substitutes verified deliverable existence, content and intended handoff for production deployment; it never invents a live release. This documentation task writes no Todoist records: its originating coordinator owns those writes.

Record `BLOCKED` with cause, affected stage, owner, exact question, options, recommendation and resume condition. Record `SYNC_PENDING` separately from execution state. Continue only independent, already authorized work whose correctness does not depend on the missing decision or record. Missing review, incorrect information or a broken journey blocks closure. Harmless cosmetic issues can be recorded as residual work.

One PR, one concern; aim for approximately 400 net lines where practical. Each PR body includes `Bites:` naming a real consumer and the observation proving the change is in force. A promised future consumer is insufficient. Serialize shared-lockfile changes. The authorized release owner follows existing PR/CI/review rules; push, PR creation and merge remain separate actions.

POST-review identifies base and head SHA, diff scope, contributor roster, test evidence and reviewer verdict. Any later implementation change requires review of the new result and relevant checks. CI must also pass for the actual merge candidate as required by the repository. Once auto-merge is armed the branch is read-only; subsequent work starts from fresh `origin/main`. This contract grants no external builder permission to arm it.

On `CHANGES_REQUIRED`, the Dux returns actionable findings to the contributor, obtains corrections, then dispatches fresh review. A requested review is never a pass. Diagnose a red check before retrying. Three reds for the same cause suspend before a fourth attempt; fix-of-fix depth remains one, then clarify the specification. Do not bypass gates to meet a delivery target.

Do not request repeated human permission within an already authorized scope. The Dux escalates material strategic questions to the imperators and out-of-mandate business choices or scope expansion to the authorizing Subhi/Zero, with a question, options, recommendation and blocked portion. Zero decides budget and authority changes. AI performs technical transport and integration; unavailable tools create a specific blocker, not a requirement that humans carry patches.

## Capacity and pilot measurements

The temporary, adjustable pilot ceiling is **four distinct pilot PRs worked per WITA calendar day**, not a quota. The conservative provisional counting rule takes the union of PR IDs newly opened OR receiving implementation/review work that day, including drafts and replacements. Count each PR once per day: repeated review adds recorded time, not another daily unit; a carried PR counts again on the next day if worked or reviewed then. Closure does not refund a unit. The Dux reconciles the pilot total before opening or working another distinct PR. There is no minimum PR production obligation within this pilot. This counting default is not a newly ratified global rule or a repeal of an older Notion item. No fixed two-PR concurrency or hourly review limit was agreed.

Start with sequential dependent implementation slices. Independent construction or review preparation may overlap when ownership and integration boundaries are explicit; final review still binds the frozen revision. Do not fragment concerns to consume capacity or bypass the ceiling.

Capture elapsed wait, review failures, rework, escaped defects and human interventions for each objective. PRE-review reducing rework is an unmeasured hypothesis. Evaluate the Dux coordination role on real objectives and retest after changes to routing, instructions or tools; a historical hierarchy description or successful document delivery is not coordinator qualification.

## Todoist and session reconciliation

Todoist remains the source of truth. The Dux updates the same task at meaningful transitions, decisions and blockers, preserving history through comments and existing fields. Do not install a second task system or assume unsupported app features.

Record: objective and acceptance; WITA timestamp; previous/new state; reason and authorization; Dux appointment/executor/contributors/independent verifier/release owner; effective session/model identities and verified availability; exact revision and links; completed review/test/consumer evidence; blockers/residuals; next action and owner; distinct pilot PRs worked today; synchronization condition.

Read back each write. An ambiguous response requires reconciliation before retrying, preventing duplicate comments or tasks. With no connector, persist an explicitly unsynced local pending update; transfer it to the same task and read it back when access returns. Do not claim continuous sync or close against stale state. If another coordinator owns writes, send it the exact update and require confirmed readback rather than duplicate writes.

At session start or a manually initiated morning session, reconcile previous results, blockers, current artifacts/PRs and new needs before selecting the objective. At session end record actual results, remaining work and next action. This workshop activates no scheduled wake-up or follow-up.
