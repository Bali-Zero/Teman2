# Beyond-SOTA 6/13 — CI, merge queue & the ship pipeline

*Scope: from `git push` to a commit on main. Deploy is lane 7; verification content is lane 5.*

## 0. TL;DR

Position in one sentence: **correctness is AT/AHEAD of SOTA (ALLGREEN queue, evidence-driven required-check curation, a queue-trap corpus nobody else has published), economics and structural-conflict management are BEHIND (every PR pays Backend Tests ~2.5×, the queue never batches, and 39% of open PRs sit DIRTY on fixed shared files).**
Biggest gap: the queue is run as a serial turnstile — `min_entries_to_merge: 1` — while 44%+ of merged PRs are docs/ledger-class; Uber cut 53% of CI cost from an *already-correct* queue, and our equivalent levers (batching, sentinel symmetry) are spec'd but unturned.
Top-3 moves:
1. **R1** — batch the queue (1→3) + make the path-sentinel symmetric across `pull_request`/`merge_group`, with a trigger-symmetry lint so batching can't reintroduce trap #9. Target: runner-min/PR 121–138 → <80, median open→merge 61 → ≤40 min.
2. **R2** — conflict-by-construction linter: predict DIRTY at PR-open by intersecting merge-base add/add hunks against every open PR (the W128 claim-set technique generalized). Target: DIRTY 39% → <10%.
3. **R3** — the queue-state oracle: one `mq state` verb encoding the 19 measured traps' attestation order, plus a lint banning raw `autoMergeRequest`/`isInMergeQueue` reads outside it. Target: sentinel false-alarm incidents (≥3 in Aug) → 0.

## 1. How Nuzantara does it today

**The spine.** A push travels: `.husky/pre-push` (840 lines) → PR open → `gh pr merge <N> --auto` **bare** (the queue owns the merge method; `--auto --squash` is rejected with "The merge strategy for main is set by the merge queue" — `.claude/skills/pipeline-ship/SKILL.md` §1) → GitHub merge queue (ruleset `19779175`, live since 2026-07-27) rebuilds the PR on a synthetic `gh-readonly-queue/main/pr-<N>-<sha>` branch and re-runs required checks against current main → squash onto main. Arming at PR-open is doctrine, not preference: `feedback_arm_automerge_default_not_leave_to_operator.md` (Zero, 2026-06-25) and CLAUDE.md §2 ("arm means freeze") make the session, never the codeowner, the merger.

**Pre-push gate.** `.husky/pre-push` resolves its own classifier/lock/tip-drift helpers from a trust root (`NUZ_PREPUSH_TRUST_ROOT` pins a reviewed-main bundle for the unattended Codex autofix runner — a repaired branch must not supply the gate that judges it; `.husky/pre-push:2-16`). `scripts/prepush_classify.py` (1,042 lines) is a path-aware **allowlist**: anything unrecognized pays the full backend suite; `.github/workflows/tests.yml` sits in `NEVER_INNOCENT_EXACT_PATHS`, `conftest.py` in `NEVER_INNOCENT_BASENAMES` (pipeline-ship §3). `scripts/prepush_suite_lock.sh` (283 lines) serializes the backend suite to one runner per machine via mkdir-atomic `/tmp/nuzantara-prepush-backend-suite.lock` with stale-holder detection — born from a measured load-68 incident with 12 concurrent suites and SIGTERM-killed pushes. A full-suite push exceeds the 2-minute tool timeout, so doctrine is detached push (`nohup … disown`) with rc streamed to a log, then `git ls-remote` verify-by-content (pipeline-ship §2, W97). `scripts/quickcheck.sh` runs advisory-only inside the hook, `|| true` load-bearing under `sh -e` (W101 decapitated-guard family, annotated in the hook itself at lines 42-49).

**Required checks & branch protection.** Classic branch protection with `strict: false` (the race the queue closes); the live count is deliberately *not* hand-copied into docs — the probe is the doc (`merge-queue-discipline.md` §2). History: 25 (2026-07-27) → 26 → **27** (2026-08-21 audit) → **Zero ruled 27→9 on 2026-08-27** → the reinstatement rule fired twice within the hour on two real catches (actionlint caught PR #5050's under-floor `timeout-minutes: 5`; guard-conformance caught PR #5045's 3 unregistered hooks) → **11 live**, snapshotted in `infra/required.d/contexts.json` (regen-only, never hand-edited; drift vs live is expected and cured by `scripts/ci/snapshot_required_contexts.py`). The reinstatement rule (§2bis): any demoted check returns to required — by anyone, no ruling — on (1) Main Red Breaker firing on main itself, or (2) a real catch. Two structural constraints on the required list: a secret-needing context is impassable for Dependabot (Snyk can never be required), and workflow-level `continue-on-error` does not keep a job's own check green.

**The queue's parameters** (ruleset 19779175, re-readable via `gh api`): `ALLGREEN`, `max_entries_to_build 5`, `max_entries_to_merge 4`, `min_entries_to_merge 1`, wait 2 min, `check_response_timeout 90`, `SQUASH`. `min_entries_to_merge: 1` means **the queue never batches** — one full CI run per PR (token-ceremony audit §2, verified on #4448/#4449/#4450). `HEADGREEN` was evaluated as a throughput knob and rejected on 2026-07-27 after reading GitHub's docs: it admits red-checked PRs into groups (runbook §6bis).

**CI cost anatomy** (all measured, `research/operations/2026-08-21-token-ceremony-ci-system-audit.md` §2 + `2026-08-23-runner-slot-audit.md`): **106 workflow files** today (`ls .github/workflows | wc -l`; 92 at the 08-21 audit — ~66 on `pull_request`, ~30 on `merge_group`; one disabled: `ai-pr-review.yml.disabled-2026-08-20-zero-value-ci-trust-gate`, 100 runs/30h with zero comments delivered). Every PR: 60-68 checks, 121-138 runner-minutes. Median open→merge over 60 PRs: **61 min** — "the median PR is one 30-minute job run twice, back to back" (pull_request run + merge_group run of Backend Tests). **Queue re-entry amplification 1.5×**: 388 merge_group runs for 258 merged PRs since sharding → Backend Tests executes **~2.5× per merged PR**. Top slot consumers: Backend Tests + Security Scanning ≈235 runner-hours/day (~94% of top-5). Detect Secrets: 19 min full-tree scan of 18,967 files per PR. GitHub "Code Quality" duplicates the custom CodeQL job at ~13.7 min/PR, not required, no REST surface (attribution corrected in §13.1 of the audit). PR mix in 7 days: 258 merged — 33% docs, **11% ledger-only** (`PENDING-ARMS.md` single-file PRs). What the second (queue) run actually catches, sampled: **cross-PR coupling on committed generated files and infra flakes, not logic regressions** (`test_deleted_at_guard_registry_matches_disk` red 3× in one morning from a sibling PR moving a committed registry — W109b class; Playwright killed by Docker Hub `toomanyrequests`).

**Workflow taxonomy** (my classification of the 106): ~14 cron-prefixed watchers (`cron-*`), ~20 lint/pin gates (`lint-*`, `cat[A-F]-*`, token-lint, symbiosis-lint), ~10 conformance/immune gates (guard-conformance, organ-conformance, immune-enforcement, hook-innocence-gate, verify-the-verifiers), 4 queue/main watchers (merge-queue-watch every 10 min with GraphQL poll + Telegram + DRY-RUN re-armer; main-red-breaker — consecutive same-job failure detector; merge-gate-integrity-watch — a *detector*, deliberately not a canary, ~71 min/day; main-push-failure-watch), core test/security (tests.yml, security.yml, semgrep, sbom, sonarqube, codeql), deploy (fly-deploy), and product-specific suites (wr2/wr3/garuda/kbli/intel).

## 2. Scars & ledger evidence in this area

This lane owns the two densest scar families in the corpus. Superscar **#9** (state read via proxy) and **#2** (exists ≠ armed) both concentrate on the ship pipeline; `MEMORY_MERGE_QUEUE_TRAPS.md` holds **~19 measured traps** (11 numbered + 4 unnumbered continuation bullets + 4 roll-up rows), every one dated and measured, several of them corrections of *earlier traps* — the trap list has its own recidivism.

**The proxy-lies cluster (#9):**
- **W111** — `gh run rerun` replays a stale merge-ref; probed by content (`git show refs/pull/N/merge`), fixed by `update-branch`/`mq requeue`. Its GOTCHA seeded trap #1: neither `autoMergeRequest` nor `isInMergeQueue` alone answers "is this armed?".
- **W118** — 11 hours of zero merges from TWO independent causes that masked each other: a third-party advisory turned a required red 87 seconds after the last merge (npm audit queries the live DB — the world changed, not the tree), and an unbounded `apt-get` inside a 10-min budget whose kill reads `cancelled`, not `failure`. "Zero check failures" was true and was the symptom. Fix: `package.json` overrides + `scripts/ci/apt_install.sh` (120s cap, fail-closed verify, 13-case corpus).
- **W124** — a DIRTY PR gets a *silent* CI: the check-suite declares `completed`/`success` on the subset that ran; read `mergeStateStatus` before waiting on checks.
- **W125** — resolving conflict markers by hand is not `--ours`: git merges non-contested hunks silently into a conflicted file; the C1 evidence pack absorbed a sibling's `l_level: L2` outside any marker. Conflicts are per-HUNK.
- **W102** — hot-zone gate's two-dot diff accused a probation member's content PR of touching CODEOWNERS. Cure: merge-base anchoring + guilt/innocence/scar-pin corpus + per-run self-test.
- **W109b / W86** — two PRs shrinking the same monotonic registry block each other with zero shared lines; DOCSYNC derived-count stale after `--auto` merged the first green push. Coupling ≠ file overlap.
- **W128** — scar *numbers* themselves collide: claims live in open PRs, not on main; antidote `scripts/lint_scar_number_collision.py` computes the claim set from main + open-PR diffs.

**The armed-state cluster (#2):**
- **W123 + 27/8 correction** — a hold honored by disarming appeared to re-arm itself; the correction (measured on #5095) established the *opposite* for lane branches: the whitelist's step-1 branch filter never matches `agent/*`, so disarm IS durable there — and the "proof" that circulated (`run → success`) was a job exiting `match=false` green. A run's `success` is not evidence of its action.
- **W126** — draft does not eject a queued entry: `convert_to_draft` 13:21, `merged` 13:31. Dequeue is a GraphQL mutation (`dequeuePullRequest`, field `id`); a queued branch also refuses pushes (GH006) — the queue enforces "arm means freeze" at ref level.
- **W69** — the P* workflows ran but were never required: "esiste-ma-disarmato" applied to the gate layer itself; also the pending-forever trap (a path-filtered required check never reports on non-matching PRs), which is why guard-conformance now always-triggers with a sentinel — which in turn created trap #9's head-green/queue-red split (same job, different work per trigger).
- **W122** — Fly release_command did the work then exited 130 on a SIGINT: red hiding a healthy organ; the inverse polarity of #2.
- **Traps #12-16** (roll-up 26/8): a red required check disarms auto-merge and green does NOT re-arm it; `gh pr checks` buckets CANCELLED outside `fail` (three consecutive "0 reds" on a FAILURE rollup); rollup `SUCCESS` over 3-4 contexts while main requires 27 (post-rerun check-run detachment under runner famine); `gh run rerun` refuses `startup_failure` runs (only close/reopen re-emits the event — and that disarms auto-merge); an armed CLEAN PR can be ejected silently with zero reds and no readable event ("arming is not definitive").
- **Trap #10** — the meta-trap: knowledge of an ambiguous field written in prose does not stop a session from encoding the ambiguous field into a background probe, which then lies autonomously with the authority of automation. Its later correction (PR #5036) went further: there is a *window* where `autoMergeRequest` is already null and `mergeQueueEntry` has not yet materialized — **no instantaneous read of those two fields, even joint, can prove "not armed"**; the authoritative probe is the arm command's own refusal (`already queued to merge`).

**Ledger/PENDING-ARMS rows** (from superscar PR-1 landing lines): `git branch -D` from a worktree is repo-wide but the guard judges cwd (#3); GitHub mergeability does not honor `merge=union`, and `autoMergeRequest` does not survive a CONFLICTING transit — re-arm via GraphQL. The whitelist test finding (`discovery_auto_merge_whitelist_lets_tier1_script_paths_through…`, 2026-08-26, verified on two machines): `scripts/tests/test_auto_merge_whitelist.py` is 24/73 red on clean origin/main **and no workflow executes it** — the reds are real executions of the real workflow step, but the test presumes CODEOWNERS (reviewer) and whitelist (auto-merge eligibility) must coincide, which was never established; branch protection as the outer net was never measured. A guard whose only executor is nobody is family #2 *inside the arming surface itself*.

**Cost baseline for discipline failures** (CLAUDE.md §2 rule 8, measured 2026-08-22): PR #4547 — a 1-file hook fix — took **14 commits, 11 adversarial rounds, ~6h**; the 44h session driving it burned 3.9M output tokens; **27 of 200 commits** landing on main over 3 days existed only to correct a claim a previous one made. That number is why rule 8 ("three rounds, then suspend") exists.

**Recurrence pattern:** the queue traps did not stop accruing after the runbook — traps #9-#19 all post-date it (24/8-28/8). What changed is *where* they land: early traps cost merges (W118: 11h), late traps cost only re-arms and probe rewrites. The corpus is converging on one invariant — **no single GitHub field is load-bearing; only refusals, terminal states, and queue-branch run existence are** — but each session still re-derives a slice of it the hard way (trap #10's sentinel, #5036's window).

**The five that matter most.**

**Uber SubmitQueue** is the reference architecture for what our queue is *not* doing: it treats the queue as an optimization problem (which subsets of pending changes are worth building, in what speculative order) instead of a serial turnstile. The 2025 paper's numbers (53% CI resources, 37% p95 wait) came from *adding intelligence to an already-correct queue* — exactly our situation: ALLGREEN correctness is solved; everything left is economics. We cannot run SubmitQueue (we don't control GitHub's queue scheduler), but its two cheap ideas — batch compatible changes, don't rebuild what can't conflict — are expressible in the queue parameters we already own and in the path-aware sentinel we already wired.

**Mergify's batching math** is the honest cost model for GitHub-queue users: batch=4 ⇒ ~25% of CI runs, paid for with one bisection round per red batch. Our measured mix (33% docs, 11% ledger-only, 28% md/json-only PRs) is the *best possible* batching population — near-zero true conflict probability, near-zero batch-failure bisection cost. `min_entries_to_merge: 1` forfeits this entirely; the token-ceremony audit already spec'd the flip (L1) with its proof probe.

**Meta's predictive selection + the flaky stack** matter jointly: both are built on *learning from execution history*, and our history is unusually rich because the queue re-runs everything (388 merge_group runs / 258 merged PRs). The SOTA insight is that repeated execution is signal, not just cost. Nobody surveyed harvests *queue-duplication itself* as their flakiness/selection corpus — they build dedicated rerun infrastructure. We already paid for the reruns.

**bors rollups** are the culturally closest precedent: a high-volume, discipline-heavy, single-trunk project that solved throughput not with speculation but with *trains* — many low-risk changes, one CI payment. A "docs/ledger train" (one PR aggregating N ledger touches, or queue-batching them) is rollups reborn.

**MergeBERT** defines the ceiling for auto-*resolution* (63–68%) — which is precisely why resolution is the wrong bet for us: W125 measured that even a careful human resolution silently absorbs foreign hunks, and a 2/3-accurate model on a business-facing repo with no human reviewer is a liability. The transferable half is *prediction*: our conflicts are structural (fixed shared paths), so predicting them at PR-open is nearly deterministic — no ML needed, just the merge-base add/add discriminator we already wrote down as trap #11.

## 5. Beyond-SOTA recommendations (ranked by impact × confidence / cost)

**R1 — Batch the queue + make the path-sentinel symmetric ("rollups without a human").**
*What:* (a) PATCH ruleset 19779175: `min_entries_to_merge 1→3`, `min_entries_to_merge_wait_minutes 2→4` — the exact L1 lever the token-ceremony audit spec'd with its proof probe (§9, "session, not operator"). (b) Extend the `change_map.py` sentinel-skip so docs/ledger/md-json-only diffs skip Backend Tests in the **merge_group** run at the same rate they do on `pull_request` — today only ~13% of queue runs skip, against a 60%+ eligible mix. (c) Enforce trigger symmetry: one lint asserting every path-filtered workflow has *identical* path semantics on `pull_request` and `merge_group` (the trap-#9 head-green/queue-red split, currently a scar, becomes a gate).
*Why beyond SOTA:* Mergify sells batching; Uber built speculation; bors used humans for rollups. Composing GitHub's own batching knob with a *scar-derived symmetry lint* — a gate that encodes trap #9 so batching cannot reintroduce the split that bit us — is a combination none of them ships, and it exploits our asymmetry: the trap corpus tells us exactly how this fails before we turn it on.
*Cost:* ~2h session + 1 PR ≤150 lines (lint) + 1 API PATCH. Gear 2.
*Risk:* family #2 — a sentinel green-without-work is by-construction theater; counterweights already live (main-red-breaker, reinstatement rule). Batch-red bisection adds latency on genuinely-red batches (measured base rate: tests.yml 9 failures/100 merge_group runs).
*Metric:* merge_group runs per merged PR 1.5 → ≤0.6; Backend-Tests executions per merged PR 2.5 → ≤1.3; runner-min/PR 121–138 → <80; median open→merge 61 → ≤40 min. Method: the audit's own probe (`gh run list --workflow tests.yml --event merge_group --created ">=D" | wc -l` vs merged PRs; re-run the 60-PR open→merge median).
*Kill criterion:* any red batch whose bisection costs >2 extra queue cycles twice in a week, or one trap-#9-class incident → revert the PATCH (one API call, reversible by design; record old JSON first, per the audit).

**R2 — Conflict-by-construction linter: predict DIRTY at PR-open from the open-PR claim set.**
*What:* a PR check that computes, for the opened PR, merge-base-anchored added-hunks per file (trap #11's discriminator: only add/add in overlapping windows forces serialization) and intersects them with **every other open PR's** diff — the exact claim-set technique `scripts/lint_scar_number_collision.py` already proved on scar numbers (W128), generalized from "W-number" to "file+hunk-window". Output: a posted verdict — "collides with #N on `evidence/pack.yml` (add/add): serialize behind it / migrate to per-task path" — plus a repo-wide table of the structural hot files (evidence/*.yml until 2026-09-05, PENDING-ARMS.md, organs_registry.yaml, contexts.json, mdx batches).
*Why beyond SOTA:* Uber's conflict analyzer prunes speculation *inside* the queue; MergeBERT resolves *after* the collision. Nobody surveyed predicts conflicts at open-time against the open-PR set — because their conflicts are incidental. Ours are structural (fixed shared paths), which makes prediction nearly deterministic and cheap — no ML, one `gh api pulls/N/files` sweep. Exploits: W128's proven claim-set lint + a known, finite hot-file list.
*Cost:* 1 PR ≤350 lines (script + tests + workflow, advisory first). Gear 2.
*Risk:* family #3 (over-match: flagging same-file different-hunk pairs that merge cleanly — trap #11's own lesson; the discriminator must stay merge-base + overlap, never "same file"). API rate limits on 30+ open PRs (cacheable).
*Metric:* DIRTY share of open PRs 39% (12/31, measured 2026-08-28) → <10%; queue ejections attributed to union-file collisions (via `queue_ejection_attribution.py`) → 0/week. Method: re-run this session's `gh pr list` probe weekly.
*Kill criterion:* two false serialization verdicts on PRs that merge cleanly → demote to comment-only until the discriminator is fixed.

**R3 — The queue-state oracle: one probe, and a ban on raw field reads.**
*What:* promote the trap corpus into a single `mq state <N>` verb whose verdict uses only the *reliable* signals in the corpus's own attestation order: (1) `gh pr merge --auto`'s refusal text ("already queued") — only when arming is intended; (2) terminal states (`mergedAt`/`CLOSED`); (3) existence of `gh-readonly-queue/main/pr-<N>-*` runs; (4) GraphQL `mergeQueueEntry`+`autoMergeRequest` *jointly, labeled non-probative for "not armed"*; plus rollup-vs-required-count (trap #15) and CANCELLED-bucket handling (trap #14). Then a conformance lint that **bans raw `autoMergeRequest`/`isInMergeQueue` reads outside `mq.sh`** — the same executable-antidote pattern the organism uses for guards (family #3 cure style) and Telegram senders (W108's gateway ban).
*Why beyond SOTA:* the corpus itself is ahead of anything published (§4); the gap is trap #10's lesson — knowledge in prose does not stop the next session from encoding the lying field into a sentinel. No surveyed system needed this (they own their queues); on GitHub's queue, an *enforced* oracle is the only correctness layer available. Composition: measured-API-behavior corpus + lint-enforced single point of truth.
*Cost:* 1 PR ≤300 lines (mq.sh verb + lint + guilt/innocence corpus). Gear 2.
*Risk:* family #3 (the lint over-matching legitimate GraphQL exploration in research scripts — scope it to sentinels/probes/workflows); the oracle itself must never auto-arm (probe ≠ mutation).
*Metric:* trap-#10-class incidents (sentinel false alarms on armed PRs: ≥3 recorded 24–27/8) → 0 in 30 days; re-arm nudges to already-queued PRs → 0. Method: grep session logs + fleet-watch reports for "re-arm"/"DISARMED" false positives.
*Kill criterion:* the oracle itself produces one false "not armed" verdict → freeze the lint, keep the verb advisory.

**R4 — Harvest the duplication: flakiness scoring from the pull_request/merge_group pair.**
*What:* a nightly job that joins per-test outcomes across the two runs every merged PR already pays for (same diff content, different base), plus queue re-entries: same-test divergence with no interfering sibling commit = flake signal; with one = coupling signal (attribution via `queue_ejection_attribution.py`). Maintain a PFS-like score per test; above threshold, auto-file a PR adding the test to `infra/merge-os/quarantine.d/` (mechanism exists, empty since birth) — **unless** it matches a `critical-floor.d` pattern, which is never quarantinable and instead escalates P1.
*Why beyond SOTA:* Meta/Atlassian/Spotify built dedicated rerun infrastructure to generate flake signal; we already run every test ~2.5× per merged PR as a *side effect of the queue* and throw the signal away. Using queue duplication as a free flakiness corpus, gated by a declared never-quarantine floor, is a composition none of them publishes. Exploits: the dual-run waste (R1 reduces it but docs-lane PRs still leave a large paired corpus), critical-floor.d, and the quarantine schema already on disk.
*Cost:* 2 PRs ≤400 lines each (harvester + scorer; quarantine auto-PR). Gear 2–3 (touches gate behavior).
*Risk:* family #2 (quarantining a real regression signal — the floor + the reinstatement rule are the counterweights); W129-class calendar flakes need the score to window by date.
*Metric:* queue ejections attributed to flaky tests → −80% in 60 days (baseline: build it from ejection-attribution data first — currently unmeasured); time-to-quarantine for a new flake: days → <24h. Method: `queue_ejection_attribution.py` weekly rollup.
*Kill criterion:* one critical-floor test auto-quarantined (must be impossible by construction — if it happens, the whole scorer stands down) or one masked real regression.

**R5 — Split "world changed" from "diff changed" in the security gates.**
*What:* W118's class, cured structurally: npm-audit (and any advisory-DB-backed gate) runs in PR/queue context against a **pinned daily snapshot** of the advisory DB, answering only "does THIS diff introduce a vulnerability not in base?"; a separate async daily job runs against the live DB and, on a new world-red, opens the fix PR itself (override/bump) instead of reddening every innocent PR mid-flight. Same decomposition for Detect Secrets: diff-scoped in PR context (the audit's L3 lever — prove equivalence on the last 20 PRs first), full-tree scan stays as the async daily.
*Why beyond SOTA:* Bazel pins builds hermetically but nobody surveyed pins the *audit database* per merge-window; the industry default (npm audit live in CI) is precisely what froze this repo for 11h off an 87-second race. The decomposition (diff-gate on snapshot + world-watch that ships its own cure) composes hermeticity with the organism's session-owns-the-fix doctrine.
*Cost:* 2 PRs ≤300 lines. Gear 3 (security posture change — see Needs-ruling).
*Risk:* family #13-adjacent: bounded advisory latency (≤24h) between world-red and gate-red; mitigated because the async job *opens the fix PR*, which is faster than today's "queue freezes, a session firefights".
*Metric:* W118-class fleet stalls (baseline: 1 × 11h in Aug) → 0; innocent-PR reds from world changes → 0; advisory-fix lead time ≤24h. Method: main-push-failure-watch + a dated log line in the async job.
*Kill criterion:* any vulnerability that would have been diff-blocked under live-DB but passed under snapshot → revert to live.

**R6 — Stacked lanes for dependent agent work (experiment).**
*What:* adopt GitHub native stacked PRs (public preview 2026-07-30, `gh-stack`) for the W109b shape — two PRs that are semantically one change split across a monotonic registry — and for assembly-line integration branches, replacing "integration branch with zero required contexts" (the measured automerge hole, PR #4899 merged unread) with a stack whose base is main and whose every layer faces the full required set.
*Why beyond SOTA (marginal):* not novel per se — the novelty is using stacks to *close the integration-branch gate hole* rather than for review ergonomics. Ranked last: preview-stage feature, unknown queue interaction (a stack entering an ALLGREEN queue is exactly the kind of thing the trap corpus exists for — expect new traps).
*Cost:* half-day experiment, no PR until proven. Gear 1 probe → Gear 2.
*Metric:* W109b-class mutually-blocking pairs/month → 0; integration-branch PRs merging without required checks → 0.
*Kill criterion:* first stack-specific queue trap that costs a merge → document, retreat, keep the trap.

## 8. §Meta-pattern

One defective belief generates most of this lane's findings: **"the unit of coordination is the artifact GitHub hands you — a field, a green, a file — rather than the entity it stands for."** Downstream instances: probes read `autoMergeRequest` instead of the arm-state machine (traps #1/#10/#16); the fleet coordinates through fixed shared files instead of per-entity paths (39% DIRTY, W109b, W125, the union-driver illusion); gates read two-dot diffs instead of merge-base authorship (W102); the queue re-runs *whole CI* instead of the semantic delta (2.5× duplication whose measured catch is coupling-and-flakes); "the run is green" stands in for "the check passed" (trap #17, §2's continue-on-error caveat). The organism's own cure pattern — superscar #9's "read the CONTENT, never the proxy" — is already the right doctrine; what this lane adds is that the cure must be *executable and enforced at the single point of use* (oracle + lint), because trap #10 proved prose knowledge does not survive contact with the next session's sentinel. Every recommendation above is the same move at a different layer: replace a proxy (field, fixed path, blanket rerun, live world-state) with the entity (state machine, per-task path, semantic delta, pinned snapshot + async watcher).
