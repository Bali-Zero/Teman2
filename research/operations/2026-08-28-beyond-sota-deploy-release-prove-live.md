# BEYOND-SOTA 7/13 — Deploy, release & prove-live

## 0. TL;DR

- **Position:** at-or-ahead of surveyed SOTA on deploy automation and post-deploy *truth* (elite DORA frequency — ≥8 deploys/day, 15/15 green, measured; prove-live-by-content instruments like the 401-vs-503 split-brain probe, the ancestry-semantics frontend sentinel, and a monthly *exercised* restore drill exceed what Google/AWS/Netflix publish about verifying a release) — but **BEHIND on structured exposure**: no deploy has ever ridden the designed dark→5%→100% ladder, no scheduled synthetic journey guards a public funnel, and release judgment is a grep for the literal string `"healthy"`.
- **Biggest gap:** the synthetic-journey + dead-man class — full doctrine in ASSEMBLY-LINE §6–7, zero daemons armed (superscar #2 acknowledged in the file's own backlog). Measured against the five real public-surface defects of 2026-08-28, that one instrument would have caught 2/5 certain (+1 with a persona matrix); today, time-to-detect a dead public funnel is unbounded — a human notices.
- **Move 1 (R1):** arm the anonymous buyer — Mini-scheduled browser-transport journey probe (sandbox tenancy, content assertions) + a dead-man receptor that flips `GARUDA_PUBLIC_ENABLED` **off** via the existing `garuda-arm.yml` allowlist actuator when the heartbeat goes silent. Nothing surveyed flips a two-platform flag on probe *silence*.
- **Move 2 (R2):** deploy-parity receptors — served `?dpl=` must change after bundle-path merges (the measured never-deployed-commit class), and every live `*.balizero.com` surface must name its repo source (the `knowledge.` orphan class).
- **Move 3 (R3):** the two-platform flag contract as code — `flags.yaml` SSOT (platforms, readers, truthiness grammar, TTL) + lint; no surveyed vendor models one flag name with two control planes.
- **Meta-pattern (§8):** every scar here is one belief — *the control plane's announcement is the state of the data plane* — and the cure is to make distrust of announcements structural (standing data-plane receptors with guilt-runs), not remembered.

## 1. How Nuzantara does it today

**Topology.** Two platforms, one repo. Backend: Fly.io app `nuzantara-rag` (two process groups, `api` public + `rag` internal-6PN, per `/Users/nuzantara/.claude/skills/fly-split-brain-verify/SKILL.md`) plus `nuzantara-postgres` (repmgr HA per `CLAUDE.md` §11). Frontend: one Vercel project builds `apps/mouth` for balizero.com and every subdomain; `apps/mouth/vercel.json` is 5 lines (`installCommand: cd ../.. && npm ci --include=dev` — monorepo root install). `apps/backend-rag/` carries both `Dockerfile` and `fly.toml` (presence verified by `ls`; not opened per lane constraint).

**Backend pipeline** (`.github/workflows/fly-deploy.yml`, 652 lines, triggers on push to backend paths + `workflow_dispatch`): a 6-job DAG. (1) `pre-deploy-gate`: import-chain smoke (the `dependencies.py`/`service_initializer` SPOF), Ruff blocking on deploy-critical rules only, 82 core tests, CVE-exception staleness, Dependabot criticals. (2) `run-migrations` via `flyctl ssh console` — against the **previous** image. (3) `deploy` rolling, 3 attempts with a 90s sleep on `failed to acquire leases` (the signature of two deployers racing). (4) `run-sql-v2-migrations-post-deploy`: re-runs `python -m backend.db.migrate apply-all` **pinned to a fresh-image machine** — the in-file comment records why: pre-deploy migrations run on the old image, so SQL added by the same PR was invisible until a manual no-op redeploy (cicatrix STRUCTURAL 2026-04-26, resolved by this job). (5) `run-python-migrations` (119/120/121, hardcoded). (6) `post-deploy-health`: 10×30s curl for the literal `"healthy"` body, **automatic `flyctl releases rollback --yes` on failure**, then an informational RAG smoke (`POST /api/chat/query`, `continue-on-error`). A separate `deploy-failure-alert` job names the failing stage for crashes before health. The workflow's own comments state the honest limit: *"`flyctl releases rollback` reverts the IMAGE only"* — schema changes from steps 2/4 survive the rollback (image and schema are decoupled by design, expand/contract is the migration author's duty).

**Deploy = migrate, as the runtime role.** The Fly `release_command` runs the migration runner with `settings.database_url` — the same DSN as the app, role `backend_rag_v2`, no `SET ROLE` anywhere (memory `discovery_the_migration_runner_is_the_runtime_role_..._2026_08_27`, measured in prod). Consequence: DDL on an object owned by `visa_ledger_owner` doesn't just fail — **it aborts the entire deploy**, taking unrelated changes on the same image down with it (W130, 2026-08-26: five GARUDA migrations, five failures, main un-deployable). The CI gate is blind to this class *by construction*: its ephemeral Postgres has the connecting role own everything, so `ALTER TABLE` cannot fail there. The countermeasures are now convention: catalog-guarded DDL (`DO $g$ ... pg_has_role ... EXECUTE`), an **external live-catalog probe** that stays red until the DDL really applied (a declined migration is recorded APPLIED and never retried), and a static guard test extended 2026-08-27 to cover functions, not just tables.

**The documented manual procedure** (`/Users/nuzantara/.claude/skills/nuzantara-deploy/SKILL.md` + `CLAUDE.md` §11) counts **12 distinct manual steps**: git status · git diff --name-only · venv activate · import smoke · 3-file pytest · `fly deploy` from **repo root** (build context trap: Dockerfile COPYs are root-relative; deploying from `apps/backend-rag` fails — scar 2026-06-02 TRAP 1) · `fly status` · `fly logs` · curl /health expecting 200/307 · browser-screenshot QA of the subdomains · fix/redeploy loop · final report. The honest post-deploy check adds the **6 steps of `fly-split-brain-verify`** (per-group status, /health, the discriminating unauthenticated `GET /api/crm/practices` expecting **401-not-503**, machine status+log read, force-start, re-probe) — **18 steps end-to-end**. Two staleness findings inside the procedure itself: the skill still says `nuzantara-postgres` is "Stolon HA" (§11 corrected to repmgr on 2026-08-09) and still lists `calendar`/`mail`/`drive` in the QA URL set (§11 removed them 2026-08-18: projects deleted, orphan DNS 404s). The skill's own header ("§11 wins") is what saves it — but a procedure that must be diffed against doctrine at each use is a scar of family #1 waiting to bite. A second ambiguity: the skill documents the *manual* `fly deploy` without stating that `fly-deploy.yml` **already deploys automatically** on any merge touching backend paths — the lease-retry loop in CI is the fossil of that race.

**Split-brain verification** is a first-class named procedure, not folklore: `/health` is wired to the `api` group only, so a dead `rag` worker leaves health=200 while every RAG/CRM call 503s (scar 503-RAG, 2026-06-02). The skill encodes the two-state probe (401 healthy / 503 dead), the *autostop-idle vs stuck-after-crashloop* disambiguation for a STOPPED machine, the old-timestamp trap in `fly logs`, and the rule that a green `fly releases` row is NOT proof the new image runs on an autostop machine. Automation exists: `cron-fly-restart-detector.yml` (\*/15) force-starts crashed-stopped machines, and — after the 2026-08-18 incident where the rag worker stopped 78s post-deploy with `exit_code=0`, invisible to the crashed-only rule — also force-starts any stopped non-standby `nuzantara-rag` machine whose process group has autostop disabled, with cooldowns and a `FLY_AUTOHEAL_PAUSED` kill switch. `cron-fly-watcher.yml` (\*/15) reads machine states and unhealthy checks (splitting `vm` pressure-noise from service checks after a 78-alert storm on 2026-08-18 buried the day's one real anomaly), and carries a `test_alert` self-probe because *an alarm whose healthy state is silence needs a way to distinguish healthy-silent from dead*.

**Frontend release** is Vercel auto-deploy on push to main — with two organism-grade additions. First, `frontend-live-sentinel.yml`: born from 2026-07-27, when balizero.com served 13-hour-old code while 25 commits landed (the Vercel GitHub App had silently lost its installation; the "Vercel Build Guard" workflow was green while verifying nothing). The sentinel asks **production which commit it is RUNNING**, not any registry whether a deploy was announced — GitHub's deployments API "measures reporting, not deploying", and a deployment can go READY while the custom domains keep serving the previous build (measured again 2026-07-30). Verdict semantics are *ancestry* ("does production include this commit"), computed against the newest commit touching bundle-reaching paths (e2e excluded), one alert per stale commit. Its comments also contain a measured platform truth: GitHub scheduled workflows declared at \*/15 delivered at a **median of 91 minutes** over 16h — "a `cron:` expression is a request, never an interval". Second, the `mini.vercel_autopromote` organ (a Mini cron promoting an already-built READY deployment so merged frontend PRs reach production with no human), whose three test corpora ran NOWHERE until `vercel-autopromote-tests.yml` armed them — the workflow's header names its own disease: superscar #2 applied to the guards of an organ built to cure superscar #2.

**Feature flags live on two platforms, and the organism knows it.** `GARUDA_PUBLIC_ENABLED` exists independently on Fly (backend routers) and on Vercel (`apps/mouth/src/app/visa/voa/flag.ts` — literal `"true"` only, `notFound()` otherwise, `force-dynamic` so a flip needs no redeploy). Setting it on one leaves the other dark, and **the dark page answers HTTP 200** carrying a Next.js 404 template with the *correct* `<title>` — so a status-code probe and a title probe both pass; only body-grep for `NEXT_HTTP_ERROR_FALLBACK` sees the dark (memory 2026-08-27). `garuda-arm.yml` is the sanctioned arming path: CI-only because no fleet machine holds a `nuzantara-rag`-scoped Fly token; a **closed hard-coded allowlist** of `GARUDA_*` names (structurally cannot touch an unrelated secret); `type: choice` inputs so the backend/frontend truthiness mismatch (`1` opens the API, leaves the page dark) cannot be typed; empty secrets are SKIPPED, not set-to-empty (absent is the honest state); its header says in bold that a green run is NOT "GARUDA VOA is live". `lint-garuda-environment-values.yml` closes the loop by delegating to a schema test so the workflow's choice list can never offer a value the DB `CHECK (environment IN ...)` rejects — the 2026-08-26 defect class where arming with the default would have broken the funnel on first write while /health stayed green.

**The ship ladder** is doctrine in `docs/factory/ASSEMBLY-LINE.md` stages 6–7: merge lands flag-off (ship dark), canary synthetic journey in prod, progressive internal → 5% → 100% with SLOs green at each step and **real users at 5%** ("no AI judge substitutes for a human failing to find the pay button"); rollback = flag off, DB stays backward-compatible; the paged alert is a **business invariant** ("paid orders in rolling 24h above 0"), plus a **synthetic transaction that really buys** (sandbox pay, refunded) every 10–15 min with a dead-man switch: probe silent 15 min → flag auto-off + owner alert. The GARUDA MANDATE operationalizes it: DONE = the journey runs in production behind the flag, synthetic probe green 48h, funnel dashboard live, then Zero signs 5 decisions and flips the flag. The file's own "Enforcement backlog" concedes the honest state: the dead-man probe, the per-PR refuter check, and six more indicative-mood rules are **tracked, not armed** (superscar #2 acknowledged in situ). Measured today: the funnel answers an anonymous visitor end-to-end in prod (201, one price, D-7 arithmetic correct, `noindex` — a correct dark launch), with exactly one residual gate (no Xendit secrets → order routes 503 by construction).

**PROVE-LIVE** is a named stage of the master loop (`.claude/skills/modus/SKILL.md` row 6): done = live in prod, proven **by content, not exit code**, against a pre-deploy baseline; probe fails → STOP-THE-LINE (no CLEAN, no CAPTURE, rollback, branch stays alive); what can't be proven this turn gets a **durable receptor**, never a fake this-turn check; a producer's own log is STILL a proxy (W89) — prove by the downstream state-delta. ## 8. §Meta-pattern

**The single defective belief: "the control plane's announcement is the state of the data plane."** Every scar this lane grounded is one reporter trusted as the world: health=200 over a dead worker (503-RAG) · a READY deployment while domains serve yesterday (07-30) · a green "Build Guard" verifying nothing (07-27) · exit 130 over completed work (W122) · `applied_by='system'` over a superuser's out-of-band hands (W130) · a `cron:` schedule delivering at 6× its declared interval · an advisory smoke that was never green watching nothing · an SLO doc describing 2-3 deploys/week over a pipeline doing 8/day. The organism's antibody — PROVE-LIVE by content, ancestry semantics, 401-vs-503 discrimination, "read the OUTPUT, not the color" — is real and in places genuinely ahead of the surveyed field. But the belief **regenerates on every new surface**, because each new reporter (a workflow, a flag, a platform, a doc) is born trusted and only loses trust by wounding; the instruments are consistently *post-hoc* (sentinel after the blackout, restart rule after 08-18, env lint after 08-26). That is the second finding inside the first: the organism's release engineering learns at the speed of its own injuries, not at the speed of its ship ladder — the ladder that would convert defect-classes into pre-paid instrument-classes (journey probe, parity receptor, fixture judge) has been doctrine for 4 days short of never-ridden.

The recursion is the sharpest edge: **the reporter-trust belief attacks the instruments themselves** (family #2 applied to its own cures — the autopromote guards that ran nowhere, the never-green smoke, the probe-that-becomes-theater risk in every §5 row). Hence the one structural rule threading all five recommendations: no receptor ships without a way for its silence to be distinguishable from health — a dead-man on the probe, a guilt-run on the judge, a self-probe on the alert channel, a seeded-mismatch test on the lint. The beyond-SOTA position, stated once: surveyed SOTA automates *judgment about announcements* (canary scores, deployment records, rollout states); this organism's asymmetry — always-on machines, a scar corpus that names every lie a reporter has told it, and sessions that own the full lifecycle — lets it automate *distrust of announcements*, standing, at every layer, including its own.
