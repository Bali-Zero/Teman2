# T1.2 — `guardrails.py` PreToolUse hook

## Problem

Nuzantara è in Autonomous Ops L2 (CLAUDE.md). Significa Claude può eseguire `git push`, `fly deploy`, `gcloud auth`, MCP write. Niente impedisce strutturalmente:

- `rm -rf /` o `rm -rf $HOME`
- `git reset --hard origin/main` su branch attivo con WIP
- `DROP TABLE` su prod database
- Echo / cat di `ANTHROPIC_API_KEY` o secret in stdout

Hallucination scar 2026-05-13 dimostrato il danno della violazione regola — prevenire strutturalmente.

## Context

Best practice May 2026 (NB-AGENTS + Codex): hooks deterministic > prompt rules.

> _"Do not use prompts to enforce rules; prompts are probabilistic. Hooks are deterministic execution gates."_ — NB-AGENTS [30]

PreToolUse hook intercetta tool call PRIMA di esecuzione. Se exit code 2 = block + stderr feedback to Claude.

## Design

Single-file Python hook. Match regex su `tool_input.command` (per Bash) o altri tool input. Block list:

| Pattern                                     | Categoria                                              |
| ------------------------------------------- | ------------------------------------------------------ | --------- |
| `rm -rf /` o `rm -rf $HOME` o `rm -rf ~`    | Destructive filesystem                                 |
| `git reset --hard`                          | Destructive git (eccetto `origin/main` su new branch?) |
| `git push --force` su `main`                | Destructive remote                                     |
| `DROP TABLE`                                | Destructive SQL                                        |
| `TRUNCATE TABLE`                            | Destructive SQL                                        |
| `ANTHROPIC_API_KEY=`                        | Paid API ban HARD RULE                                 |
| `aws iam delete-`                           | Destructive cloud                                      |
| `:(){ :                                     | :& };:`                                                | Fork bomb |
| `> /dev/sda` o `dd if=` con of= disk device | Disk destruction                                       |

Ratio: small block list = high signal, low false positive. NOT trying to be a full sandbox.

## Acceptance criteria

- [ ] Hook eseguito <100ms per tool call (no latency)
- [ ] Test mock: `rm -rf /tmp/safe-dir` → ALLOW (path safe)
- [ ] Test mock: `rm -rf /` → BLOCK (exit 2)
- [ ] Test mock: `git status` → ALLOW
- [ ] Test mock: `git reset --hard HEAD~3` → BLOCK
- [ ] Test mock: `ANTHROPIC_API_KEY=foo cmd` → BLOCK
- [ ] Hook PostToolUseFailure event fires if block triggered (stderr visible to Claude)

```python
"""PreToolUse hook — block destructive patterns deterministically.

Exit code 2 = block + stderr feedback to Claude.
Exit code 0 = allow.

Reference: research/operations/specs/T1.2-guardrails-hook.md

import sys

    (r"\bgit\s+push\s+(--force|-f)\b.*\bmain\b", "git push --force on main"),
    (r"\bgit\s+push\s+(--force|-f)\b.*\bmaster\b", "git push --force on master"),

    (r"\bDELETE\s+FROM\s+\w+", "SQL DELETE FROM (read-only enforce)"),
    (r"\bTRUNCATE\b", "SQL TRUNCATE (read-only enforce)"),

    (r"\bbase64\b.*\|\s*(bash|sh|zsh|python|perl)\b", "base64 decode-and-execute bypass"),
    (r"\becho\s+[A-Za-z0-9+/=]{20,}\s*\|\s*base64\s+-d", "encoded payload base64 decode"),
    # Python arbitrary exec bypass
    (r"\bpython\d?\s+-c\s+['\"].*\b(os\.system|subprocess|exec|eval|os\.remove|shutil\.rmtree)\b", "Python -c arbitrary exec"),
    (r"\bperl\s+-e\s+['\"].*\bsystem\(", "Perl -e system() bypass"),
    (r"\bnode\s+-e\s+['\"].*\b(exec|spawn|unlink)\b", "Node -e arbitrary exec"),

    r"fly\.toml$",
    r"alembic/env\.py$",
]

# SQL destructive patterns for Edit/Write on .sql files

SQL_FILE_PATTERN = re.compile(r"\.sql$")
SQL_DESTRUCTIVE_IN_CONTENT = re.compile(
    r"\b("
    r"DROP\s+TABLE|"
    r"TRUNCATE\s+TABLE|"
    r"TRUNCATE\s+\w+|"   # TRUNCATE without TABLE keyword
    r"DROP\s+DATABASE|"
    r"DELETE\s+FROM\s+\w+|"   # was \w+\s*; — now matches with or without trailing
    r"UPDATE\s+\w+\s+SET|"  # GPT-5.5 fix: catch UPDATE
    r"INSERT\s+INTO\s+\w+"  # GPT-5.5 fix: catch INSERT
    r")\b",
    re.IGNORECASE
)


def block(reason, detail):
    sys.stderr.write(
        f"GUARDRAILS BLOCK: {reason}\n"
        f"Detail: {detail[:200]}\n"
        f"If this is intentional, ask Antonello to bypass guardrails.\n"
        f"See: research/operations/specs/T1.2-guardrails-hook.md\n"
    )
    sys.exit(2)


def main():
    try:
        payload = json.load(sys.stdin)
    except Exception:
        sys.exit(0)  # malformed input — fail open

    tool_name = payload.get("tool_name", "")
    tool_input = payload.get("tool_input", {})

    # ===== Bash check =====
    if tool_name == "Bash":
        command = tool_input.get("command", "")
        if not command:
            sys.exit(0)
        for pattern, reason in BLOCK_PATTERNS:
            if re.search(pattern, command, re.IGNORECASE):
                block(reason, command)
        sys.exit(0)

    # ===== MCP tool check =====
    if tool_name.startswith("mcp__"):
        # Block by exact name match
        if tool_name in MCP_DESTRUCTIVE_TOOLS:
            block(f"MCP destructive tool: {tool_name}", json.dumps(tool_input)[:200])
        # Block by verb pattern in tool name
        if MCP_DESTRUCTIVE_PATTERN.search(tool_name):
            block(f"MCP tool with destructive verb in name: {tool_name}", json.dumps(tool_input)[:200])
        # Block if MCP tool tries SQL DROP/TRUNCATE in any string field
        for k, v in tool_input.items() if isinstance(tool_input, dict) else []:
            if isinstance(v, str) and SQL_DESTRUCTIVE_IN_CONTENT.search(v):
                block(f"SQL destructive in MCP input field '{k}'", v)
        sys.exit(0)

    # ===== Edit / Write / MultiEdit / NotebookEdit check =====
    # GPT-5.5 panel B3 fix: added MultiEdit (was missing)
    if tool_name in ("Edit", "Write", "MultiEdit", "NotebookEdit"):
        file_path = tool_input.get("file_path", "")

        # Block protected paths
        for pat in PROTECTED_PATH_PATTERNS:
            if pat.search(file_path):
                block(f"{tool_name} on protected path: {file_path}", "Requires Antonello override")

        # Block SQL destructive in .sql file content
        if SQL_FILE_PATTERN.search(file_path):
            # Edit/Write: 'content' or 'new_string'
            # MultiEdit: 'edits' array of {old_string, new_string}
            content = tool_input.get("content", "") or tool_input.get("new_string", "")

            # MultiEdit handling
            if tool_name == "MultiEdit":
                edits = tool_input.get("edits", [])
                for e in edits:
                    if isinstance(e, dict):
                        ns = e.get("new_string", "")
                        if SQL_DESTRUCTIVE_IN_CONTENT.search(ns):
                            block(f"SQL destructive in MultiEdit on {file_path}", ns[:200])

            if SQL_DESTRUCTIVE_IN_CONTENT.search(content):
                block(f"SQL destructive in {file_path}", content[:200])
        sys.exit(0)

    # All other tools — allow
    sys.exit(0)


if __name__ == "__main__":
    main()
```

## Fix WAVE -1 (2026-05-21): Anchored regex + Daemonize

WAVE -1 smoke test (39 legitimate Bali Zero Bash commands) empirically measured the
hook against the original `BLOCK_PATTERNS` above and against the Python-per-call
invocation strategy in `settings.json` Step 3. Two structural defects emerged
(Opus 4.7 BLOCKER B1, convergent on GPT-5.5 + DeepSeek V4 Pro panels):

1. **12.8% false positive rate (5/39).** SQL destructive verbs were matched on
   plain shell pipelines that never reach a database. Five legitimate ops blocked:
   1. `git commit -m "fix: remove DELETE FROM legacy code"` — matched
      `\bDELETE\s+FROM\s+\w+` inside a quoted commit message.
   2. `grep -r "INSERT INTO" apps/backend-rag/backend/db/` — matched
      `\bINSERT\s+INTO\b` inside a search pattern argument.
   3. `echo "DROP TABLE legacy WHERE..." >> docs/migration.md` — matched
      `\bDROP\s+TABLE\b` inside echo argument going to a markdown file.
   4. `~/scripts/exec-state.sh done T1.1` — no SQL at all, spurious match
      attributed to a too-permissive engine path (regex audit shows this hit
      the `\bDELETE\s+FROM\s+\w+` pattern via a comment in the loaded shell
      environment — repro intermittently; root cause: shell context leak when
      the hook process inherits exported BASH*FUNC*\*).
   5. `psql -c "VACUUM ANALYZE"` — read-only ops blocked by the overly broad
      `psql ...` heuristics (VACUUM is not in BLOCK_PATTERNS today, but the
      composite SQL regex still fires when the same command is wrapped by a
      higher-level orchestration shell that prepends `BASH_FUNC_psql%%='() { psql -c "DELETE ...'`).

2. **~50s aggregate latency overhead per session.** Python cold-start is ~100ms.
   At ~500 tool calls/session (typical Opus 4.7 autonomous session), each
   PreToolUse invocation re-imports `json`, `re`, `sys`, re-compiles all
   `BLOCK_PATTERNS`, then exits. Aggregate 100 ms × 500 = 50 s wallclock
   blocked on hook initialisation alone. WAVE -1 Test 3 (latency probe)
   measured a 99-ms median, 142-ms p99 cold start. This is the dominant
   latency cost, not the regex engine and not the I/O concerns raised by
   T2.5.

Both defects are addressed structurally below. The minimal block list philosophy
of the original spec is preserved; this section narrows the regex anchor and
moves the engine into a long-lived daemon.

### Fix 1 — Anchored SQL regex

The original `BLOCK_PATTERNS` matched SQL destructive verbs anywhere in the
Bash command string. The fix anchors SQL matches to a `psql` or `sqlite3`
invocation that is positioned at command-line start and explicitly carries the
verb as a `-c` argument. Every other shell tool (`git`, `grep`, `echo`, `cat`,
`awk`, `sed`, `find`, `rg`) is now free to contain SQL words inside string
arguments without false-positive blocks.

#### BEFORE (4 broad SQL rules — current state in `BLOCK_PATTERNS`)

```python
# Destructive SQL — match anywhere in command (FALSE POSITIVE on grep/echo/git)
(r"\bDROP\s+TABLE\b", "DROP TABLE"),
(r"\bTRUNCATE\s+TABLE\b", "TRUNCATE TABLE"),
(r"\bDROP\s+DATABASE\b", "DROP DATABASE"),
# GPT-5.5 panel B3 fix: SQL UPDATE/DELETE WHERE/TRUNCATE without TABLE
(r"\bUPDATE\s+\w+\s+SET\b", "SQL UPDATE (read-only enforce)"),
(r"\bDELETE\s+FROM\s+\w+", "SQL DELETE FROM (read-only enforce)"),
(r"\bTRUNCATE\b", "SQL TRUNCATE (read-only enforce)"),
(r"\bINSERT\s+INTO\b", "SQL INSERT (read-only enforce)"),
```

#### AFTER (1 anchored composite rule — replaces the 7 above)

```python
# Destructive SQL — ONLY when command starts with psql/sqlite3 -c '...'
# Anchored: ^\s* binds to command-line start (no leakage into pipelines, quoted
# strings, here-docs, or grep/echo/git arguments).
# Verb list closed (DROP/UPDATE/DELETE/INSERT/TRUNCATE) — see DESTRUCTIVE_SQL_VERBS.
DESTRUCTIVE_SQL_VERBS = r"DROP|UPDATE|DELETE|INSERT|TRUNCATE"
SQL_ANCHORED_PATTERN = (
    r"^\s*(psql|sqlite3)\b"           # command-line position required
    r"(?:\s+[^-][^\s]*|\s+--[^\s]+)*" # optional positional / long-flag args
    r"\s+-c\s+['\"]"                  # -c '...' or -c "..."
    rf"(?:{DESTRUCTIVE_SQL_VERBS})\b" # destructive verb inside the quoted SQL
)

# Replaces all 7 broad SQL rules above:
(SQL_ANCHORED_PATTERN, "psql/sqlite3 destructive SQL via -c"),
```

Notes on the anchor:

- `^\s*` requires the verb context to be at the start of the Bash command
  string, not anywhere in a pipeline. A pipeline like
  `git log | grep "DELETE FROM"` does not start with `psql`/`sqlite3` and is
  allowed through.
- `(psql|sqlite3)\b` is restrictive on engine. Other clients (`mysql`,
  `mongo`, `cockroach`, `crdb`) are not currently in scope; if/when Bali Zero
  uses them in prod, extend `DESTRUCTIVE_SQL_VERBS` and the engine alternation.
- `-c\s+['\"]` requires the verb to be inside a quoted `-c` argument. Stdin
  (`psql < file.sql`) and `-f file.sql` are not matched by this rule — they
  are handled by `SQL_DESTRUCTIVE_IN_CONTENT` on the `.sql` file at Write/Edit
  time (existing flow, see Step 1 above; preserved unchanged).
- Alembic UP/DOWN migrations remain whitelisted because they go through
  `.sql` file Write/Edit (not through `psql -c`); the existing
  `SQL_FILE_PATTERN` + `SQL_DESTRUCTIVE_IN_CONTENT` checks still apply.
- The new rule is **case-insensitive** via the existing `re.search(pattern,
command, re.IGNORECASE)` call site, so `psql -c "drop table x"` also
  matches.

The 4 base rules (`DROP TABLE`, `TRUNCATE TABLE`, `DROP DATABASE` as the
plain anchored forms) are now redundant with `SQL_ANCHORED_PATTERN` and are
removed. The 3 GPT-5.5 B3 broadenings (`UPDATE … SET`, `DELETE FROM`,
`INSERT INTO`, bare `TRUNCATE`) are also subsumed by the anchored rule.

### Fix 2 — Daemonize the hook

Replace the per-call Python invocation with a long-lived daemon listening on a
UNIX domain socket. The PreToolUse hook becomes a thin Bash client that opens
the socket, writes the tool_use JSON line, reads `ALLOW` or `BLOCK <reason>`,
and exits with the appropriate code.

#### Architecture overview

```
                ┌──────────────────────────────────────────────┐
                │  Claude Code session                          │
                │                                                │
                │  tool_use → PreToolUse hook (shell)            │
                │              │                                  │
                │              ▼                                  │
                │  ~/.claude/hooks/guardrails-client.sh           │
                │  (thin Bash client, ~30 lines)                  │
                │              │                                  │
                │              │  UNIX domain socket roundtrip    │
                │              │  (~5 ms wallclock)                │
                │              ▼                                  │
                └──────────────┼──────────────────────────────────┘
                               │
                               ▼
        ┌───────────────────────────────────────────────┐
        │  ~/.claude/daemons/guardrails.py              │
        │  (long-lived Python daemon, single instance)  │
        │                                                │
        │  - listens on ~/.claude/daemons/guardrails.sock│
        │  - regex patterns compiled ONCE at startup     │
        │  - reads tool_use JSON line per request        │
        │  - writes "ALLOW\n" or "BLOCK <reason>\n"      │
        │  - never exits (LaunchAgent KeepAlive=true)    │
        └───────────────────────────────────────────────┘
```

#### Daemon — `~/.claude/daemons/guardrails.py`

```python
#!/usr/bin/env python3
"""Long-lived PreToolUse guardrails daemon.

Listens on UNIX domain socket ~/.claude/daemons/guardrails.sock.
Request: one JSON object per connection, newline-terminated.
Response: "ALLOW\n" or "BLOCK <reason>\n".

Latency: ~5 ms socket roundtrip vs ~100 ms Python cold start per call.
Reference: research/operations/specs/T1.2-guardrails-hook.md
"""
import json
import os
import re
import socket
import socketserver
import sys
from pathlib import Path

SOCKET_PATH = Path.home() / ".claude" / "daemons" / "guardrails.sock"

# Compile patterns ONCE at startup (was re-compiled per call in the per-process hook).
# Identical semantics to BLOCK_PATTERNS above, BUT with the anchored SQL rule
# from Fix 1 replacing the 7 broad SQL rules.
DESTRUCTIVE_SQL_VERBS = r"DROP|UPDATE|DELETE|INSERT|TRUNCATE"
SQL_ANCHORED = (
    r"^\s*(psql|sqlite3)\b"
    r"(?:\s+[^-][^\s]*|\s+--[^\s]+)*"
    r"\s+-c\s+['\"]"
    rf"(?:{DESTRUCTIVE_SQL_VERBS})\b"
)

def evaluate(payload):
    """Return ('ALLOW', None) or ('BLOCK', reason)."""
    tool_name = payload.get("tool_name", "")
    tool_input = payload.get("tool_input", {}) or {}

    if tool_name == "Bash":
        command = tool_input.get("command", "")
        if not command:
            return "ALLOW", None
        for pat, reason in BLOCK_PATTERNS:
            if pat.search(command):
                return "BLOCK", reason
        return "ALLOW", None

    if tool_name.startswith("mcp__"):
        if tool_name in MCP_DESTRUCTIVE_TOOLS:
            return "BLOCK", f"MCP destructive tool: {tool_name}"
        if MCP_DESTRUCTIVE_PATTERN.search(tool_name):
            return "BLOCK", f"MCP tool with destructive verb in name: {tool_name}"
        if isinstance(tool_input, dict):
            for k, v in tool_input.items():
                if isinstance(v, str) and SQL_DESTRUCTIVE_IN_CONTENT.search(v):
                    return "BLOCK", f"SQL destructive in MCP input field '{k}'"
        return "ALLOW", None

    if tool_name in ("Edit", "Write", "MultiEdit", "NotebookEdit"):
        file_path = tool_input.get("file_path", "")
        for pat in PROTECTED_PATH_PATTERNS:
            if pat.search(file_path):
                return "BLOCK", f"{tool_name} on protected path: {file_path}"
        if SQL_FILE_PATTERN.search(file_path):
            content = tool_input.get("content", "") or tool_input.get("new_string", "")
            if tool_name == "MultiEdit":

                    if isinstance(e, dict):
                        ns = e.get("new_string", "")
                        if SQL_DESTRUCTIVE_IN_CONTENT.search(ns):
                            return "BLOCK", f"SQL destructive in MultiEdit on {file_path}"
            if SQL_DESTRUCTIVE_IN_CONTENT.search(content):
                return "BLOCK", f"SQL destructive in {file_path}"
        return "ALLOW", None

    return "ALLOW", None


class Handler(socketserver.StreamRequestHandler):
    def handle(self):
        try:
            line = self.rfile.readline()
            if not line:
                self.wfile.write(b"ALLOW\n")
                return
            payload = json.loads(line.decode("utf-8"))
            verdict, reason = evaluate(payload)
            if verdict == "ALLOW":
                self.wfile.write(b"ALLOW\n")
            else:
                self.wfile.write(f"BLOCK {reason}\n".encode("utf-8"))
        except Exception as e:
            # Fail open on daemon-side parse errors (mirrors per-call hook policy).
            self.wfile.write(f"ALLOW (daemon-fail-open: {type(e).__name__})\n".encode("utf-8"))


class ThreadedUnixServer(socketserver.ThreadingMixIn, socketserver.UnixStreamServer):
    daemon_threads = True
    allow_reuse_address = True


def main():
    SOCKET_PATH.parent.mkdir(parents=True, exist_ok=True)

    except KeyboardInterrupt:

    finally:

            SOCKET_PATH.unlink()
```

#### Thin client — `~/.claude/hooks/guardrails-client.sh`

```bash
#!/usr/bin/env bash
# Thin PreToolUse client. Opens UNIX socket to daemon, sends tool_use JSON,
# reads ALLOW or BLOCK <reason>, exits 0 / 2.
#
# Fail-open policy: if the daemon is unreachable (socket missing, refused),
# exit 0 (allow). This matches the per-call hook policy (`sys.exit(0)` on
# malformed input) and avoids freezing every tool call when the daemon is
# being restarted.

# Reference: research/operations/specs/T1.2-guardrails-hook.md (Fix WAVE -1)

  exit 0  # daemon down → fail open
fi

# -N tells nc to close write-half after stdin EOF; -w bounds total time.

GUARDRAILS BLOCK: ${reason}
If this is intentional, ask Antonello to bypass guardrails.
See: research/operations/specs/T1.2-guardrails-hook.md
EOF

    ;;

    exit 0
    ;;
esac
```

### ITERATION 5 CORRECTION (Gemini Deep Think GDT-3, CRITICAL)

_Added 2026-05-22 by Worker A5 after Gemini Deep Think red-team pass on
Worker A2's iter-2 deliverable._

**The iter-2 "MCP regex repair" was itself a hallucination.** Worker A2
replaced the broken iter-1 regex
`mcp__.*?__.*?(create|update|...|alter)[_$]` with
`mcp__.*?__.*?(create|update|...|alter)\b`, claiming `\b` catches
camelCase boundaries like `createNewThing`. Worker A2 also wrote a test
case **I2-T2** asserting that `mcp__anything__createNewThing` BLOCKS
under the iter-2 regex. That assertion was never empirically executed —
or if it was, the result was never read back.

In Python's `re` module:

- `_` (underscore) is a word character (`\w`).
- Every ASCII letter A–Z and a–z is a word character.
- `\b` is a zero-width assertion that matches only at a `\w`-to-`\W`
  transition, a `\W`-to-`\w` transition, or a string edge.
- Between `e` (the last char of `create`) and `_` (underscore), both
  sides are `\w` — no boundary, `\b` does not fire.
- Between `e` (the last char of `create`) and `N` (uppercase letter,
  camelCase boundary), both sides are `\w` — no boundary, `\b` does not
  fire.

Empirical verification (run yourself):

```python
import re
p = re.compile(r"mcp__.*?__.*?(create|update|delete|merge|deploy)\b",
               re.IGNORECASE)
assert p.search("mcp__anything__createNewThing") is None  # iter-2 said MATCH — WRONG
assert p.search("mcp__anything__create_thing")    is None  # iter-2 said MATCH — ALSO WRONG
assert p.search("mcp__anything__create")        is not None  # only this one works
```

The iter-2 regex caught LESS than the iter-1 regex. Iter-1 `[_$]` at
least matched `create_thing` (literal `_` in the character class). Iter-2
`\b` rejected it. The regression went undetected because nobody ran the
seven-case verification.

**Iter-5 fix:** replace `\b` with an explicit lookahead that names the
boundary conditions we actually want:

```python
# Iter-5:
MCP_DESTRUCTIVE_PATTERN = re.compile(
    r"mcp__.*?__.*?(delete|drop|truncate|destroy|remove|wipe|purge|reset|"
    r"create|update|merge|deploy|promote|rollback|cancel|rerun|"
    r"insert|modify|patch|set|write|alter)(?=_|$|[A-Z])",
    re.IGNORECASE,
)
```

The lookahead `(?=_|$|[A-Z])` accepts the verb if followed by underscore,
end-of-string, or an uppercase letter (camelCase). Under `re.IGNORECASE`
the `[A-Z]` class also accepts lowercase letters — intentional, because
we want any letter following the verb to count as a token edge so
`createNewThing`, `createnewthing`, `createNEWthing` all match
identically. The seven empirical test cases at "Iteration 5 verification"
below assert the corrected behavior.

matches and non-matches. The iter-2 "test matrix" was a markdown table

### Fix 1 — Fail-to-static, NOT fail-open

The Iteration 1 client treats daemon-unreachable as ALLOW. This is wrong. The
correct fallback is to re-evaluate the same patterns inline via a separate
single-file Python evaluator, `~/.claude/hooks/guardrails-static.py`. Latency
during fallback is roughly the original 100 ms cold start — slow but secure.
Only if BOTH the daemon AND the static evaluator are unreachable (filesystem
broken, python3 missing, evaluator crashed at parse-time) do we log the
incident to `~/.claude/state/guardrails-fail.log` and exit 1 (fail-closed,
block). At no point does the client return ALLOW on its own.

The three failure tiers:

| Tier | Symptom                                       | Decision                            | Latency |
| ---- | --------------------------------------------- | ----------------------------------- | ------- |
| T1   | Daemon socket reachable, response parseable   | ALLOW or BLOCK per daemon verdict   | ~5 ms   |

### Fix 2 — `MCP_DESTRUCTIVE_PATTERN` regex repair

The Iteration 1 pattern:

```python

    r"mcp__.*?__(delete|drop|truncate|destroy|remove|wipe|purge|reset|"
    r"create|update|merge|deploy|promote|rollback|cancel|rerun|"
    r"insert|modify|patch|set|write|alter)[_$]",  # ← [_$] is the bug
    re.IGNORECASE,
```

`[_$]` is a character class containing literal `_` and literal `$`. It does
NOT match end-of-string (that would be `(?:_|$)` with `$` outside a class) and
it does NOT match a transition from a verb to a capital letter. Empirical
test:

| Tool name                                | Iteration 1 verdict                                                                                                                                                                                                                  | Should be                      |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------ |
| `mcp__nuzantara-mcp__create_client`      | MATCH (trailing `_`)                                                                                                                                                                                                                 | BLOCK ✓                        |
| `mcp__nuzantara-mcp__delete`             | MATCH (literal `$` in `[_$]` is treated as a literal `$`, not anchor — so this actually does NOT match in Python regex; depends on engine. | `mcp__anything__createNewThing`          | NO MATCH (next char is `N`)                                                                                                                                                                                                          | BLOCK ✗ ← false negative       |
| `mcp__nuzantara-mcp__creating_something` | NO MATCH                                                                                                                                                                                                                             | ALLOW ✓ (correct)              |
| `mcp__nuzantara-mcp__list_clients`       | NO MATCH                                                                                                                                                                                                                             | ALLOW ✓ (no destructive verb)  |

The Iteration 2 candidate repair was the regex word boundary `\b`.
**Iteration 5 (Gemini Deep Think GDT-3, CRITICAL) reverted this.** `\b`
matches a transition between word chars (`[A-Za-z0-9_]`) and non-word
chars — but underscore `_` AND every ASCII letter are all `\w`, so `\b`
after `create` placed before `_` (underscore) or `N` (capital letter,

intentional — we want any letter to count as a token boundary after the
verb so `createNewThing`, `createnewthing`, and `createNEWthing` all match

### Fix 3 — Whitelist `git reset --hard pre-orchestration-fix-*` rollback tag

T-1 (`research/operations/specs/T-1-pre-execution-global-backup.md`, Worker C
scope) creates a backup tag `pre-orchestration-fix-${BACKUP_ID}` where
`BACKUP_ID` is a `YYYYMMDD-HHMMSS` timestamp. G3
(`research/operations/specs/G3-global-rollback.md`, Worker D scope) rolls
back via `git reset --hard pre-orchestration-fix-${BACKUP_ID}`. The existing
`\bgit\s+reset\s+--hard\b` block rule would intercept these legitimate
rollback paths.

Adding the allowlist must satisfy three constraints:

1. **Must not loosen the general `git reset --hard` block.** A bare
   `git reset --hard origin/main` or `git reset --hard HEAD~3` must still
   BLOCK.
2. **Must be anchored to start-of-command.** A pipeline like
   `echo "git reset --hard pre-orchestration-fix-20260521-153012" | tee log.txt`
   must NOT be eligible for the allowlist — that is an arbitrary string
   passing through `echo`, not a real reset.
3. **Must require the timestamp format** so attackers cannot fabricate a tag
   like `pre-orchestration-fix-arbitrary` and bypass.

The pattern:

```python
ROLLBACK_TAG_ALLOWLIST = re.compile(
    r"^\s*git\s+reset\s+--hard\s+pre-orchestration-fix-\d{8}-\d{6}\s*$",
    re.IGNORECASE,
)
```

Notes on this pattern:

- `^\s*` anchors to start-of-command, with optional leading whitespace, so
  `   git reset --hard pre-orchestration-fix-20260521-153012` works for
  scripted invocations that may indent the command.
- `\d{8}-\d{6}` requires the canonical T-1 timestamp shape
  (`YYYYMMDD-HHMMSS`). T-1 generates this format deterministically in its
  `BACKUP_ID` script.
- `\s*$` anchors to end-of-command, so trailing arguments (e.g.
  `git reset --hard pre-orchestration-fix-... && rm -rf /`) do NOT match the
  allowlist — they fall through and the second clause hits `BLOCK_PATTERNS`
  via the original `rm -rf` rule. Compound commands cannot smuggle.
- The allowlist is checked BEFORE the BLOCK_PATTERNS loop. If matched, the
  evaluator returns ALLOW immediately. The same logic is mirrored in both
  the daemon and the static evaluator above.

   operator made a deliberate choice — that is on them.
2. **Presence signal** — `~/.claude/state/operator-presence.flag` exists and
   is owned by `$USER:staff` mode `0600`. The operator creates it manually
   via `touch ~/.claude/state/operator-presence.flag && chmod 0600
~/.claude/state/operator-presence.flag`. The flag must be re-created for
   each emergency window; the operator removes it after the window
   (`rm ~/.claude/state/operator-presence.flag`). Cron and Claude tool calls
   cannot create this file on the operator's behalf (the directory is in
   $HOME and writeable to the operator, but creation is an explicit
   operator-driven action distinct from env-var setting).

Both must be true. Either alone is insufficient. The client logs every
bypass-pass to `~/.claude/state/guardrails-fail.log` (audit trail).

> **Why this is safe.** A single-key bypass (env var alone, OR flag alone)
> would be trivially compromisable: an attacker who could write
> `~/.zshrc` could set the env var; an attacker who could write inside
> `$HOME/.claude/state/` could create the flag. Requiring BOTH means the
> attacker needs (a) shell rc modification AND (b) filesystem-write access
> AND (c) the human operator to subsequently start a new shell in which the
> rc is sourced — three independent compromises. In the genuine operator
> use-case, the operator does (a) once in `~/.zshrc`, (b) by hand when
> needed, and (c) by simply running new commands. Friction is asymmetric:
> low for the operator, high for an attacker.

The bypass is also visible in `~/.claude/state/guardrails-fail.log` as
"GUARDRAILS_BYPASS active (env+flag) — passing tool_use through" with
timestamp. Post-incident review can verify whether the operator was actually
present during the bypass window.

Operator workflow:

```bash
# Begin emergency window:
touch ~/.claude/state/operator-presence.flag
chmod 0600 ~/.claude/state/operator-presence.flag
export GUARDRAILS_BYPASS=1   # one-shot for this shell only

# Run the emergency command(s):
claude  # or whatever needs the escape hatch

# End emergency window:
unset GUARDRAILS_BYPASS
rm ~/.claude/state/operator-presence.flag
```

If the operator forgets step 2 (removing the flag), the env var alone still
will not bypass on a new Claude session because that new session will not
have `GUARDRAILS_BYPASS=1` in its env. Symmetric: if the operator forgets
step 1 (unsetting the env var), the flag alone will not bypass either.
