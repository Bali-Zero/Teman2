# L5.2 — Server-Side Enforcement (post-Panel)

## TL;DR

L5.1 chiude la disciplina worktree client-side. **L5.2 chiude il gap server-side**:

1. **Bot privilege downgrade** — Claude bot non deve avere merge rights su main.
2. **Required hot-zone GitHub Action** — replica lease-check + lint-launchagents server-side al merge.
3. **CODEOWNERS scope-ristretto** — review obbligatoria SOLO su file hot-zone, SOLO per PR bot.
4. **Audit append-only** — bypass events (HUSKY=0, --no-verify, direct push) loggati su GitHub issue + Telegram per soli hot-zone events.

**Filosofia**: client hooks = ergonomia + early warning. CI server-side = enforcement non-bypassable.

**Kill switch globale**: `L5_2_SERVER_ENFORCEMENT_ENABLED=false` (env workflow).

### Componenti

#### Componente 1 — Bot privilege downgrade (P0.1)

**Stato attuale**: ipotetico Claude bot ha admin → può `merge_pull_request` + bypass branch protection.

**Action**:

- Audit `gh api orgs/Balizero1987/teams` + `gh api repos/Balizero1987/Teman2/collaborators` per identificare tutti gli admin.
- Se Claude bot esiste come account separato → downgrade da `admin` a `write` o `triage`.
- Se Claude opera con token di Antonello → creare account bot dedicato `nuzantara-bot[bot]` con permessi minimi (read + write su PR, NO merge, NO admin).
- Documentare in `~/.nuzantara-secrets.env` quale token usare per quale ruolo.

**Failure mode evitato**: bot+admin merge same actor (Codex Q1).

#### Componente 2 — Required hot-zone GitHub Action (P0.2)

**File**: `.github/workflows/hot-zone-enforcement.yml`

**Trigger**: `pull_request` events + `merge_group` events (per merge queue).

**Logica**:

1. Checkout diff base SHA (NON branch HEAD — anti `pull_request_target` trap).
2. Per ogni file in diff, classifica: `hot-zone` (migrations / sentinel / dlq / LaunchAgent wrappers / .github/workflows / auth / billing / pricing) vs `cold`.
3. Se `hot-zone` files presenti:
   - Connect Redis lease registry (production credentials da `secrets.REDIS_URL_RO`).
   - Verifica nessun lease attivo su file da altro agent task-id.
   - Re-esegue `scripts/lint_launchagents.sh` se LaunchAgent files toccati.
   - Re-esegue `scripts/lint_migration_numbers.py` (W41 lint) se migrations toccate.
   - Verifica `required_approving_review_count >= 1` su PR.
4. **Fail-closed** se Redis non raggiungibile (hot-zone files presenti). **Graceful warn** se Redis non raggiungibile (solo cold files).
5. Output: required check status `hot-zone-enforcement` con `conclusion: success | failure | neutral`. Mai `skipped`.

**Critical contracts**:

- **C1**: workflow DEVE girare anche su PR che modificano `.github/workflows/` stessi (anti workflow-self-modification trap, Codex Q6 missing failure mode).
- **C2**: required check `expected source app: github-actions` (anti CI spoofing, Codex Q4 missing failure mode).
- **C3**: NO `paths:` filter — workflow gira SEMPRE, decide internamente cosa controllare (anti skip-success trap, Codex Q5 missing failure mode).
- **C4**: `dismiss-stale-reviews` + `require-latest-push-approval` configurati su branch protection (anti approval stale race, Codex Q3 missing failure mode).
- **C5**: per merge queue, check ricalcola su latest base SHA (anti lease stale race, Codex Q8 missing failure mode).

**Empirical motivation**: cicatrix W34 documenta bypass HUSKY=0 in produzione. Senza C1-C5, ogni patch a workflow stesso o ogni PR con stale approval può bypassare.

**Branch protection update**:

- `required_approving_review_count: 1`
- `require_code_owner_reviews: true`
- `dismiss_stale_reviews: true`
- `require_last_push_approval: true`
- **Bypass actors**: solo Antonello (human) per break-glass + per scope NON-hot-zone (path filtering via CODEOWNERS).

**Effetto**: PR umane su file cold = no review needed (single-dev throughput intatto). PR bot su hot-zone = review obbligatoria. PR umane su hot-zone = review obbligatoria solo se CODEOWNERS match (Antonello rivede se stesso = no-op, ma forza una pausa cognitiva).

#### Componente 4 — Audit append-only + Telegram (P1.2)

**Mechanism A — Server-side audit GitHub issues**:

- GitHub Action `on: push` su main rileva commit signature anomala (no `Hook-Verified` trailer OR trailer forgeable → re-run server-side per validare).
- Append issue body con event log structured: `{timestamp, actor, sha, files_changed, bypass_signal, source}`.
- Issue dedicata `[AUDIT] Workflow discipline bypass log` evergreen, write-only.

**Mechanism B — Telegram real-time SOLO hot-zone**:

- Trigger: hot-zone files modified + bypass signal detected (server-side replay fail) + direct push main + workflow self-modification.
- Payload: 1-line alert via `sentinel_lib/alerter.py` retry pattern (W55 cicatrix).
- **NO Telegram per**: HUSKY=0/--no-verify su feature branch (alert fatigue, Gemini Q4).

**Mechanism C — Digest settimanale (P2.2)**:

- Cron lunedì 08:00 WITA: summary 7-day bypass events.
- Format: bypass count by file zone + actor + intent (commit msg analysis).
- Pipe via Telegram digest channel.

**Canary obbligatorio (Codex missing failure mode #14 — alert blind spot)**:

- Daily canary: Telegram bot health-check + GitHub issue write permission verify.
- Se fail 2 ticks consecutivi → fallback alert via email Antonello.

## Rollout plan

1. **Phase 0** (pre-rollout): empirical audit `gh api` per stato attuale admin/permissions/protection + Redis credentials in GitHub secrets.
2. **Phase 1** (week 1): ship Componente 1 (bot downgrade). Verify zero merge da bot via `gh api` audit periodico.
3. **Phase 2** (week 2-3): ship Componente 2 (required hot-zone Action) in `monitor-mode` (workflow gira ma `continue-on-error: true`, output solo logs). Raccogliere 1 settimana di empirical data su false positive / true positive.
4. **Phase 3** (week 4): flip Componente 2 a `enforce-mode`. Ship Componente 3 (CODEOWNERS ristretto) + branch protection update.
5. **Phase 4** (week 5-6): ship Componente 4 (audit + Telegram). Canary live + digest cron.
6. **Phase 5** (week 7+): osservazione 30 giorni. Rollback automatico se >5% PR umane bloccate per false positive.

**Kill switch globale**: `L5_2_SERVER_ENFORCEMENT_ENABLED=false` env nel workflow → workflow ritorna `neutral` invece di failure. Permette emergency disarm senza modificare branch protection.

## Backward compat
