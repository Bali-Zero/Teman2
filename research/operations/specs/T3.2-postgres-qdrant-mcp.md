### Step 1.5 — Create READ-ONLY role (DS panel blocker fix, GPT-5.5 B4 fix for password leak)

```bash
# Create dedicated read-only role for MCP connections
# Defense in depth — even if MCP server has no read-only mode, role permissions enforce.
# GPT-5.5 panel B4 fix: NEVER echo generated password to terminal/transcript

# Generate password into Keychain DIRECTLY without echoing to stdout
# ITER-5 (Gemini Deep Think GDT-5, HIGH): use hex generation — deterministic 32 chars
# Iter-2 used `openssl rand -base64 24 | tr -d '/+=' | head -c 32` which failed
# ~50% randomly: base64 alphabet includes /+=, after stripping those the result
# was SHORTER than 32 chars. Hex output has alphabet [0-9a-f] only → no filter
# needed → always exactly 32 chars (16 bytes × 2 hex chars/byte).
PG_PASSWORD_RO=$(openssl rand -hex 16)
[ ${#PG_PASSWORD_RO} -eq 32 ] || { echo "FATAL: password gen failed" >&2; exit 1; }

# Store immediately in Keychain (silent, no -w echoback)
security delete-generic-password -a "$USER" -s "PG_PASSWORD_RO" 2>/dev/null || true
echo -n "$PG_PASSWORD_RO" | security add-generic-password -a "$USER" -s "PG_PASSWORD_RO" -w -
# -w - reads password from stdin (echo -n into pipe, never on commandline ps)
# NB: if security CLI doesn't support stdin, fall back to: security add-generic-password -a "$USER" -s "PG_PASSWORD_RO" -w "$PG_PASSWORD_RO"
# (still safer than echoing because Keychain stores, then we can clear PG_PASSWORD_RO env immediately)

echo "✅ PG_PASSWORD_RO created and stored in Keychain (value never echoed)"

# Apply DDL using the password via Keychain retrieval (NOT exposing in echo)
psql "postgres://backend_rag_v2:$PG_PASSWORD@localhost:15432/postgres" << SQL

DROP ROLE IF EXISTS nuzantara_readonly;

    LOGIN

REVOKE CREATE ON SCHEMA public FROM nuzantara_readonly;
```

### Step 2 — Install Postgres MCP via scoped wrapper (GPT-5.5 B4 fix)

```bash

mkdir -p ~/scripts
cat > ~/scripts/postgres-mcp-wrapper.sh << 'EOF'

# Postgres MCP scoped wrapper — retrieves Keychain password and execs MCP
# GPT-5.5 panel B4 fix: scoped env, never global zshenv export

set -euo pipefail

# Retrieve password ONLY when needed, scoped to this process
PGPASSWORD_RO=$(security find-generic-password -s "PG_PASSWORD_RO" -w 2>/dev/null)
```

## Fix WAVE -1 (2026-05-21): Keychain CLI `-w -` is broken on macOS — use interactive prompt

### Problem (GPT-5.5 second-pass BLOCKER, empirically validated 2026-05-21)

Step 1.5 currently stores the read-only Postgres password via:

```bash
echo -n "$PG_PASSWORD_RO" | security add-generic-password \
    -s "PG_PASSWORD_RO" -a "$USER" -w - -T ""
```

The intent: read the password from stdin (`-w -`) so it never appears in `ps aux` or shell history. **The intent is wrong.** GPT-5.5 second-pass verified empirically on macOS Sequoia (Pro machine 2026-05-21):

- `security add-generic-password -w -` does NOT read stdin.
- The dash (`-`) is treated as the literal password string OR triggers an interactive prompt (depending on tty availability).
- When invoked from a non-tty pipe (the heredoc context above), the dash IS the literal password stored in Keychain.

Consequence: the Keychain item gets the wrong value (literally `-` or empty). The MCP wrapper later retrieves the wrong password → MCP connection fails → cascade of 14:25-UTC-style debug session, after Wave 0 is already in flight, harder to roll back than a pre-Wave-0 abort.

### Empirical verification (2026-05-21)

```bash
# BEFORE (broken pattern from Step 1.5 as written)
echo -n "actual-password-here" | security add-generic-password \
    -s "TEST_BROKEN" -a "$USER" -w - -T ""

# What got stored:
security find-generic-password -s "TEST_BROKEN" -w
# Output: -        ← literal dash, NOT "actual-password-here"
```

This breaks the entire downstream verification chain:

- Step 2 `~/scripts/postgres-mcp-wrapper.sh` retrieves `-` instead of password → psql connection fails.
- Step 4.5 8-test enforcement battery never runs (all 8 fail on connection, not on permission).
- T3.2 falsely appears to fail "role misconfigured" when actually the password is wrong.

### Fix — three accepted patterns (in order of preference)

#### Pattern A (primary, Antonello-grade): interactive prompt

The cleanest, ps-leak-free, broken-stdin-free path for a one-time install with operator present:

```bash
# Generate password (caller already has it in $PG_PASSWORD_RO env)
# DO NOT pass -w on commandline.
# When -w is OMITTED, `security` prompts on the controlling tty.
security delete-generic-password -a "$USER" -s "PG_PASSWORD_RO" 2>/dev/null || true
security add-generic-password -s "PG_PASSWORD_RO" -a "$USER" -T ""
# `security` opens a tty prompt: "password data for new item:"
# Operator pastes/types $PG_PASSWORD_RO once. No -w flag means no commandline exposure.
```

Trade-off: requires operator presence at install time. ACCEPTED — T3.2 is one-time install per machine, operator IS present at WAVE -1 plan execution.

#### Pattern B (automated fallback): Python helper via PyObjC Security.framework

For re-install scenarios (operator absent, automated re-provisioning):

```bash
# Write helper script that reads password from stdin and calls Security.framework
cat > ~/scripts/keychain-store-stdin.py << 'EOF'
#!/usr/bin/env python3
"""Store a Keychain generic password by reading the secret from stdin.
Avoids ps-leak (no -w "$password" on commandline) AND avoids the broken
`security -w -` stdin behavior on macOS. Uses Security.framework directly.

Usage:
    echo -n "secret" | keychain-store-stdin.py <service-name> <account>
"""
import sys
import subprocess

def main():
    if len(sys.argv) != 3:
        print("Usage: keychain-store-stdin.py <service> <account>", file=sys.stderr)
        sys.exit(2)
    service, account = sys.argv[1], sys.argv[2]
    password = sys.stdin.read()
    if not password:
        print("ERROR: empty stdin", file=sys.stderr)
        sys.exit(2)
    # Delete existing (idempotent)
    subprocess.run(
        ["security", "delete-generic-password", "-s", service, "-a", account],
        check=False, capture_output=True,
    )
    # Use `security add-generic-password -w <pw>` via subprocess with the
    # password as the LAST arg. ps-leak window is one process invocation
    # (the python subprocess), NOT the parent shell — operator can validate
    # by `ps -ef | grep security` showing the python helper, not the secret
    # in the calling shell history. Calling shell never had the password
    # in argv.
    result = subprocess.run(
        ["security", "add-generic-password",
         "-s", service, "-a", account,
         "-w", password,
         "-T", ""],
        check=False, capture_output=True, text=True,
    )
    if result.returncode != 0:
        print(f"ERROR: security exited {result.returncode}: {result.stderr}", file=sys.stderr)
        sys.exit(1)
    print(f"✅ Stored {service} in Keychain (no commandline leak in parent shell)")

if __name__ == "__main__":
    main()
EOF
chmod 0700 ~/scripts/keychain-store-stdin.py

# Usage in Step 1.5:
echo -n "$PG_PASSWORD_RO" | ~/scripts/keychain-store-stdin.py PG_PASSWORD_RO "$USER"
unset PG_PASSWORD_RO   # clear from parent shell env
```

Trade-off: brief ps-leak window in the python subprocess (`security ... -w <password> -T ""` argv visible for ~50ms). The PARENT shell never has the password in argv, so shell history is clean. For full immunity, swap subprocess `security` call with PyObjC `SecKeychainAddGenericPassword` (Security.framework binding). PyObjC is shipped with macOS system Python (`/usr/bin/python3`), no extra install needed — left as future hardening.


## Fix WAVE -1 Iteration 2 (2026-05-21)

### FIX 2 — SHA-256 hash verification, no env-var dependency (HIGH)

#### Problem (iteration-2 devils-advocate, severity HIGH)

The iteration-1 "Verification step" (after the Pattern A/B Keychain store) ends with this comparison:

```bash
STORED=$(security find-generic-password -s "PG_PASSWORD_RO" -w 2>/dev/null)
if [ "$STORED" = "$PG_PASSWORD_RO" ]; then
    echo "✅ Keychain stored value matches generated password — proceed"
else
    echo "❌ MISMATCH"
    exit 1
fi
```

This comparison ONLY works in the SAME shell session as the Step 1.5 generation, because `$PG_PASSWORD_RO` must still be in env. Multiple failure modes:

1. **Re-install scenario** — operator re-runs verification later (in a new shell, after `unset PG_PASSWORD_RO`, or after machine reboot). `$PG_PASSWORD_RO` is unset → `[ "$STORED" = "" ]` → comparison silently fails. With `set -u`, the script would error on unset-var; without it (the more permissive case), the comparison yields `[ "actual-password" = "" ]` → false → exit 1 with a misleading "MISMATCH" message that suggests Keychain corruption rather than env absence.
2. **Empty-vs-empty silent pass** — if BOTH `$STORED` and `$PG_PASSWORD_RO` are unset (e.g., Keychain entry missing AND env never set), the comparison is `[ "" = "" ]` → TRUE → "✅ proceed" is printed → operator proceeds with a NON-EXISTENT Keychain entry → MCP wrapper later fails with the confusing role-auth error described in iteration-1.
3. **Operator-induced env pollution** — if a sibling script (or `~/.zshrc` fragment) sets `PG_PASSWORD_RO=<old-value>` from a prior install, the comparison validates against the WRONG value and silently approves an outdated Keychain entry.

The root cause: the verification couples STORE-TIME state (`$PG_PASSWORD_RO` env) with VERIFY-TIME logic. They need to be decoupled.

#### Fix — SHA-256 hash file, computed at store-time, verified anywhere

Compute the SHA-256 of the generated password at STORE-TIME, persist the hash to a non-sensitive on-disk file (`~/.config/nuzantara/.pg-password-ro.sha256`, mode `0644` because hashes are non-reversible), and at VERIFY-TIME retrieve the Keychain value, compute its SHA-256, and compare against the file. No env-var dependency.

##### At STORE-TIME (during Step 1.5, after Pattern A or B succeeds)

```bash
# FIX 2 — store-time hash persistence
# Compute SHA-256 of the generated password while it is still in $PG_PASSWORD_RO env.
mkdir -p ~/.config/nuzantara
HASH_FILE=~/.config/nuzantara/.pg-password-ro.sha256

PG_PW_HASH=$(printf %s "$PG_PASSWORD_RO" | shasum -a 256 | awk '{print $1}')
# Sanity: SHA-256 hex digest is always exactly 64 chars
if [ "${#PG_PW_HASH}" -ne 64 ]; then
    echo "❌ SHA-256 computation returned ${#PG_PW_HASH} chars, expected 64" >&2
    exit 1
fi

echo "$PG_PW_HASH" > "$HASH_FILE"
chmod 0644 "$HASH_FILE"
# 0644 is safe: SHA-256 of a 32-char openssl-random base64 password is non-reversible
# (preimage attack on SHA-256 is computationally infeasible; brute-force the 32-char
# base64 search space is ~10^57 operations — outside any threat model). The hash is
# stored at 0644 to allow operator-readable verification from any subsequent shell
# session without sudo or Keychain-prompt friction.

echo "✅ Password SHA-256 written to $HASH_FILE (length=$(wc -c < "$HASH_FILE") chars)"
```

##### At VERIFY-TIME (anywhere — any shell, any session, no env dependency)

```bash
# FIX 2 — verify-time hash comparison
# No $PG_PASSWORD_RO env var needed. Works in any shell, any time.
HASH_FILE=~/.config/nuzantara/.pg-password-ro.sha256

# Retrieve Keychain value (this will tty-prompt for Keychain unlock if locked)
STORED=$(security find-generic-password -s "PG_PASSWORD_RO" -w 2>/dev/null) || {
    echo "❌ Keychain entry 'PG_PASSWORD_RO' not found — FIX 2 cannot verify" >&2
    echo "   Re-run Step 1.5 (Pattern A or B) to (re-)store the password" >&2
    exit 1
}

# Guard against empty-vs-empty silent pass (iteration-2 failure mode #2)
if [ -z "$STORED" ]; then
    echo "❌ Keychain returned empty string — Pattern C bug or unlock failure" >&2
    exit 1
fi

# Compute SHA-256 of the retrieved value
STORED_HASH=$(printf %s "$STORED" | shasum -a 256 | awk '{print $1}')

# Read the expected hash from the on-disk file
if [ ! -f "$HASH_FILE" ]; then
    echo "❌ Hash file $HASH_FILE missing — was Step 1.5 STORE-TIME hash write executed?" >&2
    exit 1
fi
EXPECTED_HASH=$(cat "$HASH_FILE")

# Guard against empty hash file (corruption / zero-byte truncation)
if [ "${#EXPECTED_HASH}" -ne 64 ]; then
    echo "❌ Hash file $HASH_FILE has ${#EXPECTED_HASH} chars, expected 64 (SHA-256 hex)" >&2
    exit 1
fi

# Constant-time comparison via shasum collision space (no timing-side-channel
# concern at this length — both strings are fixed 64-char hex digests).
if [ "$STORED_HASH" = "$EXPECTED_HASH" ]; then
    echo "✅ PASS: Keychain integrity verified — SHA-256 matches stored hash"
    # Clear retrieved value from shell env
    unset STORED STORED_HASH EXPECTED_HASH
else
    echo "❌ FAIL: Keychain hash mismatch" >&2
    echo "   Stored hash:   $EXPECTED_HASH" >&2
    echo "   Computed hash: $STORED_HASH" >&2
    echo "   The Keychain value does NOT match what was stored at install time." >&2
    echo "   Possible causes: Keychain corruption, sibling-script rewrite, manual edit." >&2
    unset STORED STORED_HASH EXPECTED_HASH
    exit 1
fi
```

#### Wire FIX 2 into Step 1.5

Append the STORE-TIME hash block immediately after the Pattern A/B `security add-generic-password` call succeeds, BEFORE `unset PG_PASSWORD_RO`:

```bash
# (Pattern A or B store succeeds — $PG_PASSWORD_RO is still in env)

# FIX 2 — write SHA-256 hash to ~/.config/nuzantara/.pg-password-ro.sha256
mkdir -p ~/.config/nuzantara
HASH_FILE=~/.config/nuzantara/.pg-password-ro.sha256
PG_PW_HASH=$(printf %s "$PG_PASSWORD_RO" | shasum -a 256 | awk '{print $1}')
[ "${#PG_PW_HASH}" -eq 64 ] || { echo "SHA-256 fail" >&2; exit 1; }
echo "$PG_PW_HASH" > "$HASH_FILE"
chmod 0644 "$HASH_FILE"

# NOW the iteration-1 verification block runs (it has $PG_PASSWORD_RO).
# After it passes, unset PG_PASSWORD_RO. Subsequent verifies use the HASH file.
unset PG_PASSWORD_RO STORED PG_PW_HASH
```

#### Replace iteration-1 verification block with FIX 2 verify-time logic

Step 4.5 enforcement tests (the 8-test battery) currently call `security find-generic-password ... -w` per test to retrieve the password. Insert the FIX 2 verify-time block ONCE before the 8-test loop. If FIX 2 verification PASSES, the 8-test battery runs; if FIX 2 FAILS, the battery is aborted with a clear "Keychain integrity failure" message rather than the misleading "permission denied for table clients" cascade.

```bash
# Before Step 4.5 8-test enforcement battery, run FIX 2 verify
bash <<'VERIFY'
HASH_FILE=~/.config/nuzantara/.pg-password-ro.sha256
STORED=$(security find-generic-password -s "PG_PASSWORD_RO" -w 2>/dev/null) || exit 1
[ -n "$STORED" ] || exit 1
STORED_HASH=$(printf %s "$STORED" | shasum -a 256 | awk '{print $1}')
EXPECTED_HASH=$(cat "$HASH_FILE")
[ "${#EXPECTED_HASH}" -eq 64 ] || exit 1
[ "$STORED_HASH" = "$EXPECTED_HASH" ] || exit 1
echo "✅ FIX 2: Keychain integrity OK — proceeding to 8-test enforcement"
VERIFY
if [ $? -ne 0 ]; then
    echo "❌ FIX 2 verification failed — ABORT before 8-test battery" >&2
    exit 1
fi

# (Iteration-1 8-test enforcement battery runs here, unchanged.)
```

#### Why hash-on-disk is safe

The hash file (`~/.config/nuzantara/.pg-password-ro.sha256`) contains exactly 64 hex chars of SHA-256 output, e.g.:

```
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
```

This is the SHA-256 of an empty string (shown for illustration; the real file contains the hash of the actual 32-char random password). Properties:

1. **Preimage resistance**: SHA-256 has no known preimage attack. Recovering the input from the hash requires ~2^256 hash operations, far beyond any feasible compute budget.
2. **Search-space size for the input**: ITER-5 the input is `openssl rand -hex 16`. That is 32 chars from a hex alphabet (16 chars: `[0-9a-f]`), giving 16^32 = 2^128 possible inputs. Brute-forcing this search space against the hash requires ~2^128 hash operations — far beyond any feasible compute budget (>10^20 years even at 10^15 hashes/second). 128-bit entropy is the same level NIST recommends for symmetric keys. The previous iter-2 base64 pattern theoretically gave more entropy (~10^57) but in practice was broken (variable-length, failed ~50% of installs).
3. **No information leakage from file metadata**: the file is just 65 bytes (64 hex + newline), `chmod 0644`. Its existence and content reveal that a password exists in the Keychain (already public via `security dump-keychain`), but reveal nothing about the value.

Compared to the iteration-1 env-var comparison: the FIX 2 approach EXPANDS the verifiable window from "same shell session" to "any time, any session, even after machine reboot" while STRICTLY REDUCING the on-disk attack surface (no plaintext, only hash).

#### Acceptance criteria update for FIX 2

- [ ] `~/.config/nuzantara/.pg-password-ro.sha256` exists, mode `0644`, content is exactly 64 hex chars + 1 trailing newline (65 bytes total: `wc -c` returns 65).
- [ ] `grep -E '^[a-f0-9]{64}$' ~/.config/nuzantara/.pg-password-ro.sha256` matches (well-formed hash).
- [ ] FIX 2 verify-time block succeeds from a freshly-spawned shell (`env -i bash -c '<verify-block>'`) with NO `$PG_PASSWORD_RO` in env.
- [ ] FIX 2 verify-time block FAILS (exit 1) with a clear "Keychain entry missing" message if the Keychain entry is manually deleted.
- [ ] FIX 2 verify-time block FAILS (exit 1) with a clear "hash mismatch" message if the hash file is corrupted (e.g., `echo "wrong" > $HASH_FILE`).
- [ ] FIX 2 verify-time block does NOT silently pass on the empty-vs-empty failure mode (`STORED=""` or hash file empty).

#### Why this matters (iteration-2 evidence)

Iteration-1 verification works ONLY in the same shell as Step 1.5 generation. The expected real-world failure timeline:

1. Operator runs Step 1.5 successfully, `$PG_PASSWORD_RO` validates, MCP installs, all 8 enforcement tests pass.
2. Operator closes the terminal. `$PG_PASSWORD_RO` is unset.
3. Days/weeks later, operator wants to RE-VERIFY (e.g., suspects sibling script corruption, post-machine-reboot integrity check, post-Keychain-restore from Time Machine).
4. Operator copy-pastes the iteration-1 verification block. `$PG_PASSWORD_RO` is unset. Comparison `[ "$STORED" = "" ]` → false → "❌ MISMATCH" → operator panics, thinks Keychain corrupted, may re-run Step 1.5 with NEW password → MCP wrapper breaks (psql still uses old role-password mapping) → cascade of debug.

OR (worse, depending on set -u state):

4'. Operator runs verification, both `$STORED` and `$PG_PASSWORD_RO` are unset → `[ "" = "" ]` → TRUE → "✅ proceed" → operator thinks Keychain is fine, but it might actually be empty/missing → MCP wrapper later fails with "FATAL: password authentication failed" → confusing debug.

FIX 2 eliminates both modes by decoupling verify-time from store-time env state.

### Failure modes mitigated by FIX 2

| Failure                                              | Iteration-1 behavior                                    | FIX 2 behavior                                                                    |
| ---------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `$PG_PASSWORD_RO` unset at verify time               | Silent mismatch OR silent empty=empty pass              | Hash file readable, compares retrieved value's hash to file → clear PASS / FAIL   |
| Sibling shell sets stale `$PG_PASSWORD_RO`           | Validates against stale env, silently approves wrong    | Verify uses hash file (unaffected by env), catches mismatch                       |
| Hash file corrupted (e.g., zero-byte truncation)     | N/A                                                     | Explicit `${#EXPECTED_HASH} -ne 64` guard → exit 1 with clear "corrupted" message |
| Keychain entry deleted between install and re-verify | iter-1 retrieves `""`, compares to `""` env → silent ✅ | FIX 2 catches via `[ -z "$STORED" ]` guard → clear "missing" error                |
| Operator re-runs verify weeks later in fresh shell   | Always fails (no env)                                   | Works identically to install-time verify                                          |

## Fix Iteration 5 (Gemini Deep Think GDT-5, HIGH): hex-only password generation

> ⚠️ ITER-2 password gen failed ~50% randomly due to base64 special chars. Iter-5 uses hex (no filter needed)

### Problem (Gemini Deep Think panel finding GDT-5, severity HIGH)

Iter-2 generated the read-only password with:

```bash
PG_PASSWORD_RO=$(openssl rand -base64 24 | tr -d '/+=' | head -c 32)
```

This produces exactly 32 characters of base64 output from 24 random bytes. The base64 alphabet is `[A-Za-z0-9+/=]` — 65 characters total. The `tr -d '/+='` step strips three of those characters (`/`, `+`, `=`). For any random base64 sample, each of those 3 characters has roughly a `3/65 ≈ 4.6%` per-position probability of appearing. Across 32 positions, the probability that **at least one** position is stripped is `1 - (62/65)^32 ≈ 78%`.

When any character is stripped, the post-filter length is `< 32`. The downstream assertion (iter-2 verification step + iter-3 FIX 2 store-time guard):

```bash
if [ ${#STORED} -ne 32 ]; then echo "FAIL"; exit 1; fi
```

→ Installation fails. Empirically: ~50-78% of installs would hit this depending on the exact 24-byte sample. Even when 32 chars survive the filter, the password generated is biased away from the full base64 alphabet (no `/+=`), reducing entropy slightly.

### Why iter-2 wasn't caught earlier

- The pattern looks correct on paper: `-base64 24` is 32 chars before any filter, and `head -c 32` enforces the cap.
- The bug manifests only when `tr -d '/+='` strips characters — which it does ~78% of the time but is invisible unless you log the post-filter length.
- Iter-2 acceptance test was `[ ${#PG_PASSWORD_RO} -eq 32 ]` — would have caught the failure if run, but the test was buried inside FIX 2 store-time hash, not before the Keychain insert.
- Random installation failure (sometimes works, sometimes fails) was attributed by iter-3/4 reviews to "Keychain CLI quirks" — not to upstream password generation.

### Fix — hex output (no filter, deterministic length)

```bash
# ITER-5 (Gemini Deep Think GDT-5): hex generation, no alphabet filtering
PG_PASSWORD_RO=$(openssl rand -hex 16)  # 32 hex chars guaranteed, alphabet [0-9a-f]
[ ${#PG_PASSWORD_RO} -eq 32 ] || { echo "FATAL: password gen failed" >&2; exit 1; }
```

Properties:

- `openssl rand -hex 16` requests 16 random bytes and emits them as 32 hex chars (each byte = 2 hex chars). Always exactly 32 chars.
- Hex alphabet `[0-9a-f]` is 16 characters. No special characters → no filter step needed.
- 16 random bytes = 128 bits of entropy. NIST-recommended symmetric key strength (sufficient for password use).
- Deterministic length: no probabilistic failure mode. Sanity check `[ ${#...} -eq 32 ]` always passes (kept as defense-in-depth).
- Postgres role password accepts hex chars without escaping. No special-char SQL-injection concern.

### Alternative rejected (documented for future audits)

A loop pattern was considered:

```bash
# Loop-and-filter approach — REJECTED in favor of hex
PG_PASSWORD_RO=""
while [ ${#PG_PASSWORD_RO} -lt 32 ]; do
    PG_PASSWORD_RO="$(openssl rand -base64 48 | tr -d '/+=' | tr -d '\n' | head -c 32)"
done
```

Why rejected: introduces nondeterministic loop, retains the iter-2 alphabet bias (still no `/+=`), and is harder to audit. The hex approach is strictly simpler.

### SHA-256 hash verification is unaffected

FIX 2 (iter-2) computes `shasum -a 256` of the password to persist a verifiable hash on disk. Hex characters `[0-9a-f]` are valid SHA-256 input bytes (each char is 1 byte in UTF-8). The hash output is still 64 hex chars regardless of input alphabet. **No change to FIX 2 verification logic is required** — the same store-time hash write and verify-time hash compare work identically:

- Store-time: `printf %s "$PG_PASSWORD_RO" | shasum -a 256 | awk '{print $1}'` → 64-char hex digest written to `~/.config/nuzantara/.pg-password-ro.sha256`.
- Verify-time: `printf %s "$STORED" | shasum -a 256 | awk '{print $1}'` → compare against the file. PASS if equal.
- The 64-char SHA-256 hex assertion (`${#EXPECTED_HASH} -ne 64`) is independent of input alphabet — still works.

The only documentation update inside FIX 2 is the search-space comment (input is now 16^32 ≈ 10^38 ≈ 2^128 instead of the iter-2 ~10^57 figure). Both are far beyond brute-force feasibility.

### Acceptance criteria update for iter-5

- [ ] Step 1.5 password generation uses `openssl rand -hex 16` (NOT `openssl rand -base64 24 | tr -d '/+='`).
- [ ] Sanity guard `[ ${#PG_PASSWORD_RO} -eq 32 ]` runs immediately after generation (catches future regressions where someone swaps the openssl call).
- [ ] FIX 2 store-time hash + verify-time hash blocks UNCHANGED (already alphabet-agnostic).
- [ ] No `tr -d`, no `head -c`, no filtering anywhere on the password generation path.

### Failure modes mitigated by iter-5

| Failure                                          | Iter-2 behavior                                                | Iter-5 behavior                                                 |
| ------------------------------------------------ | -------------------------------------------------------------- | --------------------------------------------------------------- |
| `tr -d '/+='` strips chars → length < 32         | ~78% of installs fail at length assertion                      | Hex has no chars to strip → length always 32                    |
| Alphabet bias (post-filter base64 missing `/+=`) | Slight entropy reduction (~62 chars instead of 65)             | Full 16-char hex alphabet used                                  |
| Random install failure looks like Keychain bug   | Operator wastes ~30min debugging Keychain CLI / Pattern A vs B | Length assertion either passes deterministically or never fires |
| Loop-around in CI / install scripts              | Nondeterministic test failures                                 | Deterministic — same length every run                           |
| SHA-256 verification on hex input                | N/A (worked already)                                           | Works identically (hex is valid UTF-8 input)                    |

### Why this matters (iter-5 evidence)

Iter-2 → iter-4 added defense-in-depth for Keychain CLI quirks, env-var lifetime, and re-install scenarios. None of those iterations checked the **upstream** password generator. The base64+filter pattern is a textbook foot-gun: it looks like it produces 32 chars (because `-base64 24` does), but the filter step silently shortens it. Random ~50-78% installation failure is the worst-possible failure mode for an operator: hard to reproduce, easy to attribute to wrong root cause (Keychain, role permissions, MCP wrapper, proxy), and consumes hours of debug time before someone thinks to log the post-filter length.

Iter-5 collapses the entire iter-2/3/4 generation-side complexity to a single `openssl rand -hex 16` call. Future audits should treat any "generate password" call that uses character filtering (`tr -d`, `head -c` after stripping) as a code smell — prefer hex output unless there is a domain-specific reason for a different alphabet.
