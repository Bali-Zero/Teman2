### 1.0 Headline finding — a real action-execution chain exists, but lives in a DIFFERENT app on a DIFFERENT database, and fuses two canonical objects into one row

`apps/bali-zero-magazine/` (a Cloudflare-D1-backed Next.js app, not `apps/backend-rag`) runs its own claim/lease/idempotency/receipt machine for operator-triggered ops actions (`rerun_collector`, `rebuild_edition`, `quarantine_story`, `release_story`, `refresh_research_job`) via table `ops_intents` (`apps/bali-zero-magazine/db/schema.ts:839-892`) + `ops_receipts` (`:923-946`) + `ops_target_fences` (`:894-899`) + `ops_transition_guards` (`:901-921`) + `ops_audit_events` (`:948-971`). This is architecturally the closest thing in the whole repo to the canonical action chain — **and it is the single most important structural mismatch found in this whole grounding pass**: canonical CONTRACTS.md §13 deliberately splits queue-ownership (`ActionItem`) from authorization-bearing execution (`ActionIntent`) into **two separate objects with two separate lifecycles** (§13, shared invariants, `CONTRACTS.md:722`: *"the `ActionItem` carries only queue semantics ... the `ActionIntent`"* carries the authorization-bearing fields). `ops_intents` **fuses both into one row** — there is no separate queue-ownership table with its own SLA/priority/close_reason distinct from the execution row. Any adapter has to either (a) split one legacy row into two synthesized canonical objects, inventing an `ActionItem` that never existed as a distinct record, or (b) get a ruling that the fusion is acceptable and the split is deferred to a later cutover. This is not a field-naming gap — it's a cardinality/object-boundary gap, the hardest kind to paper over with a mapping table.

Live-ness is split down the middle: `/api/operations/intents` (human-triggered path) is genuinely live, wired end-to-end to `apps/bali-zero-magazine/components/operations-board.tsx:78-89` (real client fetch) via SSR (`app/operations/page.tsx:24`). `/api/machine/operations/intents/{claim,start,heartbeat,result}` and `/effects` (the machine-to-machine path — the one an eventual research-os adapter would most plausibly integrate with) has a complete matching Python client (`apps/zantara-media/zantara_media/magazine/transport.py:589-704`, `operations_worker.py`) but **no launchd/cron/CI entry invokes it anywhere in this repo** (`git grep` for `magazine-operations-worker`/`magazine_operations_worker` across `infra/launchagents/*`, `.github/workflows/*` = zero hits outside the app/test source) — confirmed dormant, not a running daemon. `apps/bali-zero-magazine/research/operations/bali-zero-magazine/sdd/task-8-report.md` (implementers' own PR #2881 report, 2026-07-21) states verbatim: *"No production deploy, outward publication, client-data access, collector mutation, paid API call, or arbitrary command execution occurred."*

## 12. Where the newly-registered kinds' spec and code disagree (continues §7's numbering)

9. **The single most common finding across all 9 newly-registered kinds is the same finding §7 item 6 already named for the original 16 — legacy binds to a mutable current row, never a content-hash-pinned revision — but this pass shows it is not confined to receipt-shaped kinds. It applies just as hard upstream, before content or action production even begins** (TopicLock/CreativeLock's `brief_json`, DecisionPacket/RequestedActionSpec's stateful proposal rows). Nine kinds in, this reads less like a per-kind gap and more like a repo-wide default: almost nothing in this codebase's legacy layer computes or stores a content hash of a decision at the moment the decision is made.
10. **A supersession/lifecycle enum that is designed at schema time and never wired to a writer is now a confirmed three-time-independent pattern** (`naga_claim_transitions.transition_type='supersedes'`, `naga_claims.claim_status='superseded'`, `zantara_media.StoryVersionV1.lifecycle_state='amended'|'superseded'`) — worth naming as an organizational habit for whoever designs the eventual adapters, not three unrelated findings.
11. **At least five, arguably six, structurally disjoint "Claim" concepts coexist with no shared owner, schema, or ID namespace** (§11.0 finding 1) — this is a materially larger consolidation problem than any single field-mapping gap in this document, and it sits upstream of every other evidence-spine kind (Evidence, StoryCluster, DecisionPacket all reference Claim).
12. **`RequestedActionSpec`'s "carries no state" requirement, taken seriously, disqualifies nearly every "proposal"/"recommendation" table this repo has ever built** — 8 of 10 candidate mechanisms surveyed across the DecisionPacket/RequestedActionSpec and action-chain (§1) research passes combined declare a live `status` column at `CREATE TABLE` time. Only two mechanisms in the entire codebase (`cell_core.hgt_coordinator.proposal.Proposal`, DLQ's `claude_tasks/*.json`) are structurally state-free, and neither is a rich source. If Packet 04's eventual materialization primitive assumes a state-free `RequestedActionSpec` will typically be adaptable from an existing legacy proposal, that assumption does not hold for almost any legacy system surveyed this session.
