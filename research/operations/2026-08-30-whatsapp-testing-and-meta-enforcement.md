# WhatsApp testing practices and Meta's enforcement mechanics — what's official, what's folklore

**Setup this report is written for**: one WABA, one CONNECTED Cloud API number, quality rating GREEN, throughput STANDARD. Question: how to run a continuous automated test loop against our own bot without risking that number, and how driver (A) self-signed synthetic webhook POSTs compares to driver (B) an unofficial Linked-Devices client (Baileys/whatsapp-web.js).

A methodological note up front: Meta's own **Business Help Center** articles (facebook.com/business/help/…) render their body via JavaScript and returned only the page `<title>` to the fetch tool used here — every claim attributed to those two URLs is therefore **corroborated from secondary sources that cite them**, not a direct quote of Meta's text. Everything attributed to **developers.facebook.com** and **whatsapp.com/legal** below is a direct fetch of the live page. This distinction is preserved per-claim below.

## TL;DR — five things to act on

1. **Meta never sanctions self-POSTing synthetic signed webhooks as a documented practice** — but nothing in the ToS, Business Terms, or Cloud API docs prohibits it either, because driver (A) never touches a Meta server at all. It's outside Meta's documented "Test" button flow, not against Meta's rules.
2. **The one real inbound-message loop Meta documents that doesn't need a second phone number** is: send a template from your test/production number to your *own* personal WhatsApp number (already on your device), then reply from that same phone — this produces a genuine wamid and genuine signed webhook. It still requires one real handset with WhatsApp installed, just not a second Cloud API asset.
3. **A Cloud-API-number → Cloud-API-number send returning 200/wamid but never delivering is expected**, not a bug you tripped: WhatsApp accounts (Cloud API business numbers) cannot receive ordinary consumer-side messages the way a personal number does — the recipient side needs to actually be reachable as a WhatsApp client, which a pure Cloud-API-only number is not.
4. **Enforcement on your Cloud API number is driven by phone-number quality rating (7-day rolling window, most-recent-weighted) and WABA-level policy violations — not by your test *volume* alone.** A synthetic-webhook test loop (driver A) cannot touch quality rating at all, because it never sends anything through Meta's send API; it only feeds your own receiving endpoint.
5. **The unofficial-client route (driver B) is the one with real, non-deterministic ban exposure** — it's explicitly against WhatsApp's Terms of Service (unauthorized/automated access, unauthorized derivative clients), community reports describe bans within weeks-to-months even at low volume, and — this is the important part for your setup — it operates a *separate* consumer WhatsApp account outside your Cloud API/WABA entirely, so a ban there has zero mechanical connection to your Cloud API number's quality rating, but it burns a phone number and carries reputational/ToS risk on its own.

**Recommendation for this setup: driver (A).** See final section.

## 1. What Meta's own docs recommend for testing a Cloud API integration

**Free test phone number.** Confirmed via Meta's official Get Started docs (developers.facebook.com/docs/whatsapp/cloud-api/get-started/, developers.facebook.com/documentation/business-messaging/whatsapp/get-started): every new WhatsApp app is provisioned with a test WABA and a test business phone number. Messages sent from the test number are free. [Get Started](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started)

**5-recipient limit — confirmed, but via secondary sources**, since the official Get Started page fetched did not spell out the number explicitly in the section retrieved. Multiple independent secondary sources (WANotifier helpdesk, respond.io) agree: the test number can only send to up to 5 phone numbers, which must be pre-registered under **Manage phone number list** in the App Dashboard's "To" field selector; once a number is added to a test number's recipient list it cannot be removed. Real (non-test) registered numbers have no such recipient cap. [WANotifier: Test Phone Number Limitations](https://help.wanotifier.com/en/article/test-phone-number-limitations-in-direct-setup-kt0ly2/) (secondary)

**`messaging_product` field.** This is not a "sandbox switch" — it's a required literal string field (`"messaging_product": "whatsapp"`) present on every Cloud API request/webhook payload, part of the envelope shape, not a test/production toggle. NOT FOUND in official docs: any sandbox-mode behavioral flag distinct from this field.

**Webhook "Test" / sample-payload sending from the App Dashboard — this is the closest thing to an officially sanctioned synthetic-payload mechanism, and it is real and documented.** Official text: *"Send a test payload to your endpoint via the [App Dashboard](https://developers.facebook.com/apps) > WhatsApp > Configurations panel."* [Webhooks — WhatsApp Cloud API](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/set-up-webhooks/) — and per a secondary source describing the exact UI: *"select the Test button in the messages field row, which opens a new Field Sample window that displays the format of the payload sent every time a message is sent to the account"* (secondary, corroborating UI mechanics not present in the fetched text). Two important limits on this feature: (a) it sends a **fixed, generic sample** payload, not a payload you can parameterize with your own test scenario content, and (b) some webhook test sends are suppressed unless the app is in **Live mode** (secondary source claim). It is a one-shot manual UI action, not something you can loop from a cron job.

**Is there an official way to simulate an inbound message without a second real phone?** Partially. The documented pattern (per Meta's own Get Started walkthrough) is: send a template from the free test number to a recipient number you own, then **reply from that recipient's own WhatsApp app** — *"Once your webhook is set up, resend the template message and then reply back to it. You should see 4 separate webhook notifications... respond in the WhatsApp chat thread you created with yourself."* This does produce a real, Meta-issued, real-wamid, real-signature webhook — but it requires an actual phone running WhatsApp on the recipient side (it can be your own personal phone/number, which is the "created with yourself" case Meta's docs describe — so it's one real handset, not necessarily a second business asset). **NOT FOUND in official docs**: any way to generate a genuine Meta-signed inbound webhook with zero real WhatsApp client involved anywhere in the loop. Meta does not document or sanction self-POSTing synthetic signed webhooks as a testing methodology — that pattern exists only in community engineering writeups, never as Meta's own recommended flow.

## 2. Signed-webhook self-testing — the mechanics a faithful synthetic payload must reproduce

**Signature computation.** Official (developers.facebook.com/docs/graph-api/webhooks/getting-started): *"Generate a SHA256 signature using the payload and your app's App Secret"* and *"include the signature in the request's `X-Hub-Signature-256` header, preceded with `sha256=`."* So: **secret = the app's App Secret** (not an access token, not a phone-number-specific secret — one App Secret per Meta app, shared across everything registered under that app). Header format: `X-Hub-Signature-256: sha256=<hex-encoded HMAC-SHA256 digest>`.

**What exactly gets hashed — this is the part Meta's fetched pages do not spell out precisely**, and it's also the single most common place implementers get it subtly wrong (per multiple secondary how-to guides converging on the same warning): the HMAC must be computed over the **raw HTTP request body bytes exactly as transmitted** (the exact byte sequence Meta would send, including whitespace/key-ordering as serialized), **not** a JSON object you parsed and then re-serialized yourself. Re-serializing (even semantically identical JSON) changes byte layout (key order, spacing) and produces a different digest, which is why "capture raw body before any JSON-parsing middleware runs" is the standard warning across implementation guides. Verification must use a **constant-time comparison** to avoid timing side-channels (secondary-sourced best practice, consistent across guides, not explicitly stated as a Meta requirement but standard for X-Hub-Signature-256 across all Meta products).

**Verify-token/challenge handshake** (separate from payload signing, only used once at subscription time, not per-message): official — Meta sends a **GET** with `hub.mode=subscribe`, `hub.challenge` (an integer), and `hub.verify_token` (a string you configured); your endpoint must check the verify token matches and echo back `hub.challenge` verbatim. [Getting Started with Webhooks](https://developers.facebook.com/docs/graph-api/webhooks/getting-started)

**Payload envelope shape for an inbound text message** (confirmed via official payload-examples doc):
```json
{
  "object": "whatsapp_business_account",
  "entry": [{
    "id": "<WABA_ID>",
    "changes": [{
      "value": {
        "messaging_product": "whatsapp",
        "metadata": { "display_phone_number": "<business_number>", "phone_number_id": "<phone_id>" },
        "contacts": [{ "profile": { "name": "<user_name>" }, "wa_id": "<user_id>" }],
        "messages": [{ "from": "<sender_id>", "id": "<wamid>", "timestamp": "<unix_ts>", "type": "text", "text": { "body": "<content>" } }]
      },
      "field": "messages"
    }]
  }]
}
```
The `messages` array (vs. `statuses` array for delivery/read receipts) is what distinguishes an inbound-message notification from an outbound status update. [Webhooks payload examples](https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/payload-examples)

**wamid format/uniqueness.** Official: the message `id` is a `wamid.`-prefixed, base64-encoded identifier, globally unique per message. NOT FOUND in official docs: an explicit statement of the exact byte structure Meta packs into it (community sources treat it as an opaque unique token, and that's the only correct usage — do not attempt to parse or derive semantics from a wamid string).

**Retry/deduplication semantics.** Official, confirmed twice independently on developers.facebook.com: *"If a webhook request to your endpoint receives an HTTP status code other than 200, or if the webhook cannot be delivered for another reason, Meta retries delivery with decreasing frequency until the request succeeds, for up to 7 days."* An **HTTP 200** response is the only acknowledgment Meta recognizes; anything else (4xx, 5xx, timeout) is treated as delivery failure and queues a retry. **NOT FOUND in official docs**: the exact backoff schedule or the interval before the first retry. Community/secondary sources (richautomate.in engineering guide) claim a "retries any event that does not return 200 within 3 seconds" first-retry window and describe WhatsApp delivery as effectively "at-least-once" — **this specific timing figure is unconfirmed against an official Meta source** and should be treated as folklore-with-plausibility, not fact. What *is* safe to build on (it follows directly from "retries... until the request succeeds, for up to 7 days" plus no documented Meta-side dedup guarantee): **your endpoint must be idempotent on `messages[].id` / `statuses[].id`**, because duplicate delivery of the same wamid is an expected, not edge-case, occurrence.

**Where people get this subtly wrong** (converging pattern across secondary implementation guides): (1) computing the signature after a JSON body-parser middleware has already consumed/re-encoded the request body, instead of hooking in before parsing; (2) comparing signatures with a plain `==`/string-equality instead of constant-time compare; (3) treating a webhook as processed-once and not deduplicating on wamid, which breaks under Meta's documented multi-day retry behavior; (4) forgetting the `sha256=` prefix when comparing against the computed hex digest.

## 3. How Meta can block a Cloud API business number

**Quality rating (GREEN/YELLOW/RED)** — official terminology confirmed on developers.facebook.com (`"quality_rating": "GREEN"` field on the Phone Numbers API); the calculation mechanics themselves come from Meta's Business Help Center article (facebook.com/business/help/896873687365001), whose body this fetch could not retrieve directly (JS-rendered), so the following is **corroborated via secondary sources that describe/quote that same article**, not a first-party fetch: quality is a **rolling 7-day** score, weighted toward more recent messages, driven by user-side "quality signals" — blocks, in-app reports, and the *reason* a user gives when blocking (spam / didn't sign up / offensive / no longer needed / no reason given). GREEN = low block/report rate, good engagement; YELLOW = a warning state (rising blocks/reports) that risks escalating to RED if unaddressed; RED = worst-case, degrades messaging limits.

**Messaging limits / tiers** — official, from developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits: tiers are **250 → 2,000 → 10,000 → 100,000 → Unlimited unique customers per rolling window**, set at the **business portfolio level** (shared across all phone numbers in the WABA, not per-number). Escalation to 2,000 requires business verification or "send 2,000 delivered messages outside of customer service windows to unique WhatsApp user phone numbers within a 30-day moving period, using templates with a high quality rating." Beyond 2,000, automatic scaling occurs within 6 hours when messages are high-quality **and** "in the last 7 days, your business has utilized at least half of your current messaging limit." **NOT FOUND in the fetched page**: an explicit de-escalation mechanism description (it exists — see Flagged, below — but this specific page didn't spell it out).

**Phone-number status values** — official field confirmed (`status` on the Business Phone Number API, "connected" required to send/receive), full status semantics corroborated via secondary sources quoting Meta's own definitions:
- **Connected** — normal operating state, required for API messaging.
- **Flagged** — triggered when quality rating drops to low (RED). While Flagged, the business cannot advance messaging-limit tiers. If quality recovers to medium/high **within 7 days** of the Flagged transition, status returns to Connected with the tier unaffected; if it does **not** recover within that 7-day window, status still returns to Connected but the messaging-limit **tier is demoted one level**. So Flagged is explicitly a 7-day probation clock, not an instant hard block.
- **Restricted** — triggered purely by hitting your messaging-limit ceiling, independent of quality rating; while Restricted you cannot send further outgoing (business-initiated) messages until the limit window rolls over (secondary sources describe a 24-hour resumption window).
- **Banned/Disabled** — reserved for policy-violation enforcement (see WABA-level below), not a quality-rating outcome by itself.

**WABA (account)-level restrictions** — this is a *separate* enforcement track from phone-number quality, and it's the one with real permanence, confirmed on developers.facebook.com/documentation/business-messaging/whatsapp/policy-enforcement: a graduated ladder of **temporary blocks** (1 or 3 day block on sending marketing/utility/authentication templates and on adding phone numbers) → **extended blocks** (5, 7, or 30 days, blocking *all* messages and number additions) → **account lock** (indefinite, appeal-only) → **permanent removal** from the platform. Triggers named explicitly: repeated policy violations, spam, template misclassification, high-risk content categories (adult content, alcohol/tobacco sale, drugs, gambling, unsafe supplements), excessive negative user feedback. **Immediate permanent ban, no graduated ladder**, for severe-harm categories: child exploitation, scams, terrorism, sale of illegal drugs. Business verification is a separate gate (tied to tier escalation above, not directly cited as a ban trigger in the fetched enforcement page).

**Template-level enforcement** — corroborated via secondary sources (consistent with Meta's own template quality documentation pattern, not independently first-party-fetched here): individual templates carry their own quality rating; sustained negative feedback flags a template, and if unaddressed within a further 7-day window it is **Paused** (temporarily unusable), and if still unaddressed, **Disabled** outright — this is scoped to that one template, not the whole number.

**Temporary vs. permanent, summarized**: quality-rating-driven states (Flagged, Restricted, template Paused) are all **time-boxed and self-healing on a 7-day rolling clock** if the underlying signal improves. WABA-level policy-violation states escalate from days-long blocks to indefinite lock to permanent removal, and only the indefinite/permanent tiers require an **appeal** rather than simply waiting out a clock.

**What actually causes a drop** — synthesizing the above against your question's specific list: **block rate and report rate are the documented primary quality-rating inputs** (official terminology: "quality signals"); **low read rate** is claimed as a contributing factor by several 2026 secondary sources ("WhatsApp's quality score now includes read rates") but this was **not found stated as such on any page fetched directly from developers.facebook.com or facebook.com/business/help** in this research pass — treat "read rate" as a plausible but not first-party-confirmed signal. **Sending outside the 24-hour window without an approved template** doesn't degrade quality rating directly — it simply fails to send / requires a template (a functional block, not a punitive one). **Unapproved template content** is enforced at template-submission review time (rejected before it can ever send) and, per-template, via the Paused/Disabled ladder above if it slips through review and then draws complaints.

## 4. How Meta blocks an ordinary consumer number driven by an unofficial client (Baileys / whatsapp-web.js)

This is a structurally different enforcement path from Section 3 — it isn't Cloud API infrastructure at all, it's WhatsApp defending its consumer protocol (the Linked-Devices multi-device protocol that the normal WhatsApp mobile/web/desktop apps use) against reverse-engineered clients impersonating that protocol.

**Terms of Service basis** — confirmed by direct fetch of whatsapp.com/legal/terms-of-service, section "Harm To WhatsApp Or Our Users": prohibits, directly or through automated means, to *"reverse engineer, alter, modify, create derivative works from, decompile, or extract code from our Services"*; to *"gain or attempt to gain unauthorized access to our Services or systems"*; to *"interfere with or disrupt the safety, security, confidentiality, integrity, availability, or performance of our Services"*; to *"create accounts for our Services through unauthorized or automated means"*; and explicitly to *"create software or APIs that function substantially the same as our Services and offer them for use by third parties in an unauthorized manner"* — this last clause describes exactly what Baileys/whatsapp-web.js/whatsmeow are (reverse-engineered reimplementations of the Linked-Devices wire protocol). Enforcement clause, same document: *"If you violate our Terms or policies, we may take action with respect to your account, including disabling or suspending your account and, if we do, you agree not to create another account without our permission."* Availability clause: *"We may modify, suspend, or terminate your access to or use of our Services anytime for any reason, such as if you violate the letter or spirit of our Terms."*

**Detection surface** — NOT FOUND in any official WhatsApp document (WhatsApp does not publish its abuse-detection methodology, unsurprisingly). What's available is community-reported empirical pattern, converging across independent sources: WhatsApp fingerprints client behavior at the protocol layer (device-registration patterns, message-signing/session-key behavior distinct from official clients, timing/traffic-shape anomalies) and increasingly issues "your account may be at risk" warnings even to accounts doing nothing but replying to inbound messages, not just bulk-sending — see the GitHub issue thread on the `whatsmeow` library (tulir/whatsmeow#810) documenting this exact pattern across multiple unofficial-client projects simultaneously, and a checkleaked.cc dev guide summarizing the same trend. [whatsmeow #810 — "Your account may be at risk" warning](https://github.com/tulir/whatsmeow/issues/810) (secondary, but primary-adjacent: it's the library maintainers' own issue tracker aggregating real user reports)

**Risk profile — realistic, per converging secondary sources (no official numbers exist because WhatsApp doesn't publish them)**: ban risk is described as real but **non-deterministic** — reported survival windows range from roughly 2 to 8 weeks of typical use before detection, though some report bans within days and others report months of uneventful use; there's no way to predict which bucket a given account falls into. Bans reported as typically hitting the **specific phone number/account**, not a broader Meta identity, but recovery is inconsistent: some report the number becomes permanently unusable on WhatsApp, others report being able to re-register after a cooldown. **Appealability**: WhatsApp does provide an in-app "request a review" flow for banned numbers, but community reports (converging across the sources found) describe it as low-success for accounts that actually were running unofficial clients, since the ban is (by WhatsApp's own definition) correctly identifying a ToS violation, not a false positive.

**Scope**: because this operates on an entirely separate WhatsApp identity (a normal consumer number registered to the unofficial client) from your Cloud API WABA, a ban here has **no direct mechanical link** to your Cloud API number's quality rating or messaging tier — they are different systems, different phone numbers, different enforcement pipelines. The cost of a ban is losing that specific consumer number's WhatsApp usability, plus the operational disruption of your test loop, not damage to your production bot's Cloud API standing.

I did not further research techniques for evading detection or appealing/rotating past an enforced ban — several of the secondary sources above (checkleaked.cc, kraya-ai.com) offer exactly that kind of guidance; per the scope limit on this task, I noted their existence and did not detail their content.

## 5. How to stay out of trouble legitimately — the operational payoff

**Cadence.** NOT FOUND in official docs: a specific numeric "safe messages/day" cadence for testing. What's documented instead is the mechanism that makes cadence largely moot for a same-account test loop: quality rating is driven by *block rate and report rate from real end users*, and (per Section 3) is explicitly *"based on... messages your customers have received over the past 7 days."* A self-test loop where sender and recipient are both numbers you control cannot generate a block or a report — there is no third party who could ever hit "block" or "report spam" on a conversation with yourself. This is a mechanical, not a folklore, argument for why a self-test loop is structurally safe on the quality-rating axis, provided it stays entirely within your own numbers.

**Using your own numbers as both ends** — this is exactly the pattern Meta's own Get Started walkthrough uses for developer testing (Section 1: "responded in the WhatsApp chat thread you created with yourself"). It is the officially modeled testing pattern, not a workaround.

**The 24-hour session-window mechanics**, confirmed officially across developers.facebook.com and corroborated by multiple secondary sources in agreement: any inbound message from a user opens/refreshes a 24-hour window during which you may send **free-form** messages back to that user at no template cost; outside that window, only a pre-approved **Message Template** can initiate contact, and sending the first template message itself opens a fresh 24-hour window once the recipient replies.

**When a template is required**: any business-initiated message sent when no 24-hour window is currently open with that recipient. For a self-test loop where you (the tester) are also the recipient and reply promptly to every synthetic-scenario message your bot sends, the window essentially never closes — so a well-designed test loop that always has a human (or scripted) reply on the recipient side rarely needs template messages at all after the first bootstrap message.

**Opt-in requirements** — official (developers.facebook.com/documentation/business-messaging/whatsapp/getting-opt-in): businesses must obtain permission before messaging a number, stating clearly that the person is opting in and naming the business; accepted methods include SMS, web forms, IVR, or in-person/paper — the mechanism is up to the business. **NOT FOUND in official docs**: an explicit statement of whether messaging your own staff/test numbers is exempt from this requirement. Read plainly, opt-in exists to protect *third parties* from unsolicited contact; a business messaging numbers it directly owns/controls for internal testing purposes isn't the scenario the policy is aimed at, but there is no official carve-out text confirming this — treat it as a reasonable inference, not a documented exemption.

**Does messaging yourself/your own staff count toward quality signals?** Mechanically: quality rating is fed by block/report/(possibly read-rate) signals from message *recipients*. If the recipient is your own controlled number and never blocks/reports, it contributes nothing negative. It is technically still "a message received" and could in principle count toward whatever denominator underlies rate calculations, but there's no official documentation suggesting internal-number traffic is scored any differently, or that it dilutes/improves your rating either way — **NOT FOUND in official docs**, treat as neutral-by-construction rather than confirmed-neutral-by-Meta.

**What actually resets a degraded quality rating?** Official (Section 3, Flagged status mechanics): it is **not a manual reset** — it is the same rolling 7-day window recalculating itself as newer (better) message outcomes accumulate and age the bad signals out. Practically, per this same 7-day-window logic corroborated across secondary sources: stop whatever triggered blocks/reports, and the score mathematically recovers once 7 days of cleaner activity have passed. There is no documented "quality rating reset button" — only time plus better behavior. Community sources' claim that requesting business/display-name re-verification "resets" the score is **not confirmed** by any official page found in this pass.

**Documented vs. folklore, explicitly**:
- **Documented**: 7-day rolling quality window; Flagged/Restricted status mechanics and their specific triggers; messaging-limit tiers and escalation path; 24-hour session window and template requirement; opt-in core requirements; WABA-level graduated enforcement ladder; ToS prohibition on unauthorized/automated/reverse-engineered clients; webhook 7-day retry-until-200 behavior; wamid uniqueness; App Dashboard "Test" sample-payload feature.
- **Folklore / secondary-only, use with appropriate skepticism**: exact first-retry timing (~3s); read rate as a confirmed quality signal; unofficial-client ban survival windows (2-8 weeks); business-verification as a "reset" lever for quality rating; the precise internal weighting Meta gives block-vs-report-vs-read signals (Meta has never published the formula).

## What we should do — driver (A) vs driver (B) for this setup

**Driver (A): self-signed synthetic webhook POSTs to our own `/webhook/whatsapp` endpoint, Meta never involved.**
- Touches zero Meta infrastructure — cannot affect quality rating, messaging tier, phone-number status, or WABA standing, because none of Sections 3's trigger mechanisms (block, report, template misuse, policy violation) are reachable when Meta's send/receive pipeline is never invoked.
- Is not a documented Meta testing method (the "Test" button in the App Dashboard is Meta's own equivalent but fixed-payload and UI-only), but is also not prohibited by anything found in the ToS, Business Terms, or Cloud API docs — because it operates entirely on infrastructure you own (your endpoint) with a signature you compute using a secret you already legitimately hold (your own App Secret).
- Correctness risk is entirely internal/engineering, not a compliance risk: the payload must faithfully reproduce the envelope shape (Section 2) and the raw-body HMAC computation, or it tests a fiction rather than your real integration. This is the one place this driver needs real care — a synthetic payload that's shaped wrong gives false confidence.
- Can run at arbitrary frequency, unattended, in CI/cron, with no rate-limit or enforcement exposure whatsoever.

**Driver (B): unofficial Linked-Devices client (Baileys/whatsapp-web.js) sending real messages from a consumer number.**
- Carries genuine, non-deterministic ToS-violation ban risk on whatever number runs it (Section 4) — explicitly named in WhatsApp's own Terms of Service as prohibited (unauthorized/automated access, unauthorized derivative client).
- That ban risk is mechanically isolated from your Cloud API WABA/number (different system), so it cannot itself demote your production bot's quality rating — but it does put a phone number and (per the Terms) potentially your ability to "create another account without permission" at stake, and burns operator time babysitting a fragile, non-Meta-sanctioned dependency purely for the sake of test signal.
- Its only genuine advantage over (A) is testing something (A) structurally cannot: whether messages **actually traverse Meta's real infrastructure** end-to-end (real delivery, real read receipts, real timing) rather than just exercising your webhook parser. That's a meaningfully different test target, not a strictly worse one.

**Recommendation: use driver (A) as the default, continuous, high-frequency test loop** — it is free of every enforcement mechanism in Sections 3-4, requires no additional real phone number, and can run as often as useful. **Reserve any need for true end-to-end delivery verification (the thing (A) cannot test) for the officially-modeled pattern in Section 1/5**: your own real personal WhatsApp number, added once to the test-number recipient allow-list (or used against the production number within its normal opt-in), replying to your own bot manually or via a lightweight scripted reply on your own device — this stays entirely inside Meta's documented, sanctioned testing pattern and inside the "own numbers as both ends" quality-rating-safe zone from Section 5, with no need for driver (B) at all. Driver (B) is not recommended for this setup: the one thing it uniquely tests (real Meta-infrastructure traversal) is already covered by the self-numbers pattern above, so it adds ban exposure without adding test coverage you don't already have another, compliant way to get.
