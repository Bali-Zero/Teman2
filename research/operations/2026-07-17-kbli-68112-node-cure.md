# KBLI 68112 — Postgres Knowledge Graph node surgical cure

## Summary

PR #2508/#2527 (merged 2026-07-16) fixed the **canonical dataset** record for
KBLI 68112 (a code-number collision: BPS Peraturan 7/2025 = residential
leasing; PP 28/2025's older KBLI-2020 numbering = an unrelated MICE-venue
activity). The Postgres **Knowledge Graph** (`kg_nodes`/`kg_edges`) is a
separate datastore that fix never touched. A live read (dev Postgres,
2026-07-17) found the KG node still carrying the pre-fix contamination in
three places, plus a legacy shadow node whose own description IS the
MICE text. This report documents the cure, a corrected consumer-map (one
of my own initial claims did not survive independent adversarial review —
see below), and the apply+prove-live procedure. **Nothing has been applied
to prod.** The cure script defaults to dry-run; `--apply` was never run
against any database in this session.

## Ground truth: what's wrong and the fix

**Fonte-verità**: `data/source_documents/KBLI_2025_FINAL_CLEAN.json`, record
`kode_kbli_2025 == "68112"` (fetched fresh at `https://raw.githubusercontent.com/Balizero1987/Teman2/main/data/source_documents/KBLI_2025_FINAL_CLEAN.json`
— the exact same source+URL `kg_kbli_resync.py` already uses). Read verbatim
in this session; key fields:

- `uraian`: `"Kelompok ini mencakup penyewaan dan pengoperasian real estat hunian milik sendiri atau sewa."` (residential, correct)
- `per_skala`: `[]` (correctly emptied by #2508/#2527)
- `per_skala_disputed_pp28_mice`: the original MICE licensing block, preserved for audit
- `intel_2026.whatYouNeed`: corrected prose that explicitly **disclaims** the MICE collision (contains "code-number collision" verbatim)
- `_data_note`: corrected advisory pointing to KBLI 68111 as the nearest residential reference

**Three contamination points found in the KG node `kbli:68112`** (live dev
read, 2026-07-17 — see caveat above on prod-reachability):

1. `properties.uraian` — **stale, bleeds into the unrelated 6812 subgroup**:
   `"...atau sewa. 6812 AKTIVITAS REAL ESTAT (BANGUNAN DAN LAHAN) NONHUNIAN MILIK SENDIRI ATAU SEWA Subgolongan ini mencakup..."`.
   The router `kbli_notebook.py:458` (`props.get("uraian", node["description"])`)
   **prefers this field over the `description` column** — so even though
   `description` itself is already correct, this field wins whenever a
   consumer reads `properties.uraian` specifically. `kg_kbli_resync.py` (the
   already-merged sibling script) does **not** sync this field at all in its
   current main-branch form — only its own docstring's WHY section and PR
   #2528's still-unmerged patch mention adding it.
2. `properties.whatYouNeed` — **stale, still the pre-#2508 text verbatim**:
   `"...Self-Assessment document covering MICE venue standards (facilities, organization, HR) is referenced in the obligations..."`
   — the exact string `scripts/tests/test_kbli_68112_pp28_mice_collision.py`'s
   own docstring names as "the ORIGINAL bug" shape. `kg_kbli_resync.py`
   already has correct sync logic for this field (its `INTEL_KEYS` loop) —
   it has simply never been re-run against prod since #2508 shipped (per
   the corner file: "fly apply NEVER run").
3. Two wrong `REQUIRES` edges from `kbli:68112`: one to a **perizinan node
   whose properties describe agriculture licensing** ("good agriculture
   practices" / reports to "Menteri Pertanian" — a completely unrelated
   sector) and one to a **perizinan node whose `kewajiban` text literally
   names "Penyewaan Venue Penyelenggaraan Aktifitas MICE dan Event Khusus"**.
   Both entity-id hashes observed live match PR #2528's own live-audit prose
   exactly. A `REQUIRES` edge to `company:pt_pma` also exists and is
   **legitimate** (68112 is PMA-open) — must never be touched.

**Shadow legacy node `kbli_68112`** (underscore, no colon): its own
`description` column **is** the literal MICE text
(`"Penyewaan Venue Penyelenggaraan Aktifitas MICE dan Event Khusus"`),
`entity_type='kbli'` (same type as the real node), `properties={}`. It is
**not** edge-orphaned — it has 3 edges in its own small legacy subgraph
(`kbli_68112 REFERENCES peraturan_pemerintah_pp_28/2025`, plus two
`APPLIES_TO` edges pointing IN from `izin_usaha_sertifikat_standar` and
`dokumen_penilaian_mandiri`, the latter of which has its own, unrelated
contamination — its description says "...Aktivitas Perburuan" (hunting) —
a shared/generic legacy node, out of scope here).

**New systemic finding, out of surgical scope**: `kbli_68112`-style
underscore entity IDs are not a one-off — **2,384 such nodes exist** in this
KG (`SELECT COUNT(*) FROM kg_nodes WHERE entity_id ~ '^kbli_[0-9]+$'`), a
whole parallel legacy catalog predating the current `kbli:<code>` colon
convention. This is a much wider disease-class than one shadow node and
deserves its own investigation/decision — flagged here, not acted on.

## The cure script

`apps/backend-rag/backend/scripts/kg_fix_68112_node.py` (new, dry-run by
default, `--apply` gated, `--verify` standalone mode). Hardcoded to 68112
by design (not a generic `--only`-multi-code tool like its two siblings) —
this is a single-code surgical cure, not a sweep.

**What it does** (see the module docstring for the full account):
description/`properties.uraian`/`properties.{whatItMeans,whatYouNeed,
baliContext,whatChanged,zantaraOpener}`/`properties._data_note` synced from
a fresh canonical-dataset fetch; the two wrong `REQUIRES -> perizinan:*`
edges deleted (gated on canonical `per_skala == []`, never touches
`REQUIRES -> company:*`); the shadow node `kbli_68112` neutralized
(description replaced with an honest deprecation notice, `properties.
_deprecated=true` + `_superseded_by="kbli:68112"` + `_data_note` added) —
**not deleted**, its edges **left untouched** (see residual risk below).
All writes wrapped in one transaction. Post-apply verification re-fetches
canonical + re-reads the DB and checks (a) no uncorroborated MICE/Venue
text, (b) exact match against canonical, (c) zero wrong edges remain,
(d) the shadow node's deprecation markers are actually set — exits
non-zero if any check fails even after a successful write.

Unit tests: `apps/backend-rag/backend/tests/unit/scripts/test_kg_fix_68112_node.py`
(21 tests, pure functions, no DB/network — fixtures use the ACTUAL stale
values read live, not synthetic guesses). Registered in
`backend/tests/db/test_jsonb_double_encoding_class_guard.py`'s
`KNOWN_CODEC_LESS_FILES` (same raw-`asyncpg.connect()` pattern as
`kg_kbli_resync.py` — Codex-confirmed correct, see below). `docs/AI_ONBOARDING.md`'s
DOCSYNC test count regenerated in the same commit (W86 discipline).

## Adversarial review

**Reviewer**: Codex (GPT-5.6-sol, `mcp__plugin_second-opinion_codex__codex`,
`sandbox: read-only`, `model_reasoning_effort: high`), 2026-07-17, reviewing
the first draft of the script + tests + this report's claims, with no
access to this session's reasoning — a genuine generator≠grader pass, not
a self-grade.

**Initial verdict: BLOCK MERGE.** Findings, and what was done about each:

1. **Bug — shadow node could never verify clean.** `SHADOW_DATA_NOTE` read
   `"code-number-collision"` (hyphenated through) while `DISCLAIMER_MARKER`
   is `"code-number collision"` (space before "collision") — the strings
   didn't match, so `verify_node_clean` flagged the shadow node's own cure
   text as still contaminated; `--apply` could never converge to PASS. The
   original test suite missed this because it tested the description and
   an empty-properties dict in isolation, never the actual combined
   `plan_shadow_node_fix()` output. **Fixed**: corrected the string;
   added `test_shadow_data_note_itself_passes_verify_node_clean` which
   walks the real combined plan output end-to-end.
2. **Gap — verification could false-PASS real staleness.** The marker
   scan alone cannot detect the `properties.uraian` subgroup-bleed text
   (it contains neither "MICE" nor "Venue"). **Fixed**: added
   `verify_main_node_matches_canonical`, an exact-match check against a
   freshly re-fetched canonical record, run alongside the marker scan in
   `run_verification`. `--verify` now re-fetches canonical (previously
   claimed "no dataset fetch" — corrected in the docstring too).
3. **Gap — shadow deprecation markers never independently checked.** A
   row with neutral-but-untagged text would pass the marker scan without
   ever confirming `_deprecated`/`_superseded_by` were actually set.
   **Fixed**: added `verify_shadow_node_deprecated`.
4. **Bug — writes not atomic.** Three separate autocommit statements
   (main UPDATE, edge DELETE, shadow UPDATE) meant a mid-way failure left
   a partial cure with no rollback. **Fixed**: wrapped in one
   `async with conn.transaction()`.
5. **Latent bug — empty canonical `uraian` could write NULL.** If
   `update_node` were True from a properties-only change while `uraian`
   happened to be empty, `new_description` computed to `None`, which the
   SQL layer binds as NULL over a valid existing description. **Fixed**:
   `new_description` now falls back to the current description, never to
   NULL. (Not currently reachable for 68112 today — canonical `uraian` is
   non-empty — but a real latent bug; noted that the identical fragility
   exists, unfixed, in the already-merged `kg_kbli_resync.py`, out of
   scope to touch here.)
6. **Confirmed correct (no bug)**: binding an already-`json.dumps()`-
   serialized string to `properties = $N::jsonb` on a raw
   `asyncpg.connect()` with no jsonb codec registered is the CORRECT
   pattern there (PostgreSQL parses the text server-side; the "jsonb
   string-scalar double-encoding" class of bug this repo has scar tissue
   about only applies to the codec-ON pool) — same pattern as
   `kg_kbli_resync.py`. Independently confirmed, validates the
   `KNOWN_CODEC_LESS_FILES` registration.
7. **Confirmed correct (no bug)**: `REQUIRES` + `target_entity_id LIKE
   'perizinan:%'` scoping correctly preserves `company:pt_pma`-type edges.
8. **Residual risk, explicitly NOT expanded into this script** (a
   deliberate scope decision, not an oversight): the shadow node's own
   graph edges and `name` field (`"KBLI 68112"`, still similarity-matchable
   against a bare "68112" query) are left untouched. Neutralizing the
   description/properties stops the worst case (a direct false text
   assertion being read verbatim) but does not fully close the
   fuzzy-entity-resolution vector in `resolve_entities_node`. Closing that
   fully would mean either editing the shadow node's edges (a bigger,
   separate decision given 2,384 sibling nodes share this shape) or
   hardening `resolve_entities_node` itself to prefer canonical
   `kbli:`-prefixed IDs when both a colon and underscore variant match —
   both recommended as follow-ups, deliberately not done here to keep this
   PR's blast radius to the one code it's scoped to cure.
9. **Noted, not changed** (parity, not a new regression): the
   contamination-marker check is case-sensitive (`"MICE"` would not match
   `"mice"`) and disclaimer-scoped to the same string, not sentence-level —
   both are inherited VERBATIM from the already-shipped, already-reviewed
   dataset-level guard (`test_kbli_68112_pp28_mice_collision.py`), by
   deliberate design (this cure's own stated goal is for the KG-side and
   dataset-side guards to agree on what "clean" means). Improving this
   would need to happen to both guards together, not diverge one from the
   other — flagged for a future joint pass, not fixed unilaterally here.
10. **Corrected a factual overclaim in this report's first draft**: see
    the Consumer-map section above — `apps/mouth`/`apps/kbli-navigator`'s
    main `/kbli/[code]` pages read static files, not the live API. Found
    by direct inspection after Codex specifically challenged this claim;
    verified via `grep` on the actual page/component source in this turn.
