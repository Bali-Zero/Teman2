# Beyond-SOTA 12/13 — Data, schema & migration engineering

## §0 — TL;DR

**Position:** world-class at migration *authoring* (97.7% rollback coverage, migration-as-ADR headers, 5 CI gates, lint-enforced durability doctrine) and genuinely BEHIND at the layers tests cannot see — privilege catalog, driver codecs, reader maps, provenance — which produced 5 incidents in 20 days from one belief.
**Biggest gap:** CI is green-by-construction on ownership (the CI role owns everything it creates) while prod has 22 tables the app role doesn't own; the guard is text-over-migrations for a catalog-state problem, and no surveyed SOTA system (Neon, Atlas, dbt) covers this either — it is an industry blind spot we bleed from weekly.
**Top-3 moves:**
1. **Catalog contract** (R1): versioned owner+privilege artifact probed from prod; CI bootstraps the real role topology and applies migrations AS `backend_rag_v2` — kills the W130 class by construction.
2. **Codec-parity cure + lint** (R2): land `default=str` on both prod jsonb codecs, one shared prod-shaped pool fixture, lint bans bare `create_pool` in tests — kills the 10/10-green-on-broken-code class.
3. **Provenance + checksum verify** (R3): `applied_as`/`applied_via` columns, `schema_audit` reads the stored checksums — out-of-band superuser applies become visible instead of unrecorded.
**One sentence:** promote every non-schema layer of the data contract to a versioned, diffable, CI-replayed artifact — the organism already proved this pattern on outbox durability promises; generalize it.

## §1 — How Nuzantara does it today

**The store.** One Fly Postgres cluster, `nuzantara-postgres` (postgres-flex 17.7, repmgr HA — rolled 17.2→17.7 on 2026-08-09 only after an isolated restore proof; WAL archiving re-enabled the same day after discovering a legacy override had disabled it, i.e. "DONE" backups were not restorable) plus a Qdrant vector estate (`CLAUDE.md` §11, §9). Frontend data flows through the same backend; there is no second write store.

**Migrations.** `apps/backend-rag/backend/db/migrations_v2/` holds **175 files (174 SQL + `LEGACY_PROMOTION_README.md`)**, numbered to 296 with visible gaps (282, 292–295) — numbers are claimed at PR-open and resolved at merge, the W128 claim-vs-merge lag. Cadence measured from `git log --diff-filter=A`: 1/8/7/23/**47**/33/20/18 per month Jan→Aug 2026 (157 total; peak May, ~20/month steady now). **170/174 (97.7%) carry a `-- === ROLLBACK ===` section**, mandatory per `migration_base.py` and validated at runtime; the runner (`migration_manager.py`, 524 lines) extracts `rollback_sql` at apply time and stores it in `_schema_versions` alongside a `checksum` that is **computed, stored, and never re-read** (W130 GOTCHA d — a preserved proof nobody verifies). Legacy Python migrations were strangler-fig-promoted into idempotent v2 files (132–137, 142–143) mirroring `ci_bootstrap_schema.py` line-for-line, with the cutover sequenced as separate PRs (`LEGACY_PROMOTION_README.md`).

**Migration culture: the migration IS the ADR.** `296_wa_broker_jobs_live_only_unique.sql` opens with ~55 comment lines naming the prior invariant it retires, the alternative rejected (reusing `wa_outbox.attempts`) and *why* it fails under crash/reclaim, and the lock-cost premise ("table ships near-empty… ACCESS EXCLUSIVE on no meaningful traffic"). `289_visa_retention_binders_scope_to_visa_decision.sql` opens with a forensic postmortem of the 2026-08-26 outage including **measured prod counts** (`effective_period @> now()` → 4 rows; `+ policy_scope='VISA_DECISION'` → 1) and an explicit "what is NOT claimed" paragraph. This is unusual and load-bearing: in a repo where no human reviews code, the migration header is the only place the next session can learn the invariant.

**CI gates on migrations (5 named workflows, verified on disk).** (1) `migration-lint.yml` — Squawk DDL-safety lint, chosen over Atlas after the v0.38 paywall (archived scar), built required-safe via the *sentinel pattern*: no top-level `paths:` filter (a `paths:`-filtered required check hangs "Expected — waiting" forever on innocent PRs); relevance decided inside the job. (2) `lint-migration-numbers.yml` — duplicate-prefix detection born from the P0-7 dup-129/130 audit; W41 added a `push: main` trigger after W40 proved a direct-to-main commit could land dup 194 invisibly. (3) `lint-migration-rollback.yml`. (4) `catD-backend-data-invariants.yml` — pins the advertised embedding dim to the frozen model and runs the endpoint-reachability antibody as a *named* check (it was previously only inside the generic pytest sweep, where a `pytest.skip` fallback could silently no-op it — W64 "exists-but-not-armed"); deliberately **not** required at birth: a new signal observes for a cycle first (W69 lesson). (5) `restore-drill.yml` — monthly (cron `0 4 1 * *`) pg_restore from Tigris with Telegram alert on failure; the drill itself surfaced the 2026-06-06 silent-restore bug (empty `PGPASSWORD` → instant auth-fail → 0 tables restored, previously hidden because restore output wasn't surfaced). Beyond CI: `backend/tests/db/test_post_d1_migrations_guard_ledger_owned_ddl.py` — a **static text guard** over migrations >268 that classifies violations into three classes with three different cures (`owner` → catalog guard, `references` → GRANT, `unguarded-do` → a DO body must contain a conditional so it can *decline*), built through 4 adversarial rounds including a cross-family grader that corrected the attribution logic (W130).

**The runner is the runtime role.** `migration_manager.py:96` uses `settings.database_url` — the same DSN as the app, role `backend_rag_v2`, no `SET ROLE` anywhere in the chain. Fly's `release_command` is `python -m backend.db.migrate apply-all && python -m backend.db.schema_audit` (W122); `schema_audit.py` checks pending migrations, tracking divergence (`_schema_versions` vs `schema_migrations`) and `SCHEMA_AUDIT_REQUIRED_TABLES` shape.

**Roles & ownership (the live fracture).** `backend_rag_v2` is NOSUPERUSER (W38 executed). Measured 2026-08-26/27: **22 tables are not owned by the app role** — 11 `visa_ledger_owner`, 9 `zantara_rag_user`, 1 `postgres`, 1 `repmgr`; login members of `visa_ledger_owner` are all superusers (`flypgadmin`, `postgres`, `repmgr`). Consequences measured, not inferred: `conversations` (owner `zantara_rag_user`) grants the app SELECT+UPDATE but **no INSERT/DELETE — 53 live call sites write to a table they cannot write** (memory 2026-08-08); five GARUDA `SECURITY DEFINER` primitives were created owned by `visa_ledger_owner` over `backend_rag_v2`-owned tables, so their own `current_user = table_owner` guard forbade them to themselves (cured via superuser `ALTER OWNER`, 2026-08-28); widening the `policy_scope` CHECK requires a **temporary `GRANT visa_ledger_owner TO backend_rag_v2`**, since revoked — the guard test names that as the sanctioned path (memory 2026-08-28). SECURITY DEFINER appears 53 times across 11 migration files; 71 `CREATE TRIGGER` statements (audit/notify triggers) live in migrations, with DB triggers refactored to `outbox.publish` (migration 146).

**jsonb codec.** Both prod pools register a `jsonb` codec whose encoder is bare `json.dumps` (`app/core/database.py:31-32`, `app/setup/service_initializer.py:508-509` — verified this session, the `default=str` cure recommended in the 2026-08-27 memory has **not** landed). **Data invariants & tripwires.** `CLAUDE.md` §9 is the doctrine; enforcement is tests: `test_data_invariant_tripwires.py` (9 tests: frozen `text-embedding-3-small`/1536, frontend LeadSource ⊆ backend enum, KBLI `kbli_documents.metadata` nested-not-flat, retired-contact pricing, 4 PIN-hygiene tests), plus the abstain-threshold SSOT `_abstain_policy.py` — **5 named gates** (GENERATION flat 0.15; LABEL per-domain tax 0.10/visa 0.12/kbli 0.20/default 0.15; CONFIDENCE zone edges 0.15/0.60; CONTEXT_QUALITY_MIN), with the generation≠label divergence panel-ruled and tripwired against "tidying".

**Outbox durability as lint-enforced doctrine.** SYMBIOSIS Legge 3 carries a per-channel durability table (PG LISTEN/NOTIFY + `events_outbox`, atomic insert in the trigger's transaction, replay-on-reconnect capped at `max_age_minutes=60`, dispatcher-level ack with per-handler ack an acknowledged phase-2 gap) — and **every durability promise requires a `Test:` citation, enforced by `scripts/lint_symbiosis_promises.py` on CI**. 10 test files under `tests/services/events/` (outbox, callsite integration, replay, stale-TTL W36, explicit ack).

**Qdrant.** Frozen embedding pinned twice (tripwire + catD). But the estate is drifted: the 2026-07-05 reconciliation runbook measured **14 live collections / 113,818 docs vs 20 definitions, with only 6 matching**; 14 definitions point at nothing; 8 live collections — including `legal_unified_hybrid_hybrid` at 81,411 docs, the biggest — have **no definition**, and two registries disagree about what "defined" means (`collection_registry.py` vs `collection_manager.py`).

**Retention.** Conversations: Zero ruled 5 years, nothing deletes on a clock (`RETENTION_MIN_DAYS = 1826` + clock-delete kill-switch in `core/retention_policy.py`; per-subject UU PDP Art. 43 erasure deliberately exempt). ## §2 — Scars & ledger evidence in this area

This lane's territory is the densest scar field in the repo after CI itself. Superscar **#9 (state-schema mutation drift)** is literally named for it; orphans W38/W40/W128/W87 and the newest majors W130/W131 are all data-layer.

**The August 2026 role-fracture cluster — five incidents in 20 days, one defective belief.** (1) 2026-08-08: W38's NOSUPERUSER demotion left `conversations` write-dead — 53 call sites, discovered only because a cleanup job 500'd (memory `discovery_the_nosuperuser_demotion_left_conversations_write_dead`). (2) 2026-08-26: five GARUDA migrations (281, 284–287) hit `must be owner of table` in the release_command → **the whole deploy aborted**, and the migrations only exist in prod because a superuser applied them out-of-band, unrecorded (`_schema_versions.applied_by` writes the literal string `system` for every row) — W130. (3) Same day: migration 281's widening of the retention table to multi-scope silently broke the two *unscoped* Visa Oracle binders — the first GARUDA policy row activation made `count(*)==1` false and **the Visa Oracle answered nobody in prod** (289's header; memory `discovery_the_retention_gate_counted_every_scope`). (4) 2026-08-28: the five GARUDA SECDEF primitives were found broken *by construction* (owner mismatch — their own owner-guard forbade them to themselves). (5) 2026-08-28: adding a 5th `policy_scope` was found to be impossible for any migration this deploy path can run; the sanctioned path is a temporary role grant. One belief generates all five: *"the migration runner and the runtime can do whatever the schema needs"* — true until W38, false after, and nothing that runs in CI can falsify it because the CI role owns everything it creates (W130 GOTCHA a: "green by construction").

**W130 (2026-08-26, P-class: deploy-blocking).** Beyond the incident: `ADD COLUMN IF NOT EXISTS` does **not** save you (ownership is checked before the existence short-circuit); editing applied migrations buys nothing (prod won't re-run them; rollback uses the *stored* `rollback_sql`, not the file); and the guard that came out of it went through 4 adversarial rounds, with a cross-family grader (Kimi K3) catching that a FK from an app table *referencing* a ledger table needs a GRANT, not a guard — right verdict, wrong diagnosis, wrong cure without it. The nested finding: `_schema_versions.checksum` is a preserved proof nobody reads — family #2 inside the cure for family #2.

**W131 (2026-08-28).** Three xdist test probes cloned their scratch DBs `TEMPLATE`-from the **live worker database** because one name served as both namespace and template source; `ObjectInUseError` red on an innocent PR; a 36-second test duration was the unread symptom; `maxfail` hid the two sibling defects in the same file. #9 with a #3 edge: the `_pristine_dsn()` cure existed at one call site and was left off its brothers.

**W38 → the long tail.** The demotion itself was correct hardening (spec'd, verified live 2026-06-11), but its consumer contract was never written down as an *executable* invariant: which role must hold which privilege on which table for which caller. Every discovery since has been a body (a 500, an aborted deploy, an outage) rather than a red test.

**W40/W41/W128 — monotonic counters with concurrent writers.** Migration numbers collided (parallel agent wave, dup 194) → runner would hard-fail at load; cure = uniqueness lint + push-trigger + upfront number reservation in orchestrator playbooks. W128 is the same disease on scar numbers (claimed at PR-open, resolved at merge; two PRs claimed W126 three minutes apart), cured with `lint_scar_number_collision.py` computing the claim set from **open PRs, not just main**. The migrations_v2 gaps (282, 292–295) show the claim-lag is live today.

**W53/W54/W61/W88/W125 (superscar #9 members).** Schema-of-state drift: a `ts` written as ISO string crashed the sentinel's float subtraction (W54); `add_to_dlq` rebuilt queue entries and stripped `autopilot_attempts` → 4,676-escalation storm over 7 days (W61); a TERMINAL state enforced in one consumer and not the other (W53); "is this content on main" answered by SHA/patch-id proxies instead of blob comparison (W88); a clean ORT merge duplicating a ledger row with the stale copy *above* the corrected one (memory 2026-08-28) — the data layer's lesson generalized to every file that is a database.

**jsonb codec (2026-08-27, PR #5108).** The double-encode itself is ordinary; the scar-grade finding is that **six integration-test files each built their own pool without `init=`** — a fake at the wrong boundary (service instead of wire) that shared the code's imagination (W114's exact disease, one layer down). Cure direction is on the codec (`default=str` partial), *decided but not landed* — verified this session that both prod pools still register bare `json.dumps`; call sites open in PENDING-ARMS (45 rows currently match migration/jsonb/retention/qdrant/role keywords in the ledger).

**Backup/restore scars.** W106 (stale-credential constant killed 27h of Postgres dumps, with the error message blaming the working credential), W101-recidiva (errexit decapitated the backup script's own PARTIAL report; the Qdrant phase silently never ran), the 2026-06-06 silent-restore (auth-fail restored 0 tables and looked green until the drill surfaced output). Pattern: **the backup path had guardians whose failure modes matched the failures they guarded.**

**Recurrence verdict.** #9 has recurred ≥8 times and is still producing (W131 is 2 days old). The role-fracture cluster produced 5 incidents in 20 days and its executable guard covers only DDL *text*, not privilege *state* — the catalog side (`pg_class.relowner` drift, grants per caller) is explicitly "not observable from the repository at any depth" (W130 GOTCHA g). That asymmetry — text guards for a catalog problem — is the biggest open wound in this lane.

**The five that matter most.**

**Neon-style branch-per-PR (3) is the strongest external answer to this lane's worst wound — and it still misses it.** Every surveyed CI story (Neon, Atlas, dbt) tests migrations against production-*shaped data and schema*. None tests against production-shaped **privilege topology**: a Neon branch copies the catalog but CI connects as a role that owns everything, exactly like our ephemeral CI Postgres. W130's "green by construction" is therefore not a local sloppiness — it is an industry-wide blind spot, which is what makes the catalog-contract recommendation (§5 R1) a genuine beyond-SOTA composition rather than catch-up.

**pgroll (1) and Stripe (2) both formalize what migration 289 did by hand.** 289's fix moved the gate and the two binders "together" because the header author *knew* both readers. pgroll mechanizes reader-coexistence (two live schema versions); Stripe mechanizes it in time (four phases). At our scale — one application, schema applied in the same release as code — full multi-version machinery is negative-value complexity; the transferable core is *naming the readers of the changed invariant before changing it*, which today lives only in comment culture (§5 R4 turns it into a lint).

**Qdrant's official migration tutorial (6) reframes the frozen-embedding invariant.** `text-embedding-3-small` is frozen because changing it "invalidates 93,283 vectors" (tripwire docstring). The alias + named-vector pattern converts that from a permanent fear into a rehearsable ceremony: build-behind-alias, re-embed in background, atomic flip, instant rollback. The freeze then becomes a *choice with an exit*, and the tripwire's job shifts from "never change" to "never change *outside the ceremony*".

**Crypto-shredding (7) is the only surveyed mechanism whose erasure reaches backups.** The 5-year "never delete on a clock" ruling and per-subject erasure coexist fine in the live DB, but every Tigris dump retains erased subjects until dump expiry. Key-destruction erasure is the standard answer; it composes cleanly with the existing retention-policy table (a `GARUDA_*`-style scope row per key class) — but which data classes deserve per-subject keys is a Legge-5 ruling, not an engineering default.

**The restore-testing 5-level model (9) grades our drill precisely.** Existence (1), integrity (2), partial (3), full restore (4), application verification (5). The monthly drill is a solid Level 4 with alerting — and it has already paid for itself twice (the 2026-06-06 silent-restore, the WAL-archiving discovery). Level 5 costs one step: run `schema_audit` + a handful of golden queries against the restored DB. Notably, *none* of the surveyed restore tools validates the privilege catalog of the restored cluster — a restored DB with wrong owners would pass all five levels and then abort the next deploy; R1's contract check closes that too.

## §5 — Beyond-SOTA recommendations (ranked by impact × confidence / cost)

**R1 — The catalog contract: privilege-fidelity CI.** *What:* a versioned artifact `infra/db/catalog-contract.json` — for every table: owner; for every (role, table): the `has_table_privilege` truth vector; for every SECDEF function: owner + `SET search_path` presence — produced by a read-only probe of prod (existing `nuzantara_readonly` MCP / `scripts/pg.sh` path), refreshed by a scheduled lane, diffed on every refresh. Then the migration-CI job **bootstraps the ephemeral Postgres with the real role topology** (create roles, create objects, `ALTER OWNER` per contract) and runs `apply-all` **as `backend_rag_v2`**. *Why beyond SOTA:* every surveyed CI story (Neon branches, Atlas drift detection, dbt contracts) replicates schema and data; none replicates *who owns what* — and our August cluster proves privilege state is where migrations actually die. Atlas's drift detection is the nearest idea and compares schema, not ACLs. *Asymmetry exploited:* one prod cluster, a standing read-only credential, sessions that own the whole lifecycle, and a scar corpus that already enumerates the 22 non-app-owned tables. *Cost:* ~2 sessions (probe script + CI bootstrap step), flat-sub only. *Gear:* 2. *Risk:* family #9 — the contract goes stale against live `pg_class.relowner`; mitigation = the contract carries its probe timestamp, the weekly refresh diffs it, and W130's guard test keeps the text-layer backstop. Also #3: an over-strict contract blocks innocent DDL — start report-only for one cycle (W69/catD discipline). *Metric:* deploy-aborts from ownership/privilege = 0 (baseline: 1 abort + 5 incidents in Aug 2026); growth of the guard-test allowlist stops (baseline: 281/285 entries + temporary-GRANT ceremony per new scope). *Kill criterion:* two consecutive false-positive blocks on innocent migrations, or the refresh lane needs manual repair twice in 30 days. *First PR:* below (§6).

**R2 — Land the jsonb-codec cure and ban codec-less test pools.** *What:* (a) switch both prod codecs to `functools.partial(json.dumps, default=str)` and fix the 3 open call sites (PENDING-ARMS); (b) a shared `prod_shaped_pool` conftest fixture that registers the SAME codec object imported from the prod module (not a copy), and a grep-lint that fails any test file calling `asyncpg.create_pool` without `init=`. *Why beyond SOTA:* the industry answer to "test DB ≠ prod DB" is data/schema parity (Neon); nobody lints *codec/driver-layer* parity, yet that layer produced a 10/10-green-on-broken-code incident here. The composition — one canonical pool-init imported by both prod and tests, enforced by lint — is the wire-boundary-fake doctrine (W114) promoted from lesson to gate. *Cost:* 1 session. *Gear:* 2 (touches both prod pools — regression surface is every jsonb write; the existing GARUDA integration suites are the acceptance net). *Risk:* #3 — `default=str` silently stringifies types someone expected to fail loudly; mitigation: the codec change ships with a test asserting the *documented* coercion set. *Metric:* test files with bare `create_pool` N→0 (measure with the lint itself); jsonb double-encode class = structurally dead (no caller-side `json.dumps` remains — second grep-lint). *Kill criterion:* the coercion change breaks a consumer that relied on TypeError — revert to per-call-site fix.

**R3 — Migration provenance + checksum verification.** *What:* `_schema_versions` gains `applied_as` (`current_user`), `applied_via` (release_command | manual | ci), `runner_version`; `schema_audit` verifies stored checksums against the files on disk and reports divergence (turning W130's "preserved proof nobody reads" into a read proof); out-of-band applies become *visible* instead of unrecorded. *Why beyond SOTA:* migration trackers everywhere record what+when; none surveyed records *as-whom-via-what-path*, and our 2026-08-26 incident (superuser applied 5 migrations out-of-band, `applied_by='system'`, no trace) is precisely the blind spot. *Cost:* half a session; one migration + ~40 lines in runner/audit. *Gear:* 1–2. *Risk:* #9 — checksum verify must tolerate the *documented* legacy rows (`legacy_fake_checksum` literal exists in the runner) or it reds forever; allowlist by migration number with the reason. *Metric:* % of new applied rows carrying non-'system' provenance = 100; checksum divergences surfaced = 0 steady-state (any 1 is a finding). *Kill criterion:* none needed — pure observability.

**R4 — The Consumers: lint (reader-naming as a gate).** *What:* any migration that `ALTER`s an existing constraint/column or changes a row-cardinality invariant must carry a `-- Consumers:` header section naming the reader files (the 289 postmortem's lesson mechanized); a lint checks the section exists and that named paths exist on disk. *Why beyond SOTA:* Squawk/Atlas/strong_migrations grade the DDL's *danger*; none asks "who reads the invariant you are changing" — and the Visa Oracle outage was an unnamed-reader failure with perfectly safe DDL. This is consumer-map-first (existing repo doctrine for deploys) extended to the schema layer, which no surveyed system does. *Cost:* 1 session (lint + template update). *Gear:* 2. *Risk:* #3 over-match — additive-only migrations must be exempt or the lint teaches people to write junk sections; scope the trigger to ALTER/DROP of *existing* objects. *Metric:* unnamed-reader incidents (289-class) = 0; share of in-scope migrations carrying the section (baseline 0%, target 100% of new). *Kill criterion:* the section degenerates into boilerplate ("Consumers: all") in >30% of uses — then replace with grep-derived auto-suggestion instead of hand-written.

**R5 — Restore drill Level 5 + catalog check on the restored cluster.** *What:* extend `restore-drill.yml`: after restore, run `schema_audit` against the restored DB, execute ~5 golden queries (one per critical table: conversations, clients, visa_decisions, events_outbox, retention policies) asserting non-degenerate shapes, and diff the restored catalog against `catalog-contract.json` (R1). *Why beyond SOTA:* the 5-level model exists [10]; *no surveyed restore validator checks the privilege catalog of the restored cluster* — a restored DB with wrong owners passes all five levels, then aborts the next deploy. Level 5 + catalog is a composition none of them has. *Cost:* half a session. *Gear:* 1. *Risk:* #2 — a drill that greens on `|| true` is theater; every added step must fail the job (the workflow already learned this on restore.log surfacing). *Metric:* drill asserts N invariants, N: 1 (table count) → ≥7. *Kill criterion:* none — additive to an existing monthly job.

**R6 — Qdrant estate: one registry, aliases-first, rehearsed embedding migration.** *What:* (a) collapse the two registries into one and reconcile against live (the 2026-07-05 runbook's table is the worklist: 14 dead definitions, 8 undefined live); (b) introduce collection aliases and route every consumer read through them; (c) run ONE rehearsed embedding migration on a small collection using the named-vector path — background re-embed, atomic flip, rollback — and write the ceremony as a runbook. *Why beyond SOTA:* alias-swap is Qdrant-official [7]; the beyond move is coupling it to the *frozen-model tripwire*: the tripwire's assertion changes from "model never changes" to "model changes only inside the ceremony" (tripwire tests the ceremony's precondition artifacts exist), converting a fear-freeze into a governed invariant. No surveyed practice ties embedding-freeze governance to an executable ceremony. *Cost:* 2–3 sessions. *Gear:* 2 (registry) + 3 (rehearsal). *Risk:* #10 split-brain — dual registries during transition; do registry-unification as one PR, alias adoption as another. *Metric:* definitions matching live 6/20 → 20/20; consumer reads via alias 0% → 100%; one rehearsal documented with measured flip time. *Kill criterion:* rehearsal shows alias flip breaks a consumer that hardcodes collection names — pause and inventory callers first.

**R7 — Erasure that reaches backups (crypto-shredding), scope `needs-ruling`.** *What:* per-subject data keys for the conversation payload class; UU PDP Art.43 erasure = key destruction (ledgered in the retention-policy table as a new scope); dumps and 5-year retention untouched — erased subjects become noise in every existing backup without touching Tigris. *Why beyond SOTA:* crypto-shredding is known [8]; the composition with a *constraint-enforced retention-policy table* (key-class as a `policy_scope` row, activation via the staged ceremony, legal-hold interplay) is not something any surveyed system ships — and it resolves the standing tension between "never delete on a clock" and "erasure must be real". *Cost:* 3+ sessions + a design spike; *the 5th-scope lesson applies:* adding the scope row requires the temporary-GRANT ceremony (memory 2026-08-28) until R1 lands. *Gear:* 3. *Risk:* #4 (key handling is a new secret surface — keys live in the DB or KMS-equivalent, never in repo) and #2 (key-destruction that silently fails = erasure theater; destruction must be verified by failed-decrypt probe). *Metric:* erasure SLA statement changes from "live DB only" to "live DB + all backups ≤ destruction time"; probe: decrypt attempt on an erased subject's payload from the latest dump fails. *Kill criterion:* Zero rules the backup-retention of erased subjects acceptable as-is — then close as documented risk, not build.

## §8 — Meta-pattern (Gear 3)

**The single defective belief: "the schema is the contract."** The real contract has five layers — schema, **catalog** (owners, grants, role membership), **codecs** (driver-level type encoding), **readers** (every consumer of an invariant), and **provenance** (who applied what, as whom) — and this organism reproduces only the first in its tests. Every major scar in §2 is a mutation in a non-schema layer that no test could see *by construction*: W38 mutated grants (invisible → conversations write-dead); W130 mutated ownership (invisible → deploy abort); the jsonb incident mutated the codec layer (invisible → 10/10 green on broken code); 281 mutated the reader-set of a shared invariant (invisible → prod outage); the out-of-band apply mutated provenance (invisible → unrecorded superuser writes). The migration-as-ADR culture is world-class *documentation* of these layers, but documentation is the weakest binding this repo knows — its own doctrine says "hooks enforce what prompts cannot" (CLAUDE.md §7), and the data layer has not yet applied that law to itself. §5 is one move stated five ways: **promote each non-schema layer to a versioned, diffable, CI-replayed artifact** — the catalog contract (R1), the codec-in-fixture lint (R2), provenance columns (R3), the Consumers: section (R4), the restored-cluster catalog check (R5). The organism already invented this pattern once: SYMBIOSIS durability promises require lint-enforced `Test:` citations. That is the local proof the cure works; it just was never generalized past the outbox.
