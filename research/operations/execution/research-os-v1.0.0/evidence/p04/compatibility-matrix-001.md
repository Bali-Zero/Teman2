## 12. Where the newly-registered kinds' spec and code disagree (continues §7's numbering)

9. **The single most common finding across all 9 newly-registered kinds is the same finding §7 item 6 already named for the original 16 — legacy binds to a mutable current row, never a content-hash-pinned revision — but this pass shows it is not confined to receipt-shaped kinds. It applies just as hard upstream, before content or action production even begins** (TopicLock/CreativeLock's `brief_json`, DecisionPacket/RequestedActionSpec's stateful proposal rows). Nine kinds in, this reads less like a per-kind gap and more like a repo-wide default: almost nothing in this codebase's legacy layer computes or stores a content hash of a decision at the moment the decision is made.
10. **A supersession/lifecycle enum that is designed at schema time and never wired to a writer is now a confirmed three-time-independent pattern** (`naga_claim_transitions.transition_type='supersedes'`, `naga_claims.claim_status='superseded'`, `zantara_media.StoryVersionV1.lifecycle_state='amended'|'superseded'`) — worth naming as an organizational habit for whoever designs the eventual adapters, not three unrelated findings.
11. **At least five, arguably six, structurally disjoint "Claim" concepts coexist with no shared owner, schema, or ID namespace** (§11.0 finding 1) — this is a materially larger consolidation problem than any single field-mapping gap in this document, and it sits upstream of every other evidence-spine kind (Evidence, StoryCluster, DecisionPacket all reference Claim).
12. **`RequestedActionSpec`'s "carries no state" requirement, taken seriously, disqualifies nearly every "proposal"/"recommendation" table this repo has ever built** — 8 of 10 candidate mechanisms surveyed across the DecisionPacket/RequestedActionSpec and action-chain (§1) research passes combined declare a live `status` column at `CREATE TABLE` time. Only two mechanisms in the entire codebase (`cell_core.hgt_coordinator.proposal.Proposal`, DLQ's `claude_tasks/*.json`) are structurally state-free, and neither is a rich source. If Packet 04's eventual materialization primitive assumes a state-free `RequestedActionSpec` will typically be adaptable from an existing legacy proposal, that assumption does not hold for almost any legacy system surveyed this session.
13. **[ADDED — independent review round 2, 2026-08-24] At least three canonical kinds carry a MANDATORY `WorkflowRunRef`-bearing lineage field, and `WorkflowRunRef` is confirmed constructor-unreachable everywhere in this repo — which means, by this document's own evidence, those kinds cannot be constructed from ANY legacy source, not merely a hard-to-populate one.** `DecisionPacket.lineage.workflow_run_ref` (§11.5, mandatory) and `RequestedActionSpec.lineage.workflow_run_ref` (§11.6, mandatory) already carried this finding individually; `TopicLock.lineage: RequiredWorkflowLineage` (`topic_lock.py:84`, added to §11.7's table this pass) is a third, sharper instance — `RequiredWorkflowLineage` (unlike the generic optional `Lineage` most kinds carry) makes `workflow_run_ref` non-Optional at the type level, not just a convention. A repo-wide grep for `WorkflowRunRef(` (an actual instantiation, not a type annotation) returns exactly one hit — the class's own definition (`primitives.py:405`) — confirmed this session. Any adapter for any of these three kinds is blocked on a prerequisite this document has not previously named as a single, shared, cross-kind blocker: something, somewhere, has to start constructing `WorkflowRunRef` objects before any of the three can be built from legacy data, independent of and prior to every other per-field ruling this document asks for on any of them.

**This is recorded as findings about the section's structure, not as a diligence failure of the
author who caught all four** — a number restated in prose next to a table that can change is a
cache with no invalidation mechanism, and four recurrences under someone actively re-running the
script after every edit is the strongest available evidence that care was never going to be the
mechanism that held. The structural fix applied before landing: §0 no longer restates its own
count anywhere except the one summary table, and the embedded script now re-derives that table's
own claimed numbers from the file text and diffs them against a fresh computation, printing
`VERDICT: MISMATCH` and exiting nonzero if they disagree — so a future edit that forgets to
re-sync the table fails loudly instead of shipping a confident wrong number.

**Recurrence 4 is a sibling defect, not the same one, and the structural fix above does not cover

writing anchors" was already the lesson drawn from a dry-run catch two passes earlier in this same
session; it did not prevent this recurrence, because an abstraction does not fire at the moment of
typing. The concrete version, checkable at the point of use: **hand-composing an anchor from memory
is itself an act of retyping a measurement, and it fails the same silent way a restated number
does — invisible until the next comparison. Before trusting any anchor string against a file you
did not just read, either paste it in verbatim from a fresh read of that file, or run the match and
inspect the failure — never retype a quotation from memory and assume it is exact.**
