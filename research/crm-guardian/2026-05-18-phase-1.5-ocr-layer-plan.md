# CRM-Guardian Phase 1.5 — OCR / content layer plan

**Status**: PLANNING (Phase 1 bulk paused 2026-05-18 01:32 WITA after smartness audit on 6 outputs).
**Branch parking lot**: `feat/crm-guardian-phase1-bulk-enqueue` (PR not opened — bulk script ships anyway, it's needed for retry-after-OCR-fix).
**Owner**: Antonello (Zero).

## TL;DR

Phase 1 worker passes only Drive file **metadata** (filename, mime, modifiedTime) to
Gemini CLI. Gemini's job is to extract `passport_number`, `visa.valid_until`,
`paid_up_capital_idr`, `tax_records[]`, etc. — but those fields live in PDF
**content** that the worker never opens. Gemini, asked to fill them, does one of:

- Returns `null` (honest, most fields).
- **Hallucinates plausible values from filename tokens** (severe — Sofia Mueller's
  `identity.full_name` was overwritten with "Andrey Pozdnyakov" because that name
  appeared in many filenames; Oleksandr Ozolin became "Snizhana Yaroshenko").

Phase 1.5 adds an **OCR / text-extraction layer** that resolves PDF content
to text BEFORE the Gemini summary call, so the model can ground assertions in
actual document substance instead of pattern-matching filenames.

## Phase 1.5 — proposed design

### Goal

Stop the worker from passing only metadata. Pre-process each Drive file through
an OCR/text-extraction step, then feed Gemini the **content** alongside metadata.

### Three viable approaches

| Option                                 | Stack                                                                                                                                  | Cost | Coverage                                           | Latency/client                | Sovereignty  |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------------------------------------------------- | ----------------------------- | ------------ |
| **A — Tesseract + pdf2text**           | tesseract (already in nuzantara-mcp ocr-tesseract MCP) + pdfminer.six for native-text PDFs                                             | €0   | PDF text + image OCR (Indonesian + English models) | +30-90s/client (40-200 files) | Local Pro M4 |
| **B — qwen2.5vl:7b vision via Ollama** | local Ollama (already in stack) on Pro M4                                                                                              | €0   | PDF page→PNG→VLM, handles handwritten + tables     | +120-300s/client              | Pro M4 only  |
| **C — Hybrid (recommended)**           | Tesseract for evident-text PDFs (akta/NIB/NPWP printed) + qwen2.5vl for scanned/handwritten (passport, visa stamps, photographed docs) | €0   | Best-of-both                                       | +60-180s/client               | Pro M4       |

**Recommended: Option C (Hybrid)**. Tesseract is faster for printed documents (90% of CRM Drive content: NIB, NPWP, akta, SK, visa printouts). qwen2.5vl is the fallback for scanned passports + handwritten endorsements.

### Architecture sketch

```
[Drive folder]
  → list files (existing list_drive_files)
  → for each file:
    → if pdf with text layer: pdfminer.six extract → text
    → if pdf scanned: rasterize → tesseract -l ind+eng → text
    → if image: tesseract -l ind+eng → text
    → if photographed/handwritten: qwen2.5vl:7b → text (fallback when tesseract confidence low)
  → cache content_hash → text in postgres table: crm_guardian_file_content_cache
    (so re-runs don't re-OCR — skip if file_id + modifiedTime match)
  → assemble enriched FILE_INVENTORY with text snippets
  → call gemini CLI with content (truncate per-file to N kchars to bound prompt size)
```

### New table — content cache

Migration draft (NOT applied yet — needs sign-off):

```sql
CREATE TABLE crm_guardian_file_content_cache (
  file_id TEXT PRIMARY KEY,                  -- Google Drive file_id
  modified_time_ms BIGINT NOT NULL,          -- Drive modifiedTime in ms
  content_hash TEXT NOT NULL,                -- sha256(text) for change detect
  text_content TEXT NOT NULL,                -- truncated OCR output
  extracted_at TIMESTAMPTZ DEFAULT NOW(),
  extractor TEXT NOT NULL,                   -- 'tesseract' | 'qwen25vl' | 'pdfminer'
  confidence REAL                             -- 0-1 self-reported by extractor
);

CREATE INDEX ix_content_cache_modtime ON crm_guardian_file_content_cache (modified_time_ms);
```

Reason for cache: bulk re-runs (Phase 1.5 retry of 1882 eligible clients) will hit
the same PDFs many times if a client is enqueued multiple times. OCR cost dominates;
caching cuts re-OCR to 0 on unchanged files.

### Prompt v3

`L1_extraction_v3.md` MUST include:

1. **Explicit identity guardrail**:

   > The `identity.full_name` MUST be exactly the client name provided in
   > `<CROSS_FOLDER_CONTEXT>.client.full_name`. Do NOT substitute it with
   > another person found in the filenames. If the CRM full_name is absent
   > from the document content, return the CRM value AND add an
   > `extraction_notes` entry: "CRM full_name <X> not found in any document — possible mis-link".

2. **Content-vs-filename rule**:

   > For every field, prefer content extraction over filename inference. If only
   > filename is available, add `extraction_notes` entry noting "filename-only,
   > content not verified" — and DO NOT populate the field unless filename is
   > unambiguous (e.g. "Passport - <Name>.pdf" → `documents[].doc_type = "passport"`,
   > but NOT `passport_number`).

3. **Date provenance**:

   > `timeline[].event_date` MUST come from document content (issued date, akta date,
   > visa valid-from). Do NOT use `modifiedTime` (which is upload date). If only
   > modifiedTime is available, leave event_date null and note: "upload date only —
   > document date unknown".

4. **Confidence calibration**:
   > 0.4 = filename-only metadata, no OCR. 0.6 = some OCR but key fields missing.
   > 0.8 = full OCR with cross-folder verification. 1.0 = OCR + cross-doc consistency
   > check passed. Current Phase 1 outputs scored 0.4-0.7 — this was OVER-CALIBRATED
   > given the metadata-only diet; calibration must be tightened in v3.

### Targeted file-class extraction

To keep OCR bounded, Phase 1.5 prioritizes content extraction for the doc_types
that matter for CRM compliance:

| doc_type                    | Reason                                                  | Extractor priority                                         |
| --------------------------- | ------------------------------------------------------- | ---------------------------------------------------------- |
| `passport`                  | passport_number, expires_at, nationality, DOB           | tesseract (printed MRZ band) → qwen25vl (handwritten)      |
| `evisa`                     | visa_type, sponsor, valid_until                         | tesseract (almost all e-visas are printed PDF)             |
| `nib`                       | nib_number, issue date                                  | tesseract                                                  |
| `npwp`                      | npwp_number                                             | tesseract                                                  |
| `akta`                      | akta_number, capital, shareholders%, registered_address | tesseract (often >10 pages — page 2-3 is the critical one) |
| `sk`                        | sk_kemenkumham number                                   | tesseract                                                  |
| `LKPM` / `Laporan_Kegiatan` | period, realization, employment_count                   | tesseract (Excel→pdf or scanned)                           |
| `SPT` / `Bukti_Potong`      | period, amount, status                                  | tesseract                                                  |
| Other                       | metadata only (filename + modifiedTime)                 | none                                                       |

This keeps OCR work bounded: a typical client has 50-200 files, only ~30-50% are
in priority list (akta + npwp + nib + passport + evisa + LKPM + SPT). The
remaining 50-70% (random photos, drafts, screenshots) stay metadata-only.

### Capacity math

Pro M4 single tesseract worker: ~10-30 pages/sec printed PDF. qwen2.5vl on Pro M4
GPU: ~1-3 pages/sec scanned. Typical akta is 10-20 pages, tesseract 1-2s per akta.
Typical passport scan: 1-2 pages, qwen2.5vl 0.5-1s.

Per-client cost (avg 50 priority files, mix 80% tesseract / 20% qwen2.5vl):

- Tesseract: 40 files × 5 pages × 0.5s = 100s (10-page average for akta + 1-page for npwp/nib)
- qwen2.5vl: 10 files × 2 pages × 0.8s = 16s
- **Total OCR per client: ~120s**

Combined with gemini CLI call (~70s avg seen in Phase 1):

- **Per-client total: ~190s** (3:10min)

Phase 1.5 throughput @ 300s tick / max=5 jobs (Option C):

- 5 clients × 190s = 950s tick duration → 16 min effective per tick
- Cadence becomes back-to-back (not 5min) due to lockfile → **~5 client every 16 min = ~19 client/h**
- 727 active-linked / 19 = 38h = ~2 days
- 1882 full = ~100h = ~5 days

Slower than Phase 1's 60 client/h but with usable content. Tradeoff acceptable
because the value of a USEFUL summary at 19/h > meaningless summary at 70/h.

### Cache hit second-pass economics

After first bulk pass, Phase 1.5 retry of any client only re-OCRs files added/changed
since last extraction (content_hash mismatch on modifiedTime). For 727 clients with
~5% file churn / month, second-pass OCR ≈ 5% of first-pass = ~5h re-OCR / month.
