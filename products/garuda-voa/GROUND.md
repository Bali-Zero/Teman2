## 1. G1 verdict

**G1 BLOCKED.** One `unknown` controls eligibility and a customer-facing promise:

- **F25 — the Safe Clock's calendar-day anchor.** Nothing in the engine defines the timezone of
  "today". The engine is pure (`safe_clock.py`, `intake.py` read no wall clock); the single
  production caller injects `date.today()` — host-local, no TZ (`internal_preview_cli.py:272`).
  This `unknown` moves the issuance ACCEPT/DECLINE cutoff (F23, eligibility) and the
  `submit_by_date` / D-7 dates a public funnel would display (F10/F15, promise) by ±1 day.
  In the current owner-only CLI it is tolerable (known host); as a customer-facing product it is
  exactly what G1 exists to catch.

Everything else touching the three controlled surfaces is `verified` or `assumption` (G1's wording
blocks only `unknown`). The two `assumption` rows that most deserve resolution before launch,
because they sit on the promise surface: **F10** (D-7 is verbatim-published but Ngurah-Rai-specific
at best, self-contradicted on its own page, and challenged by an unverified Pasal 97 reading —
AUDIT §2/§4.1; only Zero may revisit ruling 2026-07-27(b)) and **F19** (the mandate's "PNBP + 3jt"
composition matches nothing in the catalogue — actual all-inclusive prices are 790.000/850.000 IDR,
owner-confirmed 2026-08-23).

## 2. Freshness

Grep evidence (this session): inside `apps/backend-rag/backend/services/garuda_flow/` there is **no
comparison of `today` against any verification date** — `RETRIEVED_ON`
(`nationality_eligibility.py:99`) is a string constant read by nothing at runtime; the D-7/D-14
verification dates live only in docstrings (`constants.py:14-16`); the eVOA truth-sheet date
("verified 14 Jul 2026") lives only in comments (`constants.py:62-67`, `intake.py:247-249`). The
price catalogue's `metadata.last_updated` (`bali_zero_official_prices_2026.json:13`, value
`2026-05-06`) is **never read by `PricingService`** (`pricing_service.py:121-219` loads
`services` only) nor by `garuda_flow/pricing.py`; the only reader anywhere is
`services/visa_engine/pricing_adapter.py:4,75-79` — a different service, whose own docstring calls
it "provenance, not an invented expiry clock".

The ONE staleness signal that exists today: the operating calendar's coverage bound —
`is_open` returns `False` outside `COVERAGE_START/COVERAGE_END` and `last_open_day_before` returns
`None` (`operating_calendar.py:130-134,154`), which the intake turns into a DECLINE
(`ARRIVAL_DATE_UNCONFIRMED`, `intake.py:236-238`), plus a test-time guard
(`test_operating_calendar.py:129-139`). Rules, nationality list, and prices have **no equivalent**.

Smallest honest mechanism: give each truth-source a machine-read stamp next to the data it covers —
`RETRIEVED_ON` already exists for nationalities; add `RULES_VERIFIED_ON` (covers D-7/D-14/90-day/60-day)
in `constants.py` and start reading the catalogue's existing `metadata.last_updated` in
`pricing.py` — plus one `MAX_AGE_DAYS` per class. The writer is whoever re-verifies: the stamp
changes in the same commit as the re-verification (the nationality module already mandates this
convention in prose at `nationality_eligibility.py:80-83`). The readers are `build_verdict` and
`price_for_case`: if `today − stamp > MAX_AGE_DAYS`, the funnel declines to sell (verdict) or
reports the price unavailable (price), exactly like the calendar's existing fail-closed path; a
test per stamp pins the comparison the way `test_no_calendar_date_beyond_coverage_end` pins the
calendar.

## 4. Prices

`PricingTool` is the data source **by lineage, not by call**: the GARUDA module never instantiates
the `PricingTool` class. The call chain, every hop opened in this session:

1. `internal_preview_cli.py:165` — `price_for_case(request.case_type)`
2. `garuda_flow/pricing.py:44-58` — maps case type to the exact key (`:17-18`), calls
   `service.get_service_by_key(key)` on a **module-level `PricingService()` instance created at
   import** (`pricing.py:19`)
3. `services/pricing/pricing_service.py:192-219` — `get_service_by_key`, exact-match only, `None`
   when unloaded or unknown
4. `pricing_service.py:121-154` — `_load_prices` reads
   `apps/backend-rag/backend/data/bali_zero_official_prices_2026.json` (`_PRICING_FILENAME`,
   `:29`), which holds `"B1 Visa on Arrival (VOA)" → "790.000 IDR"` and
   `"B1 Visa on Arrival Extension" → "850.000 IDR"` under `services/single_entry_visas`
   (verified by parsing the JSON in-session).

The real `PricingTool` (`services/rag/agentic/tools.py:557-561`) wraps the same `PricingService`
via the `get_pricing_service()` singleton (`pricing_service.py:644-648`), so the data source is
identical — but note two differences: GARUDA holds its own non-singleton instance (the JSON is read
once at module import; mitigated today because the CLI spawns a fresh Python process per request,
per AUDIT §3 Finding 7), and `pricing.py`'s docstring ("Exact-key PricingTool bridge") overstates
the connection. **No price literal is hardcoded in `garuda_flow`** — the only literals
(790_000/850_000) live in `test_pricing.py:29-34` as stub fixtures, and the fail-closed behaviour
on any missing/malformed/drifted row is pinned by 12 parametrized cases
(`test_pricing.py:50-72`).
